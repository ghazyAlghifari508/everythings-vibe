## 1. Mission

Perbaiki pengalaman Thinking pada chat VibePlan Existing Codebase.

Current implementation shows an animated Orb beside the main Thinking header and another Orb inside the expanded activity timeline.

It also exposes generic technical activity labels:

```
Permintaan diterima server
Model mulai menghasilkan respons
Hasil tersimpan di server
```

User does not want these messages.

They provide little practical value, look like fabricated AI thinking, and create a cluttered interface.

The user wants a clean agent-style progress display resembling mature AI coding harnesses: one primary status, truthful progress, optional meaningful details, and correct lifecycle timing.

**Do not simulate reasoning that the model/provider does not actually expose.**

## 5. Optional Expandable Activity — Only When Useful

A disclosure is allowed only when there are genuine, meaningful details.

Example:

```
◌ Menyusun pertanyaan klarifikasi...       9.4s

   ˅ Aktivitas
```

When expanded, it may show verified work stages.

For example, only if actually supported by the system:

```
   ✓ Konteks repository tersedia
   ◌ Menyusun pertanyaan
```

Do not fabricate these details from time elapsed.

Do not synthesize fake events to make the interface seem busy.

Do not render the expandable activity button when there is no genuinely useful content to show.

The collapse/expand interaction should hide or reveal details without affecting the underlying operation.

## 6. Distinguish Three Different Kinds of Information

### A. Transport Events

```
HTTP request accepted
Worker operation created
Database write completed
```

Keep these in logs/diagnostics.

Do not show them as AI reasoning.

### B. Real Operation Stages

```
Questions generation
Feature generation
PRD generation
AC generation
Task generation
```

These can provide honest user-facing progress.

### C. Actual Model-Provided Reasoning or Summaries

If the provider supports an approved user-visible reasoning summary or equivalent output, investigate how to safely consume it.

If not supported, do not invent reasoning text.

Do not expose hidden chain-of-thought.

Do not use another model to fabricate what the first model was supposedly thinking.

A model with no public reasoning output can still provide an excellent, accurate operation-status UI.

## 8. Single Animation Rule

At any given moment, the same operation should have:

```
ONE PRIMARY ACTIVE THINKING INDICATOR
```

Not:

```
Orb in header
+
Orb in active activity
+
Spinner in composer
+
Another spinner inside result card
```

If the composer displays a send/stop control, preserve its legitimate functionality, but avoid giving the user several competing animations representing the same operation.

Use simple checkmarks or text for completed activity rows.

An animated activity icon should not duplicate the primary Orb.

## 9. Timer Lifecycle

The elapsed timer must represent a real operation.

Correct:

```
RUNNING
   │
   ▼
Timer advances
   │
   ▼
COMPLETED / FAILED / CANCELLED
   │
   ▼
Timer stops
```

Requirements:

- Do not start a timer before operation acceptance.
- Prefer authoritative operation timestamps.
- Do not reset elapsed time on ordinary rerenders.
- Do not leave timers running after success.
- Do not leave timers running after failure.
- Refresh/reconnect must reconcile current operation status.
- Do not merge timing from two separate attempts.
- Do not create fake stage delays.

A completed operation may display its final duration, but must not continue ticking.

## 10. Correct Activity Lifecycle

Inspect DurableWorker operations and the existing operation stream.

Build the UI using genuine state:

```
queued
running
completed
failed
cancelled
```

Follow existing server contracts.

Do not create artificial `thinking` and `generating` phases when the backend cannot observe the distinction.

If the backend only knows a request is running, showing one honest operation label is better than fake detailed activity.

If there are verifiable internal stages, display those selectively and meaningfully.
