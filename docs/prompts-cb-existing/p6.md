## 3. Verified Double Close Root Cause

In `src/components/ui/dialog.tsx`, `DialogContent` already renders its own Close button.

Meanwhile `codebase-resync-modal.tsx` adds another `DialogClose` inside `DialogHeader`.

Therefore both buttons appear.

**Fix by using exactly one Close control.**

Prefer the existing Dialog primitive's built-in Close, or extend the shared component using an explicit backward-compatible option if truly required.

Do not use CSS to hide one of the duplicated buttons while leaving two interactive elements in the accessibility tree.

## 6. Layout Requirements

### A. Header

- Exactly one Close button.
- Properly aligned title.
- Repository name as subtitle.
- No unnecessary duplicate icon/button.
- No overly large padding.
- Consistent typography with the initial sync flow.
- Do not add decorative backgrounds.

### B. Modal Body

- Clear three-step hierarchy.
- Comfortable line-height.
- Prompt container scrolls internally where needed.
- Long CLI tokens/commands must not break modal width.
- Avoid nesting scroll areas unnecessarily.
- Copy button must have a comfortable hit target.
- Clipboard behavior must copy the complete valid prompt.
- Prompt preview can be constrained in height without truncating copied content.
- Preserve monospace formatting and real line breaks.

### C. Footer

Current implementation uses:

```
bg-charcoal/60
```

This creates a visibly different footer surface from the modal.

Use the modal's existing background token consistently.

A subtle top divider is enough.

Footer must not look like a detached second panel.

Avoid excessive empty space above the footer.

### D. Responsive Behavior

- Centered on desktop.
- Mobile-friendly width and height.
- Internal content scrolling if needed.
- Header/footer remain accessible.
- Correct focus restoration.
- Escape key closes consistently when permitted.
- No layout shift in the workspace behind the modal.
- No clipped controls or duplicate scrollbars.

## 7. Sync Step Lifecycle

Do not use purely decorative step indicators.

Represent real re-sync statuses:

```
Step 1 — Instructions available
     │
     ▼
Step 2 — Agent/CLI connected
     │
     ▼
Step 3 — Snapshot received & verified
     │
     ▼
[Selesai] enabled
```

Progress indicators:

- Pending → neutral.
- Active → spinner.
- Completed → checkmark.
- Failed → accessible failure feedback.

Do not use stacked green success cards.

Reuse `SyncStageList` or initial onboarding step components whenever technically appropriate.

## 8. Preserve Existing Re-Sync Correctness

- Keep dedicated re-sync instructions distinct from initial sync.
- Continue using the official CLI.
- Do not modify source code as part of re-sync.
- Do not create duplicate repository history.
- Do not remove PRD/AC/Task.
- Do not reset active feature.
- Do not regenerate planning.
- Do not enable Selesai because of an old successful snapshot.
- Selesai must be gated by current session verification.
- If modal closes and reopens, recover the same active attempt.
- Do not auto-close on success.
- Do not fabricate agent connection status.

## 9. Repository Name

The screenshot still displays "Repository Lokal".

For this modal, use the repository's authoritative stored identity, not a hardcoded generic name.

Inspect the existing repository naming service and use its canonical value.

Do not introduce another hardcoded fallback such as "My Repository" or "Local Project" to conceal a missing identity.

If repository identity is missing due to an upstream data issue, preserve data integrity and report the upstream cause instead of inventing a name.

Do not perform an unrelated large naming-system migration as part of this visual phase.
