## 6. Fix Potential Impact Area Classification

Current issue:

```
idx === 0 -> Database & State
idx === 1 -> Application & Logic
otherwise -> Interface & Routing
```

Ini salah karena kategori ditentukan dari posisi array, bukan makna atau bukti.

Contoh akibatnya:

```
Database & State
  Katalog dan halaman detail proyek

Application & Logic
  Sistem navigasi dan tata letak responsif

Interface & Routing
  Penyajian sertifikat

Interface & Routing
  Interaksi tema

Interface & Routing
  Alur kontak
```

Kategori duplikat terjadi karena semua item setelah indeks kedua diberikan heading yang sama.

Jangan menyelesaikan ini dengan menambahkan kategori statis baru berdasarkan indeks yang lebih banyak.

### Recommended Information Architecture

Untuk ringkasan repository awal, gunakan section:

```
Bagian aplikasi
```

Contoh konseptual:

```
+------------------------------+
| Halaman proyek               |
| Daftar dan detail karya      |
+------------------------------+

+------------------------------+
| Navigasi dan tampilan        |
| Menu, layout, dan tema       |
+------------------------------+

+------------------------------+
| Sertifikat dan keahlian      |
| Informasi kompetensi         |
+------------------------------+

+------------------------------+
| Halaman kontak               |
| Informasi dan formulir       |
+------------------------------+
```

Ini contoh untuk repository portofolio yang terlihat pada screenshot. Jangan hardcode kategori tersebut.

Penting:

- `impactAreas` pada schema saat ini berarti area yang mungkin terdampak fitur baru.
- `Bagian aplikasi` berarti modul/fungsi aplikasi yang teridentifikasi.
- Kedua konsep tidak boleh diperlakukan sebagai data yang identik jika memang memiliki makna berbeda.

Periksa apakah `moduleMap`, `relevantFiles`, `findings`, atau hasil analysis lain menyediakan sumber data yang lebih benar untuk `Bagian aplikasi`.

Jika perlu memperluas contract analysis, lakukan dengan validasi dan backward compatibility yang jelas.

Jangan membuat classification palsu hanya untuk mengisi card.

Jika data hanya berupa teks tanpa kategori valid, tampilkan sebagai list informatif tanpa heading kategori yang mengada-ada.

### Quality Rules

Judul temuan harus:

- Jelas.
- Ringkas.
- Menggambarkan fungsi atau kondisi nyata.
- Tidak terdengar seperti judul laporan AI generik.

Detail harus:

- Menjelaskan fakta.
- Menghindari pengulangan judul.
- Menyebut konsekuensi bila relevan.
- Tidak menggunakan promosi kosong.

Uncertainty harus:

- Spesifik.
- Menjelaskan apa yang belum diketahui.
- Menjelaskan mengapa informasi itu penting bila relevan.
- Tidak menuduh aplikasi bermasalah tanpa bukti.

## 9. Replace Generic "Perlu Verifikasi" Badges

Saat ini setiap finding dengan uncertainty dapat menghasilkan badge:

```
[Perlu verifikasi]
```

Badge menggunakan nuansa kuning/amber dengan background transparan.

Masalahnya:

- Terlihat seperti warning serius.
- Tidak menjelaskan tingkat kepentingan.
- Dapat muncul berulang.
- Tidak selalu ada action untuk user.
- Menggunakan gaya visual AI generik.

Rekomendasi:

- Hilangkan badge warning generik untuk ketidakpastian biasa.
- Gunakan heading/description yang membedakan fakta dan keterbatasan.
- Gunakan neutral inline disclosure jika perlu.
- Warna peringatan hanya untuk masalah yang benar-benar membutuhkan tindakan.
- Jangan menambahkan tooltip tersembunyi sebagai satu-satunya cara membaca penjelasan.

Contoh:

```
Hal yang belum dapat dipastikan

Pengiriman formulir kontak
Mekanisme server untuk mengirim pesan
belum terlihat pada source yang tersedia.
```

Jika suatu temuan memang memerlukan keputusan user sebelum planning dapat dilanjutkan, berikan action yang jelas, bukan sekadar badge.

## 10. Improve Limitations Section

Current limitations:

- Sebagian source tidak tercakup snapshot.
- Implementasi pengiriman form belum dapat diverifikasi.

Informasi seperti ini tetap berguna jika benar-benar menjelaskan keterbatasan analisis.

Tetapi jangan menjadikannya sekumpulan peringatan panjang tanpa konteks.

Recommended:

```
Hal yang belum dapat dipastikan
  - Mekanisme tertentu tidak terlihat
    pada source yang tersedia.
```

Untuk detail snapshot yang panjang, gunakan progressive disclosure atau existing collapsible component apabila sesuai.

Jangan menyembunyikan keterbatasan penting.

Jangan menampilkan:

```
Semua temuan di atas tanpa
ketidakpastian tercatat.
```

Kalimat itu redundan dan tidak perlu.
