## 1. Mission

Redesign sistem revisi VibePlan Existing Codebase menjadi workflow yang eksplisit, aman, dapat diaudit, dan dikendalikan user.

Saat ini, sistem revisi terlalu bergantung pada interpretasi AI. User tidak mempunyai kontrol yang memadai untuk menentukan dokumen mana yang perlu direvisi, bagian apa yang boleh berubah, dan apa dampaknya terhadap planning yang telah diselesaikan.

Target akhir:

- Plan: menyusun planning fitur baru.
- Revise: mengajukan perubahan terhadap dokumen planning yang sudah tersedia.
- Revisi bisa menargetkan Feature Specification, PRD, Acceptance Criteria, atau Task.
- AI wajib menghasilkan proposal perubahan terlebih dahulu.
- User dapat meninjau diff sebelum menerapkan.
- Dokumen aktif tidak boleh berubah sebelum approval.
- Revision history harus tersimpan.
- Status Kanban yang sudah berjalan harus terlindungi.
- Greenfield dan Existing Codebase tetap terisolasi.

**Jangan membangun AI revision system yang langsung menimpa dokumen hanya karena model menganggap sebuah perubahan lebih baik.**

## 3. Current Architecture Problems

### Problem A — Revision intent is implicit

Existing composer mode:

```
type CodebaseComposerMode =
  | "create"
  | "clarify"
  | "revise";
```

Mode berasal dari kondisi workspace, bukan pilihan eksplisit user.

Ketika planning tersedia, pesan dapat diarahkan otomatis ke revision handler.

### Problem B — Revision currently leans toward PRD

`use-workspace-revision.ts` mengirim request:

```
{
  mode: "revise",
  message: buildRevisionRequest(...)
}
```

melalui shared `/api/chat` workflow.

Audit keterbatasannya, terutama apakah Feature Specification, AC, dan Task benar-benar mempunyai revision contracts masing-masing.

### Problem C — Unsafe downstream changes

Perubahan pada Feature Specification atau PRD dapat membuat AC dan Task tidak lagi sesuai.

Jangan menganggap semua downstream artifacts tetap valid setelah upstream artifact berubah.

### Problem D — AI decides too much

AI tidak boleh:

- Memperluas scope tanpa persetujuan.
- Mengganti kebutuhan user dengan rekomendasi yang lebih mudah.
- Menghapus requirement yang belum diminta.
- Mengubah banyak dokumen sekaligus tanpa approval.
- Mengklaim perubahan aman tanpa memeriksa dependencies.
- Mengubah Task In Progress/Done secara otomatis.

## 5. Explicit Revision Domain Contract

Implementasikan revision request yang mempunyai target jelas.

Konsep minimum:

```
projectId
codebaseId
targetArtifactKind
targetArtifactVersionId
userInstruction
optionalReferences
sourceSnapshotId
```

Jangan hanya mengirim satu string instruction yang kemudian ditebak AI.

Gunakan schema validation yang sesuai standar project, misalnya Zod jika sudah digunakan.

Validasi:

- Project milik user yang benar.
- Target artifact memang tersedia.
- Target version sesuai yang dibuka user.
- Feature terkait repository yang benar.
- Referenced files berasal dari snapshot yang diizinkan.
- AI context tidak mencampur project lain.
- Stage mempunyai izin untuk memulai revision.

Jika ada stale version, hentikan apply dan minta user memuat perubahan terbaru.

## 6. Supported Artifact Targets

### A. Feature Specification

User bisa merevisi definisi fitur.

Contoh:

"Tambahkan dukungan multi-kategori pada filter artikel."

Impact analysis harus memeriksa PRD, AC, dan Task.

Jangan otomatis menganggap seluruh downstream artifact valid.

### B. PRD

User dapat mengubah requirement, user flow, acceptance expectations, atau bagian tertentu dalam dokumen.

Perubahan harus dipertahankan dalam batas yang user minta.

Jangan menulis ulang seluruh PRD jika cukup mengubah satu bagian.

### C. Acceptance Criteria

User dapat merevisi acceptance criteria tertentu.

Contoh:

"Tambahkan kriteria bahwa filter tersimpan pada URL."

Perubahan tidak boleh otomatis mengubah semua requirement lainnya.

Evaluasi dampak terhadap Task yang berasal dari AC tersebut.

### D. Task

User bisa meminta revisi task breakdown.

Contoh:

"Pisahkan task pencarian frontend dan integrasi data."

Pastikan tidak ada silent destructive update terhadap task yang sedang berjalan.

### E. Kanban Progress

Kanban progress tidak diregenerasi seperti dokumen.

Status To Do/In Progress/Done dan hasil agent implementation harus tetap menjadi workflow terpisah.

Jangan menganggap AI revision sebagai izin mengubah progress.

## 7. AI Revision Workflow

Wajib dua tahap: PROPOSE dan APPLY.

### PROPOSE

1. Ambil artifact version aktif.
2. Ambil instruction asli user.
3. Ambil references yang benar.
4. Kumpulkan dependent artifacts.
5. Tentukan perubahan yang memang diperlukan.
6. Generate proposed revision.
7. Validate output schema.
8. Validate scope.
9. Generate real diff.
10. Compute potential downstream impact.
11. Persist proposal sebagai pending review.

**Tidak boleh mengganti dokumen aktif pada tahap ini.**

### APPLY

1. User membuka proposal.
2. User melihat perubahan.
3. User menerima, menolak, atau meminta perubahan proposal.
4. Server memverifikasi permission dan current artifact version.
5. Server memverifikasi impact approval.
6. Jika valid, buat immutable revision version.
7. Set version baru sebagai active version secara atomik.
8. Simpan audit metadata.
9. Tandai dependent artifacts yang membutuhkan review.
10. Pertahankan history dan task progress.

Gunakan database transaction untuk perubahan yang harus konsisten.

Jangan mengandalkan state frontend sebagai bukti approval.

## 8. Diff &amp; Impact Analysis

Tampilkan diff pada bagian yang benar-benar berubah.

Prioritaskan structured/section-aware diff jika format dokumen memungkinkan; gunakan line-based diff jika sesuai.

Contoh impact graph:

```
FEATURE SPECIFICATION
        │
        ▼
       PRD
        │
        ▼
        AC
        │
        ▼
       TASK
```

Aturan:

- Revisi Feature dapat memengaruhi PRD/AC/Task.
- Revisi PRD dapat memengaruhi AC/Task.
- Revisi AC dapat memengaruhi Task.
- Revisi Task harus melindungi Kanban progress.
- Tidak semua revisi otomatis menimbulkan impact.

Bedakan:

```
VALID
NEEDS_REVIEW
STALE
REPLACEMENT_PROPOSED
```

Jangan menciptakan impact result palsu.

Untuk dampak yang tidak bisa dipastikan secara deterministik, tampilkan sebagai "Perlu ditinjau", bukan "Aman".

## 9. Versioning &amp; Persistence

Periksa versioning yang sudah tersedia sebelum membuat schema baru.

Requirements:

- Setiap approved revision menghasilkan versi yang dapat ditelusuri.
- Versi sebelumnya tidak ditimpa atau dihapus.
- Pending proposal disimpan terpisah dari active artifact.
- Proposal tetap dapat dibuka setelah refresh.
- Rejected proposal tidak mengubah artifact aktif.
- User dapat memeriksa version history.
- Simpan siapa yang menyetujui, kapan, dan terhadap versi mana.
- Revisions bersifat idempotent terhadap duplicate apply request.
- Active version harus tidak ambigu.
- Revisions tidak boleh lintas repository/project.

Jika memerlukan migrasi Drizzle/PostgreSQL, lakukan secara terkontrol dengan mempertimbangkan legacy data.

Jangan melakukan destructive migration.

## 10. Task &amp; Kanban Safety

Ini bagian yang wajib diuji secara serius.

Jika terdapat Task In Progress atau Done:

- Jangan mengganti task secara otomatis.
- Jangan mereset status ke To Do.
- Jangan menghapus subtask history.
- Jangan menghapus implementation notes.
- Jangan memindahkan tugas ke project lain.
- Jangan memaksakan regenerated task tree.

Jika revisi memerlukan perubahan Task, tampilkan proposal reconciliation.

User harus mengetahui task mana yang:

```
unchanged
added
modified
superseded
needs_review
```

Status completion historis harus tetap dapat ditelusuri.

Audit penggunaan `confirmedImpact` dan PRD lock pada shared Greenfield endpoint.

Jangan pernah mengirim `confirmedImpact: true` secara otomatis hanya karena task yang terdampak ditemukan.

Server harus memvalidasi approval yang benar.

## 11. AI Prompt &amp; Output Quality

AI revision instruction harus mengutamakan user intent, bukan kemudahan implementasi.

Wajib:

- Mempertahankan requirements yang tidak diminta untuk berubah.
- Menggunakan snapshot codebase yang benar.
- Mengikuti existing architecture dan constraints.
- Tidak mengarang file, route, dependency, atau API.
- Tidak mengubah fitur lain di luar scope.
- Tidak menghapus requirement tanpa alasan eksplisit.
- Melaporkan konflik requirement jika ada.
- Mengutamakan minimal necessary changes pada artifact target.
- Menghasilkan diff dan impact yang dapat diverifikasi.

Jangan menjadikan AI impact classification sebagai satu-satunya pengaman. Validasi ownership, version, status Task, dan approval harus dilakukan backend.

## 12. CLI Handoff Compatibility

Perhatikan rencana Existing Codebase handoff melalui:

```

```

Di repository milik user.

Handoff harus membaca **approved active versions**, bukan pending draft revisions.

Jika handoff sudah tersedia:

- Pertahankan kontrak CLI.
- Jangan mengekspor proposal yang belum disetujui sebagai dokumen final.
- Jangan menghapus progress Kanban.
- Jika diperlukan ekspor versi terbaru, lakukan melalui workflow CLI yang memang berwenang mengakses repository lokal.
- Jangan membuat website mengklaim telah menulis file lokal padahal tidak mempunyai akses.

## 14. Testing Requirements

Tambahkan tests untuk:

1. Revise Feature Specification tanpa mengubah PRD sebelum approval.
2. Revise PRD tidak langsung mengubah AC/Task.
3. Revise AC menghasilkan proposal yang tepat.
4. Revise Task menjaga progress Kanban.
5. Rejected proposal tidak mengubah artifact aktif.
6. Approved proposal menghasilkan version baru.
7. Old version tetap accessible.
8. Duplicate apply request tidak membuat duplicate version.
9. Concurrent revisions mendeteksi stale version.
10. Unauthorized revisions ditolak.
11. Proposal dapat dipulihkan setelah refresh.
12. Impact dependencies ditandai dengan benar.
13. AI output yang tidak valid tidak boleh diterapkan.
14. Tidak ada silent Task reset.
15. Tidak ada automatic `confirmedImpact`.
16. Existing Greenfield behavior tetap aman.
17. Handoff hanya menggunakan approved versions.
18. Credit accounting/idempotency konsisten untuk AI proposal generation.

Gunakan unit tests, API integration tests, database transaction tests, typecheck, lint, dan build sesuai kebutuhan repository.

**STRICT: Jangan menjalankan browser QA, Playwright, Puppeteer, browser automation, manual browser testing, atau screenshot testing.**

## 15. Definition of Done

Sistem revisi bukan lagi sekadar prompt yang dikirim ke model.

User dapat memilih target dokumen, memberikan instruksi, menerima proposal, meninjau diff dan dampaknya, lalu menyetujui atau menolak secara eksplisit.

Versi lama tetap tersimpan, Task/Kanban terlindungi, dan frontend/backend memiliki contract yang konsisten.

Laporan akhir wajib menjelaskan:

- Root cause sistem revisi lama.
- Architecture baru.
- Schema/API changes.
- Lifecycle propose/apply.
- Versioning.
- Impact analysis.
- Tests yang benar-benar dijalankan.
- Risiko yang belum terselesaikan.

Jangan menyatakan implementasi berhasil hanya karena tombol Revise sudah muncul.
