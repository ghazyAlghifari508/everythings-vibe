## 1. Objective

Redesign UI pertanyaan klarifikasi pada VibePlan Existing Codebase menjadi antarmuka pilihan jawaban yang profesional, informatif, mudah dipindai, dan konsisten dengan visual aplikasi.

Pengguna merasa tampilan sekarang terlalu generik dan sederhana. Masalahnya bukan sekadar ukuran border atau warna, tetapi struktur informasi dan kualitas komponen.

Hasil akhir harus terasa seperti interface developer tool atau coding agent yang matang, dengan decision cards yang terstruktur. Gunakan referensi pola interaksi dari tool profesional, bukan menyalin branding atau desain produk lain secara mentah.

**WAJIB mencari, mengevaluasi, dan menggunakan ready-made UI components. Jangan membuat UI dari nol jika komponen yang cocok sudah tersedia.**

Tetap pertahankan komponen Existing Codebase yang sudah ada dan lakukan refactor terarah, bukan membuat aplikasi atau workflow baru.

## 2. Problems to Fix

**A. Recommended option position**

Rekomendasi AI muncul di urutan selain pertama.

Target: opsi dengan rekomendasi valid WAJIB tampil pada posisi paling atas.

**B. Missing descriptions**

Setiap opsi hanya mempunyai teks singkat.

Target: SEMUA opsi memiliki heading dan description, bukan hanya rekomendasi.

**C. Redundant recommendation panel**

Di bawah pilihan terdapat card terpisah berisi:

```
Rekomendasi: ...
Alasan berdasarkan codebase: ...
```

Panel tersebut harus DIHAPUS dari tampilan.

Alasan rekomendasi dipresentasikan di dalam description opsi rekomendasi pertama, bukan menjadi container tambahan.

**D. Generic option cards**

Baris opsi tampak seperti radio input standar yang hanya diberi border dan padding.

Target: selectable cards yang benar-benar menunjukkan hierarki informasi dan state pilihan.

**E. Generic recommendation badge**

Badge saat ini menggunakan hijau transparan dan border bernuansa hijau.

Target: badge netral, solid, minimal, dan tidak menggunakan glow/gradient/blur.

**F. Weak question container**

Card pertanyaan utama terasa terlalu datar dan belum mempunyai hierarki antara progress, pertanyaan, opsi, dan action.

Target: struktur visual yang lebih matang tanpa menambah dekorasi yang tidak perlu.

## 3. Mandatory Component Discovery

Sebelum mengimplementasikan JSX atau styling, WAJIB eksplorasi library berikut:

1. HeroUI: [https://heroui.com/](https://heroui.com/)
2. shadcn/ui: [https://ui.shadcn.com/](https://ui.shadcn.com/)
3. Magic UI: [https://magicui.design/](https://magicui.design/)
4. ReactBits: [https://reactbits.dev/](https://reactbits.dev/)
5. Thinking Orbs: [https://www.thinkingorbs.com/#orbs](https://www.thinkingorbs.com/#orbs)
6. affectUI: [https://www.affectui.com/components](https://www.affectui.com/components)
7. TuffUI: [https://tuffui.com/](https://tuffui.com/)
8. CUI: [https://yappologistic.github.io/CUI/](https://yappologistic.github.io/CUI/)
9. SakaniUI: [https://www.sakaniui.com/](https://www.sakaniui.com/)

Periksa juga reusable components yang sudah tersedia di repository, termasuk komponen di `src/components/ui`.

Component discovery harus dilakukan sebelum memutuskan membuat komponen sendiri.

Untuk setiap kandidat yang relevan, nilai:

- Kesesuaian fungsi.
- Dukungan heading dan description.
- Kemampuan controlled selection.
- Dukungan single-select dan multi-select.
- Keyboard accessibility.
- Focus, selected, disabled, dan hover state.
- Integrasi React 19 dan Tailwind CSS 4.
- Konsistensi dengan design system EvVibe.
- Biaya dependency tambahan.
- Kemudahan reuse di existing architecture.

Jangan sekadar menyebut nama library pada laporan. Identifikasi komponen nyata dan jelaskan pilihan akhirnya.

**Komponen utama yang direkomendasikan:**

- HeroUI v3 `RadioGroup` / `Radio` / `Description`.
- Alternatif: shadcn/ui RadioGroup dengan pola Choice Card, Field, dan FieldDescription.
- Untuk multi-select, evaluasi HeroUI Checkbox atau affectUI Checkbox Card.
- Untuk badge, gunakan komponen Chip/Badge siap pakai dengan varian netral dan solid.
- Gunakan Button yang sudah tersedia di project atau komponen library yang sesuai.

HeroUI sudah terdaftar sebagai dependency proyek. Utamakan reuse dependency ini sebelum memasang library baru.

Jika HeroUI tidak cocok dengan kebutuhan tertentu, gunakan shadcn/ui atau alternatif yang benar-benar memenuhi kriteria.

Jangan menggunakan Magic UI, ReactBits, atau Thinking Orbs untuk menambahkan animasi dekoratif pada card pertanyaan. Library tersebut hanya digunakan jika ada kebutuhan nyata dan komponen yang tepat.

Tidak boleh membuat ulang radio group, checkbox, card selection, atau badge dari nol jika library menyediakan solusi yang layak.

**Custom styling diperbolehkan untuk integrasi desain dan penyesuaian komponen. Custom interaction primitive hanya boleh dibuat bila opsi siap pakai memang tidak memenuhi kebutuhan, disertai alasan teknis.**

## 5. Expected Visual Architecture

Contoh tampilan yang DIINGINKAN:

```
+------------------------------------------------------+
| PERTANYAAN 1                             1 dari 4   |
|------------------------------------------------------|
|                                                      |
| Informasi apa saja yang perlu dicari saat            |
| pengunjung menggunakan pencarian proyek?             |
|                                                      |
| Pilih cakupan pencarian yang sesuai dengan            |
| kebutuhan portofolio.                                |
|                                                      |
| +--------------------------------------------------+ |
| | ( ) Judul, deskripsi, dan teknologi   [Rekomendasi]| |
| |                                                  | |
| |     Pengunjung bisa menemukan proyek melalui     | |
| |     nama, ringkasan, atau teknologi yang          | |
| |     digunakan, tanpa harus mengetahui judulnya.  | |
| +--------------------------------------------------+ |
|                                                      |
| +--------------------------------------------------+ |
| | ( ) Judul dan deskripsi proyek                   | |
| |                                                  | |
| |     Pencarian mencakup nama dan ringkasan         | |
| |     proyek, tanpa mencocokkan teknologi.          | |
| +--------------------------------------------------+ |
|                                                      |
| +--------------------------------------------------+ |
| | ( ) Judul proyek saja                            | |
| |                                                  | |
| |     Pencarian hanya mencocokkan nama proyek.      | |
| |     Cocok untuk daftar proyek sederhana.         | |
| +--------------------------------------------------+ |
|                                                      |
| +--------------------------------------------------+ |
| | ( ) Tentukan sendiri                             | |
| |                                                  | |
| |     Pilih bagian informasi yang ingin dicari.     | |
| +--------------------------------------------------+ |
|                                                      |
|------------------------------------------------------|
|                                         [Konfirmasi] |
+------------------------------------------------------+
```

ASCII di atas menunjukkan struktur, bukan instruksi membuat UI monospaced atau menyalin ukuran mentah.

Hal yang WAJIB:

1. Recommended option adalah pilihan pertama.
2. Badge berada di area heading opsi pertama.
3. Heading dan description berada di dalam setiap pilihan.
4. Semua opsi memakai struktur yang konsisten.
5. Tidak ada lagi recommendation panel di bagian bawah.
6. Opsi lain tetap terlihat dengan kepentingan visual yang setara.
7. Tombol Konfirmasi tetap berada di footer.
8. User harus memilih secara eksplisit.

## 6. Recommended Ordering Logic

Gunakan data rekomendasi dari FIX 01.

Urutan visual:

```
Original data:
A
B
C <- recommended
D

Rendered UI:
C <- recommended
A
B
D
```

Jangan melakukan sort berdasarkan label.

Jangan menyamakan recommended dengan selected.

Jangan mengubah stable option IDs.

Jangan menyebabkan jawaban tersimpan berpindah ke opsi lain setelah reload.

Jangan mengubah urutan kanonis yang digunakan oleh persistence apabila memang diperlukan untuk pemetaan data.

Implementasi sorting sebaiknya menjadi pure presentation transformation yang dapat diuji secara terpisah.

Jika tidak ada rekomendasi valid, jangan memalsukan label rekomendasi.

## 7. Rich Choice Card Design

Setiap answer card harus mempunyai:

- Selection control.
- Heading yang jelas.
- Description dengan hierarki lebih rendah.
- Optional recommendation badge.
- Clickable surface yang jelas.
- Hover state.
- Selected state.
- Focus-visible state.
- Disabled state yang masuk akal.

Struktur visual:

```
CHOICE CARD
  |
  +-- Selection control
  |
  +-- Text content
        |
        +-- Heading
        |     |
        |     +-- Recommendation badge (optional)
        |
        +-- Description
```

Gunakan layout yang tetap rapi ketika heading atau description membungkus menjadi beberapa baris.

Jangan menempatkan radio control di tengah tinggi keseluruhan deskripsi panjang jika itu membuat posisi antarcard terlihat tidak konsisten. Pilih alignment yang mempertahankan kesejajaran heading.

Card tidak boleh mempunyai:

- Nested interactive elements yang invalid.
- Double-click behavior.
- Radio yang sulit difokuskan.
- State selected palsu.
- Animated gradient yang tidak dibutuhkan.
- Glow permanen.
- Border bertumpuk.
- Hover transform yang berlebihan.
- Ornamen ikon acak.
- Shadow besar di setiap pilihan.

Selected state harus terlihat dari perubahan border/control/background yang konsisten, bukan hanya perubahan warna teks.

## 8. Recommendation Badge Design

Hapus gaya sebelumnya:

```
border-emerald/30
bg-emerald/10
text-emerald
```

Jangan menggantinya dengan varian transparan biru, ungu, atau warna neon lainnya.

Gunakan badge solid dengan warna netral dan radius kecil.

Contoh:

```
[Direkomendasikan]
```

Karakter visual:

- Solid background.
- Foreground kontras.
- Neutral palette.
- Tanpa blur.
- Tanpa gradient.
- Tanpa glow.
- Tanpa glassmorphism.
- Tidak harus full pill.
- Padding kecil dan proporsional.
- Tidak lebih dominan daripada heading jawaban.

Gunakan komponen Chip atau Badge yang siap pakai.

Warna hijau tidak cocok sebagai default untuk rekomendasi karena rekomendasi adalah saran, bukan indikator keberhasilan.

Badge hanya muncul pada opsi yang mempunyai rekomendasi valid.

## 9. Remove Redundant Recommendation Panel

Saat ini terdapat:

```
[Option A]
[Option B]
[Option C - Recommended]
[Option D]

+-------------------------------------------+
| Rekomendasi: Option C                     |
| Alasan berdasarkan codebase: ...          |
+-------------------------------------------+
```

Target:

```
[Option C - Recommended]
  Heading
  Description / relevant reasoning

[Option A]
  Heading
  Description

[Option B]
  Heading
  Description

[Option D]
  Heading
  Description
```

Hapus rendering `CodebaseAdaptiveQuestionRecommendation` dari card utama.

Periksa apakah komponen tersebut masih digunakan di tempat lain. Jika sudah tidak memiliki consumer, hapus dead code dan test yang tidak relevan, lalu ganti dengan tests yang menguji struktur dan behavior baru.

Jangan meninggalkan hidden duplicate panel.

Jangan memindahkan panel itu menjadi tooltip, accordion, popover, atau expandable explanation baru.

Informasi yang relevan harus langsung bisa dibaca di deskripsi opsi rekomendasi.

## 10. Improve Main Question Card

Card utama saat ini terasa kurang mempunyai struktur.

Perbaiki:

**Question progress**

Tampilkan dengan ukuran kecil dan alignment konsisten:

```
PERTANYAAN 1                         1 dari 4
```

**Question heading**

Heading harus menjadi fokus utama. Jangan menyamakan ukurannya dengan label metadata.

**Supporting copy**

Jika backend menyediakan penjelasan singkat yang berguna, tampilkan sebagai supporting information.

Jangan mengarang deskripsi statis yang diulang untuk semua pertanyaan.

**Answer area**

Gunakan gap yang konsisten. Ukuran card tidak perlu dibuat berlebihan, tetapi harus cukup lapang untuk dua tingkat teks.

**Footer**

Pisahkan area action secara halus. Tombol Konfirmasi harus mudah ditemukan tetapi tidak mendominasi card.

Jangan menambahkan:

- Progress bar dekoratif.
- Stepper kedua.
- Header tambahan yang mengulang judul.
- Panel recommendations baru.
- Ikon robot/AI.
- Informasi teknis tentang model.
- Statistik palsu.
- Animasi loading buatan.
- Gradient hanya agar tampak modern.

Modernisasi harus berasal dari visual hierarchy, spacing, typography, state design, dan penggunaan komponen yang tepat.

## 11. Custom Answer and Multi-Select

Opsi "Lainnya" atau jawaban kustom juga harus menggunakan konsep heading + description.

Contoh:

```
Tentukan sendiri
Pilih bagian informasi yang ingin
disertakan dalam pencarian.
```

Saat opsi ini dipilih:

- Input jawaban muncul secara natural sebagai bagian dari opsi tersebut.
- Jangan membuat card kedua di luar opsi.
- Focus input bekerja dengan benar.
- Input tidak terhapus saat parent rerender.
- Konfirmasi tidak aktif jika jawaban kustom kosong.
- Existing answer-edit flow tetap bekerja.

Untuk multiselect:

- Gunakan checkbox, bukan radio.
- Semua pilihan tetap mempunyai heading + description.
- Beberapa pilihan dapat dipilih tanpa menghilangkan state lainnya.
- Checkbox keyboard interaction tetap benar.
- Hindari pengiriman dua kali atau kehilangan pilihan setelah restore.

## 12. Responsive and Accessibility

Lakukan responsive design berdasarkan ukuran container, bukan asumsi lebar viewport saja.

Pastikan:

- Teks panjang bisa wrap.
- Heading dan badge tidak saling tumpang tindih.
- Badge dapat turun ke baris berikutnya jika diperlukan.
- Tidak ada horizontal overflow.
- Area klik nyaman di desktop dan perangkat sentuh.
- Keyboard navigation tetap bekerja.
- Focus indicator terlihat.
- Description terhubung secara semantik dengan pilihan.
- Selected dan disabled states terbaca dengan benar oleh assistive technology.
- Dark mode menggunakan kontras yang layak.

Gunakan semantik dari komponen library yang dipilih. Jangan membuat radio group manual yang kehilangan accessibility behavior.

## 14. Required Tests

Periksa behavior menggunakan targeted automated tests:

1. Recommended option rendered first.
2. Stable option identity after presentation ordering.
3. Recommended is not auto-selected.
4. Title and description are associated with each option.
5. No separate recommendation panel.
6. Selection and confirmation.
7. Edit answer.
8. Multi-select.
9. Custom answer.
10. Restored question state.
11. Keyboard accessibility.
12. No regression on answered-question compact card.
13. No accidental cross-feature data leakage.

Jangan membuat test yang hanya menegaskan class Tailwind tertentu atau snapshot pixel.

Gunakan relevant Vitest, Biome, dan typecheck. Tidak perlu browser automation.

## 15. Strict Design Rules

- WAJIB reuse ready-made library components.
- WAJIB melakukan component discovery sebelum implementasi.
- Jangan membuat custom UI hanya karena lebih cepat.
- Jangan membuat UI generik berupa beberapa `<div>` ber-border sebagai pengganti choice card yang proper.
- Jangan memasang banyak library tanpa kebutuhan.
- Jangan menambahkan animasi dekoratif.
- Jangan gunakan gradient, blur, atau glassmorphism pada badge.
- Jangan membuat recommendation explanation card baru.
- Jangan mengubah copy generation secara hardcoded pada frontend.
- Jangan mengubah bagian lain dari aplikasi.
- Jangan menjalankan browser QA, Playwright, Puppeteer, atau screenshot QA.
- Jangan commit, push, merge, atau deploy tanpa izin.

- Rekomendasi valid selalu tampil pertama.
