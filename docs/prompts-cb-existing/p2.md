## 1. MISSION

Perbaiki pengalaman user ketika membuat sesi sync Existing Codebase, meninggalkan halaman sebelum menjalankan prompt CLI, kemudian kembali melalui History.

User melaporkan:

1. Klik Hubungkan Repository.
2. Kredit cukup.
3. Prompt CLI berhasil ditampilkan.
4. User belum menyalin ataupun menjalankan prompt.
5. User meninggalkan halaman.
6. User membuka Project Tersimpan.
7. User memilih repository yang sinkronisasinya belum selesai.
8. Prompt sebelumnya hilang.
9. UI menggantinya dengan pesan teknis bahwa token hanya dikirim sekali.
10. User harus menekan "Coba lagi", padahal belum melakukan apa pun.

**Product problem:** Sistem gagal membedakan recovery normal dari error.

User tidak perlu mengetahui detail internal penyimpanan token.

Namun keamanan one-time credential harus dipertahankan.

## 2. NON-NEGOTIABLE REQUIREMENTS

- Repository yang sudah dibuat harus tetap sama ketika user kembali.
- History tidak boleh mendapatkan repository duplikat.
- Planning, snapshot, dan data existing tidak boleh dihapus.
- Jika prompt masih tersedia secara aman dalam memori aplikasi dan masih valid, tampilkan prompt yang sama.
- Jika prompt asli sudah tidak bisa dipulihkan, tampilkan recovery action yang jelas.
- Jangan otomatis mengganti credential saat user membuka halaman.
- Jangan mematikan token yang mungkin sedang digunakan agent secara diam-diam.
- Jika token sudah kedaluwarsa sebelum upload, user dapat membuat prompt baru untuk repository tersebut.
- Jika CLI sedang berjalan, tampilkan progress aktual, bukan recovery prompt.
- Jika upload sudah selesai, lanjutkan analysis lifecycle, bukan meminta sync ulang.
- Jangan menghidupkan kembali credit approval.
- Kredit cukup tetap menghasilkan prompt CLI langsung ready saat new onboarding.

Current architecture:

- Sync token is generated server-side.

- Session read returns metadata, not raw token.
- `useOnboardingRecovery` attempts to recover the existing session.

**Keep the one-time credential security architecture.**

Do not attempt to reverse the token hash.

## 4. UNDERSTAND THE ACTUAL FAILURE

Current recovery flow is conceptually:

```
History
   │
   ▼
Open unfinished repository
   │
   ▼
GET repository status
   │
   ▼
Session waiting_for_cli
   │
   ▼
POST recover
   │
   ▼
Original token not available
   │
   ▼
HTTP 409 recovery required
   │
   ▼
Technical error + "Coba lagi"
```

This presentation is wrong.

The user has not necessarily encountered a failed sync.

The original session exists, but its credential may no longer be available to the browser.

Treat it as a recoverable user action, not a failure requiring generic retry.

## 6. CASE A — SAFE IN-MEMORY PROMPT RECOVERY

Investigate whether current TanStack Start application architecture can safely preserve a short-lived sync prompt across client-side route navigation within the same running application instance.

If feasible:

- Use an existing app-level state provider or lifecycle-bound memory abstraction.
- Key entries by authenticated user, codebase ID, session ID, and validity.
- Keep raw credential in memory only.
- Do not serialize to HTML.
- Do not persist to database in plaintext.
- Do not store in localStorage.
- Do not store in sessionStorage.
- Do not put token in URL.
- Do not put token in logs or analytics.
- Do not expose token through generic loader data or History API.
- Clear entries on logout, credential expiration, replacement, and account change.
- Respect session expiry from server.
- Do not reuse a prompt for another codebase/session.
- Do not introduce global memory that can mix users during SSR.

If the app instance can recover the valid prompt:

```
User enters onboarding
        │
        ▼
CLI prompt generated
        │
        ▼
Navigate to History
        │
        ▼
Return to same repository
        │
        ▼
Valid credential still available
in safe client memory
        │
        ▼
SAME CLI PROMPT VISIBLE
```

**However, never fabricate successful recovery.**

If a secure memory implementation is not feasible or would create serious complexity, retain the secure one-time behavior and implement clear replacement UI instead.

Do not introduce a new browser storage/security vulnerability just to avoid one extra recovery click.

If server confirms a usable snapshot:

```

```

Then:

- Do not offer a new CLI token as the default action.
- Do not request the user to upload the repository again.
- Restore analysis progress or completed state.
- If analysis failed, expose the existing analysis retry flow.
- Keep the same snapshot.
- Do not create another History entry.

## 11. SAFELY REPLACE A SESSION

Audit:

```
src/features/codebase/services/sync-session-prepare.server.ts
src/features/codebase/services/sync-session-route.server.ts
```

Current `prepareSyncSession()` already uses:

- Advisory transaction locking.
- Latest session lookup.
- Credential usability checks.
- Explicit `replaceSessionId`.
- Prevention of replacement for uploaded snapshots.
- Prevention of replacement while a valid CLI connection is active.

Preserve and strengthen these safeguards.

When user explicitly clicks `Buat prompt baru`:

1. Verify the authenticated user owns the codebase.
2. Verify the active session belongs to that codebase.
3. Lock and recheck latest session state.
4. Reject replacement if CLI is actively syncing.
5. Reject replacement if snapshot upload already completed.
6. Revoke/invalidate the old waiting credential when replacement is permitted.
7. Create a new credential for the same codebase.
8. Return the new one-time prompt.
9. Update frontend active session identity atomically.
10. Reset only session-specific progress, not repository/planning data.

No race should create duplicate repository records.

No repeated click should produce uncontrolled session chains.

## 12. EXPLICIT ACTION &amp; IDEMPOTENCY

Protect against:

- Double click on `Buat prompt baru`.
- Repeated POST due to network retry.
- Response lost after replacement committed.
- Multiple tabs targeting the same session.
- Refresh during replacement.
- Concurrent CLI handshake.
- Stale session ID returned after newer replacement.
- Session expiration during request.

Use existing server locking and idempotency protections where possible.

A lost replacement response must not force a new codebase.

Do not weaken security by returning an old plaintext token that was not designed to be retrievable.

## 13. FRONTEND STATE OWNERSHIP

Current `useOnboardingRecovery` may set:

```
setError(result.message)
```

when the server returns a recovery-required result.

Do not present a normal recovery requirement as generic error.

Model the distinction clearly:

```
PROMPT_READY
PROMPT_UNAVAILABLE_RECOVERABLE
PROMPT_EXPIRED_RECOVERABLE
CLI_ACTIVE
UPLOAD_COMPLETE
SESSION_REPLACEMENT_PENDING
SESSION_REPLACEMENT_FAILED
```

These names are conceptual; use project conventions.

Do not mix:

```
PROMPT_UNAVAILABLE
+
SPINNER CONNECTING AGENT
```

unless server actually reports a real CLI connection.

When replacement succeeds, obsolete recovery message must disappear.
