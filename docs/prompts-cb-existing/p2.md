## 1. Mission

Audit dan tingkatkan reliability proses AI generation pada Existing Codebase, khususnya:

- Question generation.
- Feature Specification generation.
- PRD generation.
- Acceptance Criteria generation.
- Task/Kanban generation.

Target: refresh browser, temporary network disconnection, tab close, dan request timeout tidak menyebabkan hilangnya progres yang telah disimpan, duplicate generation, double credit usage, atau workspace yang tidak mampu melanjutkan proses existing.

**Jangan mengklaim seluruh proses refresh-safe sebelum mekanisme backend-nya benar-benar mendukung.**

## 3. Existing Risks to Investigate

Current implementation already has partial protection:

- `featuresStatus` untuk membedakan pending/generating/completed.
- Feature generation idempotency checks.
- Artifact hydration.
- Persisted stage reconciliation.
- SSE streaming untuk beberapa generation operations.
- Client run state dengan startedAt/finishedAt.

Namun perlu diverifikasi:

1. Apakah request AI tetap berjalan ketika browser refresh?
2. Apakah response stream disconnect membatalkan model generation?
3. Apakah in-progress state disimpan di DB?
4. Bagaimana mendeteksi operasi yang berhasil di backend tetapi tidak diterima client?
5. Bagaimana memulihkan status `generating` setelah process crash?
6. Apakah double generation mengonsumsi kredit dua kali?
7. Apakah retry mengirim ulang seluruh generation?
8. Apa yang terjadi ketika user berpindah feature saat request berjalan?
9. Apakah restart worker/server menghasilkan stuck operation?

## 5. Implementation Strategy

### A. Reuse Infrastructure Before Building New Systems

First inspect:

- Existing DB generation statuses.
- Worker/queue infrastructure.
- Existing background jobs.
- Existing polling/SSE infrastructure.
- Existing project and artifact version tables.
- Existing request idempotency mechanisms.

Reuse these whenever possible.

Do not introduce an unnecessary new queue provider or multiple overlapping job systems.

If durable execution cannot safely be implemented using existing infrastructure, introduce the smallest cohesive architectural change that fully supports it. Document any deployment or migration requirements.

Do not simulate background execution with a client timer or a promise stored only in browser memory.

### B. Durable Operation Identity

Each accepted generation operation must have a stable identity.

Associate the operation with:

- Authorized owner/project.
- Codebase and source snapshot where relevant.
- Generation stage.
- Input revision or content hash.
- Attempt/status.
- Creation and completion timestamps.
- Persisted artifact/version ID after success.
- Error classification after failure.

Use idempotency keys and appropriate database constraints.

An identical retry must not create a second operation when the first operation is still running or has already succeeded.

A genuinely changed input may require a new operation/version.

### C. Correct Lifecycle

Suggested states:

```
queued
  ↓
running
  ├── completed
  ├── failed
  └── cancelled
```

Add retry/lease states only when technically needed.

Do not mark an operation completed based solely on an HTTP 200 or a finished SSE stream.

Completion must correspond to a valid persisted artifact or completed question set.

### D. Refresh Recovery

On workspace hydration:

1. Resolve active project and feature.
2. Load persisted artifacts.
3. Load latest relevant generation operation.
4. Reconcile operation status against persisted artifacts.
5. Reconnect to events/polling if still running.
6. Present the accurate stage without restarting generation.

Do not execute new AI generation automatically during hydration.

If the operation completed before refresh, load the persisted artifact.

If the operation failed, show one contextual retry action.

If the operation is still running, resume monitoring the existing operation.

### E. Network Disconnection

Distinguish:

- Request never reached server.
- Request accepted but acknowledgment lost.
- Server job still running.
- Job completed but response lost.
- Backend job failed.

Client must reconcile the operation before retrying.

Never assume a network exception means the server did not accept the request.

For offline input drafts, prioritize server-backed persistence. If browser-local draft recovery is required, do not persist credentials, sync tokens, or sensitive source contents insecurely. Avoid silent auto-submission when connectivity returns if it could trigger paid generation.

Show concise connection feedback only when relevant:

```
Koneksi terputus
Progres tersimpan. Menghubungkan kembali...
```

Only use "Progres tersimpan" when persistence has actually been confirmed.

### F. Server Crash / Stuck Generation

If durable jobs are introduced:

- Track job ownership/lease when required.
- Detect abandoned in-progress jobs.
- Use bounded retries/backoff.
- Prevent duplicate worker execution.
- Reconcile partial results.
- Preserve already-persisted artifacts.
- Record terminal failure states.

A process restart must not leave the project permanently stuck in `generating`.

### G. Credits and Idempotency

Generation retry must never silently double-charge the user for one accepted operation.

Audit billing/credit reservation, deduction, refund, and completion semantics.

Make accounting idempotent using stable operation identity and database transactions.

If the model/provider fails, expose the actual outcome and ensure accounting follows existing product policy.

### H. Project Isolation

Switching from Feature A to Feature B must never cause:

- Feature A result displayed in Feature B.
- Feature B task generation using Feature A inputs.
- Stale request overwriting the current editor.
- Workspace returning to the wrong stage.

Use explicit project and operation identity checks.

### I. AI Streaming

Maintain genuine streaming where available.

If reconnecting to a stream, either replay persisted events or show the current known operation status. Do not fabricate earlier streamed tokens.

Do not expose raw private model reasoning as a requirement. Show safe, high-level activity events that genuinely originate from execution.

## 8. Testing Matrix

Mandatory non-browser tests:

- Refresh while questions are generating.
- Refresh while Feature is generating.
- Refresh while PRD/AC/Task is generating.
- Disconnect after server accepts request.
- Disconnect before server receives request.
- Response lost after successful artifact persistence.
- Duplicate requests with same idempotency key.
- Different inputs with different operation identities.
- Server process/worker interrupted.
- Stale generating status recovered correctly.
- Failed operation retried once.
- Two browser tabs monitoring the same operation.
- Project switch during generation.
- Credit accounting remains correct.
- Unauthorized users cannot read operation state.
- Completed artifact never regenerated on simple reload.

Use integration tests, mocked network interruptions, controlled abort signals, and isolated job lifecycle tests.

If DB migrations are required, validate migration compatibility and rollback/recovery implications.

**Do not perform browser QA, Playwright, Puppeteer, browser-based E2E, manual browser verification, or screenshot testing.**

## 9. Definition of Done

Each stage has reliable persisted state, idempotent execution, explicit recovery semantics, and UI reconciliation.

If a long-running request remains intrinsically connection-bound after implementation, state that limitation clearly. Do not claim full refresh safety without proving it.

Final report:

- Durable operation model.
- Schema/API changes.
- Recovery strategy.
- Credit safety verification.
- Automated test results.
- Remaining limitations and deployment requirements.
