# P09 — Scalable Feature Plan Management

**Branch:** `feature/vibeplan-existing-codebase`  
**Complexity:** COMPLEX

## Problem statement

The Existing Codebase workspace allows multiple feature plans under one synchronized repository.

Currently, `CodebasePlanSwitcher` renders feature plans in a dropdown using a direct `[plans.map](http://plans.map)(...)` approach.

As the number of plans grows, the dropdown may become too long and difficult to navigate.

There is also no clear feature-level management action directly within this switcher.

Users need a scalable way to find, organize, archive, and, when appropriate, delete feature plans.

## Critical distinction

A repository and a feature plan are different entities.

Example:

```
Repository: Ghazy Portofolio
│
├── Filter dan Pencarian Proyek
├── Sistem Tema
├── Optimasi Navigasi
├── Perbaikan SEO
└── Integrasi Form Kontak
```

Deleting a feature must not delete the repository or unrelated feature plans.

## Required improvements

### 1. Searchable dropdown

Add search so users can find plans by name.

Search should be responsive and should not trigger unnecessary server requests for every keystroke if the currently loaded dataset can be filtered locally.

For a large dataset, examine whether existing server-side pagination/search is more appropriate.

### 2. Bounded list height

Set a reasonable maximum height for the dropdown list with an internal scroll region.

The dropdown must not extend beyond the viewport.

Keep the search and `Buat fitur baru` actions accessible.

### 3. Useful plan metadata

Show:

- Feature name.
- Current planning readiness.
- Relevant task progress when available.
- Clear active selection.

Avoid technical IDs, meaningless badges, decorative status dots, and unnecessarily long timestamps.

### 4. Feature management actions

Introduce contextual actions via an existing Dropdown Menu primitive:

```
[...]
  Ubah nama
  Arsipkan
  Hapus fitur
```

Archive is preferred as a non-destructive way to declutter active plans.

If archive requires new persistence, inspect the existing schema and design a proper versioned change. Do not simulate archive only by hiding data locally.

### 5. Permanent deletion safety

Permanent deletion must use a feature-specific server action with:

- Authentication.
- Tenant ownership verification.
- Feature ownership under the correct repository.
- Explicit destructive confirmation.
- Correct artifact and dependency cleanup.
- Clear handling of active plan deletion.
- Correct handling of deleting the last feature.
- Protection against accidentally deleting repository onboarding context or unrelated plans.

Do not reuse repository deletion merely because it is easier.

## Confirmation UX

```
Hapus fitur?

"Filter dan Pencarian Proyek" beserta
planning dan riwayat terkait akan dihapus
secara permanen.

Tindakan ini tidak dapat dibatalkan.

[Batal]                  [Hapus fitur]
```

Only state that all related data will be deleted if the backend contract actually guarantees that behavior.

Never silently delete planning data.

## State synchronization

After archive, rename, or delete:

- Update the plan list using the server's authoritative result.
- Preserve stable active plan identity.
- Do not show stale documents from a deleted plan.
- Do not navigate to a nonexistent feature.
- Reconcile workspace history correctly.
- Ensure active Kanban and conversation states belong to the selected feature.

## Mandatory component exploration

Inspect HeroUI, shadcn, Magic UI, React Bits, ThinkingOrbs, AffectUI, TuffUI, CUI, and SakaniUI.

Use existing Dropdown Menu, searchable Command/Combobox, ScrollArea, and Alert Dialog components where suitable.

Do not implement a custom dropdown, keyboard interaction engine, or destructive dialog from scratch when available components already solve those concerns.
