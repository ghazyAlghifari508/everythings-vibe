# FIX 09 — Existing-Codebase-Aware Planning Generation &amp; Strict Scope Grounding

**Repository:** `ghazyAlghifari508/everythings-vibe`  
**Branch:** `feature/vibeplan-existing-codebase`

## Mission

Perbaiki kualitas pipeline AI planning Existing Codebase agar Feature Specification, PRD, Acceptance Criteria, dan Task benar-benar didasarkan pada:

1. Permintaan asli user.
2. Jawaban klarifikasi yang sudah diberikan.
3. Source code dan arsitektur repository yang tersedia.
4. Perubahan implementasi yang benar-benar diperlukan.

Existing Codebase tidak boleh menghasilkan implementation plan seolah-olah user sedang membangun aplikasi baru dari nol.

Ini adalah perbaikan AI orchestration, prompt architecture, context grounding, dan output validation — bukan sekadar mengubah wording prompt.

## Reported Problem

Contoh nyata:

User memiliki aplikasi Ocean Guard, yaitu website edukasi dan konservasi laut berbasis React/Vite.

User meminta fitur pencarian artikel dan filter kategori.

Namun hasil Task/Kanban ikut memasukkan pekerjaan seperti:

- Sistem manajemen akun.
- Autentikasi klien.
- RBAC Route Guard.
- Dashboard.
- Penyimpanan sesi yang tidak diminta.

Task tersebut tidak otomatis relevan hanya karena sistem secara umum mengenali layer frontend/backend atau karena model dapat menghubungkannya dengan suatu AC.

### Known Concern

Task generation sudah menerima codebase context, tetapi masih menggunakan shared `TASK_GENERATION_PROMPT` yang memiliki aturan 5-layer decomposition sangat ketat.

Investigasi apakah aturan tersebut membuat AI menganggap setiap layer wajib diimplementasikan, bahkan ketika perubahan hanya menyentuh client-side behavior.

Jangan langsung menyimpulkan bahwa satu prompt adalah satu-satunya penyebab. Scope expansion bisa bermula sejak Feature Specification, PRD, atau AC.

## Workstream A — Separate Planning Modes

Bedakan secara eksplisit:

**Greenfield mode**

AI merencanakan aplikasi baru berdasarkan kebutuhan user.

**Existing Codebase mode**

AI merencanakan perubahan terhadap aplikasi yang sudah ada.

Kedua mode boleh berbagi validation schemas, output models, dan reusable utilities.

Tetapi instruksi generasi harus mempertimbangkan perbedaan fundamental tersebut.

Jangan menduplikasi seluruh service layer hanya untuk memiliki dua prompt.

Implementasikan composition/conditional directives yang jelas berdasarkan `projectMode`.

## Workstream B — Build an Accurate Change Scope

Sebelum menghasilkan planning pada existing codebase, AI perlu memahami:

- Existing relevant functionality.
- Relevant components/modules.
- Current data flow.
- Existing routing.
- Available dependencies.
- Relevant conventions.
- Technical constraints.
- Requested behavior.
- Missing behavior.
- Unchanged areas.

Gunakan codebase analysis/context yang benar-benar tersedia. Jika metadata yang tersedia tidak cukup untuk menentukan suatu file atau perilaku, jangan mengarangnya.

Jika perlu, perbaiki konteks yang dipasok ke generator agar mencakup bukti yang relevan, tanpa otomatis membanjiri model dengan seluruh repository.

Prioritas source of truth:

1. Explicit user intent dan confirmed answers.
2. Verified repository evidence.
3. Persisted Feature/PRD/AC yang telah divalidasi scope.
4. Technical inference yang benar-benar diperlukan.

Inference tidak boleh berubah menjadi product requirement baru tanpa dasar.

## Workstream C — Conditional Technical Decomposition

Untuk existing codebase, setiap technical layer harus bersifat kondisional.

Jangan mewajibkan:

- Database migration.
- Backend endpoint.
- Authentication.
- Authorization system baru.
- Dashboard.
- State management library baru.
- Infrastructure baru.

Hanya karena template 5-layer memilikinya.

Contoh:

Jika pencarian artikel bisa dilakukan dari data lokal menggunakan komponen dan state yang sudah ada, task harus memanfaatkan pendekatan tersebut.

Jika repository menggunakan server-side search API, task boleh mencakup perubahan service/API apabila benar-benar diperlukan.

Jika kebutuhan pencarian secara eksplisit mensyaratkan login atau permission, task terkait authorization boleh dibuat berdasarkan requirement dan bukti tersebut.

Dengan kata lain:

**Jangan melarang layer teknis tertentu secara mutlak, tetapi wajibkan justifikasi yang dapat ditelusuri.**

### Decomposition Rules

- One task = one coherent implementation deliverable.
- Task tidak boleh membangun ulang komponen yang cukup dimodifikasi.
- Pisahkan tanggung jawab bila memang dibutuhkan.
- Jangan membuat layer fiktif.
- Jangan memaksakan jumlah task.
- Jangan membuat empty/fake supporting tasks.
- Jangan membuat task yang hanya ada karena contoh di system prompt.
- Pertahankan priority berdasarkan impact, bukan layer.
- Gunakan file path aktual hanya jika didukung repository evidence.

## Workstream D — Scope-Aware Feature &amp; PRD

Pastikan Feature Specification dan PRD tidak melebar dari kebutuhan awal.

PRD harus menjelaskan:

- Existing product context.
- Requested feature behavior.
- User flow yang terdampak.
- Relevant screens.
- Data flow.
- Technical constraints.
- Integrasi dengan bagian existing.
- Non-goals / out-of-scope bila relevan.

Jangan secara otomatis membuat daftar screen seperti Dashboard, Account Settings, Admin Panel, Login, atau Register jika tidak termasuk requirement.

Untuk existing aplikasi frontend-only, jangan mengarang internal database schema.

Jangan membangun system architecture baru hanya demi melengkapi template PRD.

Jika suatu perubahan memerlukan penambahan modul baru, jelaskan alasannya berdasarkan kebutuhan nyata.

## Workstream E — AC &amp; Task Traceability

Pastikan setiap Acceptance Criterion berhubungan dengan requirement yang valid.

Task harus mengacu pada Feature/PRD/AC yang berada dalam scope original request.

Namun **AC coverage saja tidak cukup** untuk menjamin tidak ada scope creep.

Perbaiki validation agar juga mempertimbangkan konsistensi:

- Original intent.
- Confirmed clarification answers.
- Feature scope.
- PRD requirements.
- AC.
- Task deliverables.
- Repository context.

Jangan menggunakan hardcoded keyword blacklist seperti "dashboard", "account", atau "authentication" untuk menolak output. Fitur tersebut bisa relevan dalam project lain.

Gunakan mekanisme validasi scope yang generalizable dan berbasis evidence.

Jika output tidak dapat dibuktikan relevan, jangan diam-diam memasukkannya ke task tree.

Jika PRD/AC upstream sudah terkontaminasi scope yang salah, sistem harus mampu mengidentifikasi masalah tersebut daripada menganggap semua task valid hanya karena AC juga salah.

## Workstream F — Existing Code Reuse

Hasil AI harus mengutamakan:

- Reuse existing functions.
- Reuse existing components.
- Reuse existing styles.
- Reuse existing routes.
- Reuse existing API/data contracts.
- Extend existing modules where appropriate.
- Preserve backward compatibility.

Jangan menyuruh coding agent membuat ulang seluruh aplikasi.

Jika file/modul tertentu disebut dalam task, path dan fungsinya harus berasal dari repository evidence yang memang ada, atau dinyatakan secara jelas sebagai proposed new file.

Jangan mencampurkan keduanya.

## Workstream G — Data Safety &amp; Existing Task Progress

Ini sangat penting.

User mungkin sudah memiliki 30 task, dan AI coding agent telah mengimplementasikan beberapa di antaranya.

Perbaikan generator **tidak boleh otomatis**:

- Menghapus task lama.
- Mereset Kanban.
- Mengubah completed task menjadi To Do.
- Menghapus PRD/AC versions.
- Mengganti active planning tanpa konfirmasi.
- Mengonsumsi credit untuk regenerasi yang tidak diminta.

Perbaikan prompt berlaku untuk generasi berikutnya.

Jika diperlukan mekanisme memperbaiki planning legacy yang sudah tidak relevan, gunakan revision/regeneration workflow yang eksplisit dan aman.

Pertahankan histori dan progress lama sampai user menyetujui tindakan yang berdampak terhadap data.

## Workstream H — Quality Verification

Buat scenario-based tests untuk beberapa kelas aplikasi.

### Scenario 1 — Frontend-Only Article Search

Repository React/Vite, artikel lokal, user meminta search/filter.

Expected:

- Client-side search jika cocok dengan arsitektur.
- Category filtering.
- URL state hanya jika diminta.
- Empty state dan reset behavior.
- Tidak ada auth/dashboard/DB baru tanpa dasar.

### Scenario 2 — Existing Backend Search

Repository memiliki API search dan database.

Expected:

- Task mengikuti arsitektur existing.
- Backend/API changes hanya jika requirement membutuhkannya.
- Tidak membangun backend kedua.

### Scenario 3 — Existing Auth Feature

User memang meminta fitur login/permission.

Expected:

- Auth-related tasks diperbolehkan.
- Task mengikuti arsitektur existing dan requirement.

### Scenario 4 — Small UI Revision

User hanya meminta perubahan kecil pada existing screen.

Expected:

- Scope dan jumlah task proporsional.
- Tidak membangun screen, route, API, atau data model baru secara tidak perlu.

### Scenario 5 — Complex Feature

User meminta fitur lintas frontend/backend/data.

Expected:

- Dekomposisi lengkap jika memang diperlukan.
- Semua task memiliki requirement traceability.
- Tidak ada scope expansion tanpa justifikasi.

### Scenario 6 — Existing Implementation Already Covers Requirement

Repository sudah memiliki sebagian behavior yang diminta.

Expected:

- Tidak membuat task untuk membangun ulang fitur yang sudah benar.
- Hanya merencanakan perubahan yang masih dibutuhkan.
- Existing behavior dipertahankan.

Tests harus memverifikasi kontrak prompt/context/validation dan dapat menggunakan fixtures tetap, tanpa memerlukan pemanggilan AI live untuk setiap test.

Jika evaluasi berbasis model tersedia dalam toolchain existing, gunakan sebagai evaluasi tambahan, bukan sebagai satu-satunya bukti correctness.

## Constraints

- Jangan hardcode product-specific task examples sebagai hasil final.
- Jangan menambah unrelated requirements.
- Jangan menghapus greenfield behavior yang sudah benar.
- Jangan mengubah task schema tanpa kebutuhan.
- Jangan membuat abstraksi prompt besar yang tidak diperlukan.
- Jangan menyamakan model compliance dengan task correctness.
- Jangan menyembunyikan scope creep melalui filtering UI.
- Jangan membuat fallback output generik saat context grounding gagal.

Jika perubahan menyentuh UI, lakukan component discovery pada shadcn, HeroUI, Magic UI, React Bits, dan Thinking Orbs sebelum implementasi. Wajib reuse komponen siap pakai yang sesuai; tidak perlu membuat UI baru jika fokus perubahan cukup pada backend.
