## 4. CONFIRMED ROOT CAUSE CANDIDATES

### A. Backend Creates New IDs for Every Request

Current `handleCodebaseCreate()` membuat:

```
const id = crypto.randomUUID();
```

Lalu memasukkan codebase baru:

```
await tx.insert(codebases).values({
  id,
  userId: user.id,
  name: codebaseName,
});
```

Selanjutnya dibuat sync session baru.

Tidak ditemukan server-side idempotency key yang mengikat pengulangan request pada satu logical onboarding attempt.

Artinya, repeated valid POST dapat membuat banyak repository.

### B. Frontend Guard Only Prevents Concurrent Requests

Current frontend menggunakan:

```
const createInFlight = useRef(false);
```

Ini membantu mencegah request bersamaan selama ref tersebut masih true.

Namun setelah request selesai:

```
createInFlight.current = false;
```

User masih dapat memicu request lagi.

**Ref guard bukan pengganti server-side idempotency.**

### C. Stale Locked Prompt Encourages Repeated Clicks

Pada flow sebelumnya, `creditStatus` lama dapat mempertahankan locked prompt meskipun backend sudah membuat repository dan mengembalikan session payload.

Akibatnya user mengira klik pertama gagal.

### D. Response Parsing Failure After Successful DB Commit

`requestCreateCodebase()` dapat mengembalikan outcome `rejected` jika response yang diterima tidak memenuhi schema yang diharapkan.

Tetapi backend mungkin sudah berhasil membuat repository.

Jika user mencoba lagi dengan request baru, repository lain dapat dibuat.

**Perbaiki recovery setelah partial success atau lost response, bukan hanya click handler.**

## 6. IMPLEMENT TRUE SERVER-SIDE IDEMPOTENCY

Satu logical onboarding attempt harus mempunyai stable identity.

Contoh kontrak konseptual:

```
type CreateCodebaseRequest = {
  onboardingAttemptId: string;
};
```

Ini contoh, bukan keharusan menggunakan nama tersebut.

The server must bind:

```
authenticatedUserId + onboardingAttemptId
```

to one logical repository creation.

### Required behavior

```
REQUEST A
  onboardingAttemptId = X
       │
       ▼
  Create Codebase A
       │
       ▼
  Create initial Sync Session A
       │
       ▼
  Commit
```

Repeated request:

```
REQUEST B
  onboardingAttemptId = X
       │
       ▼
  Existing operation found
       │
       ▼
  RETURN / RECOVER Codebase A
```

Not:

```
REQUEST B
  onboardingAttemptId = X
       │
       ▼
  Create Codebase B  ❌
```

### Implementation Requirements

- Use a stable idempotency key tied to authenticated user and logical attempt.
- Generate new identity only for a genuinely new onboarding intent.
- Enforce uniqueness at database level.
- Use atomic transaction or conflict-safe database operation.
- Prevent race conditions between simultaneous requests.
- Correctly handle two requests arriving before the first transaction commits.
- Do not depend only on client-side debounce.
- Validate idempotency key format and ownership.
- Reject attempts to reuse the same key with incompatible operations.
- Keep idempotency metadata bounded and lifecycle-managed.
- Do not expose another user's repository through key guessing.
- Do not use repository name as an idempotency identifier.

**A frontend** `useRef`**, disabled button, or 500 ms debounce is insufficient by itself.**

## 7. DISTINGUISH RETRY FROM INTENTIONAL NEW REPOSITORY

Very important:

A user can intentionally connect two different repositories.

Do not implement naive global deduplication by repository name.

Both repositories may legitimately use the same folder name.

### Correct semantics

```
INTENT A — Hubungkan repository
    └── onboardingAttemptId A
        └── Repository A

Repeated action / retry A
    └── onboardingAttemptId A
        └── SAME Repository A

INTENT B — Hubungkan repository baru
    └── onboardingAttemptId B
        └── Repository B
```

Jangan menjadikan seluruh kunjungan ke `/plan/codebase?intent=new` sebagai satu attempt yang selalu sama untuk selamanya.

Sebaliknya, jangan pula membuat attempt baru setiap React rerender.

Define explicit lifecycle for:

- New user intention.
- Refresh of existing intention.
- Retry of failed request.
- Return to existing incomplete repository.
- Explicitly starting another repository.

## 8. FRONTEND ATTEMPT IDENTITY

Frontend should:

1. Establish one onboarding attempt identity when user explicitly starts connection.
2. Reuse that identity across repeated request attempts.
3. Preserve the nonsecret identity across refresh/recovery when needed.
4. Never generate a new identity just because a component rerendered.
5. Prevent duplicate in-flight requests.
6. Bind successful response to the current attempt.
7. Ignore stale responses from older attempts.
8. Disable or remove create action once creation succeeds.
9. Show actual CLI prompt after success.

Session storage may be considered for the NONSECRET attempt identity if consistent with project conventions.

**Do not store raw sync tokens in localStorage/sessionStorage merely to solve duplicate creation.**

The backend remains authoritative.

## 10. ONE-TIME SYNC TOKEN RECOVERY

Current sync credentials are designed to be delivered once, while only their hash is persisted.

Preserve this security model.

If original response containing the raw token is lost:

- Server must not pretend the original plaintext token can be recovered from its hash.
- Recover original repository identity using idempotency metadata.
- If necessary, provide a secure flow to issue a replacement sync session/token under the SAME repository.
- Do not mint a new repository.
- Do not rotate active CLI credentials silently while an agent may be using them.
- Verify session state before replacement.
- Ensure old token invalidation is explicit and safe.
- Keep credential lifetime bounded.
- Do not log plaintext tokens.
- Do not expose raw credentials in History list API.

Expected:

```
REPOSITORY A EXISTS
       │
       ▼
Raw token unavailable
       │
       ▼
Issue a valid replacement session
for Repository A
       │
       ▼
CLI prompt ready

History:
Repository A only
```

Not:

```
Repository A
Repository B
Repository C
```

## 11. SESSION CREATION AND DATABASE ATOMICITY

Current create flow inserts:

```
Codebase
   +
Initial Sync Session
```

within one transaction.

Preserve atomicity.

If new idempotency mapping is introduced, it must be consistent with that transaction.

Required invariant:

```
ONE ATTEMPT
    │
    ├── ONE CODEBASE ID
    │
    └── ONE CANONICAL INITIAL SYNC OPERATION
```

Additional replacement sessions are allowed only through explicit safe session recovery, still attached to the same codebase.

Never create multiple repositories because a session token expired.

If persistence fails:

- Roll back incomplete creation appropriately.
- Return typed error.
- Do not leave orphan session rows.
- Do not claim success before commit.

## 13. HISTORY SEMANTICS FOR INCOMPLETE REPOSITORIES

Avoid polluting History with repeated unfinished placeholders.

However, **do not automatically delete all records named "Repository Lokal".**

A provisional name alone does not prove a repository is duplicate or abandoned.

Distinguish:

```
A. Legitimate synced repository
B. Incomplete but recoverable sync session
C. Truly abandoned empty onboarding record
D. Duplicate accidentally created by repeated POST
```

Recommended:

- Prevent C/D from being generated repeatedly.
- Keep B recoverable.
- Preserve snapshots and planning artifacts.
- For legacy duplicates, provide safe cleanup or review based on verified relationships and absence of valuable data.
- Do not silently merge or delete repositories with plans, snapshots, or ongoing tasks.
- Do not assume two records with the same name represent the same local repository.

If existing duplicate records need manual cleanup, use the existing History bulk-delete feature.

Do not introduce destructive automatic migration without evidence.
