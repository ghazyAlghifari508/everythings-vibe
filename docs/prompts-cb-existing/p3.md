## 1. Objective

Fix the broken **Sync Ulang** functionality in VibePlan Existing Codebase.

The user successfully synchronized a repository, completed AI analysis, and entered the three-panel workspace. However, clicking **Sync ulang** produces errors related to an expired or unavailable sync token.

Reported symptoms:

```
Salin instruksi sync ulang

Token sync sudah kedaluwarsa atau belum tersedia.

[Dapatkan token baru]
```

When attempting to recover:

```
Sesi sync gagal dibuat. Coba lagi.

[Coba lagi]
```

The backend has also returned HTTP `409`, including the error code:

```
SYNC_SNAPSHOT_UPLOADED
```

This is a fundamental lifecycle problem.

**Resync is NOT equivalent to retrying an existing initial sync session.**

A repository that already has a completed snapshot must be allowed to start a new synchronization operation without replacing or corrupting the completed snapshot.

Do not work around this by ignoring server errors, disabling guards, or automatically creating a different codebase.

## 3. Three Operations That MUST Remain Distinct

### Operation A — Resume an Unfinished Sync

```
Repository A
    │
    ▼
Existing waiting session
    │
    ▼
Recover available session information
    │
    ▼
Continue the SAME attempt
```

This is not resync.

### Operation B — Replace an Expired, Unused Session

```
Repository A
    │
    ▼
CLI never connected
    │
    ▼
Session/token expired
    │
    ▼
Explicit replacement
    │
    ▼
New credential under Repository A
```

This is recovery.

### Operation C — Synchronize an Existing Repository Again

```
Repository A
    │
    ├── Completed Session 1
    │      └── Snapshot 1
    │             └── Analysis 1
    │
    ▼
USER CLICKS "SYNC ULANG"
    │
    ▼
Create Session 2 for Repository A
    │
    ▼
New CLI prompt
    │
    ▼
Upload Snapshot 2
    │
    ▼
Analysis 2
    │
    ▼
Update repository context safely
```

**Operation C must not require replacing Session 1.**

Implement explicit server semantics for these different intentions, following the existing architecture and naming conventions.

A dedicated `resync` action is acceptable if warranted by the current implementation.

## 5. Repository and Snapshot Integrity

The following invariants are mandatory:

```
Codebase A
│
├── Sync Session 1
│   ├── Snapshot 1
│   └── Analysis 1 READY
│
├── Existing Feature Plans
│   ├── Feature
│   ├── PRD
│   ├── AC
│   └── Tasks / Kanban progress
│
└── Sync Session 2
    ├── Snapshot 2
    └── Analysis 2
```

Requirements:

- Keep the same `codebaseId`.
- Create a new `syncSessionId` for a genuine new resync attempt.
- Do not create another repository History entry.
- Do not delete previous snapshots.
- Do not delete feature plans.
- Do not reset PRD, AC, or task progress.
- Do not silently overwrite a user's revisions.
- Do not bind an old analysis to a new snapshot.
- Do not switch the workspace to an incomplete snapshot.
- A failed new resync must not destroy the previously usable workspace.
- A successful new snapshot can become the current snapshot only according to an explicit, consistent lifecycle.
- Existing plan references to older snapshots must be handled safely.

If necessary, document how the workspace chooses its active snapshot and what happens to planning documents created before the resync.

Do not invent new repository identities or placeholder names.

## 6. Idempotency and Concurrency

Resync requests must tolerate:

- Rapid double-click.
- Multiple tabs.
- Lost HTTP response.
- Network retry.
- Refresh while creating the session.
- Closing and reopening the modal.
- An existing active resync session.
- CLI handshake racing with a new request.
- Stale client session IDs.

Expected behavior:

```
Same user
Same repository
Same logical resync attempt
           │
           ▼
       ONE active attempt
```

Do not allow:

```
Click 1 → Session 2
Click 2 → Session 3
Click 3 → Session 4
Click 4 → Session 5
```

merely because the user clicked repeatedly.

Use existing transaction locking and idempotency infrastructure.

When a request with the same logical attempt identity is repeated, safely resolve to the same authoritative operation rather than creating unrelated sessions.

If the operation already completed, do not automatically create a new one during a retry of the same request.

A genuinely new resync must still be possible after the previous operation completes.

## 7. Handle HTTP 409 Semantically

Current behavior collapses different server results into:

```
Sesi sync gagal dibuat. Coba lagi.
```

This is unacceptable.

Audit error handling for:

```
SYNC_SNAPSHOT_UPLOADED
SYNC_SESSION_ACTIVE
SYNC_SESSION_STALE
SYNC_SESSION_EXPIRED
CODEBASE_SESSION_RECOVERY_REQUIRED
CODEBASE_SESSION_REPLACEMENT_FAILED
```

and other actual error codes present in the codebase.

Correct behavior:

- Completed snapshot on previous session → normal new resync should not enter a replacement conflict.
- Already active resync → restore or show its current state.
- Stale session ID → fetch authoritative current session before deciding.
- Expired unused session → safe explicit replacement.
- Unauthorized → reject without leaking repository data.
- Insufficient credits → existing credit-restriction experience.
- Genuine backend failure → actionable error with a functional retry.

Do not return a fake success response simply to suppress HTTP 409.

Do not swallow exceptions.

Do not treat a completed snapshot as evidence that a new resync attempt is already complete.

## 9. Token and Security Requirements

For the new resync attempt:

- Generate a new credential tied to the new session.
- Validate ownership and authorization.
- Preserve existing one-time token security.
- Never use the completed session's old token as the new resync token.
- Never expose token hashes or secrets in logs.
- Never save raw tokens in localStorage/sessionStorage.
- Do not put raw tokens in URLs.
- Do not invalidate a legitimately active upload unexpectedly.
- Enforce token expiration server-side.

The server should return actual prompt/session information, not a fabricated placeholder.

## 10. Backend → Frontend Contract

Avoid ambiguous responses.

A successful new resync attempt should return the data needed by the frontend, such as:

```

syncSessionId
snapshot/attempt identity as applicable
session status
expiry
one-time CLI credential/prompt data
```

Use existing schemas and validation conventions.

Do not introduce duplicate schema definitions if shared contracts already exist.

When requesting a new session, do not serialize `sessionId: null` when the endpoint requires an omitted property or a valid string.

Do not use stale `activeSessionId` as though it necessarily represented a current resync attempt.

Keep old initial-sync and recovery operations compatible.
