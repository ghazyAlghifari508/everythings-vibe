# FIX 03: Correct Durable Generation Retry Lifecycle and Per-Attempt Timer

**COMPLEXITY: COMPLEX**  
**PRIORITY: P0 — BLOCKER**  
**CATEGORY: Durable Generation / Retry / Timing / Worker Lifecycle**

Repository: `ghazyAlghifari508/everythings-vibe`

Target branch: `feature/vibeplan-existing-codebase`

**Prerequisite: FIX 01 and FIX 02 completed and verified.**

## 1. Objective

Perbaiki perilaku retry generation pada Existing Codebase Workspace, khususnya ketika pembuatan pertanyaan klarifikasi gagal lalu pengguna memilih `Coba lagi`.

Masalah yang dilaporkan:

- Percobaan pertama gagal setelah sekitar 43 detik.
- Saat menekan `Coba lagi`, timer tidak kembali ke awal.
- Timer dapat meneruskan durasi sebelumnya.
- UI terlihat seperti memproses ulang, tetapi tidak jelas apakah backend benar-benar melakukan attempt baru.
- Durable worker pernah mengulang operasi gagal akibat masalah persistence.

Target: setiap retry yang benar-benar memulai execution attempt baru mempunyai identitas, timestamp, status, dan durasi yang benar.

## 2. Inspect the Existing Implementation

Periksa:

- `src/features/codebase/services/durable-generation.server.ts`

- `src/features/codebase/services/durable-worker.ts`

- Generation request/response schemas and credit lifecycle.

Initial finding:

Ketika failed operation di-retry, operation record dapat digunakan kembali. Sebagian timestamp direset, tetapi `createdAt` tetap merepresentasikan creation time awal operation.

Frontend kemudian dapat menggunakan `op.createdAt` untuk menetapkan awal timer.

Ini berpotensi membuat timer menghitung sejak operasi lama, bukan attempt baru.

Verifikasi seluruh data flow sebelum implementasi.

## 3. Separate Operation Identity and Attempt Identity

Satu durable operation dapat mempunyai beberapa execution attempts.

Jangan menyamakan:

- Operation creation timestamp.
- Attempt start timestamp.
- Queue timestamp.
- Worker claim timestamp.
- Operation completion timestamp.
- UI display timestamp.

Target conceptual lifecycle:

```
OPERATION: questions-123
|
+-- ATTEMPT 1
|     started: T1
|     finished: T2
|     status: failed
|     duration: T2 - T1
|
+-- ATTEMPT 2
      started: T3
      finished: T4
      status: completed
      duration: T4 - T3
```

Setiap retry yang sah harus mempunyai clock yang tidak mewarisi waktu attempt sebelumnya.

Gunakan identitas attempt atau revision yang konsisten dengan durable operation schema saat ini.

Jangan menambahkan tabel baru jika field dan model yang sudah tersedia mampu merepresentasikan attempt secara aman.

## 4. Correct Timer Behavior

Expected:

```
Attempt 1
00.0s -> 12.0s -> 43.8s
FAILED

User clicks "Coba lagi"

Attempt 2
00.0s -> 01.0s -> 02.0s
RUNNING
```

Saat attempt selesai, timer berhenti pada durasi aktual.

Jangan membuat timer mulai lagi ketika UI rerender.

Jangan menggunakan `createdAt` dari operation pertama sebagai awal attempt kedua.

Jangan menggunakan `updatedAt` jika timestamp tersebut berubah karena heartbeat atau polling.

Jika operation baru queued tetapi belum mulai dieksekusi, tentukan semantik waktunya secara jelas:

- Apakah yang diukur waktu sejak request diterima?
- Atau waktu actual execution dimulai?

Pilih satu semantik yang konsisten dan jujur. Untuk indikator "Menyusun pertanyaan", utamakan waktu attempt aktif, atau beri status menunggu ketika worker belum mulai.

Tidak boleh mengklaim AI sedang berpikir ketika worker masih queued.

## 5. Retry Must Perform a Real Recovery

Ketika tombol `Coba lagi` ditekan:

1. Pastikan operasi sebelumnya benar-benar gagal atau dapat di-retry.
2. Validasi bahwa tidak ada active attempt yang masih berjalan.
3. Gunakan durable generation API yang sudah tersedia.
4. Jangan membuat parallel duplicate jobs.
5. Jangan memulai ulang seluruh repository sync.
6. Pertahankan feature prompt pengguna.
7. Pertahankan snapshot/repository context yang sah.
8. Jangan menghapus PRD, AC, atau Tasks yang sudah tersimpan.
9. Jangan menghapus hasil operation lain.
10. Jika attempt berhasil, simpan artifact dan lanjutkan alur biasa.

Jika server menyatakan operation yang sama sebenarnya masih berjalan, jangan membuat attempt baru hanya karena user menekan tombol.

Dalam kondisi reconnect, UI harus menampilkan status operation aktual.

## 6. Coordinate With FIX 01

FIX 01 memperbaiki question schema dan persistence.

FIX 03 harus memastikan retry memakai jalur generation dan persistence yang sudah diperbaiki.

Periksa bahwa:

- Schema rejection menghasilkan error terstruktur atau bounded repair.
- Gagal persist tidak dianggap completed.
- Worker retry tidak menggandakan handoff.
- Operation tidak berhenti pada status running selamanya setelah failure.
- Error yang dapat dipulihkan tidak menyebabkan loop retry tanpa batas.
- Retry tidak menghilangkan informasi kegagalan aktual dari diagnostics.

Jangan mengatasi schema rejection dengan membuat infinite retry loop.

## 7. Credit and Idempotency Safety

Periksa mekanisme kredit yang sudah ada.

Target:

- Tidak ada double charge akibat retry yang salah.
- Tidak ada duplicate artifact.
- Tidak ada duplicate generation operation yang berjalan bersamaan.
- Retry mengikuti aturan reservation, settlement, dan reconciliation kredit.
- Kegagalan accounting tidak disembunyikan oleh UI.
- Jangan memanipulasi saldo kredit langsung di database.

Jangan mematikan billing guard atau limit percobaan demi membuat retry berhasil.

## 8. UI State Expectations

```
INITIAL
No generation running

   |
   v

QUEUED
Menunggu proses generasi

   |
   v

RUNNING
Menyusun pertanyaan klarifikasi...

   |     Questions rendered
   |     Timer frozen
   |

         Timer frozen

         Retry available if recoverable
               |
               v

         New attempt lifecycle
         No inherited duration
```

Status harus berasal dari server atau state request yang benar-benar diketahui.

Jangan membuat fake processing steps.

## 9. Required Tests

Tambahkan/perbarui targeted tests:

1. First attempt timer starts correctly.
2. Failed attempt timer freezes.
3. Retry resets attempt timing.
4. Reconnect to an active attempt retains actual elapsed duration.
5. Completed attempt does not restart.
6. Multiple rapid retry clicks do not create duplicate execution.
7. Retry after persisted artifact success does not regenerate unnecessarily.
8. Retry after invalid generation output.
9. Retry after persistence failure.
10. Stale worker callback cannot overwrite newer attempt status.
11. Page remount/recovery preserves the correct operation state.
12. Billing/idempotency remains intact.
13. Max attempts behavior remains enforced.

Check both server and frontend timing logic.
