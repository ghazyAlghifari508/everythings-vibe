# PHASE 03 — Recover Failed Codebase Analysis From an Existing Snapshot

**COMPLEXITY: COMPLEX**  
**PRIORITY: P0 — Recovery, Idempotency &amp; Snapshot Safety**

## 1. Mission

Perbaiki recovery AI analysis pada fitur Existing Codebase.

Ketika CLI berhasil mengunggah source code tetapi AI analysis gagal, user harus bisa melanjutkan analisis menggunakan snapshot yang sudah tersimpan.

**Jangan mewajibkan sync ulang ketika source code sebenarnya sudah berhasil diterima.**

Perbaikan harus menangani failure akibat kredit, provider, network, timeout, invalid output, dan status operasi yang tertinggal.

## 3. Target Behavior

### Successful Upload, Failed Analysis

```
✓ 69 file tersimpan
✕ Analisis belum berhasil

Source code tidak perlu dikirim lagi.

         [Coba Analisis Lagi]
```

User menekan retry:

```
Existing Snapshot ID
        │
        ▼
Check existing analysis
        │
   ┌────┴─────┐
   │          │
 Ready      Missing/Failed
   │          │
   ▼          ▼

              │

              │
```

Jangan membuat repository atau snapshot baru hanya karena retry analysis.

## 4. Requirements

### A. Separate Upload and AI Analysis

Server harus membedakan:

- Snapshot uploaded.
- Analysis not started.
- Analysis pending.
- Analysis ready.
- Analysis failed.
- Analysis blocked due to billing/eligibility.

Jangan menyamakan insufficient credits dengan model provider failure.

Jangan mengklaim analysis selesai ketika CLI hanya berhasil upload.

### B. Existing Snapshot Reuse

- Retry menerima snapshot ID yang valid.
- Periksa owner dan codebase relationship.
- Jangan meminta token CLI baru.
- Jangan meminta manifest upload ulang.
- Jangan membuat history repository duplikat.
- Jangan membuat project baru yang tidak diperlukan.
- Pertahankan source snapshot dan seluruh planning existing.

Jika snapshot corrupt/tidak lengkap, tampilkan error khusus. Hanya kondisi tersebut yang mungkin memerlukan tindakan sync ulang.

### C. Analysis Attempt Identity

Setiap attempt memiliki status yang persisten.

Audit existing pending/ready/failed records.

Aturan:

- Ready analysis untuk snapshot yang sama digunakan ulang.
- Pending attempt yang valid dipantau, bukan diduplikasi.
- Failed attempt dapat diulang secara eksplisit.
- Retry berulang karena double click tidak membuat banyak model calls.
- Response lama tidak menimpa analysis yang lebih baru.
- Analysis dari snapshot berbeda tidak boleh tertukar.

Gunakan existing DB constraints dan operation identity yang tersedia.

### D. Credit-Aware Recovery

Integrasikan kebijakan Phase 01.

- Jika kredit belum cukup, arahkan user memenuhi eligibility.
- Jangan retry AI otomatis saat kredit masih tidak cukup.
- Jangan menagih kembali operasi yang sama secara tidak sengaja.
- Jika user memperoleh kredit atau allowance baru, lanjutkan analisis dari snapshot tersimpan.
- Validasi quote dan entitlement sebelum attempt baru dimulai.
- Jangan menyembunyikan biaya di belakang tombol "Coba Lagi".

Jika retry merupakan operasi berbayar baru, user harus mendapatkan informasi biaya yang tepat sebelum konfirmasi.

### E. Failure Classification

Gunakan error code yang jelas:

```
ANALYSIS_NOT_STARTED
ANALYSIS_PENDING
ANALYSIS_FAILED
ANALYSIS_OUTPUT_INVALID
CREDIT_REQUIRED
PROVIDER_UNAVAILABLE
SNAPSHOT_INCOMPLETE
```

Sesuaikan dengan error model existing.

Frontend tidak perlu menampilkan kode tersebut.

Contoh user-facing:

```
Analisis belum berhasil.
Source code kamu tetap tersimpan.

              [Coba Lagi]
```

### F. Network, Refresh &amp; Stale Status

- Refresh harus memulihkan attempt terbaru.
- Jika model masih memproses, lanjutkan monitoring status yang sama.
- Jika provider request telah gagal, tampilkan failure dan tindakan retry.
- Jika respons client hilang tetapi hasil sudah persisted, gunakan hasil existing.
- Jangan menjadikan pending sebagai status yang tidak bisa berakhir selamanya.
- Audit crash/restart behavior untuk background execution.
- Jika durable execution belum tersedia, implementasikan atau dokumentasikan batasan secara jujur.

Tidak boleh membuat progress palsu.

### G. Retain Existing Ready Results

Jika analisis ulang gagal tetapi hasil analisis lama yang valid untuk snapshot yang sama masih tersedia, jangan membuang hasil lama.

Jika snapshot baru berbeda, jangan diam-diam menggunakan analisis snapshot lama sebagai konteks untuk feature generation baru.

Pertahankan histori dan versi.

## 5. UX Constraints

Gunakan satu recovery action yang jelas.

Tidak boleh:

- Menampilkan Sync Ulang sebagai solusi default untuk AI analysis failure.
- Menampilkan dua retry buttons.
- Menampilkan CTA Buka Workspace sebelum readiness terpenuhi.
- Menciptakan status "Sukses" hanya karena retry request diterima.
- Menambahkan teknis seperti `analysisAttemptId` pada UI publik.
- Menampilkan giant error card di luar area analisis.

## 7. Tests

Wajib uji:

1. Upload success + analysis failed → retry tidak upload ulang.
2. Retry memakai snapshot ID yang sama.
3. Double click menghasilkan satu attempt efektif.
4. Existing ready result digunakan ulang.
5. Pending analysis dipantau, tidak dibuat ulang.
6. Insufficient credits tidak memanggil model.
7. Credit restored → analysis bisa dilanjutkan.
8. Network response hilang setelah server berhasil.
9. Refresh saat analysis pending.
10. Provider failure dan invalid output.
11. Stale analysis tidak salah dianggap ready.
12. Cross-user access ditolak.
13. Re-sync tidak menghapus plan existing.
14. Credit ledger tidak double-charge.
15. Retry selesai → workspace readiness diperbarui.

Gunakan integration/unit tests non-browser, typecheck, lint, dan build.

**Jangan menjalankan browser QA, Playwright, Puppeteer, browser E2E, atau screenshot testing.**

## 8. Completion

Laporan akhir harus menjelaskan failure handling, idempotency, credit lifecycle, snapshot reuse, dan regression tests.

**Definition of Done:** kegagalan AI analysis dapat dipulihkan dari snapshot yang sudah ada tanpa mengulang upload, kehilangan data, atau menagih kredit secara tidak benar.
