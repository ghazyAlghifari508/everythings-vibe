# PHASE 03 — Lock Finalized Clarifications &amp; Introduce Completed Planning State

**Repository:** [https://github.com/ghazyAlghifari508/everythings-vibe](https://github.com/ghazyAlghifari508/everythings-vibe)  
**Target branch:** `feature/vibeplan-existing-codebase`

## Objective

Perbaiki lifecycle workspace Existing Codebase agar interaksi mengikuti status planning yang sebenarnya.

Ada dua target:

1. Jawaban klarifikasi yang sudah digunakan untuk menghasilkan Feature Specification tidak boleh terus diedit secara bebas.
2. Setelah Task/Kanban berhasil dibuat dan tersimpan, composer utama harus berhenti menerima pesan. Workspace masuk ke completed/read-only planning mode.

Jangan menghapus riwayat pertanyaan, dokumen, Task, atau kemampuan AI agent handoff.

## Existing Problems

- Setiap answered question masih menampilkan tombol "Ubah" meskipun user sudah mencapai Task.
- User bisa mencoba mengganti keputusan requirements yang menjadi dasar dokumen downstream.
- Setelah Task selesai dibuat, composer tetap tersedia karena sistem menggunakan `composerMode: "revise"`.
- User tidak memahami tujuan terus mengirim pesan setelah seluruh planning selesai.

## Workstream A — Clarification Locking

Saat stage masih clarification dan belum menghasilkan spesifikasi final, jawaban yang telah diberikan boleh diedit.

Ketika Feature Specification sudah berhasil dipersist:

- Pertanyaan dan jawaban menjadi read-only.
- Hilangkan tombol "Ubah" dari tampilan answered questions.
- Jangan menggunakan disabled button yang masih terlihat tetapi tidak berguna.
- Jangan mengubah jawaban lama hanya pada local React state.
- Pastikan saved answers tetap konsisten dengan spesifikasi yang dihasilkan.
- Jangan membuka kembali edit mode akibat refresh atau hydration race condition.

Gunakan persisted artifact state untuk menentukan locking.

Jika Feature Specification belum tersimpan atau generation gagal, user tetap dapat memperbaiki jawaban dan mencoba lagi.

Pastikan tidak ada submission handler atau API yang diam-diam menerima perubahan jawaban finalized tanpa workflow revisi yang valid.

## Workstream B — Completed Planning State

Saat Task tersimpan dan workspace benar-benar mencapai Handoff:

- Composer tidak ditampilkan.
- Tidak ada placeholder "Jelaskan perubahan yang kamu inginkan".
- Tidak ada tombol Send atau textarea disabled.
- Tidak ada teks "Fitur aktif" yang berdiri sendiri di bawah chat.
- Tidak ada CTA revisi generik.
- Tidak ada tombol generasi ulang Feature/PRD/AC/Task yang sudah selesai.
- Tampilkan completion feedback sederhana.
- Pertahankan akses ke dokumen, Kanban, dan handoff AI agent.

### Proposed End State

```
✓ Planning selesai
30 task siap dikerjakan

[Siapkan Handoff]  [Buka Kanban]
```

Jangan membuat completion section menjadi card berlebihan. Reuse existing handoff controls dan sesuaikan posisi/spacing.

Aksi "Buat fitur baru" tetap berada di dropdown Fitur Repository.

## Workstream C — Correct State Resolution

Completed mode harus berasal dari bukti Task yang benar-benar tersimpan.

Jangan bergantung pada:

- Jumlah chat messages.
- Keberadaan label "Task".
- Status request HTTP sementara.
- Hardcoded stage flag.
- Lamanya loading.
- Local state yang belum direkonsiliasi.

Pastikan reopen dari History langsung kembali ke completed state setelah data terverifikasi.

Selama hydration masih pending, jangan menampilkan composer aktif sesaat lalu tiba-tiba menghilangkannya.

Jika Task generation gagal sebelum persistence, user tetap mempunyai cara yang jelas untuk retry.

## Workstream D — Preserve Workflow Capabilities

Jangan menghapus:

- AI handoff.
- CLI export.
- Existing task status tracking.
- File preview.
- Version history.
- Repository feature switcher.
- Revision infrastructure backend.

Jika revisi planning perlu dilakukan setelah tahap Task, gunakan workflow eksplisit yang terpisah dan aman, bukan membuka composer umum secara otomatis.

Jangan membuat hidden shortcut yang diam-diam mengubah planning final.

## UI Standards — Mandatory Component Discovery

Sebelum coding:

1. Periksa existing components di repository.
2. Cari padanan siap pakai di shadcn/ui dan HeroUI.
3. Evaluasi Magic UI, React Bits, atau Thinking Orbs jika ada kebutuhan status/progress yang nyata.
4. Gunakan komponen existing/ready-made yang relevan.
5. Custom compose hanya bagian yang tidak disediakan komponen tersebut.

Referensi wajib dieksplor:

[https://ui.shadcn.com/](https://ui.shadcn.com/)  
[https://www.heroui.com/](https://www.heroui.com/)  
[https://magicui.design/](https://magicui.design/)  
[https://reactbits.dev/](https://reactbits.dev/)  
[https://www.thinkingorbs.com/#orbs](https://www.thinkingorbs.com/#orbs)

Tidak perlu memasang library animasi bila tidak dibutuhkan.

**Dilarang membangun UI baru dari nol tanpa mengevaluasi komponen siap pakai.**

Hindari green cards, badge berlebihan, gradient dekoratif, dan status copy yang tidak berguna.

## Automated Tests

Uji:

- Unanswered question dapat dijawab.
- Answered question dapat diedit selama clarification.
- Setelah Feature tersimpan, tombol Ubah hilang.
- Reopen tidak membuka edit mode.
- Task generated membuat composer hilang.
- Task 0/30 tetap dianggap planning complete.
- Failed Task generation tidak mengunci workspace secara salah.
- Task hydration pending tidak menyebabkan flicker composer aktif.
- Feature baru tetap memiliki composer aktif.
- Existing Kanban dan handoff tetap berfungsi.

Jalankan tests non-browser, typecheck, lint, dan build.

**Jangan menjalankan browser QA, Playwright, Puppeteer, browser E2E, atau screenshot testing.**

## Definition of Done

Workspace memiliki lifecycle yang jelas: clarification dapat diedit pada tahap yang tepat, hasil finalized bersifat read-only, dan setelah Task dibuat user diarahkan ke handoff serta Kanban, bukan chatbot yang terus meminta instruksi.
