## 4. Investigate Original Exception

Cari exception dari transaksi yang terjadi sebelum error diklasifikasikan `persistence`.

Periksa:

- State dan expiry reservasi.
- Subscription ownership.
- Reserved amount.
- Final charge calculation.
- Ledger constraints.
- Database uniqueness/foreign key.
- Concurrent transaction conflicts.
- Analysis row update result.
- Output serialization.
- Idempotency key collision.
- Operation identity mismatch.

Tambahkan structured diagnostic logging internal yang aman.


Jangan log raw sync credentials, source code, secrets, atau model output sensitif.

## 5. Credit Operation Trace

Jangan menganggap error kedua sebagai sebab utama.

Audit existing `reserveActiveCreditOperation()` dan `buildAnalysisIdempotencyKey()`.

## 7. Concurrency Safety

Test these cases:

### A. Reconciliation while AI runs

```
ANALYSIS: RUNNING
      │
      ├───────────┐
      │           │
      ▼           ▼
MODEL CALL     RECONCILIATION
      │           │
      └─────┬─────┘
            ▼
       FINALIZATION
```

Ensure reconciliation doesn't inappropriately release a still-valid reservation.

### B. Duplicate trigger

```
POST analysis
POST analysis again
```

Must not generate duplicate active attempts or double-charge.

### C. Retry after released operation

A new valid attempt must not attempt settlement of an already released operation.

### D. Response lost after server success

Client retry should discover the already-persisted READY result instead of paying twice.

### E. Process crash during finalization

Reconcile billing and analysis consistently after restart.

Use database locks, conditional updates, and idempotency compatible with existing architecture.
