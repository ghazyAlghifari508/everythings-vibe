## 1. Objective

Refine user-facing error messages and workspace controls without changing backend success/failure semantics.

Problems:

1. Error messages use repetitive red text, red translucent background, and red borders.
2. Some messages are too generic.
3. Users cannot clearly distinguish failed generation, persistence failure, sync failure, and temporary status-read issues.
4. `Coba lagi` can appear without enough explanation.
5. `Sync ulang` button looks like a generic bordered badge.
6. `69 file tersinkron` is styled almost like an action button even though it is informational.
7. UI has inconsistent hierarchy between actions, status, and technical metadata.

Do not solve technical failures by hiding their messages. FIX 01–04 should already address the underlying bugs.

This task improves the communication and presentation of remaining recoverable errors and header controls.

## 4. Fix Error Message Information Structure

Every error should communicate:

1. What failed.
2. Whether existing data is preserved.
3. What the user can do next.

Do not dump internal exception strings into the primary UI.

Example for failed question persistence:

```
+---------------------------------------------+
| (!) Pertanyaan belum berhasil dibuat        |
|                                             |
| Hasil pertanyaan tidak dapat disimpan.      |
| Permintaan fiturmu tetap tersedia.          |
|                                             |
| [Coba lagi]                                 |
+---------------------------------------------+
```

Use this copy only if data-preservation behavior is verified.

Do not say the prompt is safe if the application actually loses it.

For connectivity problems:

```
Koneksi ke server terputus

Status proses belum dapat diperbarui.
Periksa kembali statusnya sebelum
memulai percobaan baru.

[Periksa status]
```

Do not suggest rerunning an expensive operation when status is unknown.

For a confirmed generation failure:

```
Pertanyaan belum berhasil dibuat

Proses sebelumnya berhenti.
Kamu bisa mencoba membuatnya kembali.

[Coba lagi]
```

For session creation failure:

```
Sinkronisasi belum bisa dimulai

Sesi baru tidak berhasil dibuat.
Coba buat instruksi sync ulang.

[Coba lagi]
```

All copy must correspond to actual error state and recovery semantics.

## 5. Error Visual Style

Avoid using the same styling for every error:

```
border-crimson/30
bg-crimson/10
text-crimson
```

Do not simply replace crimson with:

- Amber translucent.
- Green translucent.
- Purple gradient.
- Blue blurred background.

Use a neutral inline message surface.

Recommended:

- Neutral background.
- Subtle border.
- Clear heading.
- Secondary explanation.
- One primary recovery action.
- Small severity icon.
- Consistent spacing.
- Rounded corners matching the existing design system.

Critical failures may use a restrained severity accent, but do not color every part of the component red.

No decorative glow, large drop shadow, animated gradient, or excessive rounded card.

Error severity must also be communicated by words and accessibility semantics.

Reference:

[https://atlassian.design/foundations/content/designing-messages/error-messages](https://atlassian.design/foundations/content/designing-messages/error-messages)

## 6. One Primary Error Per Operation

Check if the same failure is shown simultaneously in:

- Thinking status.
- Error banner.
- Stage error row.
- Toast.
- Modal.

Avoid duplicate messages that compete for attention.

Choose one primary presentation for each operation.

Supporting details may remain in diagnostics, not multiple repeated alerts.

When an operation is retried:

- Old error should stop being displayed as the current active failure.
- New attempt state should become visible.
- Retry action should be disabled while request is being submitted.
- Do not hide a still-running operation behind a new error from a stale response.

Maintain proper screen reader announcements.

## 7. Preserve Error Diagnostics

Keep structured error codes and relevant server logs.

Frontend should use safe user-facing messages.

Debugging details remain available for developers:

- Error code.
- Operation ID.
- Attempt identity.
- Stage.
- Relevant timestamp.
- Request correlation.

Do not log or expose raw sync credentials, authorization tokens, or private source contents unnecessarily.

Do not replace all backend errors with a generic success-shaped object.

## 8. Improve Workspace Header Controls

Current:

```
[Sync ulang] [69 file tersinkron]
```

Both appear as similarly styled bordered surfaces.

Recommended:

```
[↻ Sync ulang]    [file icon] 69 file tersinkron
```

The first is an action.

The second is informational metadata.

Use the existing Button component for Sync ulang.

For file count, use plain text with a subtle icon, not another button-like badge.

Keep the actual count dynamic.

Do not hardcode 69.

Do not make file count interactive if it does not have a meaningful action.
