# FIX 08 — Replace Tail-Word Feature Naming With Meaningful, Stable, Indonesian-Language Feature Titles

**COMPLEXITY: MEDIUM**  
**PRIORITY: P2**  
**CATEGORY: Feature Naming / Planning UX / Prompt Understanding**

Repository: [https://github.com/ghazyAlghifari508/everythings-vibe](https://github.com/ghazyAlghifari508/everythings-vibe)

**Prerequisite:** FIX 07 completed.

## 1. Mission

Fix the generation of poorly named feature plans in VibePlan Existing Codebase.

Example user prompt:

```
Sediakan fitur interaktif pada halaman portofolio yang
memungkinkan calon klien atau perekrut menyaring proyek
berdasarkan rumpun teknologi atau bidang tertentu, serta
mencari judul proyek melalui kolom pencarian langsung.
Tampilkan pemberitahuan yang jelas ketika hasil pencarian
tidak ditemukan dan sediakan opsi untuk mereset seluruh
filter secara instan demi kemudahan eksplorasi karya.
```

Actual generated feature title:

```
Demi Kemudahan Eksplorasi Karya
```

**REJECTED.**

That is a fragment of the user's final sentence, not a meaningful feature name.

A correct title should identify the functionality being planned.

For this example:

```
Pencarian dan Filter Proyek Portofolio
```

Another valid concise option:

```
Fitur Pencarian dan Filter Portofolio
```

Do not create poetic, generic, motivational, or incomplete names.

## 2. Confirmed Root Cause

Inspect:

```
src/features/codebase/services/feature-project-route.server.ts

src/features/greenfield/services/prd-naming.ts
```

The current feature creation flow calls:

```
deriveProjectNameSync(prompt)
```

The shared synchronous fallback ultimately uses:

```
const tail = words.slice(-4);
```

This selects the final four words of the user's prompt.

That method is inappropriate for naming specific features inside an existing application.

**Do not simply change** `slice(-4)` **to** `slice(0, 4)`**.**

Both approaches can produce unrelated phrases.

## 3. Required Naming Semantics

A feature title must describe:

```
PRIMARY FUNCTION
+
TARGET ENTITY / CONTEXT
```

Examples:


| User request                                 | Expected title                         |
| -------------------------------------------- | -------------------------------------- |
| Add search and filters to portfolio projects | Pencarian dan Filter Proyek Portofolio |
| Add a blog to a portfolio website            | Blog Portofolio                        |
| Add login and user authentication            | Autentikasi Pengguna                   |
| Add an order-status dashboard                | Dashboard Status Pesanan               |
| Add filtering to a list of articles          | Filter dan Pencarian Artikel           |
| Fix mobile navigation responsiveness         | Perbaikan Navigasi Mobile              |


These are examples of semantic quality, not a hardcoded dictionary that the naming algorithm must depend on.

## 4. Naming Rules

Generated titles should:

- Be concise.
- Be meaningful in Indonesian when the user's prompt is Indonesian.
- Describe functionality, not desired emotional benefit.
- Prefer concrete nouns and verbs converted into feature nouns.
- Avoid marketing language.
- Avoid simply copying the last sentence.
- Avoid implementation layers unless they genuinely define the feature.
- Avoid irrelevant references to the repository name.
- Avoid duplicating the same feature title unnecessarily.
- Remain readable in the feature dropdown and History.
- Preserve explicit user-given feature names.

Recommended typical length:

```
2–6 meaningful words
```

Do not enforce a rigid limit when a slightly longer title is needed for clarity.

## 5. Naming Source of Truth

Investigate how the existing feature creation pipeline produces:

- Initial prompt.
- Questions.
- Feature specification.
- PRD.
- Feature project record.
- Visible feature name in dropdown.

Choose a naming strategy that uses actual feature intent.

Preferred approach:

1. Extract the primary requested action.
2. Identify its main object/domain.
3. Build a concise functional title.
4. Validate the title.
5. Persist it once the title is sufficiently reliable.

If the existing AI generation process already produces structured feature context suitable for naming, reuse that context.

If an additional AI naming operation is considered, evaluate cost, latency, failure behavior, and existing billing rules first.

Do not silently create an extra billable model call just to name a feature.

If intent is not yet sufficiently clear, do not fabricate an elaborate feature title. A provisional label may be used internally until actual information is available.

Do not expose a nonsensical fragment as the final title.

## 6. Preserve Explicit User Naming

If the user explicitly names a feature, preserve that name.

Example:

```
Bikin fitur bernama "Smart Project Finder"
```

Expected:

```
Smart Project Finder
```

Do not replace it with an AI-generated phrase.

Likewise, manual rename must take precedence over automatic rename.

## 7. Stable Naming Across the Lifecycle

Expected:

```
User describes feature
        │
        ▼
Feature identity created
        │
        ▼
Meaningful title assigned
        │
        ▼
Questions
        │
        ▼
Feature / PRD / AC / Tasks
        │
        ▼
Same stable feature identity
```

Do not change the feature title every time the user answers a question.

If an initial provisional name genuinely needs refinement, use a controlled one-time update consistent with existing identity and manual-rename precedence.

Do not generate a new project ID merely because its title changes.

Do not overwrite names on every workspace reload.

Do not rename existing user-created features silently as part of a migration.

Preserve existing dropdown layout and behavior.
