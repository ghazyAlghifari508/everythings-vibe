## 1. Mission

Tambahkan kemampuan multiple select, delete selected, dan delete all pada History/Project Tersimpan Existing Codebase.

**Gunakan pengalaman multi-select delete dari fitur VibeScrape sebagai referensi implementasi utama. Jangan menciptakan interaction pattern baru.**

Target:

- Select satu repository.
- Select banyak repository.
- Select seluruh item yang terlihat.
- Select semua repository dalam filter saat ini jika memang didukung backend.
- Delete selected.
- Delete all repositories milik user.
- Confirmation jelas sebelum penghapusan.
- Setelah delete berhasil, selection, pagination, count, dan History diperbarui.
- Repository dan dependent artifacts terhapus sesuai existing deletion contract.

## 4. Selection Semantics

Selection needs to be predictable.

Support:

### Individual Selection

- Checkbox per row.
- Click checkbox does not open repository.
- Selected count updates immediately.

### Select Visible Page

- Select all currently rendered rows.
- Indeterminate state when only some are selected.

### Select All Filtered Results

If supported, make this explicitly different from selecting only one page.

Example:

```
10 dari 34 repository dipilih.

[Pilih semua 34 hasil]
```

### Delete All

This means all owned History repositories, not just the current pagination page.

Do not overload a button with ambiguous meaning.

If the search filter is active, distinguish:

- Delete selected.
- Delete all matching filter.
- Delete entire History.

Only expose operations that are backed by correct server behavior.

## 6. Backend Architecture

Existing single-delete endpoint is not sufficient for efficient bulk deletion.

Implement/reuse a secure batch deletion boundary following established route conventions.

Requirements:

- Server identifies authenticated user.
- Every requested codebase must belong to user.
- No cross-tenant deletion.
- Validate request schema.
- Normalize/deduplicate IDs.
- Enforce reasonable batch limits.
- Preserve established codebase cascade semantics.
- Delete related Feature, PRD, AC, Task, and other dependent records correctly.
- Reconcile active background operations if deleting in-progress repository.
- No orphan rows.
- No accidental deletion of unrelated repositories.
- Return actual deleted/skipped counts.
- Make repeated requests safe.
- Use transaction boundaries appropriate to existing schema.

Do not make frontend send dozens of uncontrolled DELETE requests if a single batch service can do the work safely.

Reuse the existing single-delete domain operation where feasible rather than maintaining two inconsistent deletion implementations.

## 7. Concurrency &amp; Filtering Safety

If user chooses "Select all matching":

- Freeze an authoritative selection snapshot before destructive confirmation.
- Do not delete new repositories created after that selection confirmation.
- Prevent filter changes from silently expanding selected scope.
- Handle pagination correctly.
- Avoid stale selected IDs after a delete.
- Ensure current page adjusts when last item is deleted.
- Handle partially stale IDs gracefully.

Follow the proven VibeScrape approach when applicable.

## 8. Post-Delete Behavior

After successful deletion:

- Remove deleted entries from History.
- Clear relevant selection.
- Recompute counts/pagination.
- Invalidate or refresh cached list.
- Clear onboarding pointers only for deleted codebase IDs.
- Do not remove pointers to unaffected repositories.
- Show one concise success toast.
- No duplicated notifications.

If partial deletion occurs, accurately report what succeeded and what did not.

Never show "Semua berhasil" unless server confirms it.
