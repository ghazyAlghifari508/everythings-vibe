## 1. MISSION

Perbaiki progress sinkronisasi agar user dapat melihat proses yang benar-benar berlangsung.

Saat ini beberapa stage langsung muncul dengan centang tanpa sempat menampilkan loading.

User ingin proses yang jelas:

```
Menunggu agent
    ↓
Agent terhubung
    ↓
Menyiapkan source code
    ↓
Mengunggah repository
    ↓
Analisis AI
    ↓
Ready
```

**Jangan membuat loading palsu, artificial delay, atau animasi yang hanya meniru proses backend.**

## 3. Why Instant Checkmarks Happen

Current sync stage mapping includes:

```
waiting_for_cli
connected
scanning
filtering
uploading
uploaded
```

Polling only samples status at certain intervals.

If stages finish between polls, frontend might see:

```
Waiting -> Uploaded
```

without painting intermediate running stages.

**Do not solve this by intentionally delaying successful sync completion.**

## 4. Required Initial State

Immediately after a valid sync session exists:

```
3  Pantau progres

   ○ Menyiapkan source code

```

Spinner must be visible for the genuine waiting state.

No "Menghubungkan server..." when eligibility hasn't completed or a valid session doesn't exist.

## 6. Event-Driven Progress Strategy

Audit existing event infrastructure.

If sufficiently reliable events already exist, reuse them.

Otherwise consider persisted progress events with SSE or an equivalent supported transport.

Desired conceptual flow:

```
CLI / SYNC API
      │
      ▼
REAL STATUS EVENTS
      │
      ▼
PERSISTED EVENT TIMELINE
      │
      ▼
SSE / SUPPORTED STREAM
      │
      ▼
REACT PROGRESS UI
```

Event examples:

```
agent.connected
source.preparing
source.prepared
upload.started
upload.completed
analysis.started
analysis.completed
analysis.failed
```

Do not emit an event unless the actual backend process supports and observes it.

If full event streaming would require CLI protocol updates, verify compatibility and scope before changing it.

## 7. Event Identity

Use a stable:

```
sessionId
eventId / sequence
timestamp
stage
status
```

to prevent:

- Duplicate event rendering.
- Out-of-order updates.
- Stale session results.
- Old failed attempt overriding new running attempt.
- Incorrect timestamps.

On reconnect, restore server-reported state and missed events where infrastructure supports replay.

No raw sync token in event stream.

## 8. Fast Stages

If actual operation runs too quickly for an intermediate spinner frame:

- Preserve event chronology.
- Keep current state accurate.
- Allow a compact activity history if useful.
- Never pretend a stage is running after it already completed.

The user wants authentic progress, not deliberately slowed progress.

## 9. Analysis Progress

Treat AI Analysis separately from CLI upload.

Do not show fake thoughts like:

```
AI sedang memahami semua arsitektur...
AI sedang mengecek ribuan dependency...
```

unless backend has observable real activities corresponding to those labels.

When retry begins, current pending/running state must replace stale failed status.

When complete, stop spinner/timer.

When error occurs, show the failure near the analysis stage.

## 12. Definition of Done

No fake activity, no misleading instant success caused by missing state observability, and no contradictory credit/session loading.

Report event sources, streaming/polling decisions, reused components, files changed, and tests.
