# P05 — Unified Planning Stage Card

**Branch:** `feature/vibeplan-existing-codebase`  
**Complexity:** COMPLEX  
**Dependency:** P03 and P04 completed.

## Background

Currently, generated planning documents appear as individual clickable file cards. The next-stage actions, such as Generate PRD, Generate AC, or Generate Task, are rendered separately below them.

The implementation uses several disconnected presentation components:

- `codebase-chat-workspace-artifacts.tsx`
- `codebase-chat-workspace-stage-handoffs.tsx`
- `codebase-stage-handoff.tsx`
- `codebase-file-card.tsx`
- `codebase-chat-workspace.tsx`

This causes excessive component fragmentation and weak visual association between generated documents and the next action.

## Objective

Replace the fragmented presentation with **one unified planning stage card** that progressively displays all completed documents and contextual actions.

Do not change the actual generation pipeline, document format, persistence logic, or backend stage contracts unless required to fix a verified issue.

## Stage-specific actions


| Last completed stage  | Left action | Right action |
| --------------------- | ----------- | ------------ |
| Feature Specification | Revisi      | Buat PRD     |
| PRD                   | Revisi      | Buat AC      |
| AC                    | Revisi      | Buat Task    |
| Task                  | Revisi      | Buat Handoff |


Do not create a different large card for every stage. Maintain one cohesive surface whose contents evolve as more documents are completed.

## Document row behavior

Each row should contain:

- Appropriate document icon.
- Human-readable document name.
- Short, genuinely useful description or status.
- Clear persisted/processing/error state.
- Open affordance for side-panel preview.

Clicking a row must open the already available document preview. Preserve Copy, Download, and existing error handling.

Do not invent new document viewers.

Document rows must reflect actual persisted artifacts. A stage must not be marked complete merely because an API request was accepted.

## Revision action

The left-side `Revisi` button must:

1. Switch the existing composer into Revise mode.
2. Resolve the current stage's document as the revision target.
3. Attach a real `@` artifact reference, not just a plain string that looks like a mention.
4. Focus the composer.
5. Preserve any relevant existing draft unless the user explicitly replaces it.
6. Respect existing revision proposal, review, apply, and reject flows.
7. Preserve revision credit policies and server-side authorization.

When the user opens another document from the list, its detail view must allow revision of that specific document too.

Never allow a revision to silently target the wrong artifact.

## Generation action

Right-side buttons must invoke the existing stage-generation handlers and maintain current operation lifecycle semantics.

Required behavior:

```
Buat PRD
   ↓
Actual generation request
   ↓
Loading state from real operation
   ↓
Server confirms persisted PRD
   ↓
PRD row added
   ↓
Next action becomes Buat AC
```

Handle retry and failure using current operation contracts.

No fake progress, fabricated completion times, or optimistic successful artifact states.

## Handoff boundary

When Task becomes available, change the right action into `Buat Handoff`.

This should initiate or reveal the existing handoff workflow, which will be redesigned in P06.

Do not duplicate the handoff prompt or create another conflicting export mechanism.

## UI component requirements

Mandatory discovery before implementation:

- Existing reusable primitives in repository.
- HeroUI.
- shadcn.
- Magic UI.
- React Bits.
- ThinkingOrbs.
- AffectUI.
- TuffUI.
- CUI.
- SakaniUI.

Use ready-made components for list items, buttons, progress indicators, disclosure, or transitions as appropriate.

Avoid manually rebuilding existing Button, Card, ScrollArea, Tooltip, or Disclosure primitives.

A subtle transition when a document becomes available is acceptable, but avoid excessive animated-list replay, glowing borders, giant shadows, or decorative AI badges.

The design should feel like an integrated product workflow, not an assortment of unrelated dashboard components.

- PRD generation success/failure/retry.

- Partial artifact hydration.
