**COMPLEXITY: COMPLEX**  
**PRIORITY: P1 — Navigation Integrity, State Recovery, Session Lifecycle**

## 1. MISSION

Perbaiki onboarding Existing Codebase yang mencampur konteks sesi lama dengan pembuatan sesi baru.

Reported behavior:

1. User melakukan CLI sync.
2. Snapshot repository berhasil diunggah.
3. AI analysis gagal.
4. User meninggalkan halaman onboarding.
5. User kembali ke VibePlan dan mencoba memulai sync baru.
6. UI menampilkan "Buat sesi baru".
7. Tetapi bagian bawahnya masih menunjukkan progress/analisis dari sesi sebelumnya.
8. User tidak memahami apakah sedang membuat repository baru, melanjutkan repository lama, atau menunggu analisis lama.

**Ini adalah bug lifecycle dan navigation intent, bukan sekadar masalah copywriting.**

Target akhir: setiap entry point harus mempunyai konteks operasi yang tidak ambigu.

## 3. ROOT PROBLEM

Saat ini aplikasi mempunyai beberapa state yang dapat hidup bersamaan:

```
Session payload
Recovered sync status
Last sync status
Analysis result
Analysis error
Analysis retry state
Onboarding step
Current project pointer
```

Jika session payload baru belum ada tetapi recovered status lama masih ada, UI dapat merender kombinasi yang tidak sesuai.

Ini perlu diperbaiki melalui authoritative operation identity dan explicit navigation intent.

Jangan hanya menghapus teks "Buat sesi baru".

## 4. REQUIRED NAVIGATION INTENTS

Implementasikan pemisahan jelas antara tiga konteks.

### A. START NEW REPOSITORY

User memilih:

```
[Hubungkan repository]
```

Expected:

```
NEW REPOSITORY ONBOARDING
          │
          ▼
Fresh valid sync session
          │
          ▼
CLI instructions
          │
          ▼
Waiting for agent
```

Behavior:

- Tidak otomatis menampilkan analysis attempt dari repository sebelumnya.
- Tidak mengembalikan old project pointer tanpa alasan.
- Tidak menampilkan old sync progress.
- Tidak menampilkan old error.
- Tidak memakai session token lama.
- Tidak menghapus repository yang sebelumnya gagal.
- Tidak membuat duplicate project akibat React rerender.

Jika perlu memilih antara membuat baru dan melanjutkan yang lama, keputusan harus sesuai action yang user pilih—jangan menebaknya berdasarkan data lama.

### B. RESUME INCOMPLETE SYNC

User memilih dari History:

```
[Lanjutkan Sinkronisasi]
```

Expected:

```
EXISTING REPOSITORY
       │
       ▼
Read authoritative last sync status
       │
       ├─ Active valid session
       │     └─ Monitor existing session
       │
       ├─ Expired token, upload incomplete
       │     └─ Create replacement sync session
       │
       └─ Upload already completed
             └─ Continue analysis lifecycle
```

Jangan membuat sesi baru jika CLI upload sudah berhasil dan hanya analisis yang gagal.

### C. RETRY FAILED ANALYSIS

User memilih:

```
[Coba Analisis Lagi]
```

Expected:

```
EXISTING SNAPSHOT
       │
       ▼
Verify snapshot uploaded
       │
       ▼
Recheck billing eligibility
       │
       ▼
Retry AI analysis
       │
       ▼
Monitor new analysis attempt
```

Tidak ada prompt CLI baru.

Tidak ada upload ulang.

Tidak ada project baru.

Tidak ada pergantian repository context.

### State 1 — Waiting for Agent

```
Sync codebase dengan everything-vibe

1  Salin instruksi
2  Buka AI coding agent
3  Pantau progres

   ◌ Menunggu agent terhubung...
```

### State 2 — Sync Running

```
3  Pantau progres

   ✓ Agent terhubung
   ◌ Menyiapkan source code...
```

### State 3 — Upload Completed, Analysis Running

```
3  Pantau progres

   ✓ Sinkronisasi selesai
   ◌ Menganalisis repository...
```

**No "Buat sesi baru" in this state.**

### State 4 — Upload Completed, Analysis Failed

```
3  Pantau progres

   ✓ Sinkronisasi selesai
   ✕ Analisis belum berhasil

   [Coba Analisis Lagi]
```

**No "Buat sesi baru" in this state.**

### State 5 — Session Expired Before Upload

```
Sesi sinkronisasi berakhir.

[Buat sesi baru]
```

Only show this if the repository genuinely needs another upload attempt.

### State 6 — Ready

```
✓ Repository siap

[Buka Workspace]
```

No stale failure.

No sync-token recovery.

No repeated model invocation.

## 6. SEPARATE SESSION IDENTITY FROM ANALYSIS IDENTITY

Use explicit identity relationships:

```
CODEBASE
   │
   ├── SYNC SESSION A
   │       │
   │       └── SNAPSHOT A
   │                │
   │                ├── ANALYSIS ATTEMPT 1 FAILED
   │                │
   │                └── ANALYSIS ATTEMPT 2 RUNNING
   │
   └── SYNC SESSION B
           │
           └── SNAPSHOT B
```

Requirements:

- Session A status never appears as session B active progress.
- Analysis attempts always link to the correct snapshot.
- Snapshot A result never becomes Snapshot B analysis automatically.
- Project ownership validated.
- Active attempt ID controls retry UI.
- Old polling results ignored after switching session context.
- No stale React closure updating a different project.

## 7. RESET ON NEW SESSION

When a fresh session has actually been created:

- Clear visible old errors.
- Clear visible old progress.
- Clear old analysis presentation.
- Bind new prompt credential to new session.
- Reset stage indicators.
- Reset active polling target.
- Abort/ignore old in-flight polling responses.
- Preserve old session and snapshot in backend for History.

**Do not delete historical data to make the UI look clean.**

Use atomic state transitions or a cohesive session reducer where appropriate.

Avoid unrelated `setState` calls that can race.

## 8. TOKEN EXPIRATION AND REOPEN

Sync tokens may expire or only be returned once.

Distinguish:

```
Token unavailable
```

from:

```
Repository requires new sync
```

Those are not equivalent.

If snapshot already exists, the absence of a token should not block analysis recovery.

If upload is incomplete and token expired, new session creation is valid.

Do not persist secret token in localStorage.

Do not mint new tokens automatically in a loop.

Do not reuse expired tokens.

## 9. ANALYSIS RETRY STATE

After clicking retry:

```
OLD FAILED ATTEMPT
          │
          ▼
NEW ATTEMPT STARTING
          │
          ▼
NEW ATTEMPT RUNNING
          │
          ▼
SUCCESS / FAILURE
```

The old error must not stay visible as active error while the new attempt is running.

Use backend-confirmed attempt status.

No fake thinking text.

No duplicate retry CTA.

No manual frontend timer used as the source of truth.

## 13. DEFINITION OF DONE

The system must always know whether the user is:

- Creating a new repository connection.
- Continuing an incomplete CLI sync.
- Retrying failed analysis for an uploaded snapshot.
- Opening an already-ready repository.

No mixed old/new statuses.

No repeated upload for AI analysis failure.

No duplicate projects due to recovery.

No stale UI that mentions "Buat sesi baru" while an uploaded snapshot is already being analyzed.

Create/check off todos, follow repository rules, preserve unrelated changes, and close the goal only after tests pass.

Final report must include navigation intent model, state before/after, stale-response handling, files modified, and automated test results.
