## 4. UNDERSTAND THE EXISTING FINALIZATION

Pada `analysis.server.ts`, finalization melakukan settlement kredit sebelum menyimpan analisis sebagai READY.

Secara konseptual:

```
await db.transaction(async (tx) => {
  if (deps.settle) {
    await deps.settle(tx, analysisId);
  }

  await tx
    .update(codebaseAnalyses)
    .set({
      status: "ready",
      output: analysis,
      updatedAt: new Date(),
    });
});
```

Saat transaksi gagal, update READY tidak boleh dianggap berhasil.

Pada `credit-settlement.ts`, terdapat pengecekan state terminal, expiry, final charge, subscription ownership, reserved credits, dan database update conflict.

Temukan titik aktual yang menyebabkan transaksi gagal.

Jangan berasumsi semua failure dari `stage: persist` adalah exception yang sama.

## 5. REQUIRED ROOT CAUSE ANALYSIS

### A. Find the Original Exception

Implementasikan diagnostic logging internal yang mencatat penyebab transaksi gagal secara aman.

Minimal:

```
analysisAttemptId
projectId
snapshotId
creditOperationId
creditOperationState
creditOperationExpiresAt
analysisStage
errorName
errorCode
databaseErrorCode (when available)
failureCategory
elapsedMs
```

Identifikasi exception sebelum cleanup/release tambahan dijalankan.

Penting: logging saat ini tidak boleh berhenti pada:

```
category: persistence
```

Jika error mempunyai `cause` chain, gunakan error serialization yang aman untuk mendapatkan akar exception.

Jangan log:

- Sync tokens.
- API keys.
- Secret values.
- Raw repository source contents.
- Prompt pribadi user.
- Full sensitive model output.

Jangan mengirim internal database errors ke frontend publik.

### B. Trace Who Released the Credit Operation

Temukan setiap code path yang dapat membuat:

```
reserved/running/settling -> released
```

Audit:

- Explicit failure cleanup.
- Credit reservation reconciliation.
- Expiry jobs.
- Concurrent requests.
- Retry handlers.
- Aborted operations.
- Credit operation reuse.
- Subscription balance reconciliation.

Tambahkan audit evidence saat state berubah:

```
operationId
previousState
nextState
reason
actor/component
correlationId
timestamp
```

Jika perlu, gunakan transactional event log atau structured audit logging sesuai sistem yang sudah ada.

**Goal: bisa menjawab dengan bukti "siapa yang melepaskan operation ini, kapan, dan mengapa".**

### C. Verify Reservation Identity

Periksa apakah setiap analysis attempt menggunakan reservation yang benar.

Skenario risiko:

```
Attempt A
   └─ Credit Operation X

Attempt B
   └─ Accidentally reuses X

X has already been released

Attempt B finalization
   └─ FAILED
```

Pastikan idempotency key, analysis ID, snapshot ID, dan operation ID saling konsisten.

Audit `reserveActiveCreditOperation()` yang sudah tersedia.

Jangan membuat idempotency key baru secara acak hanya untuk menghindari collision tanpa memahami kontrak existing.

### D. Verify Settlement and Database Transaction

Periksa urutan:

1. Validated AI output tersedia.
2. Credit operation valid.
3. Settlement dihitung.
4. Credit ledger diperbarui.
5. Analysis output tersimpan.
6. Analysis status menjadi READY.
7. Transaction commit.

Jika salah satu langkah gagal:

- Transaction harus konsisten.
- Tidak ada successful charge untuk analysis yang gagal disimpan sebagai READY.
- Tidak ada operation settled tanpa referensi analysis yang konsisten.
- Tidak ada analysis READY yang belum benar-benar tersimpan.
- Tidak ada credits reserved yang menggantung selamanya.

Audit database constraints dan transaction conflicts, bukan hanya business logic.

### E. Examine Reconciliation Race Conditions

Reproduksi kemungkinan ini:

```
Analysis starts
      │
      ▼
Credit operation RUNNING
      │
      ├───────────────┐
      │               │
      ▼               ▼
AI generation      Credit reconciliation
      │               │
      │          Releases operation?
      │               │
      └───────┬───────┘
              ▼
         Final settlement
              │
              ▼
        Conflict / failure
```

Ini hipotesis pengujian, bukan root cause yang sudah dipastikan.

Periksa locking, leases, expiration checks, dan conditional updates.

Pastikan reconciliation tidak melepaskan operasi yang masih valid dan sedang dikerjakan hanya karena status sementara terlambat berubah.

Namun jangan mempertahankan reservation aktif tanpa batas.

Gunakan retry/recovery policy yang bounded.

## 8. CREDIT LIFECYCLE CORRECTNESS

Target state transitions:

```
RESERVED
   │
   ▼
RUNNING
   │
   ├── Success -> SETTLED
   │
   └── Failure -> RELEASED
```

Pastikan:

- `SETTLED` tidak bisa direlease sembarangan.
- `RELEASED` tidak bisa langsung disettle oleh attempt baru.
- Release berulang tidak mencatat ledger ganda.
- Retry operation menggunakan identity yang valid.
- Reservation expiry ditangani sesuai policy.
- Cleanup errors tidak menutupi original exception.
- Abnormal terminal state tetap dilaporkan sebagai integrity concern.

Jangan membuat semua error menjadi no-op.

## 10. FAILURE RECOVERY

Setelah failure:

- Snapshot tetap tersimpan.
- History tetap memiliki repository terkait.
- User tidak perlu sync ulang.
- Retry analysis memakai snapshot yang sama.
- Tidak membuat duplicate repository.
- Tidak membuat multiple active attempts untuk satu logical operation.
- Tidak menagih dua kali.
- Ready analysis yang sudah tersimpan tetap aman.

Error API harus mempunyai code yang dapat dibaca frontend.

Contoh:

