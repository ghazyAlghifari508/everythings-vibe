## 1. Mission

Perbaiki mekanisme penyimpanan pertanyaan/jawaban, Feature Specification generation, retry, dan error handling dalam workflow Existing Codebase.

Masalah terpenting: user telah menjawab seluruh pertanyaan klarifikasi, tetapi ketika menyusun Feature Specification terjadi kegagalan penyimpanan. Saat user memilih "Coba lagi", sistem justru menghasilkan ulang pertanyaan dan menghapus jawaban sebelumnya.

**Target utama: setiap jawaban yang sudah diberikan harus dapat dipulihkan, dan retry harus mengulang operasi yang gagal saja, bukan seluruh workflow.**

Perbaiki akar masalah, bukan sekadar menyembunyikan alert.

## 3. Confirmed Root-Cause Candidates

### Problem A — Answers only stored locally

`use-workspace-questions.ts` memperbarui jawaban menggunakan:

```
setChatAnswers(current => ({
  ...current,
  [questionId]: trimmed
}))
```

State ini belum menjamin persistence di database.

Ketika save gagal sebelum Feature Generation, jawaban bisa belum memiliki persisted copy yang dapat dipulihkan.

### Problem B — Wrong retry callback

`CodebaseChatWorkspaceMessages` menerima `onRetryQuestions` meskipun run yang gagal dapat berupa:

- questions
- feature
- prd
- ac
- task

Saat callback question retry dipanggil, `fetchAiQuestions()` membuat ulang pertanyaan.

Pada successful question response terdapat:

```
setAiQuestions(...)
setChatAnswers({})
```

Ini dapat menghapus seluruh jawaban yang sudah diberikan.

### Problem C — Multiple independent error states

Saat ini error tersebar pada:

- `run.error`
- `specError`
- `stageError`

State tersebut bisa memiliki lifecycle berbeda sehingga error lama dapat muncul kembali setelah retry.

### Problem D — Save failure hides actual cause

`saveHandoff()` mengembalikan boolean sehingga HTTP 400/401/404/409/429/500 dan network error sama-sama terlihat sebagai pesan generik.

Jangan langsung menyimpulkan bahwa kegagalan selalu berasal dari database.

## 4. Desired Architecture

Pisahkan tiga operasi:

```
GENERATE QUESTIONS
       │
       ▼
Persist Question Set
       │
       ▼
COLLECT ANSWERS
       │
       ├── Q1 saved ✓
       ├── Q2 saved ✓
       ├── Q3 saved ✓
       ├── Q4 saved ✓
       └── Q5 saved ✓
       │
       ▼
FINALIZE HANDOFF
       │
       ├── FAILED
       │      │
       │      ▼
       │   Retry save only
       │      │
       │      ▼
       │   Existing answers preserved
       │
       └── SUCCESS
              │
              ▼
      GENERATE FEATURE
              │
              ├── FAILED
              │      ▼
              │   Retry Feature only
              │
              └── SUCCESS
                     ▼
              Feature persisted
```

**Tidak boleh kembali ke Generate Questions jika operasi yang gagal adalah Save Handoff atau Generate Feature.**

## 5. Implementation Requirements

### A. Durable Question &amp; Answer Persistence

Evaluasi existing Ask Handoff storage terlebih dahulu.

Gunakan schema dan persistence infrastructure yang sudah ada selama mendukung requirement. Jangan langsung membuat sistem database kedua.

Requirements:

- Pertanyaan yang telah berhasil dihasilkan harus dapat dipulihkan dari server.
- Jawaban dikaitkan dengan stable question ID dan project ID.
- Simpan progres jawaban secara bertahap atau melalui autosave yang reliable.
- Gunakan explicit save status jika proses penyimpanan asynchronous.
- Pastikan response save bukan sekadar asumsi dari React state.
- Restore jawaban secara benar setelah reload.
- Hindari stale writes yang menimpa jawaban terbaru.
- Jangan membuat duplicate question sets hanya karena retry.
- Jaga jawaban custom "Lainnya" serta multiple selections.
- Pertahankan kompatibilitas record Ask Handoff lama.

Gunakan revision/version check atau concurrency mechanism yang sesuai agar dua tab tidak diam-diam menimpa jawaban satu sama lain.

Jika server gagal menyimpan jawaban, jangan mengklaim jawaban sudah tersimpan permanen.

### B. Stage-Aware Retry Contract

Jangan gunakan satu generic retry callback yang salah mengidentifikasi operasi.

Representasikan failure secara eksplisit, misalnya:

```
questions.generate
questions.persist
answers.save
handoff.finalize
feature.generate
feature.persist
prd.generate
ac.generate
task.generate
```

Sesuaikan nama dengan existing domain architecture. Jangan membuat terlalu banyak abstraction bila tidak diperlukan.

Retry behavior:

- Questions generate failed → retry Generate Questions.
- Answers save failed → retry Save Answers.
- Handoff finalize failed → retry Finalize Handoff.
- Feature generate failed → retry Feature Generation.
- Artifact persistence uncertain → periksa server lebih dulu, jangan langsung generate ulang.
- 409 already generating → baca current operation status.
- Unauthorized/session expired → tampilkan recovery autentikasi yang sesuai, bukan melakukan infinite retry.

Jangan menjalankan AI model lagi ketika masalah sebenarnya hanya kegagalan menyimpan jawaban.

### C. HTTP Error Contract &amp; Observability

Periksa mengapa `save-handoff` gagal.

Audit khusus `ask-options-route.server.ts` yang melakukan rate-limit sebelum memproses action `save-handoff` dan `get-handoff`.

Pisahkan rate limiting untuk request AI generation dan operasi penyimpanan/pembacaan yang lebih ringan bila kebijakan layanan memerlukannya, dengan tetap menjaga perlindungan abuse.

Kembalikan machine-readable error code yang stabil.

Contoh:

```
HANDOFF_VALIDATION_FAILED
SESSION_EXPIRED
PROJECT_NOT_FOUND
HANDOFF_LOCKED
RATE_LIMITED
PERSISTENCE_FAILED
NETWORK_UNAVAILABLE
```

Nama final disesuaikan dengan sistem error existing.

Frontend harus mengubahnya menjadi pesan user-facing yang sederhana dan dapat ditindaklanjuti.

Server log boleh mencatat operation ID, project ID yang aman, HTTP status, dan failure classification.

Jangan log token, credential, secret, isi prompt sensitif, atau raw AI reasoning.

### D. Error Lifecycle

Gunakan active-operation error state yang konsisten.

```
Attempt 1: FAILED
         │
         ▼
   User clicks Retry
         │
         ▼
Attempt 2: RUNNING
   old error cleared
         │
         ▼
Attempt 2: SUCCESS
   error removed
```

Error dari attempt lama tidak boleh muncul lagi saat request berikutnya sedang berjalan.

Jangan menggunakan timeout sebagai pengganti state reconciliation.

### E. Contextual Error Placement

Jangan menampilkan seluruh error di paling atas chat.

Contoh:

```
User request
Q1 ✓
Q2 ✓
Q3 ✓
Q4 ✓
Q5 ✓

✕ Gagal menyimpan jawaban
  Jawaban tetap tersedia.

                  [Coba lagi]
```

Error harus berada dekat operasi yang gagal.

Jika Feature Generation gagal, tempatkan error setelah clarification summary, bukan sebelum pertanyaan.

### F. Single Primary Action

Saat operasi belum dimulai:

```
[Buat Spesifikasi Fitur]
```

Saat berjalan:

```
◌ Menyusun spesifikasi...
```

Saat gagal:

```
✕ Gagal menyusun spesifikasi
                     [Coba lagi]
```

Saat berhasil:

```
✓ Spesifikasi siap
                     [Lihat Spesifikasi]
```

Jangan menampilkan "Coba lagi" dan "Buat Spesifikasi Fitur" sebagai dua tindakan aktif untuk operasi yang sama.

Block duplicate requests saat in-flight.

### G. Data Safety

- Jangan reset `chatAnswers` saat retry selain regenerasi pertanyaan yang memang disengaja user.
- Jangan menghapus handoff lama sebelum penyimpanan versi baru tervalidasi.
- Jangan menimpa plan project lain.
- Jangan menjalankan ulang generation untuk artifact yang ternyata sudah tersimpan.
- Pertahankan ownership validation.
- Pastikan request terlambat dari feature A tidak mengubah feature B.
- Jangan mengonsumsi kredit ulang akibat transport retry.

## 7. Required Automated Tests

Wajib tambahkan regression tests untuk:

1. Save jawaban gagal → lima jawaban tetap utuh.
2. Retry save tidak memanggil question generation.
3. Retry Feature tidak membuat pertanyaan baru.
4. Successful save dapat direstore dari persisted storage.
5. Jawaban "Lainnya" tetap tersimpan.
6. Retry tidak menghasilkan duplicate projects.
7. Error lama hilang setelah retry dimulai.
8. Tombol generate biasa tidak muncul bersamaan dengan retry aktif.
9. HTTP 400/401/404/409/429/500 dipetakan dengan benar.
10. Delayed responses tidak menimpa data project berbeda.
11. Double click tidak menghasilkan duplicate requests.
12. Server berhasil menyimpan tetapi respons hilang → retry melakukan reconciliation.
13. Existing greenfield Ask flow tidak mengalami regresi.

Jalankan focused unit/integration tests, typecheck, lint, dan build sesuai scripts repository.

**STRICT: SKIP seluruh browser QA. Jangan menjalankan Playwright, Puppeteer, browser automation, browser E2E, manual browser testing, maupun screenshot visual testing.**

## 8. Definition of Done

- User tidak harus menjawab ulang karena Save Handoff gagal.
- Retry selalu tepat sasaran.
- Semua pertanyaan dan jawaban dapat dipulihkan.
- Error contextual dan tidak menetap setelah operasi berubah.
- Tidak ada duplicate CTA.
- Tidak ada duplicate generation akibat retry.
- Server dan frontend konsisten tentang status penyimpanan.

Laporan akhir wajib memuat root cause, perubahan database/API/frontend, test results, dan risiko residual yang belum teratasi.

Jangan mengklaim bug selesai hanya karena alert tidak muncul lagi.
