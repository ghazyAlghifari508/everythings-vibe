## 1. Objective

Perbaiki fondasi sistem pertanyaan klarifikasi AI pada VibePlan Existing Codebase agar setiap pilihan jawaban mempunyai judul dan deskripsi yang jelas, rekomendasi AI dapat ditampilkan pada posisi pertama, dan seluruh informasi tetap benar ketika disimpan, diedit, dipulihkan, atau digunakan untuk generasi Feature, PRD, AC, dan Task.

**Scope FIX 01 hanya model data, generation prompt, validation, mapping, dan persistence. Jangan melakukan redesign visual card pada tahap ini. Redesign UI dikerjakan pada FIX 02 setelah kontrak datanya siap.**

Masalah yang dilaporkan pengguna:

1. Rekomendasi AI terkadang berada di urutan kedua, ketiga, atau berikutnya. Pengguna menginginkan rekomendasi selalu menjadi opsi pertama.
2. Semua opsi sekarang hanya berupa teks pendek, sehingga perbedaan dan konsekuensi setiap pilihan kurang jelas.
3. Penjelasan alasan rekomendasi justru ditempatkan di panel terpisah di bawah seluruh opsi.
4. Pengguna menginginkan setiap pilihan mempunyai heading dan description langsung pada pilihan tersebut.
5. Heading dan description harus tersedia untuk SEMUA pilihan, bukan hanya opsi rekomendasi.
6. Copy harus natural, informatif, spesifik, mudah dipahami, tidak ambigu, dan tidak memakai pola bahasa AI generik.

Jangan menyelesaikan masalah ini hanya dengan mengubah urutan array atau menambahkan description buatan di frontend. Perbaiki sumber data yang menghasilkan dan menyimpan opsi.

## 3. Target Data Contract

Untuk pertanyaan baru di Existing Codebase, setiap opsi wajib mempunyai minimal:

- Stable identity.
- `label` atau `title` sebagai heading utama.
- `description` sebagai penjelasan singkat.
- Identitas rekomendasi yang valid jika pertanyaannya memiliki rekomendasi.

Utamakan mempertahankan nama `label` untuk heading apabila itu mengurangi perubahan pada existing consumers dan format jawaban yang disimpan.

Contoh bentuk konseptual:

```
{
  id: "search-scope",
  question: "Informasi apa saja yang perlu dicari?",
  type: "select",
  options: [
    {
      label: "Judul, deskripsi, dan teknologi",
      description: "Pengunjung dapat mencari proyek melalui nama, ringkasan, atau teknologi yang digunakan."
    },
    {
      label: "Judul dan deskripsi proyek",
      description: "Pencarian mencakup nama dan ringkasan proyek tanpa menggunakan informasi teknologi."
    },
    {
      label: "Judul proyek saja",
      description: "Pencarian hanya mencocokkan nama proyek."
    }
  ],
  recommended: 0,
  recommendationReason: "..."
}
```

Ini hanya contoh kontrak semantik. Final TypeScript/Zod schema harus disesuaikan dengan arsitektur aktual.

Ketentuan:

1. Identitas opsi tidak boleh bergantung pada posisi visual setelah sorting.
2. Jangan mengganti label jawaban yang tersimpan menjadi gabungan `label + description`.
3. Description adalah informasi pendukung, bukan bagian dari nilai jawaban.
4. Jangan mengubah jawaban user menjadi teks penjelasan AI.
5. Hindari parallel arrays yang rawan kehilangan kesesuaian indeks.
6. Hindari dua sumber kebenaran berbeda untuk satu opsi.
7. Jangan menambahkan type bypass atau unsafe casting.

**Penting:** Pisahkan urutan kanonis dari urutan tampilan.

Jika rekomendasi awalnya berada pada indeks 2, identitas dan nilai rekomendasinya tetap mengarah ke opsi yang benar. Pada FIX 02, opsi tersebut akan ditampilkan pertama.

Jangan memindahkan isi array secara permanen hanya demi kebutuhan tampilan jika itu dapat merusak referensi indeks, saved answers, atau hydration.

## 4. Recommendation Semantics

Untuk pertanyaan single-select baru di Existing Codebase, AI harus berusaha menghasilkan satu rekomendasi yang paling tepat berdasarkan konteks repository dan kebutuhan fitur.

Aturan:

- Rekomendasi harus mengarah ke opsi yang benar-benar ada.
- Indeks atau ID rekomendasi harus divalidasi.
- Rekomendasi tidak boleh otomatis menjadi selected answer.
- Pengguna tetap bebas memilih opsi alternatif.
- Opsi rekomendasi nantinya wajib tampil pertama, bukan berdasarkan urutan mentah dari AI.
- Jangan menandai sebuah opsi sebagai rekomendasi hanya karena posisinya pertama.
- Jangan membuat klaim berbasis repository tanpa bukti dari snapshot atau analisis yang tersedia.

Jika generation menghasilkan rekomendasi yang invalid, hilang, atau tidak sesuai kontrak, gunakan jalur validation/repair yang sudah tersedia. Jangan secara diam-diam memilih indeks 0.

Jika repository tidak mempunyai bukti yang cukup untuk menyatakan suatu opsi lebih unggul, jangan memalsukan keyakinan AI. Tangani melalui fallback yang jujur. Invariant "rekomendasi harus pertama" berlaku setiap kali rekomendasi valid tersedia.

Untuk multiselect, jangan secara otomatis menerapkan semantik single-select atau mengubah pilihan menjadi radio button. Pertahankan kemampuan memilih beberapa opsi.

## 5. Generate Meaningful Heading and Description

Perbaiki generation prompt Existing Codebase supaya AI menghasilkan jawaban dengan kedalaman yang cukup.

**Heading:**

- Menjelaskan apa yang akan dipilih.
- Pendek, tetapi tidak dipotong secara paksa menjadi frasa yang kehilangan makna.
- Spesifik terhadap pertanyaan.
- Menggunakan Bahasa Indonesia natural.
- Tidak memakai jargon internal aplikasi jika pengguna tidak membutuhkannya.
- Tidak menyamakan opsi yang konsekuensinya berbeda.

**Description:**

- Menjelaskan dampak, cakupan, perilaku, atau batasan pilihan.
- Biasanya satu atau dua kalimat ringkas.
- Membantu user membandingkan opsi.
- Tidak sekadar mengulang heading dengan kata lain.
- Tidak menambahkan klaim yang tidak didukung repository.
- Tidak semuanya diawali pola kalimat identik.
- Tidak terlalu pendek sampai kehilangan manfaat.
- Tidak dipanjangkan hanya demi memenuhi jumlah kata.

Untuk rekomendasi, explanation harus sudah dapat dibaca dari opsi yang direkomendasikan, termasuk alasan yang relevan jika tersedia.

`recommendationReason` boleh dipertahankan sebagai metadata terstruktur untuk compatibility atau internal logic. Namun jangan membuat frontend menampilkan dua penjelasan yang mengulang informasi yang sama.

Contoh yang tidak diterima:

```
Judul:
Judul dan teknologi

Deskripsi:
Pilihan terbaik untuk pengalaman
pencarian yang optimal dan efisien.
```

Masalah: generik, tidak menjelaskan perilaku, dan menggunakan klaim kualitas tanpa bukti.

Contoh yang diharapkan:

```
Judul:
Judul, deskripsi, dan teknologi

Deskripsi:
Pengunjung bisa menemukan proyek melalui
nama, ringkasan, atau teknologi yang
digunakan, meskipun belum mengetahui
judul proyeknya.
```

Untuk opsi alternatif:

```
Judul:
Judul proyek saja

Deskripsi:
Pencarian hanya mencocokkan nama proyek.
Cocok jika pengunjung biasanya sudah
mengetahui proyek yang ingin dibuka.
```

Semua contoh hanya referensi kualitas copy. AI harus tetap menyesuaikan isi dengan konteks pertanyaan aktual.

## 6. Copy Quality Rules

Hindari AI slop, termasuk:

- "Solusi terbaik untuk kebutuhan Anda."
- "Memberikan pengalaman yang optimal."
- "Lebih fleksibel dan efisien."
- "Meningkatkan produktivitas secara signifikan."
- Kalimat promosi tanpa informasi konkret.
- Penggunaan istilah teknis berlebihan.
- Deskripsi berulang di semua opsi.
- Klaim palsu tentang implementasi repository.
- Saran yang membuat semua opsi terdengar sama bagusnya.

Gunakan pertanyaan evaluasi berikut:

1. Apa yang berubah ketika pilihan ini dipilih?
2. Apa perbedaannya dari pilihan lain?
3. Apakah user awam bisa memahami konsekuensinya?
4. Apakah alasannya benar-benar relevan dengan fitur?
5. Apakah informasi dapat dipertanggungjawabkan?

Jangan hanya menambahkan larangan bahasa pada prompt. Perbaiki format output dan proses validasinya agar AI terdorong memberikan informasi yang benar-benar berguna.

Pertahankan kemampuan bertanya tentang keputusan produk yang belum jelas, bukan menanyakan ulang fakta teknis yang sudah diketahui dari repository.

Ini bagian kritis.

Periksa:

- `serializeAskQuestions()`
- `restoreAskState()`
- `parseRestoredQuestions()`
- `useWorkspaceHandoffPersistence()`
- `useWorkspaceQuestions()`
- Server handoff schemas.
- Existing Codebase question generation operation.
- Edit-answer flow.
- Submitted answer mapping.

Pastikan:

- Pertanyaan baru menyimpan heading dan description.
- Data tersimpan dapat dipulihkan tanpa kehilangan description.
- Identitas rekomendasi tetap benar.
- Jawaban lama tetap bisa dibaca.
- Format lama `string[]` tidak menyebabkan error.
- Data lama tidak dimigrasikan secara destruktif.
- Pembukaan history tidak otomatis mengulang generation.
- Tidak ada konsumsi kredit hanya karena mengakses pertanyaan lama.
- Jawaban tidak tertukar ketika rekomendasi dipindahkan secara visual pada FIX 02.
- Greenfield tetap menggunakan kontrak sebelumnya jika memang tidak masuk scope.

Jika deskripsi tidak tersedia pada data legacy, jangan mengarang fakta yang tidak ada. Gunakan compatibility rendering yang jujur dan tidak menghilangkan opsi atau jawaban tersebut.

Kalau shared parser perlu mendukung format baru, buat pemisahan validasi yang jelas untuk Existing Codebase dan Greenfield tanpa menduplikasi seluruh pipeline.

## 9. Required Automated Tests

Tambahkan atau perbarui targeted tests untuk:

1. Parsing opsi baru dengan heading dan description.
2. Penolakan data generation yang tidak memenuhi kontrak.
3. Validasi rekomendasi terhadap opsi yang benar.
4. Legacy options berupa string.
5. Serialization dan restoration round-trip.
6. Single-select answer integrity.
7. Multiselect behavior tetap benar.
8. Jawaban hasil edit tetap konsisten.
9. Rekomendasi tidak otomatis terpilih.
10. Tidak ada regression pada Greenfield.
11. Tidak ada perubahan makna ketika opsi ditampilkan dalam urutan berbeda.
12. Restore history tidak memicu generation baru.

Gunakan deterministic fixtures untuk validasi struktur dan behavior. Jangan membuat unit test yang bergantung pada kata-kata persis hasil AI.

Jalankan targeted Vitest, Biome, dan typecheck yang relevan. Laporkan kegagalan yang benar-benar terjadi, jangan melemahkan test untuk memaksa hasil hijau.

- Setiap opsi baru Existing Codebase mempunyai heading dan description bermakna.
- Kontrak rekomendasi terstruktur dan tervalidasi.
