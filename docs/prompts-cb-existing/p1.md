**Jangan menganggap expired CLI token sebagai penyebab sebelum ada bukti. Jangan menyelesaikan masalah dengan menghapus validasi kredit, memaksa status** `ready`**, atau menelan error.**

## 5. Mandatory Root Cause Investigation

### A. Trace the Original Persistence Exception

Identifikasi exception asli ketika transaction gagal.

Bedakan:

- Credit settlement failure.
- Subscription origin mismatch.
- Credit operation already terminal.
- Credit reservation expired.
- Invalid final charge.
- Insufficient reserved credit.
- DB constraint violation.
- Serialization/deadlock/transaction conflict.
- Failed analysis output persistence.
- Stale or mismatched analysis operation identity.

Jangan hanya mencatat `category: persistence` dan berhenti.

Tambahkan structured internal diagnostic logging yang aman:

```
analysisAttemptId
codebaseId
snapshotId
creditOperationId
operationState
operationExpiresAt
stage
errorCategory
errorCode
durationMs
```

Hindari logging token CLI, API keys, source code repository, atau output AI sensitif.

### B. Trace Credit Operation State

Audit operasi reserve → running → settling → settled/released.

Verifikasi:

- Apakah satu analysis attempt memakai satu credit operation yang tepat?
- Apakah operasi lama dapat digunakan ulang secara tidak sengaja?
- Apakah idempotency key mengembalikan reservation yang sudah terminal?
- Apakah retry menghasilkan operation yang baru dengan identity konsisten?
- Apakah reconciliation dapat mengubah operasi aktif saat AI masih bekerja?
- Apakah credit operation telah expired saat dicoba settle?
- Apakah analysis ID dan credit operation reference benar-benar cocok?

Audit `buildAnalysisIdempotencyKey`, reservation retry loop, dan expiration reconciliation.

### C. Investigate 404 Separately

Identifikasi request mana yang mengembalikan 404.

Jangan menganggap semua 404 berasal dari snapshot hilang.

Audit perbedaan antara:

- Codebase-scoped ID.
- Onboarding project ID.
- Analysis project ID.
- Snapshot ID.
- Sync session ID.

Pastikan GET/POST analysis menggunakan scope dan resource identity yang benar.

404 untuk resource missing harus dibedakan dari 502 karena analysis processing failure.

## 6. Target Lifecycle

```
UPLOAD COMPLETED
       │
       ▼
SNAPSHOT STORED
       │
       ▼
CREDIT ELIGIBILITY CHECK
       │
       ▼
RESERVE / AUTHORIZE OPERATION
       │
       ▼
ANALYSIS ATTEMPT PENDING
       │
       ▼
MODEL GENERATION
       │
       ▼
OUTPUT VALIDATION
       │
       ▼
PERSIST / FINALIZE TRANSACTION
       │
       ├── Failure
       │     ├── Record actual error
       │     ├── Reconcile credit safely
       │     └── Preserve snapshot for retry
       │
       └── Success
             ├── Analysis READY
             ├── Credit accounting finalized
             └── Workspace becomes available
```

**Invariant utama:**

- Tidak boleh ada successful charge tanpa approved billing basis dan hasil analisis final yang berhasil tersimpan.
- Tidak boleh ada analysis READY yang belum melewati validasi output dan finalization yang diperlukan.
- Tidak boleh ada duplicate charge untuk satu logical attempt.
- Tidak boleh ada snapshot yang terhapus akibat analysis failure.
- Tidak boleh ada analysis dari snapshot berbeda yang secara diam-diam dipakai.

## 7. Persistence &amp; Transaction Correctness

Audit penggunaan transaksi yang sama untuk:

1. Credit settlement.
2. Analysis status update.
3. Analysis output persistence.
4. Associated operation accounting.

Pastikan transaction rollback benar-benar konsisten.

Jika hasil model selesai tetapi finalization gagal, pertimbangkan strategi recoverable validated output agar retry finalization tidak selalu harus membayar model generation ulang.

Namun jangan memperkenalkan penyimpanan hasil sensitif baru tanpa mempertimbangkan authorization, retention, encryption, dan lifecycle.

Reconcile DB state dengan benar setelah process crash atau timeout.

Tidak boleh membuat fake ready result sebagai fallback.

## 8. Cleanup Must Be Safe and Idempotent

Saat analysis gagal, logic `releaseCreditOperation` tidak boleh menjadi secondary error yang menutupi root cause.

Current error:

```
Credit operation is not active
```

Audit kapan operasi dapat berada pada:

```
reserved
running
settling
settled
released
failed
refunded
```

Implementasikan safe terminal-state handling yang benar.

Contoh prinsip:

```
ACTIVE, not finalized → release according to policy
ALREADY RELEASED     → no duplicate release
ALREADY SETTLED      → inspect consistency; don't silently release
ALREADY REFUNDED     → no duplicate refund
UNKNOWN/INVALID      → raise internal integrity signal
```

Jangan mengubah semua exception menjadi successful no-op. State yang tidak konsisten harus tetap terdeteksi dan dapat diperbaiki.

Credit ledger harus tetap akurat.

## 9. Concurrency and Retry Safety

Test kasus:

- Dua request analysis untuk snapshot sama.
- Double click retry.
- Provider response datang terlambat.
- Reconciliation berjalan bersamaan dengan settlement.
- Reservation expired sebelum finalization.
- Retry setelah failed operation.
- Refresh client ketika analysis pending.
- Server restart ketika generation atau finalization.
- Successful generation tetapi response HTTP hilang.
- Existing READY analysis dipanggil kembali.

Satu snapshot tidak boleh menciptakan beberapa competing active attempts akibat duplicate request biasa.

Gunakan locking, idempotency, dan optimistic concurrency yang sesuai dengan existing architecture.

## 10. Credit Accounting Requirements

Jangan melakukan:

```
analysis.status = "ready";
```

hanya untuk melewati gating.

Jangan memberi kredit gratis sebagai workaround.

Jangan menambah nilai saldo secara manual.

Tidak boleh ada pemotongan kredit tanpa sebab yang dapat ditelusuri.

Periksa rollback, reserve, release, dan settle menggunakan actual ledger tests.

Jika terdapat credit operation lama yang corrupt, sediakan strategi repair/migration yang aman dan dapat diaudit, bukan SQL mass-update tanpa verifikasi.

Tetapi di server log, pertahankan diagnostic detail yang cukup untuk root cause.

Gunakan correlation ID/attempt ID untuk mencocokkan frontend request dengan error backend.
