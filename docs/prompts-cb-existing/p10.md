## Background

The repository analysis UI now produces reasonably useful sections such as:

- Ringkasan aplikasi.
- Teknologi repository.
- Struktur repository.
- Bagian aplikasi.
- Temuan arsitektur.
- Hal yang belum dapat dipastikan.

However, some statements remain too absolute, generic, repetitive, or weakly supported by source evidence.

Observed examples include:

1. Concluding that an application has no dynamic database dependency without clearly stating the limits of inspected files.
2. Reporting placeholder assets as a confirmed architectural finding without making supporting evidence easy to inspect.
3. Repeating the same placeholder-assets claim in both confirmed findings and uncertain findings.
4. Treating the presence of SEO-related files as proof of SEO quality.
5. Displaying architectural findings without clear evidence and practical implications.

## Objective

The analysis should help a user understand:

1. What the application actually does.
2. Which technologies and architectural patterns are detectable.
3. How major parts of the repository interact.
4. Which claims are supported by source evidence.
5. Which findings are uncertain.
6. What architectural considerations matter for future feature planning.

Do not fabricate a more impressive-looking report.

## Core analysis rules

### Evidence first

Every important finding should have traceable evidence where available.

Example:

```
Finding:
Konten proyek dikelola lewat data lokal.

Evidence:
src/content/projects.json
src/content.config.ts

Implication:
Perubahan field proyek harus menjaga
kompatibilitas dengan schema konten.
```

Example paths must be replaced by paths that actually exist in the inspected snapshot.

If precise line ranges are unavailable, do not invent them.

### Distinguish claim types

Separate:

- Verified from inspected source.
- Strong inference from repository structure.
- Unverified or insufficient evidence.

Do not label all interpretations as certain.

### Avoid absolute negative claims

Instead of:

`Aplikasi tidak menggunakan database.`

Prefer a scope-aware statement when appropriate:

`Tidak ditemukan konfigurasi database pada bagian repository yang berhasil dianalisis.`

This distinction matters when the snapshot is limited or some files were excluded.

### Avoid duplicated uncertainty

If the factual finding is:

`Beberapa asset mengarah ke placeholder.`

The uncertainty should explain what remains unverified, not repeat the entire statement as another finding.

For example:

`Belum dapat dipastikan apakah asset asli tersedia di lokasi yang tidak termasuk snapshot.`

### Don't equate existence with quality

The existence of an SEO verification file does not prove SEO optimization is good.

Similarly, using a framework does not automatically prove that its best practices are followed.
