## 1. Objective

Perbaiki lifecycle Sync ulang pada Existing Codebase agar setiap percobaan mempunyai sesi yang jelas dan progress yang benar-benar berasal dari sesi tersebut.

Bug yang dilaporkan:

1. Setelah initial sync berhasil, user membuka workspace.
2. User menekan `Sync ulang`.
3. Modal re-sync terbuka.
4. Padahal prompt re-sync belum dijalankan, seluruh progress terlihat selesai.
5. Sesi/prompt baru tidak selalu tersedia.
6. API session pernah mengembalikan HTTP 503.
7. UI masih menawarkan `Selesai` meskipun user belum memulai re-sync.

Tujuan FIX 04 adalah memperbaiki state dan backend session correctness. Visual modal akan diperbaiki pada FIX 05.

## 4. Diagnose HTTP 503 Correctly

Periksa seluruh transaction flow:

```
User clicks Sync ulang
          |
          v
Generate Request Identity
          |
          v
POST Session Endpoint
          |
          v
Validate Authentication
          |
          v
Check Existing Sessions
          |
          v
Prepare Re-sync Session
          |
          v
Transaction / Database
          |
          +-- Success -> New Session
          |
          +-- Failure -> Structured Error
```

Investigasi kemungkinan:

- Unique constraint.
- Incorrect request ID reuse.
- Stale idempotency record.
- Wrong session status.
- Transaction conflict.
- Migration/schema mismatch.
- Multiple concurrent session requests.
- Incorrect recovery branch.
- Insufficient permission.
- Existing active session.
- Database connection failure.

Ini daftar investigasi, bukan daftar penyebab yang sudah terbukti.

Identifikasi exception sebenarnya dari server-side diagnostics yang aman.

Jangan hanya mengganti status 503 menjadi 200.

## 5. Session Identity Must Be Explicit

Re-sync baru harus memiliki identity yang berbeda dari initial sync yang sudah selesai.

Target:

```
INITIAL SYNC
Session A
├── Connected
├── Uploaded
└── Analysis ready

USER OPENS RE-SYNC

RE-SYNC
Session B
├── Created
├── Waiting for agent
├── Connected
├── Uploaded
└── Analysis ready
```

Session A tidak boleh menjadi sumber progress Session B.

Initial snapshot tetap tersedia selama re-sync berlangsung.

Gunakan current-attempt identity untuk mengikat:

- Prompt credential.
- Sync status.
- Progress rows.
- Upload progress.
- Analysis status.
- Completion verification.
- Recovery state.

Jangan memakai status terakhir secara otomatis jika tidak cocok dengan current attempt.

## 6. Prevent Stale Status Leakage

Periksa logic seperti:

```
payload?.sessionId ??
activeSessionId ??
status?.sessionId
```

Jangan menggunakan fallback ke status lama untuk mengklaim bahwa current re-sync berhasil.

Pastikan:

- Opening a fresh re-sync does not display old completion.
- New attempt starts with honest waiting state.
- Polling is bound to current session.
- SSE events are associated with the correct session.
- Late responses from previous session cannot overwrite current progress.
- Session refresh does not accidentally attach unrelated status.
- Completion requires verified current attempt.
- No false checkmarks.

Jika browser memulihkan sesi re-sync yang memang masih aktif, jangan membuat sesi kedua tanpa kebutuhan.

Bedakan valid session recovery dengan stale session reuse.

## 7. Idempotency and Concurrent Sessions

Server harus menjadi source of truth.

Periksa behavior:

- Double-click Sync ulang.
- Request timeout followed by retry.
- Two tabs opening re-sync.
- Reload while awaiting agent.
- Session already connected.
- Expired session.
- Failed session.
- Previously completed session.
- Session request returns a restored in-progress session.
- Credential cannot be returned again after server intentionally discards it.

Gunakan existing request ID/idempotency mechanism dengan benar.

Jangan membuat unlimited duplicate sessions.

Jangan mencabut credential dari active CLI upload hanya demi membuat token baru.

## 8. Prompt Availability and Recovery

Harus ada perbedaan jelas antara:

1. Prompt baru tersedia.
2. Sesi sedang disiapkan.
3. Credential tidak lagi tersedia, tetapi session masih berjalan.
4. Session completed.
5. Session expired.
6. Session creation failed.
7. Sesi lama sudah digantikan.

Jika prompt baru bisa dibuat secara aman, berikan action untuk membuatnya.

Jika CLI sedang melakukan upload, tampilkan progress tanpa mengganti token.

Jika sesi sudah selesai, jangan pura-pura prompt masih diperlukan.

Jangan menyimpan raw sync token secara permanen atau mengembalikannya melalui status endpoint biasa.

## 9. Preserve Repository and Planning Data

Jangan menghapus planning lama otomatis.
