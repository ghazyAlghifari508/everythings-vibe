## 1. MISSION

Perbaiki progress sinkronisasi Existing Codebase agar setiap tahap memiliki status yang jelas, live, dan berasal dari kejadian sistem sebenarnya.

Current problem:

User menjalankan AI coding agent dan melakukan CLI sync.

Namun UI sering langsung berubah menjadi:

```
✓ Agent terhubung
✓ Source code siap
✓ Sinkronisasi selesai
```

User tidak sempat melihat status loading saat proses berlangsung.

Hal ini terasa seperti progress yang tiba-tiba muncul, bukan operasi yang dipantau realtime.

Target:

- Waiting stage terlihat sejak awal.
- Agent connection memiliki pending/loading state.
- Saat koneksi berhasil, state menjadi completed.
- Berikutnya terlihat status source preparation.
- Upload menampilkan progress nyata saat tersedia.
- Analisis AI mempunyai lifecycle terpisah.
- Failure tidak mengubah tahapan yang sebenarnya berhasil.
- Browser refresh/reconnect tidak membuat progress palsu.
- Status dapat ditelusuri ke backend events.
- Jangan menggunakan artificial delay untuk memaksa setiap spinner tampil.

**Buat progress yang benar-benar observable, bukan animasi mock.**

## 5. EVENT-DRIVEN STATUS DELIVERY

Prioritize authentic server events over relying solely on periodic status snapshots.

Recommended architecture:

```
CLI
  │
  ▼
VibeEverything Sync API
  │
  ├── agent.connected
  ├── source.preparing
  ├── source.prepared
  ├── upload.started
  ├── upload.progress
  ├── upload.completed
  ├── analysis.started
  ├── analysis.completed
  └── analysis.failed
          │
          ▼
Persisted Status/Event Timeline
          │
          ▼
SSE or Existing Event Infrastructure
          │
          ▼
React Sync Progress UI
```

Events above are desired semantic events, not an assumption that all are already implemented.

Do not invent events the backend cannot actually observe.

Inspect existing event/streaming infrastructure before adding new systems.

### SSE

Use Server-Sent Events when appropriate for unidirectional updates.

Reference:

[https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)

Requirements:

- Authorized stream connection.
- Scoped session and project.
- Event IDs or sequence numbers.
- Reconnection support.
- Event replay or state reconciliation.
- No duplicated stage handling.
- Cleanup on unmount.
- Heartbeat where needed.
- Bounded retention.
- Fallback to existing polling if live stream unavailable.

Do not store raw sync tokens in progress events.

If existing infrastructure already supports equivalent streaming, reuse it instead of implementing another SSE system.

## 6. REAL EVENT TIMELINE

Progress event state should be linked to actual server timestamps.

Example:

```
type SyncProgressEvent = {
  sessionId: string;
  eventId: string;
  stage: string;
  state: "pending" | "running" | "completed" | "failed";
  occurredAt: string;
};
```

This is conceptual, not a fixed implementation requirement.

Use the actual schema and naming conventions.

A completed event must not be emitted when an operation is merely accepted.

An event must not be emitted twice because the frontend rerenders.

Late old-session events must not overwrite current session.

## 7. FIRST STAGE LOADING

The first row must be visible as soon as sync instructions/session are ready.

Before CLI connects:

```
◌ Menunggu agent terhubung...
```

When the backend confirms agent connection:

```
✓ Agent terhubung
```

When source preparation actually starts:

```
◌ Menyiapkan source code...
```

Do not wait until the first completed poll to render the first waiting spinner.

This directly addresses the complaint that "Agent terhubung" appears already checked without a visible preceding state.

## 8. HANDLE VERY FAST OPERATIONS HONESTLY

Important:

Some stages may complete faster than the browser can visually paint them.

Do not artificially slow down CLI upload or hold every spinner for several seconds just to make animation visible.

Instead:

- Persist event chronology.
- Render current stage accurately.
- Provide a compact activity timeline if useful.
- Replay missed events on reconnection when supported.
- Preserve timestamps.
- Never show completed before confirmation.

If a stage starts and finishes too quickly for the user to see a running frame, correct event delivery and chronological activity data are the solution—not fake delays.

Avoid exposing unnecessary technical details such as raw internal operation IDs on the main progress view.

## 10. ANALYSIS AS SEPARATE STAGE

AI analysis is not the same as uploading the repository.

Required:

```
Sync completed
    ↓
Analysis pending/running
    ↓
Analysis ready/failed
```

Analysis progress must come from actual persisted attempt status.

Use active attempt identity to ensure old errors do not override a new retry.

Never generate fake model thoughts.

Don't display "Menganalisis..." if a request has not yet been accepted unless explicitly showing short "Memulai analisis..." state.

## 11. REFRESH AND RECONNECT

On refresh:

1. Load session ID.
2. Fetch latest server status.
3. Load relevant event timeline.
4. Resume stream from last event ID where supported.
5. Reconcile completed stages.
6. Continue current running status.
7. Do not restart CLI or AI generation.
8. Do not show stale events from another session.

When stream disconnects:

```
Koneksi pembaruan terputus.
Menghubungkan kembali...
```

Only show this when relevant.

Do not falsely mark sync failed because the browser lost the event connection.
