# FIX 04 — Context-Aware Next-Screen Suggestions and Professional Prompt Shortcuts

**Severity:** P1 HIGH  
**Complexity:** MEDIUM–COMPLEX  
**Target:** `feature/vibedesign-design-studio`  
**Execution order:** 04/08. Kerjakan setelah FIX 03 selesai.

## 1. User complaint

Shortcut prompt pada canvas saat ini terlihat terlalu malas dan generik.

Contoh yang muncul:

- Buat Eksplor
- Buat Pesanan
- Buat Akun
- Buat Profil

Padahal user ingin rekomendasi kontekstual seperti Google Stitch, yang menggambarkan **apa yang perlu didesain berikutnya**, bukan sekadar nama halaman.

Contoh gaya referensi:

"Generate the Explore &amp; Highlights home screen"

"Generate the Music &amp; Events Radar festival screen"

"Add an Expense Splitting modal or detail screen"

Tugasmu bukan menerjemahkan label ke bahasa Inggris. Tugasmu adalah meningkatkan kualitas rekomendasi dan presentasi berdasarkan kebutuhan project.

## 3. Desired behavior

Suppose the existing project is a travel app with:

```
Existing screens:
✓ Pencarian Destinasi
✓ Eksplorasi Paket
✓ Detail Paket
✓ Checkout
✓ Konfirmasi & E-Tiket
```

Suggested next screens should be justified by the current product workflow.

Example:

```
        CANVAS

┌────────────────────────────────────────────┐
│ ↪ Buat halaman riwayat perjalanan          │
│   Lihat pesanan, pembayaran, dan e-tiket.  │
├────────────────────────────────────────────┤
│ ↪ Rancang wishlist paket wisata            │
│   Simpan favorit dan bandingkan destinasi. │
├────────────────────────────────────────────┤
│ ↪ Tambahkan profil traveler                │
│   Kelola identitas dan data penumpang.     │
└────────────────────────────────────────────┘

┌────────────────────────────────────────────┐
│ Minta revisi, atau jelaskan halaman baru...│
│                                            │
│ [Skill] [Theme]                         ↑  │
└────────────────────────────────────────────┘
```

Ini visualisasi pola UI. Nama dan isi suggestion harus berasal dari project masing-masing, bukan daftar hardcode yang sama untuk semua user.

## 4. Suggestion quality

Setiap suggestion harus memiliki:

- stable ID;
- concise action-oriented title;
- short contextual description;
- complete editable prompt;
- evidence/source indicating why suggested;
- target intent `add_screen`;
- existing-screen deduplication.

Usulan kontrak data jika memang diperlukan:

```
type SuggestedScreen = {
  id: string;
  title: string;
  description: string;
  prompt: string;
  reason: string;
  intent: "add_screen";
};
```

Jangan tambah field jika existing schema sudah mendukungnya.

### Candidate source priority

Use, in order:

1. Explicit user request/PRD.
2. Remaining screen plan from shared blueprint.
3. Incomplete user journey implied by existing screens.
4. Navigation destinations without matching screens.
5. Domain-specific feature recipes.
6. Generic platform defaults only when truly appropriate.

The system should understand that a travel app may benefit from itinerary, saved trips, booking history, and account details, while a finance app may need transaction categories, reports, goals, or settings.

Don't suggest duplicate pages based on minor naming differences or synonyms.

## 5. Prompt quality

Clicking a suggestion must populate an editable composer with detailed, useful instruction.

Example suggestion:

**Label:**  
"Rancang halaman riwayat perjalanan"

**Prompt inserted into composer:**

"Buat satu halaman Riwayat Perjalanan untuk aplikasi Jelajahin. Tampilkan daftar pesanan sebelumnya dan perjalanan mendatang, ringkasan paket, tanggal keberangkatan, status pembayaran, serta akses detail pesanan dan e-tiket. Gunakan navigasi, warna, tipografi, header, dan komponen yang konsisten dengan layar project yang sudah ada. Jangan mengubah halaman lain."

This is a pattern, not an exact hardcoded string.

Avoid:

- purely repetitive "Buat X";
- extremely generic "Tampilkan konten utama";
- recommendation unrelated to the project;
- copy pretending to understand features absent from the brief;
- overly long suggestion titles.

## 6. UI component-first workflow

Before editing UI, inspect existing reusable components and:

- shadcn/ui
- HeroUI
- Magic UI
- React Bits
- Thinking Orbs
- affectUI

Candidates worth evaluating:

- card / button primitives;
- suggestion cards;
- scroll area;
- tooltip;
- composable list item;
- compact recommendation surface.

Prefer existing installed components, then install/use a compatible ready-made component if it genuinely improves the result.

Do not build an unrelated custom component library.

Follow dark-mode Studio appearance and Google Stitch's quiet, compact recommendation style.

Do not use glowing gradients, decorative sparkles, excessive pills, or unrelated motion.

Accessibility requirements:

- proper button semantics;
- keyboard focus;
- visible selected/hover state;
- complete prompt available without inaccessible truncation;
- responsive placement;
- no overlap with canvas zoom controls or frames.

## 7. Performance and UX behavior

- Show 2–3 high-quality suggestions by default, not a forced wall of generic cards.
- A click populates the composer; it does not automatically submit.
- User can edit before submitting.
- Suggestions refresh after a new page is created.
- Existing page should never be silently regenerated.
- Project zoom/pan should never call AI or rebuild suggestions.
- Polling state should not trigger expensive recomputation.
- Keep revision-based caching.
- Do not introduce an expensive model call on every canvas render.
- If model-assisted suggestion generation is justified, it must be optional/asynchronous relative to canvas readiness, cached and bounded, with safe deterministic fallback.
- Prefer fewer meaningful recommendations over filler.
