# P4 — Rebuild the Existing Studio Chat Presentation Into a Floating AI Design Conversation

**Complexity: COMPLEX**  
**Execution order: 04/11**

## 1. Objective

Improve the existing persistent chat workspace to deliver the intended Google Stitch-inspired interaction.

Do NOT rebuild the conversation backend from scratch if the current persistence and job synchronization already work.

The required changes concern:

- Floating panel layout.
- User message bubbles.
- Collapsible long prompts.
- Structured assistant responses.
- Meaningful conversation content.
- Animated opening and closing.
- Restoration of the transparent workspace header.
- Correct composer placement.

No reverse engineering is requested. Implement the behavior explicitly described below using the existing application and supplied visual references.

## 2. Reported problems

Current chat panel:

- Touches the top, left, and bottom boundaries of the workspace.
- Has a full-height sidebar divider.
- Compresses the canvas like a conventional dashboard sidebar.
- Displays the heading "DESIGN AGENT".
- Repeatedly shows "Anda — Diterima".
- Repeatedly shows "Design agent — Selesai".
- Displays long initial prompts in full.
- Renders assistant and user messages with nearly identical visual structure.
- Displays plain text status messages instead of useful design explanations.
- Exposes unrelated technical failures within the conversation.
- Opens/closes instantly without appropriate animation.
- Uses a chat toggle inside the workspace navbar.
- Introduced navbar background and border that the user never requested.

All these problems must be addressed.

## 4. Restore workspace header

The workspace must have transparent or floating header controls over the canvas.

Remove the unnecessary full-width solid background and bottom divider introduced by the previous implementation.

Preserve:

- Project navigation/menu.
- Project title.
- Export.
- User profile.
- Other legitimate existing controls.

Do not move the chat toggle into the navbar.

Visual target:

```
+---------------------------------------------------------+
| [Menu] Project title                      [Export] [User]|
|                                                         |
|     Dotted canvas continues behind header               |
|                                                         |
|  [Floating chat panel]      [Frame] [Frame] [Frame]      |
|                                                         |
+---------------------------------------------------------+
```

Header controls can have their own appropriate backgrounds and borders. The entire header should not become a large opaque bar.

## 5. Floating chat panel

Create a panel positioned over the canvas, with visible margins at the top, left, and bottom.

The panel must not resemble a traditional sidebar attached to the application shell.

Suggested layout:

```
+--------------------------------------------------------------+
| [Menu] Jelajahin — Domestic Travel Booking App       [Export]|
|                                                              |
|  +-----------------------+                                   |
|  | Agent icon     [><]   |       [Frame 1]    [Frame 2]      |
|  |                       |                                   |
|  |       [User message]  |                                   |
|  |                       |       [Frame 3]    [Frame 4]      |
|  | Assistant response    |                                   |
|  | formatted in Markdown |                                   |
|  |                       |                                   |
|  | [4 pages created]     |                                   |
|  |                       |                                   |
|  | [Action cards >>>]    |                                   |
|  | [Composer          ↑] |                                   |
|  +-----------------------+                                   |
+--------------------------------------------------------------+
```

Use the current dark EvVibe visual identity.

A subtle translucent surface/backdrop blur may be used when appropriate, but avoid excessive transparency that makes text unreadable over bright frames.

Do not reproduce the Google Stitch logo or proprietary assets.

## 6. Open and close interaction

When collapsed:

```
[Menu] Jelajahin — Travel Booking App

[ Floating agent icon ]

                         [Canvas frames]
```

The reopen control should float near the upper-left canvas area, below the project menu.

When expanded:

- The floating panel appears smoothly.
- Internal collapse control is placed in the panel's upper-right area.
- Use a compact icon representing collapse/minimize.
- No permanently visible "DESIGN AGENT" heading is necessary.

Use short, controlled opacity/transform transitions.

Preserve:

- Conversation history.
- Composer draft.
- Selected frame and element attachments.
- Expanded user messages.
- Appropriate scroll position.
- In-flight jobs.
- Canvas pan and zoom.

Do not trigger frame regeneration or remount the entire workspace when toggling the panel.

Respect reduced-motion preferences.

On narrow screens, adapt the floating panel into an accessible drawer or appropriate overlay without making the canvas unusable.

## 7. User message design

Render user messages as right-aligned bubbles.

```
                    +----------------------+
                    | Buat aplikasi travel|
                    | untuk liburan...   v |
                    +----------------------+
```

Requirements:

- Right-aligned.
- Distinguishable from assistant messages.
- Comfortable padding and line height.
- Reasonable maximum width.
- Preserve the complete original prompt in storage.
- Collapse long messages by default.
- Show an expansion chevron only when content exceeds the threshold.
- Clicking the expansion control reveals the full original prompt.
- User can collapse it again.
- Short messages do not need an expansion control.

Do not truncate the actual stored content.

Do not replace the original prompt with an AI-generated summary and discard the original.

Preserve intentional paragraphs, lists, and attachments when the message is expanded.

## 8. Assistant message design

Render assistant responses on the left, with clean typography and genuine Markdown support.

Support:

- Paragraphs.
- Bold emphasis.
- Bullet lists.
- Numbered lists.
- Section headings when useful.
- Inline code where relevant.
- Safe links.
- Existing structured result components.

Do not place a large background bubble behind every assistant statement.

Remove visual label repetition:

- "Anda — Diterima"
- "Design agent — Selesai"
- "DESIGN AGENT"

Accessibility semantics may still identify message authors without repeating these labels visually.

Use a mature Markdown rendering solution such as the project's existing renderer or `react-markdown` if compatible.

Do not render unsanitized model-generated HTML.

## 9. Genuine AI conversation content

The assistant must not merely transform job progress into text such as:

```
Rencana layar: Jelajah, Detail Paket, Pemesanan, Tiket Saya.
4 halaman selesai diproses.
```

That is a job summary, not an adequate design-agent conversation.

The assistant should understand and respond to the user's actual request.

For initial generation:

1. Explain the actual intended design direction and relevant user journey when planning becomes available.
2. Start generation without waiting for a separate decorative response call.
3. Update frame availability truthfully.
4. Provide a useful result explanation when appropriate.
5. Offer contextual next actions through the mechanism implemented in P5.

For follow-up generation:

- Explain what the requested additional screen contributes.
- Describe its relationship to existing screens.
- Report what genuinely changed.

For revision:

- Explain the requested changes and completed outcome.
- Do not claim unrelated features have been created.

## 10. Example of desired response quality

For a completed travel project:

"Saya telah merancang aplikasi Jelajahin dengan fokus pada kemudahan menemukan paket wisata, membandingkan harga, dan menyelesaikan pemesanan.

**Alur utama desain**

- **Jelajah:** pencarian destinasi, pemilihan tanggal, dan rekomendasi perjalanan.
- **Detail Paket:** informasi itinerary, fasilitas, ketersediaan, serta rincian biaya.
- **Pemesanan:** pengisian informasi peserta dan simulasi pembayaran.
- **Tiket Saya:** akses tiket, jadwal keberangkatan, dan informasi perjalanan.

Navigasi utama ditempatkan pada halaman tingkat atas, sementara halaman detail menggunakan navigasi kontekstual agar pengguna dapat kembali ke alur sebelumnya."

Then show an actual result component:

```
[ 4 halaman dibuat                 Lihat v ]
```

The response must be based on actual generated content.

For a complex publisher payout brief, the response may contain more detailed subsections:

- Design approach.
- Main operational flows.
- Status-based navigation.
- Required validation states.
- Constraints requested by the user.
- Relevant next improvements.

Adapt length to the complexity of the user's request.

Never falsely claim:

- A design was published when it was only generated.
- A real bank transaction was executed.
- Production backend integration exists.
- Industry research was performed when it was not.
- All screens succeeded when some failed.

Do not invent references to Stripe, Wise, Zoho, or other products just to make the answer sound impressive.

## 11. Separate conversation content from system metadata

Do not display these raw data structures inside the message timeline:

- Planning JSON.
- Internal validation payloads.
- Worker diagnostics.
- Raw DB errors.
- Provider errors.
- Raw queue status objects.
- Unrequested technical brief repetition.

A long initial user brief should remain accessible through the expandable user message.

A genuine user-facing failure should be displayed only in the relevant recovery context, not as an unexplained chat paragraph.

Keep the internal job statuses and diagnostics intact.

## 12. Avoid performance regressions

Where possible, produce design explanation content alongside the existing planning response.

Use actual frame results to produce truthful completion summaries.

Do not add a second multi-thousand-token LLM request merely to generate conversational copy.

Do not block frame generation until an unnecessary narrative finishes streaming.

User experience and generation latency must both remain priorities.
