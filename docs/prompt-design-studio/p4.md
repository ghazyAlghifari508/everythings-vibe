## 2. STAGE-AWARE SKILL CONTEXT

Current implementation sudah memiliki stage-aware context selection. Jangan menghapus sistem tersebut dan membangun ulang tanpa alasan.

Evaluasi apakah konteks yang dipilih masih berlebihan atau kurang relevan.

Target:

```
ORIGINAL UPSTREAM SKILL
         |
         v
VERIFIED SECTION REGISTRY
         |
         v
RELEVANCE SELECTOR
         |
    +----+----+----+
    |         |    |
    v         v    v
PLANNING   FRAME  REVISION/CORRECTION
    |         |    |
    v         v    v
ONLY RELEVANT VERIFIED GUIDANCE
```

Contoh:

- Planning: brand, typography direction, visual identity.
- Frame: platform-specific composition, UI hierarchy, component rules.
- Revision: requested changes, design preservation, relevant improvement rules.
- Correction: precise defect, minimal guidance required to fix it.

Jangan memasukkan 25 section hanya karena masih muat dalam character budget.

Jangan menghapus section penting hanya karena ingin menekan token.

Pertahankan provenance per section.

## 4. OPTIMIZE DUPLICATED CONTEXT

Audit apakah:

- Shared blueprint dikirim berulang tanpa kebutuhan.
- Canonical shell yang seharusnya deterministik masih diminta AI berkali-kali.
- CSS rules yang sama dikirim di system dan user prompts.
- Skill guidance panjang dikirim lagi saat koreksi kecil.
- Dataset besar disalin ke prompt padahal hanya beberapa rekomendasi yang diperlukan.
- Previous generated HTML menyebabkan prompt correction sangat besar.

Terapkan perubahan terukur dan kompatibel.

Jangan menghapus requirement pengguna, [DESIGN.md](http://DESIGN.md), atau shared blueprint demi mengecilkan prompt.

## 5. PROMPT CACHING

Periksa gateway/model provider yang digunakan.

Jika mendukung prompt prefix caching, evaluasi kemungkinan:

- Stable system prompt prefix.
- Reused verified skill sections.
- Shared blueprint fragments.
- Provider-supported caching hints.

Jangan menambahkan fake cache marker atau mengklaim cache hit tanpa data.

Jangan membuat cache lintas proyek yang membocorkan informasi user.

## 6. CORRECTION COST

Masalah sebelumnya:

```
Full HTML generated
      |
      v
Minor validation issue
      |
      v
Full AI regeneration
      |
      v
Several additional minutes
```

Target:

```
Full HTML
   |
   v
Validation
   |
   +--> deterministic safe repair
   |
   +--> focused AI correction
   |
   +--> bounded full correction only if necessary
```

Pertahankan validation dan safety checks.

Jangan memperbaiki masalah unsafe JavaScript dengan menghilangkan security validation.

Jangan membuat infinite retry.

## 7. PARALLEL GENERATION

Studio sebelumnya menggunakan concurrency tiga frame.

Verifikasi lagi kondisi terbaru.

Jangan meningkatkan concurrency secara membabi buta.

Ukur provider throughput, rate limits, queueing, memory, dan biaya koreksi.

Pastikan frame yang selesai lebih dahulu bisa persisted independently.

Tetapi jangan mencampurkan task ini dengan redesign polling/shimmer frontend kecuali ada dependency nyata yang menghambat.

## 8. PERFORMANCE GOALS

Kecepatan lebih baik tanpa menurunkan kualitas.

Gunakan target:

- Lower time to first frame.
- Lower average token cost.
- Fewer unnecessary correction calls.
- Faster single-frame additions.
- Stable concurrent generation.
- Similar or improved output completeness.

Target satu menit boleh menjadi performance aspiration, tetapi jangan mengklaim semua proyek lima frame bisa selesai dalam satu menit tanpa bukti.
