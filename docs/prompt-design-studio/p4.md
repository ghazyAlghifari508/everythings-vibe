# 4. Eliminate Technical Text Leakage Into Rendered UI

## User-observed problem

A generated financial-report screen visibly contains unexpected technical text resembling:

- `[code]`
- `skipped`
- implementation notes;
- references to charting libraries;
- irrelevant technical explanations.

This text does not belong in the final application interface.

### Correct output

The AI must produce a valid, self-contained HTML design, without exposing its generation commentary.

Target:

```
WRONG FRAME
┌───────────────────────────────┐
│ Laporan                       │
│ [code] skipped client side... │
│ charting library...           │
│ implementation notes...       │
│                               │
│    dashboard content          │
└───────────────────────────────┘

CORRECT FRAME
┌───────────────────────────────┐
│ Laporan Analitik              │
│                               │
│ [Metrics] [Charts]            │
│                               │
│ [Transactions / Reports]      │
│                               │
└───────────────────────────────┘
```

The exact technical leakage shown in screenshots is evidence of the symptom, not necessarily the complete root cause.

## Required investigation

Inspect:

1. Raw streamed model response.
2. HTML extraction.
3. Sanitized/enforced HTML.
4. Persisted `htmlCode`.
5. Actual DOM used for visual capture.
6. Visual preview returned to the client.

Determine exactly where technical prose enters the final rendered content.

### Strengthen the output contract

The existing system prompt already requests a complete standalone HTML document without commentary.

A prompt instruction alone is not enough.

Implement stronger validation where appropriate:

- Require a complete, parseable HTML document.
- Detect stray model notes outside the document.
- Detect recognizable accidental commentary within generated output when confidently distinguishable from legitimate UI text.
- Verify body structure and expected renderable content.
- Detect incomplete or obviously malformed code fences.
- Handle truncation explicitly.
- Reject output that violates the response contract.

Do not rely only on naive regex replacement.

Do not remove legitimate code blocks from user-requested developer tools, code editors, documentation screens, or programming products.

A visible code block may be a valid part of the user's intended application.

Validation must distinguish accidental generation commentary from actual product content.

### Recovery

When an output violation is detected:

- Do not persist it as a successful ready frame.
- Apply a targeted bounded corrective generation/retry.
- Include precise validation feedback.
- Preserve successful other frames.
- Mark persistent failures accurately.
- Avoid infinite retries.

If output is invalid, a clean failed/retry state is preferable to presenting obviously broken HTML as a successful design.

# 5. Fix Unexpected Blank Gutters and Cropped Frame Content

## Symptoms

In the screenshots:

- Certain frames have large unexplained empty regions.
- Some content appears compressed into only part of the artboard.
- Some frame regions extend below/behind navigation or other UI.
- The image area and intended app layout do not align.

Do not assume a single CSS property causes everything.

### Required investigation

Inspect the captured dimensions and the generated HTML geometry.

Specifically evaluate:

- Root/body/document widths.
- Viewport meta.
- `box-sizing`.
- Width/min-width/max-width.
- Flex and grid overflow.
- `overflow-x`, `overflow-y`, and clipping.
- Nested scroll containers.
- Absolute and sticky positioning.
- Fixed-height sections.
- Large minimum heights.
- CSS transforms.
- Margins extending beyond the document bounds.
- Image intrinsic dimensions.
- Long page content and screenshot height.
- Missing fonts/assets.
- Canvas artboard sizing and image display.

Do not alter the preview to stretch incorrectly just to fill empty space.

### Desired geometry

```
Correct mobile frame:

       390 CSS px (or canonical mobile width)
    ┌─────────────────────────────┐
    │ App Header                  │
    ├─────────────────────────────┤
    │                             │
    │ Content fills intended area │
    │                             │
    │ Cards align correctly       │
    │                             │
    │ Scrollable page content     │
    │                             │
    ├─────────────────────────────┤
    │ Consistent bottom nav       │
    └─────────────────────────────┘

Incorrect:

    ┌─────────────────────────────┐
    │ Content compressed │ empty  │
    │                    │ gutter │
    │ overlapping block  │        │
    └─────────────────────────────┘
```

### Rendering requirements

- Preserve the actual generated HTML proportions.
- Preserve real document height.
- Keep screenshot pixel dimensions consistent with metadata.
- Avoid accidental non-uniform image scaling.
- Avoid inappropriate `object-fit: cover`.
- Avoid incorrectly clipping long mobile pages to a single viewport.
- Use the same canonical width configuration throughout generation and capture.
- Respect existing maximum capture dimensions.

A legitimate full-page screenshot may be much taller than a phone viewport.

Do not squeeze content into a fixed-height phone mockup.

### Diagnose from persisted evidence

If the local database/project fixtures are available, inspect the actual affected frame's HTML, output metadata, and visual asset safely.

If not, create deterministic regression fixtures that reproduce the relevant structural failure patterns.

Do not fabricate a root-cause explanation solely from screenshots.

# 6. Enforce One Shared Design System Across All Frames

## Current issue

The project already has a Shared Design Blueprint, but frame designs still diverge.

Examples:

- Different navbar positioning.
- Different icon sets.
- Different header treatments.
- Different button/card geometry.
- Different visual density.
- Different bottom-navigation structure.

The blueprint must be a stronger source of truth.

### Target

```
ONE PROJECT BLUEPRINT
│
├── Colors
├── Typography
├── Spacing
├── Radius
├── Icon System
├── Navigation Contract
├── Shared Components
│
├── Frame 1: Ringkasan
├── Frame 2: Anggaran
├── Frame 3: Tambah Transaksi
└── Frame 4: Laporan

All frames follow the same shared shell.
Only screen-specific content and active nav state differ.
```

## Required changes

Inspect `studio-design-blueprint.ts`.

Evaluate whether the current schema provides sufficiently enforceable definitions for:

- Navigation structure.
- Navigation labels.
- Navigation ordering.
- Icon mapping.
- Bottom-bar geometry.
- Header geometry.
- Shared components.
- Font and typography scales.
- Surface colors.
- Borders and radii.
- Spacing.

The current validation of shared navigation labels is not sufficient.

A frame can include every required label while still rendering the navbar incorrectly.

### Improve design contract enforcement

Choose a maintainable approach based on the current architecture.

Possible approaches include:

- Stronger structured component contracts.
- Shared CSS token definitions.
- Validated component/layout metadata.
- A canonical navigation markup specification.
- Shared shell generation reused across screens.
- Structural postgeneration validation.

Do not blindly create a hardcoded React navbar inside screenshots if the output architecture is standalone HTML.

Avoid fragile string replacements that accidentally rewrite user content.

The chosen strategy must support different app domains and platforms.

### Mobile navigation requirements

For screens belonging to the same project:

- Identical navigation items and order.
- Identical icon style.
- Consistent labels and sizing.
- Consistent bottom spacing.
- Consistent positioning strategy.
- Consistent selected-state treatment.
- Only the active destination changes.

The project's shared design reference must remain authoritative.

### Distinguish real variation from drift

Not every frame should look identical.

A payment form, dashboard, and report naturally have different content.

What must remain consistent is the product's visual system, reusable controls, navigation, and interaction conventions.

Do not enforce identical card layouts across unrelated screen roles.
