## Mission

Improve VibeDesign Studio's actual AI-generated UI quality.

Recent generated Metriq SaaS screens show several problems:

- Transaction table is clipped on the right.
- Some content has insufficient space or poor sizing.
- UI occasionally looks like a generic dashboard template.
- Typography is too small or poorly prioritized.
- Forms and data tables feel crowded.
- Added screens sometimes use less refined layouts than the initial screens.
- Generated designs can be technically valid but visually weak.
- The user can generate visually repetitive or underdeveloped interfaces, especially without a [DESIGN.md](http://DESIGN.md) reference.

The goal is professional, domain-appropriate, polished, reliable HTML prototypes.

Do not solve this by hardcoding one impressive dashboard for every project.

## 1. Diagnose CSS and Content Clipping

Observed example:

```
TRANSACTION FRAME

┌────────────────────────────────────────────┐
│ Sidebar │ Form │ Transaction Table          │
│         │      │                            │
│         │      │ Date | Customer | Amount | │
│         │      │ Status | More Columns... ->│
└────────────────────────────────────────────┘
                                          X
                                  Content clipped
```

Required behavior:

```
DESKTOP FRAME

┌────────────────────────────────────────────┐
│ Sidebar │ Main Content                     │
│         │                                  │
│         │ [Summary Metrics]                │
│         │                                  │
│         │ [Transaction Form] [Table Area]   │
│         │                    [scrollable]   │
│         │                                  │
└────────────────────────────────────────────┘
```

For narrower layouts:

```
┌─────────────────────────┐
│ Header                  │
├─────────────────────────┤
│ Summary Metrics         │
├─────────────────────────┤
│ Transaction Form        │
├─────────────────────────┤
│ Transaction Table       │
│ Horizontal table scroll │
└─────────────────────────┘
```

Audit:

- `min-width` defaults on flex/grid children.
- Fixed pixel widths.
- Wide tables without contained horizontal scrolling.
- Invalid responsive breakpoints.
- Grid columns that exceed parent width.
- Uncontrolled SVG/image width.
- Form controls extending beyond card boundaries.
- Missing `minmax(0, 1fr)` / `min-width: 0` where appropriate.
- Canonical-shell CSS overrides.
- CSS selectors that collide with generated content.
- Incorrect sizing assumptions at Studio's capture viewport.

Do not hide overflow globally and call the issue fixed.

Where a wide data table genuinely needs more width, put horizontal scrolling inside a properly bounded table container.

## 2. Build a Domain-Aware Quality Contract

A finance SaaS dashboard, creative portfolio, travel application, and e-commerce product should NOT all have the same layout.

Create a practical quality contract for generation:

### Visual hierarchy

- Clear primary focal point.
- Meaningful title hierarchy.
- Action priority.
- Readable supporting information.
- Consistent spacing.
- Balanced density.

### Product-specific UX

- Components match the actual user journey.
- Relevant content is complete.
- Forms show appropriate field groups.
- Tables have meaningful columns.
- Dashboard metrics provide context.
- Charts have clear labels and legends.
- Empty, error, and loading states are appropriate to the feature.

### Visual composition

- Appropriate whitespace.
- Intentional typography.
- Balanced card sizes.
- No gratuitous large shadows.
- No random floating elements.
- No disconnected icons.
- No generic purple-gradient SaaS layout repeated across products.
- No decorative filler replacing useful content.

### Technical quality

- Safe HTML.
- Responsive CSS.
- Accessible labels.
- No unnecessary scripts.
- No accidental clipping.
- Shared shell respected.
- No overlapping content.
- No uncontrolled fixed/sticky elements.
- Content remains readable at the intended viewport.

Make requirements concrete and testable where possible.

Do not add pages of vague instructions that merely increase token cost.

## 3. Component-First Design Strategy

The user explicitly requires professional prebuilt UI/component exploration.

Before changing the generation architecture, investigate reusable components and patterns from:

- [https://ui.shadcn.com/](https://ui.shadcn.com/)
- [https://www.heroui.com/](https://www.heroui.com/)
- [https://magicui.design/](https://magicui.design/)
- [https://reactbits.dev/](https://reactbits.dev/)
- [https://www.thinkingorbs.com/#orbs](https://www.thinkingorbs.com/#orbs)
- [https://www.affectui.com/components](https://www.affectui.com/components)

Document which component systems or patterns are applicable.

**Important technical constraint:**

Generated Studio frames currently use standalone HTML/CSS.

A React component from shadcn/ui or HeroUI cannot be pasted into static HTML and expected to execute.

Implement an architecture-appropriate solution:

- Reuse ready-made React components in the Studio application UI when needed.
- For generated static prototypes, establish tested, reusable HTML/CSS component patterns with inspiration or adapted implementations from compatible sources, respecting their licenses.
- If component-library usage requires a build/runtime change, evaluate and document the trade-off before implementing it.
- Do not introduce runtime dependencies that silently fail in the static preview renderer.

Avoid creating each button, card, table, tab, and input entirely from scratch inside every AI response.

However, do not force irrelevant visual effects or components merely to satisfy a library checklist.

The component system must improve actual output quality.

## 4. Shared Shell and Layout Boundaries

Studio already includes a canonical shell with:

- Header.
- Navigation.
- Shared design tokens.
- Icon mapping.
- Density settings.
- Active destination behavior.

Preserve this architecture.

The generated screen body must integrate with the shell instead of redefining it.

Define clear boundaries:

```
SHARED SHELL (STUDIO CONTROLLED)
├── Global app header
├── Global navigation
├── Theme tokens
├── Typography baseline
└── Global layout rules

SCREEN BODY (AI GENERATED)
├── Screen-specific title/actions
├── Feature content
├── Forms/tables/charts
├── Contextual tabs
└── Screen-specific states
```

Do not allow generated content to create duplicate sidebars or conflicting global navigation.

Do not impose shell CSS that destroys legitimate nested components.

## 5. Improve Content Density

Metriq illustrates two extremes that should be avoided:

### Too sparse

```
[Heading]
[Large empty space]
[Three generic cards]
```

### Too dense

```
[Many tiny metrics][Tiny labels]
[Large form full of cramped fields]
[Wide table with unreadable columns]
```

### Better

```
┌───────────────────────────────────────────┐
│ Catat Transaksi              [Export]     │
│ Kelola pemasukan dan pengeluaran bisnis.  │
├─────────────┬─────────────┬───────────────┤
│ Inflow      │ Outflow     │ Net Cash Flow │
├─────────────────┬─────────────────────────┤
│ Form Transaksi  │ Transaksi Terbaru       │
│                 │                         │
│ Grouped fields  │ Filter / Search         │
│ Primary action  │ Structured table        │
└─────────────────┴─────────────────────────┘
```

This is a structural example, NOT a mandatory hardcoded design.

Adapt layout to the product and available space.

## 6. Quality Validation

Current HTML validation can accept content that is structurally valid but visually poor.

Improve automated validation where feasible:

- Unsafe overflow-prone CSS patterns.
- Unbounded fixed-width elements.
- Invalid nesting.
- Missing accessible names.
- Generated duplicate global shell.
- CSS collisions with canonical shell.
- Empty content sections.
- Missing required content.
- Improper content containers.
- Incorrect use of platform viewport.
- Suspiciously empty or tiny screen bodies.

Separate:

**Hard failures:** unsafe or invalid output.

**Quality warnings:** potentially weak composition that cannot be judged reliably from static code alone.

Do not reject excellent designs based on brittle heuristics.

Do not claim automated DOM/CSS inspection can perfectly evaluate visual aesthetics.

Use bounded model correction only for issues that genuinely need semantic redesign.
