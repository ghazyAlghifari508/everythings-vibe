# PROMPT 04 — Optimize Time to First Usable Studio Frame Without Sacrificing Quality

**Complexity: VERY COMPLEX**  
**Execution order: 04 of 13**

## Goal

The product target is:

**The first complete, valid, visually usable frame should become visible on the canvas within 60 seconds after the user submits the initial prompt.**

This does not mean all 3–4 frames must finish within 60 seconds.

The metric must include the time until the user actually receives the first usable visual result, not merely the time until a database row becomes ready.

This is an optimization target that must be measured honestly, not an unconditional guarantee.

## 1. Review existing optimizations FIRST

Read all of `docs/[studio-generation-latency.md](http://studio-generation-latency.md)` and the related tests.

Previously implemented:

- Initial frame concurrency is already 3.
- Frame ready results are persisted independently.
- A configured 2-second inter-batch worker delay was already removed.
- Shared planning is persisted and reusable on recovery.
- Correction prompts no longer blindly repeat the full original prompt.
- Studio has bounded retry/correction.
- Status polling is approximately 1,500 ms.
- Preview capture is lazy and separate from HTML generation.
- Timing events include planning, first token, output, frame-ready, and `frame-visible`.

DO NOT propose these as new improvements unless source inspection proves they regressed.

## 2. Establish baseline instrumentation

Inspect actual timing events, model adapter, and Studio worker execution.

Measure:

- Initial API request time.
- Queue wait.
- Worker startup.
- Planning TTFT and full planning duration.
- Input size/tokens.
- Frame-generation TTFT.
- Frame-generation total output time.
- Output tokens and token throughput.
- Correction frequency and duration.
- Validation and persistence time.
- Preview capture delay.
- Preview asset response latency.
- Client image-load/visibility signal.
- Time to first usable frame.
- Time to all frames completed.
- Failure rates and quality regressions.

Do not confuse client `img.onload` with verified compositor paint or viewport intersection. If introducing better client-visible measurement, keep clock skew and telemetry limitations explicit.

Distinguish mock measurements from live-provider results.

Do not infer average latency from one long log.

## 3. Study comparable implementations

Use Prompt 01's findings about OpenDesign, Doop, OpenUI, and Stitch.

Inspect whether there is real evidence for:

- Incremental HTML delivery.
- Progressive preview.
- Early generation of a useful first screen.
- Reuse of design tokens instead of duplicating large context.
- Independent frame readiness.
- Bounded correction.
- Worker capacity or per-project dependency management.

Do not claim a reference product is faster without comparable measured scenarios.

## 4. Evaluate performance options

Evaluate each option against speed, quality, complexity, provider compatibility, and recovery behavior:

A. Reuse existing shared blueprint efficiently.

B. Reduce redundant prompt context while preserving design requirements.

C. Use a bounded and validated provider/model configuration that can produce complete HTML at adequate quality.

D. Ensure frame 1 can become ready independently of slower siblings.

E. Improve scheduling of the first frame within the existing aggregate model-concurrency limit.

F. Reduce deterministic validation/correction overhead where safe.

G. Avoid recapturing identical HTML previews.

H. Evaluate progressive preview only if a safe draft/final distinction can be maintained.

I. Reduce avoidable asset/font waits without showing incomplete assets as completed results.

J. Consider preparing a first screen while other screen-specific work is queued, but only after confirming shared design-system consistency and project semantics.

Do not simply raise concurrency above 3 or remove worker locks without real throughput evidence and an alternate aggregate-cap policy.

Do not shorten content until the generated UI becomes shallow, generic, or malformed.

## 5. Progressive rendering decision

If research supports incremental preview, design it with a strict separation:

```
Model stream
      |
      +---- Draft HTML preview (optional)
      |        |
      |        +---- Explicitly unfinished
      |        +---- Never counted as usable frame
      |
      v
Validated final HTML
      |
      v
Persisted result
      |
      v
Preview ready + displayed
      |
      v
TTFUF measurement stops
```

Temporary draft previews must not be saved as final revisions.

They must not execute untrusted generated scripts or cause invalid UI to be counted as success.

If the approach increases complexity without meaningful measured speed improvement, reject it.

```
t = 00s   User submits initial prompt
t = 04s   Job acquired (example only)
t = 13s   Shared planning available
t = 18s   First-frame generation starts
t = 49s   HTML validated and persisted
t = 54s   Preview available and visible

```

These numbers are hypothetical target illustrations, NOT observed benchmarks.

## 7. Benchmark procedure

Use controlled representative fixtures:

- Web portfolio.
- Web dashboard.
- Mobile commerce app.
- Mobile travel app.
- With and without a selected theme.
- With and without custom [`DESIGN.md`](http://DESIGN.md).

When actual provider calls are permitted, record model configuration, requested token budget, output usage, correction attempts, latency, and credits/cost per attempt.

Compare equivalent scenarios before and after the change.

Do not silently spend production credits or create large numbers of live jobs. If credentials or permitted test budget are missing, complete mock-based checks and mark live measurements as pending.

Ensure p50/p95 are used only with meaningful sample counts. Do not turn a small cohort into a reliable SLA.

## 8. Testing

Use targeted unit/integration and timing-report tests.

Existing examples include:

- `studio-latency.test.ts`
- `studio-timing-report.test.ts`
- `studio-worker-loop.test.ts`
- Relevant worker/persistence tests.

Do not execute Chromium-based Studio visual tests during this phase.

Verify:

- First frame does not wait for all siblings.
- Ready frames persist while others are running.
- Cache reuse does not return stale HTML.
- Prompt optimization preserves [DESIGN.md](http://DESIGN.md) and core quality contract.
- No extra generation due to harmless advisory warnings.
- Retries remain bounded.
- Scheduling does not violate aggregate concurrency.
- Output safety and quality checks remain enabled.
