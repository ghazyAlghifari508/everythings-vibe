# P2 — Remove Overly Rigid Visual Composition and Implement Real Image Assets

**Complexity: VERY COMPLEX**  
**Execution order: After P1.1, before P3**  
**Replaces the previous P2**

## 1. Objective

Improve VibeDesign's actual generated web and mobile designs by removing overly restrictive visual composition mechanisms.

The AI must be capable of independently designing a website or mobile application based on its domain, purpose, user journey, theme, and design requirements.

The engine should enforce quality and security without imposing the same visual template across unrelated projects.

Additionally, implement a legitimate real-image pipeline so photography-based designs do not rely on fabricated SVG landscapes, CSS artwork, or invented image URLs.

## 2. Reported problems

Current output repeatedly exhibits:

- Mobile app bars containing only a title.
- Generic back arrows and text-only headers.
- Website navbars with three links and an arbitrary filled CTA.
- The last navigation link styled as though it were a login button.
- Portfolio websites filled with generic text cards.
- Weak differences between website and mobile composition.
- Travel and product imagery represented by simplistic code-generated drawings.
- Inconsistent media geometry.
- Text clipping, awkward wrapping, and overlapping components.
- Weak understanding of why particular UI components belong in a screen.

Do not apply superficial CSS patches only to the reported sample projects.

Repair the generic generation architecture.

## 4. Change the canonical renderer's responsibility

The canonical renderer should coordinate shared project identity and essential semantic relationships.

It should not dictate the precise appearance of all generated headers and navigation layouts.

### Current restrictive approach

```
AI generates main content only
           |
           v
Engine inserts predetermined header
           |
           v
Engine inserts predetermined navigation
           |
           v
Different products inherit similar anatomy
```

### Desired approach

```
AI understands product and user journey
           |
           v
Shared navigation intent + design identity
           |
           v
AI designs appropriate visual composition
           |
           v
Engine verifies semantic relationships,
consistency, safety, and essential quality
```

Preserve appropriate deterministic contracts for:

- Stable screen and destination identifiers.
- Product identity.
- Theme/design tokens.
- Valid navigation targets.
- Shared project relationships.
- Accessibility constraints.
- Security.
- Duplicate shell detection.
- Export and revision integrity.

Do not require exact header markup or one predefined navigation structure when equally valid alternatives exist.

Evaluate whether the existing canonical system should become a semantic contract with flexible visual assembly rather than a fixed header generator.

Preserve legacy project compatibility.

Do not rewrite historical HTML merely because the new renderer supports more flexibility.

## 5. Website navigation

The AI must independently determine the appropriate navigation based on the actual information architecture.

A public portfolio, restaurant, marketplace, travel website, and authenticated SaaS workspace should not all inherit the same header arrangement.

Examples:

```
Portfolio:
[Brand]     Work    About    Contact
```

```
Restaurant:
[Brand]     Menu    Our Story    Location    [Reserve]
```

```
Storefront:
[Brand]     Categories     Search     Account     Cart
```

These are examples, NOT predefined templates.

Do not:

- Force exactly three navlinks.
- Automatically promote the last link into a CTA.
- Turn an ordinary link into a login-style button.
- Force an avatar/account control onto every public website.
- Force a sidebar onto every web project.
- Insert a generic page-title header above every public hero.

Separate normal navigation destinations from primary actions.

A CTA can be appropriate if it represents a genuine product goal.

For example, "Reserve a Table" may be appropriate for a restaurant, but a generic "About & Contact" link should not be promoted solely because it is the last navigation item.

Allow the AI to decide the appropriate visual form.

## 6. Mobile navigation and app bars

The AI should understand navigation depth and screen purpose.

Top-level destinations do not inherently need a back arrow.

Nested screens may require back navigation.

The app bar can contain different elements depending on context:

- Product brand.
- Current location.
- Search.
- Notification.
- Profile/account access.
- Contextual title.
- Back.
- Save/share.
- Relevant contextual actions.

Do not mandate a fixed subset.

Visual illustrations:

```
Discovery:
+---------------------------+
| Brand       Search   User |
|                           |
| Discovery content         |
+---------------------------+
```

```
Detail:
+---------------------------+
| <   Detail Package   Save |
|                           |
| Actual destination photo  |
| Relevant package details  |
+---------------------------+
```

```
Profile:
+---------------------------+
| Account          Settings |
|                           |
| Profile and account tasks |
+---------------------------+
```

These layouts should communicate relevant design reasoning, not be copied literally into every generated project.

Allow appropriate alternative headers or no separate header where the design genuinely warrants it.

Bottom navigation should represent actual primary destinations, not every generated screen.

Do not force detail, checkout, confirmation, and other nested screens into one universal top-level tab bar.

Keep navigation semantics coherent across the project.

## 7. Remove generic card-wall composition

Use the revised `evvibe-design` skill to guide visual reasoning.

The engine must not force a particular arrangement of hero, card grids, metrics, testimonials, or content sections.

For a portfolio website, the actual work should influence composition.

For a restaurant website, food, atmosphere, menu, and reservation journey may influence composition.

For an editorial website, reading experience may dominate.

For a dashboard, efficient information access may dominate.

Let the product determine the design.

Prevent meaningless decoration, fabricated metrics, fake testimonials, and arbitrary status indicators.

Retain functional badges and genuine status indicators where appropriate.

Do not turn anti-slop into a universal monochrome or minimalist style.

Theme and [DESIGN.md](http://DESIGN.md) remain meaningful visual inputs.

## 8. Real image pipeline

When a design requires photography, obtain legitimate real image assets through supported sources.

Do not ask the model to invent URLs.

Do not use SVG landscapes or CSS shapes to impersonate destination photographs.

The image pipeline is a media capability of VibeDesign, NOT a component browsing system.

Target:

```
AI planning identifies image requirements
                     |
                     v
Approved image provider resolves assets
                     |
                     v
Validate relevance, source, format, and usage rights
                     |
                     v
Provide approved asset references to the generator
                     |
                     v
AI places actual images within its design
```

Reuse existing asset infrastructure where practical.

Each image requirement may contain:

- Subject.
- Purpose.
- Relevant search query.
- Preferred aspect ratio.
- Applicable screen or content association.
- Alt-text intent.

Do not require a separate model call for each asset.

Use the existing planning stage to identify relevant media needs where possible.

## 9. Provider implementation

Evaluate a legitimate image provider, such as Unsplash, Pexels, or another appropriately licensed source compatible with the product.

Verify actual provider terms and technical constraints before implementing.

Do not assume all providers permit identical downloading, hotlinking, caching, or redistribution.

Requirements:

- Supported API or authorized retrieval mechanism.
- Configurable credentials.
- Relevant search results.
- Valid image URLs.
- Allowed content types.
- Bounded asset size.
- Appropriate dimensions.
- Attribution/source metadata where required.
- License-compatible caching.
- Deduplication.
- Timeouts.
- Bounded retries.

Use safe server-side fetching.

Protect against private-network URL access, unsafe redirects, inappropriate protocols, oversized responses, and unsupported image types.

Do not expose credentials in generated HTML or client responses.

User-provided assets should retain appropriate precedence.

Do not blindly copy copyrighted brand imagery or book covers without appropriate usage rights.

## 10. Image validation and fallback

Do not equate the existence of an HTTPS URL with a verified available photograph.

Maintain a validated asset contract compatible with existing preview/export services.

For new provider-backed assets, ensure the generator uses actual resolved asset references.

An unresolved image must not silently become a fabricated landscape.

If no suitable asset is available:

- Preserve intended layout geometry.
- Use an honest neutral fallback where appropriate.
- Record the actual asset failure.
- Avoid unnecessary complete-frame regeneration.
- Maintain meaningful adjacent content.

Do not remove essential images from an image-led design merely to avoid implementing retrieval.

SVG remains acceptable for icons, genuine vector logos, charts, diagrams, and explicitly requested illustrations.

## 11. Responsive layout and CSS ownership

The same generated HTML should support meaningful responsive presentation later through P6 and P9.

Preserve and strengthen:

- Fluid layouts.
- Readable mobile controls.
- Intrinsic sizing.
- Appropriate wrapping.
- Media aspect ratios.
- Scrollable carousels where useful.
- Content containment.
- Shared design tokens.
- Appropriate desktop and mobile navigation behavior.

Avoid global CSS that forces the same dimensions on all cards, images, buttons, or sections.

Do not use universal overflow hiding to conceal layout defects.

A mobile frame must not be forced into a fixed small content shell forever when the user switches to a wider viewport.

However, resizing alone cannot guarantee a completely different platform-specific layout. Ensure responsive HTML is actually designed to adapt.

Do not regenerate legacy documents automatically.

## 12. Preserve future editor and prototype contracts

This phase must remain compatible with:

- P3 adaptive planning.
- P6 responsive live renderer.
- P7 element selection.
- P8 deterministic and AI editing.
- P9 device switching.
- P10 interactive prototype viewer.

Maintain meaningful semantic identifiers.

Do not make the editor depend on an exact hardcoded navbar DOM tree that every design must use.

Where navigation relationships are known, preserve them so P10 can connect safe prototype actions.

Do not implement arbitrary generated JavaScript.

P10 will own the interactive mock runtime.

## 14. Performance requirements

Preserve the first-usable-frame target of less than 60 seconds.

Do not:

- Introduce additional LLM calls simply to select UI components.
- Introduce a comprehensive design browsing loop.
- Add unbounded image searches.
- Serialize work that can safely execute concurrently.
- Increase correction attempts to disguise poor generation quality.

Reuse cached assets where permitted.

Use bounded retrieval concurrency and provider timeouts.

Maintain independent frame readiness.

Measure actual image retrieval overhead and prompt sizes.

Do not claim faster generation without evidence.
