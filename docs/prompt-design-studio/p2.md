# PHASE 2 — Fix AI Frame Validation, Contract Failures, Reliable Retry &amp; Actionable Error States

**Priority: P0 — CRITICAL**  
**Complexity: COMPLEX**  
**Branch:** `feature/vibedesign-design-studio`

## 1. Problem Statement

VibeDesign Studio currently generates frames that may be rejected by its own HTML validation contract.

Observed error example:

```
Output tidak memenuhi kontrak:
Label navigasi hilang dari navigasi:
Tentang & Kontak.

Lebar tetap melebihi viewport.
```

The resulting frame becomes failed.

When the user clicks "Coba lagi", another generic error may appear:

```
Permintaan retry gagal. Coba lagi.
```

The user needs reliable frame recovery, not repeated opaque failure messages.

**Your objective is to address actual generation contract mismatches, retry mechanics, and error propagation.**

Do not simply remove validation so invalid frames can pass.

Investigate whether planning contracts and HTML generation prompts agree on:

## 4. Navigation Contract

Current failure indicates that expected navigation labels may be missing.

For example:

```
Shared navigation:
Beranda | Proyek | Tentang & Kontak
```

Every applicable screen must preserve that navigation structure, while its active destination changes.

Implement clear shared invariants:

```
FRAME A                 FRAME B                 FRAME C
Beranda [ACTIVE]        Beranda                 Beranda
Proyek                  Proyek [ACTIVE]         Proyek
Tentang & Kontak        Tentang & Kontak        Tentang & Kontak [ACTIVE]
```

Requirements:

- Do not invent different nav structures independently for each frame.
- Do not let screen-specific prompts override the shared navigation contract accidentally.
- Handle legitimate combined labels and special characters.
- Distinguish actual navigation labels from unrelated page text.
- Prevent duplicate nav bars.
- Validate consistency without requiring impossible or ambiguous markup.
- Keep mobile and desktop contracts appropriate to their platforms.

If the extraction logic is too fragile, improve it.

Do not fix failures using arbitrary text insertion into HTML.

## 5. Viewport Overflow Validation

Audit the existing fixed-width checks.

Potential failure:

```
Viewport width: 390px
Generated content: width 1200px
Result: content exceeds viewport
```

Investigate whether overflow is caused by:

- Explicit fixed width.
- `min-width`.
- Incorrect CSS layout.
- Tables without responsive wrappers.
- Embedded image dimensions.
- Generated absolute positioning.
- CSS rules that only apply at other breakpoints.
- Validator false positives.

The solution should preserve usable layouts.

Do not globally remove overflow validation or automatically shrink entire pages with CSS transforms.

Prioritize correct responsive structures.

## 6. Corrective Generation Strategy

The current pipeline allows a bounded corrective generation attempt.

Improve this process so the model receives a precise, compact explanation of the violation.

Example internal corrective instruction:

```
Validation:
- Required navigation label "Tentang & Kontak" missing.
- Container exceeds mobile viewport width.
- Preserve the approved theme and all valid content.

Repair these failures without redesigning unrelated sections.
Return a complete valid document.
```

This is an INTERNAL instruction, not text displayed in the public UI.

Requirements:

- Preserve the original user brief.
- Preserve valid generated sections.
- Do not lose the selected design reference or design skill.
- Avoid unnecessary complete re-generation where a safe deterministic correction is possible.
- Bound token usage, correction attempts, and latency.
- Record the specific validator results for diagnostics.

Use deterministic repair only where correctness is demonstrable. Do not blindly manipulate arbitrary model HTML.

## 7. Retry Must Be Reliable

Audit:

```
POST /api/studio/frame
action: retry
```

and related retry services.

A retry must:

1. Verify user ownership.
2. Verify the requested frame exists.
3. Verify whether retry is allowed.
4. Avoid duplicate active retry jobs.
5. Preserve completed frames.
6. Reset only the required failed state.
7. Requeue reliably.
8. Start or resume processing through the established job mechanism.
9. Return a clear response contract.
10. Let frontend reflect retry state immediately.

Expected behavior:

```
Frame failed
     |
     v
User clicks [Coba lagi]
     |
     v
Retry request accepted
     |
     v
Frame returns to shimmer
     |
     v
Re-generate / correct frame
     |
  +--+--+
  |     |
Ready  Failed
  |     |
  v     v
Preview  Actionable recovery message
```

Never create an unbounded retry loop.

Handle races such as two retry requests for the same frame.

## 8. Error Taxonomy &amp; Public Copy

Separate errors into meaningful categories:

- Invalid user input.
- Frame generation failure.
- HTML contract violation.
- Provider temporarily unavailable.
- Rate limit.
- Request timeout.
- Storage failure.
- Preview capture failure.
- Retry already running.
- Missing/deleted project.
- Authentication or authorization failure.

Use stable internal error codes.

Public-facing messages should be short and helpful.

Examples:

**Temporary provider failure**

"Desain belum berhasil dibuat. Coba lagi."

**Retry already running**

"Halaman ini sedang dibuat ulang."

**Network interruption**

"Koneksi terputus. Periksa koneksi lalu coba lagi."

**Preview problem**

"Pratinjau belum bisa ditampilkan. Coba muat ulang pratinjau."

Do not show raw validator diagnostics in the public frame.

Never display:

- Internal prompt instructions.
- Contract JSON.
- Stack traces.
- Model/provider identifiers unnecessarily.
- Technical exception messages.
- Internal debugging metadata.

Technical details belong in structured server diagnostics.

## 9. Fix Generic Retry Error Handling

Investigate whether the frontend discards the actual HTTP error response.

Do not keep this kind of behavior:

```
if (!response.ok) {
  throw new Error("Permintaan retry gagal. Coba lagi.");
}
```

when the server returns actionable, safely classified error information.

Use an established API error contract.

Preserve actual error category without exposing sensitive backend details.

Ensure the UI knows whether the retry was rejected, queued, already active, or completed.
