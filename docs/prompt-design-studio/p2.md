## TUJUAN

Perbaiki pipeline generasi HTML/CSS VibeDesign Studio agar mampu menghasilkan prototype yang benar-benar layak sebagai tampilan aplikasi profesional, baik web maupun mobile.

Masalah yang dilaporkan user bukan hanya selera desain, melainkan kecacatan nyata:

1. Frame memiliki jarak kosong yang tidak masuk akal dengan tepi atas, bawah, kanan, atau kiri.
2. Konten utama ada yang terpotong di batas frame.
3. Form dan tabel melampaui lebar viewport.
4. Tombol hapus/close pada search memiliki kotak terlalu besar sehingga menimpa input.
5. Segmented control seperti `Semua (24)`, `Aktif (15)`, `Trial (6)`, `Menunggak (3)` melampaui card.
6. Chevron dropdown menempel terlalu dekat dengan sisi kanan.
7. Tombol `Export CSV` dan kontrol pembanding periode tidak sejajar atau tidak berada pada area action yang semestinya.
8. Beberapa card memiliki card kecil yang terlalu rapat.
9. Label pendek seperti `Resmi` terpecah menjadi `Res` dan `mi`.
10. Teks, badge, input, dan komponen lain dipaksa menumpuk.
11. Skeleton loading tiba-tiba muncul sebagai bagian dari halaman normal.
12. Badge/status redundan muncul tanpa tujuan.
13. Hasil AI sering generik, berantakan, terlalu sederhana, atau tidak mempunyai prioritas visual yang matang.
14. Output kadang dianggap valid secara teknis padahal layout secara struktural masih cacat.

**Jangan menyelesaikan masalah dengan CSS global** `overflow: hidden`**, memperpanjang tinggi frame secara paksa, atau menyembunyikan bagian yang rusak.**

## LANGKAH 2 — PERBAIKI SPATIAL LAYOUT CONTRACTS

Gunakan aturan komponen yang eksplisit, bukan hanya kalimat seperti "create beautiful UI".

### A. Search input

SALAH:

```
┌───────────────────────────────┐
│ 🔍 Jaya                 ┌────┐│
│                         │ X  ││
│                         └────┘│
└───────────────────────────────┘

Close button terlalu besar
dan mengganggu area pencarian.
```

BENAR:

```
┌───────────────────────────────────┐
│ 🔍  Jaya                       ×  │
└───────────────────────────────────┘

Icon X menjadi trailing action
dengan area klik proporsional.
```

Pastikan clear button memiliki hit area yang memadai tanpa membuat tampilannya menimpa teks atau border field.

### B. Segmented control

SALAH:

```
┌────────────────────────────────┐
│ [Semua] [Aktif] [Trial] [Menunggak
└────────────────────────────────┘
                            OVERFLOW
```

BENAR:

```
┌────────────────────────────────────────────┐
│ [ Semua ] [ Aktif ] [ Trial ] [ Menunggak ] │
└────────────────────────────────────────────┘
```

Ketika ruang tidak cukup:

- Gunakan horizontal scrolling yang jelas, atau
- Gunakan layout alternatif yang tepat untuk viewport.
- Jangan memaksa seluruh label berdesakan.
- Jangan memotong label tanpa mekanisme untuk membaca nilai lengkap.

### C. Dropdown

SALAH:

```
┌───────────────────────────────┐
│ Semua Paket (Starter...)     ˅│
└───────────────────────────────┘
```

BENAR:

```
┌───────────────────────────────┐
│ Semua Paket               ˅  │
└───────────────────────────────┘
```

Chevron harus memiliki padding kanan yang wajar dan tidak ditempelkan pada border.

Teks panjang bisa diringkas secara semantik, misalnya `Semua Paket`, daripada memaksakan daftar pilihan lengkap ke label tombol.

### D. Action alignment

Untuk laporan analitik:

```
┌──────────────────────────────────────────────────┐
│ Laporan Analitik                                 │
│ Analisis performa pelanggan dan pendapatan       │
│                                                  │
│ [7 Hari] [30 Hari] [90 Hari] [Kustom]            │
│                              [Bandingkan]        │
│                                    [Export CSV]  │
└──────────────────────────────────────────────────┘
```

Ini hanya contoh prinsip pengelompokan, bukan template layout wajib.

Untuk web, letakkan primary actions dalam action group yang masuk akal, biasanya dekat kanan header atau toolbar.

Untuk mobile, susun ulang mengikuti lebar viewport. Jangan mengecilkan seluruh tombol hingga tidak terbaca.

### E. Teks pendek tidak boleh terpecah

SALAH:

```
┌───────┐
│ Res   │
│ mi    │
└───────┘
```

BENAR:

```
┌───────────┐
│  Resmi    │
└───────────┘
```

Gunakan kombinasi yang tepat antara:

- `white-space: nowrap`
- `min-width`
- `minmax(0, 1fr)`
- `flex-shrink`
- Responsive layout
- Proper text-overflow behavior

Jangan hanya menambahkan `nowrap` secara global, karena itu dapat memunculkan overflow baru.

Bedakan:

- Control labels: cenderung tidak boleh dipecah.
- Deskripsi: boleh membungkus secara alami.
- Long-form content: harus fleksibel.
- Tabel: boleh memiliki horizontal scroll jika memang diperlukan.

### F. Tabel mobile dan desktop

SALAH:

```
┌───────────────────────────┐
│ Item     Qty      Harga   │
│ Paket                Rp...│
│ Wisata Bali              │
│ Escape                   │
│ 4H3M                     │
│                    CUT!  │
└───────────────────────────┘
```

BENAR:

```
MOBILE

┌────────────────────────────┐
│ Rincian Pembayaran         │
├────────────────────────────┤
│ Bali Escape 4H3M          │
│ 2 orang                   │
│ Rp3.900.000/orang         │
│ Total: Rp7.800.000        │
├────────────────────────────┤
│ Asuransi                  │
│ 2 orang                   │
│ Total: Rp150.000          │
└────────────────────────────┘
```

Untuk data tabular kompleks, gunakan responsive table atau contained horizontal scrolling bila sesuai.

Tidak semua tabel desktop harus dipaksakan tetap berbentuk tabel pada mobile.

## LANGKAH 3 — BEDAKAN APPLICATION SHELL DAN PAGE CONTENT

Studio telah memiliki canonical shell.

Tentukan secara jelas:

```
STUDIO OWNED
├── Global Header
├── Main Navigation
├── Theme Tokens
├── App Container
└── Platform Layout

AI OWNED
├── Feature-specific Content
├── Search / Filters
├── Forms
├── Tables
├── Charts
└── Contextual Actions
```

AI tidak boleh memasukkan body margin atau layout wrapper yang menyebabkan gap ganda.

Canonical shell tidak boleh merusak struktur yang valid dari AI.

Periksa penyebab double padding, nested fixed widths, dan konflik class/global selectors.

## LANGKAH 5 — BUAT QUALITY GATE

Pisahkan:

### Hard validation

- HTML valid.
- CSS valid.
- Tidak ada unsafe script.
- Required content tidak hilang.
- Tidak ada duplicate app shell.
- Komponen tidak mempunyai overflow struktural yang terbukti.
- Tidak ada elemen utama yang keluar dari viewport.
- Form controls mempunyai accessible name.
- Layout dasar sesuai web/mobile.
- Content region memiliki isi yang bermakna.

### Quality checks

- Visual hierarchy.
- Density.
- Spacing consistency.
- Control alignment.
- Typography.
- Component grouping.
- No pointless skeleton.
- No duplicate badges.
- No generic placeholder content.
- Consistent use of design tokens.

Gunakan deterministic repair untuk masalah yang aman dan jelas.

Gunakan bounded AI correction ketika membutuhkan redesign semantik.

Jangan menjadikan seluruh quality warning sebagai hard failure yang menyebabkan generation mengulang tanpa henti.

Jangan menurunkan validasi hanya supaya angka success meningkat.

## ACCEPTANCE CRITERIA

- Akar masalah diidentifikasi pada tahap pipeline yang benar.
- Search clear button tidak menimpa field.
- Segmented control tidak overflow.
- Dropdown mempunyai spacing benar.
- Teks singkat tidak terbelah per karakter/suku kata.
- Tabel mobile dan desktop memiliki strategi responsive.
- Frame tidak mempunyai gap atau clipping yang tidak disengaja.
- Tidak ada duplicate global shell.
- Tidak ada skeleton dekoratif yang tidak diminta.
- UI tidak terlalu padat maupun kosong tanpa alasan.
- Reusable component patterns diterapkan.
- Quality gate mampu menangkap defect yang relevan.
- Security validation tetap aktif.
- No browser QA.
