## 3. Repair the canonical navigation ownership model

The canonical shell should guarantee shared identity and consistency, not force every screen to use the same simplistic header.

Separate:

- Shared product navigation.
- Screen-specific header.
- Primary action.
- Contextual actions.
- Navigation hierarchy.
- Device-specific presentation.

### Public website

A destination should be represented as a normal navigation link unless there is a real reason to promote it to a primary CTA.

```
BAD:

[Brand]     Beranda     Studi Kasus     [Profil & Kontak]
                                                ^
                                      Arbitrarily styled CTA
```

```
GOOD:

[Brand]       Beranda    Tentang    Proyek    Kontak
```

Or, when conversion is actually important:

```
[Brand]       Tentang    Proyek       [Hubungi Saya]
```

Both can be valid depending on the brief.

Do not use a filled final navigation link as a universal pattern.

Do not force a fixed number of navigation destinations.

### Mobile application

Support contextual header contracts.

```
TOP LEVEL:
Brand / Context             Relevant actions

DETAIL:
Back        Contextual title       Save/Share

CHECKOUT:
Back        Checkout               Step if needed

PROFILE:
Profile identity                  Settings
```

Back navigation requires a meaningful parent or navigation history.

Do not show repeated back arrows across unrelated top-level destinations.

Allow the model to influence component composition while maintaining shared design tokens and safe structural contracts.

Do not solve this by letting the model duplicate the canonical header.

## 5. Build the real image pipeline

Inspect existing asset infrastructure before introducing a new provider.

The system must be able to discover legitimate external image assets appropriate to the user's requested design.

Target:

```
Shared planning
      |
      v
Identify image requirements
      |
      v
Resolve actual assets through approved provider
      |
      v
Validate source and asset metadata
      |
      v
Pass approved asset references to generation
      |
      v
Generated HTML uses approved images
      |
      v
Preview and export resolve assets correctly
```

Each image requirement should contain the minimum needed context:

- Purpose.
- Subject.
- Relevant search query.
- Appropriate aspect ratio.
- Preferred visual style.
- Alt text intent.
- Screen/component association.

Example:

```
Requirement:
Travel destination photography

Subject:
Uluwatu coastal temple, Bali

Usage:
Destination card

Preferred media:
Real destination photograph, landscape format
```

Do not send a vague instruction such as "Use nice images" and rely on the model to invent URLs.

## 6. Provider and asset policy

Evaluate legitimate image providers compatible with EvVibe's commercial use, configuration, and expected cost.

Use provider-supported API access and licensing requirements.

Possible providers may include Unsplash, Pexels, or other appropriately licensed sources, depending on verified availability.

Do not blindly assume their APIs have identical storage, hotlinking, attribution, or redistribution rules.

Implement:

- Configurable provider credentials.
- Search result validation.
- Relevant subject selection.
- Supported content type validation.
- Appropriate size limits.
- Source metadata.
- Caching permitted by the provider's policy.
- Deduplication.
- Fallback handling.
- Timeout and bounded retries.

Any server-side fetch mechanism must enforce appropriate URL validation, network boundaries, redirect validation, and asset size limits.

Do not permit arbitrary fetches to internal services or private network addresses.

Do not expose provider credentials in generated HTML.

## 7. Asset fallback

If a photographic image cannot be resolved:

- Preserve layout dimensions.
- Use an appropriate neutral fallback or another verified relevant asset.
- Record the asset failure for diagnostics.
- Avoid pretending a random illustration is an actual destination photograph.

Do not replace a failed photo with generated geometric SVG art unless the user explicitly requests illustration.

A missing optional image should not force regeneration of the entire frame.

User-provided assets should take precedence where appropriate.

## 8. Performance constraints

Image retrieval must not unnecessarily block first-frame generation.

Use bounded retrieval concurrency, shared asset reuse, and caching consistent with provider policy.

Where dependencies permit, resolve assets in parallel with non-dependent planning or generation preparation.

Preserve the target of first usable frame under 60 seconds.

Do not add unlimited image searches or repeated model calls to select individual images.

Do not claim latency improvement until measured.

## 9. HTML and responsive layout

Preserve and strengthen existing fixes for:

- Gutter consistency.
- Text wrapping.
- Product image sizing.
- Control dimensions.
- Horizontal scrolling.
- Mobile content width.
- Desktop content alignment.
- Theme and [DESIGN.md](http://DESIGN.md) fidelity.
- Preview/export parity.

Do not introduce global CSS rules that override every image ratio or force all cards to the same width.

Generated HTML should react to responsive viewport changes. The shared renderer introduced in P6 must be able to use the same document at desktop, tablet, and mobile sizes.

Do not hardcode a mobile-only max width that prevents appropriate desktop reflow.
