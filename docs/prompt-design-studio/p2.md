# TASK 02 — Fix Studio Infinite Shimmer, Realtime Frame Synchronization, Preview Loading, and Navigation-Away Recovery

**Priority:** P0 / CRITICAL  
**Complexity:** COMPLEX  
**Branch:** `feature/vibedesign-design-studio`

## Mission

Fix the severe Studio problem where a generated frame has already finished on the backend but remains in shimmer state on the canvas until the user refreshes, sometimes for an extremely long time.

The user also wants generation to continue safely when navigating from VibeDesign to VibeScrape or other application routes.

The desired experience is:

**AI finishes -&gt; frame persists -&gt; frontend receives updated state -&gt; preview becomes available -&gt; frame appears automatically.**

No manual reload should be required.

Other relevant facts from recent code inspection:

- Status polling is implemented in `use-studio-status.ts`.
- Poll interval is approximately 1.5 seconds.
- Requests have timeout, backoff, and a maximum failure count.
- Visual preview loading uses `IntersectionObserver`.
- Preview loading is deferred until an artboard approaches the viewport.
- Studio canvas is zoomable and pannable.
- Worker jobs are persisted and run outside the page component.
- Some generated frames require a full browser refresh to display their completed content.

Verify all current facts against the latest HEAD.

## 2. Fix Status Synchronization

Audit the existing polling implementation.

Focus on potential issues such as:

- Polling stops after five failures.
- Stale status is retained after temporary connection problems.
- A stale `initialData` reference unintentionally restarts the effect.
- Older requests override newer status.
- Response schema parsing fails.
- `updatedAt` timestamps are compared incorrectly.
- Reconciliation prevents a completed frame from replacing an older state.
- Active-job state becomes inconsistent with actual frame status.
- The canvas stops polling before every relevant frame reaches a terminal state.
- A job completes, but the frontend continues rendering `queued` or `generating`.

Implement reliable state recovery and reconciliation.

If using TanStack Query or another existing query abstraction fits the architecture, evaluate it. Do not add a second overlapping polling system.

**Requirements:**

- Status updates automatically while the workspace is open.
- Completed frames appear independently.
- Temporary network errors do not permanently freeze the canvas.
- Permanent authorization failures terminate safely.
- Request races cannot move a frame backward from `ready` to `generating`.
- Retry/backoff remains bounded.
- Terminal frame states are respected.
- Polling does not continue unnecessarily after all work has finished.

## 3. Fix Preview Loading on Zoomable Canvas

Inspect how `IntersectionObserver` behaves with scaled, translated, and panned artboards.

Current conceptual issue:

```
HTML READY
   |
   v
Preview fetch waits for intersection
   |
   v
Frame not intersecting expected viewport
   |
   v
Fetch does not start
   |
   v
Shimmer remains visible
```

Do not assume intersection is the confirmed root cause. Prove or eliminate it.

Consider a reliable loading policy where:

- Ready frames near the visible viewport are prioritized.
- At least one ready frame receives a prompt preview request.
- Frames becoming visible after pan/zoom are fetched.
- Offscreen previews do not create an unbounded request storm.
- Failed image loads surface an actionable error state.
- A ready frame with missing HTML never shimmers forever.
- Previous successfully captured previews remain usable during revisions.

Avoid making visibility the only condition for initializing a required preview if that can deadlock the user experience.

## 4. Separate Generation State and Preview State

A completed backend frame is not the same thing as a successfully loaded preview image.

Represent these conditions accurately:

```
Generation:
queued -> generating -> ready / failed

Preview:
not-requested -> loading -> available / failed

Canvas:
shimmer -> preview
        -> recoverable preview error
        -> generation error
```

A frame whose generation is `ready` but whose image cannot load must display a preview-specific recovery state.

It must not pretend generation is still running.

Avoid conflating image retry with AI regeneration.

Requirements:

- Refreshing the page does not enqueue duplicate generation.
