# PROMPT 02 — Repair Studio Generation Concurrency, Job Dependencies, and Race Conditions

**Complexity: VERY COMPLEX**  
**Execution order: 02 of 13**

## Context and objective

VibeDesign Studio supports multi-frame generation. A user may initiate four screens and, before they finish, submit another instruction such as "Tambahkan halaman Profil".

The system must accept valid user intent without corrupting initial planning, duplicating frames, overwriting successful HTML, or losing jobs.

Use the evidence and architecture report produced by Prompt 01. Verify every finding against the current local code before modifying anything.

Known prior architecture:

- Initial frames run with concurrency 3.
- Initial jobs receive dispatch priority.

- Individual frame results are persisted before the entire initial job completes.
- Existing recovery can skip previously completed HTML.

These are mechanisms to preserve, not casually replace.

## 2. Investigate the planning race

A previously identified risk concerns `persistStudioPlannedFrames()`.

The function can classify the frame set as already planned using a check resembling:

```
existing.some((frame) => !isTemporarySlot(frame))
```

If an `add_screen` request inserts an actual frame before initial planning has finished, the function may mistake that new frame for evidence that the initial frame slots were already planned.

Verify whether this behavior is reproducible and which transaction boundaries permit it.

Do NOT patch this simply by changing one boolean without understanding database invariants.

Distinguish:

- Initial provisional frames.
- Planned initial frames.
- Newly added frames.
- Revisions of existing frames.
- Failed frames.
- Ready frames.

Use explicit job/frame ownership or equivalent existing persisted relationships. Do not infer ownership from display order or naming conventions.

## 3. Define the concurrency policy

The desired product behavior:

```
INITIAL REQUEST:
Generate 4 screens
        |
        v
Planning in progress
        |
        +--------------------------+
        |                          |
        v                          v
Initial work continues      User sends:
                             "Add Profile"
                                     |
                                     v
                            Message/request persisted
                                     |
                                     v
                          Wait for required blueprint
                                     |
                                     v
                          Generate Profile when safe
                                     |
                                     v
                        Profile joins existing project
```

Required invariants:

1. An accepted user request must be durable.
2. New jobs must have explicit dependencies.
3. Initial planning must not be corrupted by later operations.
4. Generation of Profile must not require regenerating unrelated initial frames.
5. The new frame must reuse the appropriate project design context.
6. Ready sibling frames must remain byte-identical unless user intentionally edits them.
7. Two identical network retries must not produce two frames.
8. A user may submit another message without silently canceling prior work.
9. Queue order and prioritization must be deterministic and documented.
10. Shared model concurrency must remain bounded.

Prefer dependency-aware scheduling over a blanket policy that disables the composer during generation.

Do not force the Profile job to wait for every initial frame if it only depends on persisted planning and sufficient worker capacity. However, do not bypass the existing aggregate provider limit.

## 4. Revision requests during generation

Also investigate:

- Revise a frame that is `generating`.
- Revise a frame that is `ready` while siblings remain generating.
- Revise two selected frames.
- Request new pages twice in quick succession.
- Retry a failed frame while another request is queued.
- Reload the workspace during these operations.

Recommended behavior:

**Generating frame:** keep a revision request queued with a dependency on the version that will be produced. Do not let the initial writer and revision writer update the same HTML simultaneously.

**Ready frame:** a revision may proceed safely when its target version is known and write ownership is controlled.

**Multiple selected frames:** preserve explicit frame targets, isolate partial failures, and prevent unrelated screens from changing.

**Stale target:** reject or rebase only through an explicitly validated policy; never silently overwrite a newer revision.

## 5. Implementation strategy

Design a minimal durable operation model compatible with existing Drizzle tables and worker architecture.

Possible attributes to evaluate:

- operation ID
- project ID / owner
- job type
- target frame ID(s)
- base revision/version
- dependency state
- idempotency key
- lifecycle status
- created/started/completed timestamps

Do not add a parallel queue architecture if existing Studio jobs can support the requirements with targeted extensions.

Preserve:

- Tenant authorization.
- Credit/accounting invariants.
- Worker lease fencing.
- Recovery after worker interruption.
- Job cancellation semantics.
- Frame revision history.
- Existing API compatibility or a safe transition.

Do not remove the advisory lock simply to start more requests. Its current purpose is aggregate concurrency protection.

## 6. Error and recovery behavior

If a new request is queued:

- API should acknowledge that it was accepted.
- User-visible state must distinguish accepted/queued from generating/completed.
- Failed dependency must not leave downstream jobs permanently hanging without an explainable terminal or recoverable state.
- A worker crash must not lose the request.
- Recovery must not create duplicates.
- A rejected request should retain the user's draft when the future chat UI is implemented.

This task owns backend job guarantees. Do not build the new chat panel here.

## 7. Targeted tests

Create deterministic tests for:

- `add_screen` while initial planning is pending.
- `add_screen` while three initial frames are generating.
- First initial frame ready, others pending.
- Duplicate submissions with same idempotency identity.
- Distinct intentional requests with similar text.
- Two queued add-screen operations.
- Revision of a pending target.
- Revision of an already ready frame.
- Worker lease loss and recovery.
- Partial job failure followed by retry.
- Stale base revision.
- Multiple projects competing for bounded capacity.
- Credits unchanged for rejected duplicates.
- No cross-user job visibility.
- No lost, replaced, or duplicated initial frames.

Ensure tests cover the previously identified provisional-frame race rather than only testing the happy path.

Use targeted Vitest/integration tests and appropriate local mocks. No browser QA or Playwright E2E.
