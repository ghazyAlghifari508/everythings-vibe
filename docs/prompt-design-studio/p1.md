## 1. Misi

Perbaiki pipeline generasi VibeDesign Studio yang masih sangat lambat, kadang menghabiskan waktu beberapa menit, memproduksi output terlalu panjang, gagal validasi lalu memulai correction mahal, atau membuat user menunggu tanpa kejelasan status.

Tujuan sebenarnya adalah **reliable, bounded, observable, quality-preserving generation**, bukan sekadar mengganti shimmer atau memasang timeout agresif.

## 4. Root-cause investigation

### A. Provider output and token accounting

Audit perbedaan:

- configured max output tokens,
- requested max tokens,
- provider-reported `outputTokens`,
- `textTokens`,
- reasoning tokens,
- finish reason,
- transport/gateway behavior.

Kasus penting: provider bisa melaporkan `finishReason: "stop"` tetapi nilai `tokenLimitExceeded` bernilai true karena jumlah token yang dilaporkan lebih besar daripada konfigurasi.

Jangan menganggap ini otomatis truncated output. Bedakan provider finish reason, effective token cap, dan accounting. Audit kontrak SDK/provider menggunakan dokumentasi terbaru yang sesuai versi package terpasang.

Perbaiki observability agar hasil diagnosis tidak mencampurkan kondisi "stopped normally", "hit ceiling", "provider incomplete", dan "invalid HTML".

### B. Planning yang terlalu lama

Audit ukuran dan struktur system/user prompt planning, including:

- [DESIGN.md](http://DESIGN.md) reference;
- skill instructions;
- PRD;
- blueprint schema;
- duplicate quality rules.

Kurangi redundansi dan berikan kontrak output planning yang benar-benar ringkas serta terstruktur. Pertahankan nama produk, kebutuhan user, screen plan, design tokens, navigasi bersama, dan screen count.

Jangan mengurangi token dengan memotong bagian penting secara arbitrer.

### C. Correction amplification

Saat validasi gagal, sistem sekarang dapat memasukkan:

1. prompt semula;
2. correction instructions;
3. HTML sebelumnya yang sangat panjang.

Ini bisa membuat correction jauh lebih mahal daripada generation pertama.

Rancang correction strategy:

- Klasifikasikan masalah yang bisa ditangani secara deterministik versus yang membutuhkan AI.
- Untuk CSS yang bisa diperbaiki dengan aman dan terbukti, gunakan targeted deterministic repair dan revalidate.
- Jangan otomatis melakukan blanket removal `position: fixed/sticky` karena bisa mengubah komponen valid secara semantik.
- Untuk AI correction, berikan masalah spesifik dan konteks minimal yang relevan.
- Jika dokumen lengkap memang harus dikirim, jelaskan alasan dan ukur ukurannya.
- Hindari nested retry dan repeated full-document generation.
- Jangan mengubah HTML yang sudah valid hanya untuk mengejar estetika pada task ini.

### D. Worker queue / health

Audit:

- queued → claimed → planning → generating → completed/failed;
- worker active versus idle;
- worker healthy tetapi concurrency penuh;
- lease renewal;
- lease loss;
- stale jobs;
- reconnect/recovery;
- repeated submission;
- idempotent retry.

Jangan menganggap job berumur lebih dari 60 detik yang belum `claimedBy` otomatis berarti worker mati.

Jika health worker tidak bisa diketahui secara akurat, tampilkan status antrean yang netral daripada diagnosis palsu.

### E. Bounded concurrency

Initial frame generation sudah memiliki concurrency cap. Pertahankan bounded parallelism jika terbukti efektif.

Jangan:

- membuat unlimited parallel requests;
- menaikkan concurrency tanpa memperhitungkan rate limit provider;
- memperbarui semua frame menjadi generating saat hanya satu frame ditambah;
- menghapus hasil frame yang telah completed;
- mengulang seluruh project saat satu frame gagal.

Verifikasi session-level concurrency lock dan transaksi database supaya dua worker tidak memproses job identik secara bersamaan.

## 5. Target architecture

```
USER SUBMIT
    |
    v
VALIDATE + PERSIST PROJECT/JOB
    |
    v
QUEUED -----------> HEALTH / QUEUE STATUS
    |
    v
CLAIM JOB (lease + ownership)
    |
    v
BOUNDED PLANNING
    |
    v
PERSIST SCREEN SLOTS + BLUEPRINT
    |
    +---- FRAME A GENERATION ---- VALIDATE ---- SAVE ---- PREVIEW
    |
    +---- FRAME B GENERATION ---- VALIDATE ---- SAVE ---- PREVIEW
    |
    +---- FRAME C GENERATION ---- VALIDATE ---- SAVE ---- PREVIEW
    |           (bounded parallelism)
    |
    v
FINAL JOB STATUS

If one frame fails:
FRAME B -> classified failure -> bounded recovery
FRAME A / C remain ready and unchanged.
```

### Expected worker states

```
Queued:
"Menunggu giliran diproses."

Generating:
"Sedang membuat halaman."

Completed:
Render the actual completed frame.

Failed:
Display a recoverable error based on the failed stage.

Worker unavailable:
Only if supported by a real health signal.
```

Jangan membuat estimasi waktu palsu atau progress persentase tanpa data.

Pastikan tidak mencetak raw user prompt, raw [DESIGN.md](http://DESIGN.md), API keys, auth tokens, atau data sensitif ke logs.

Sediakan ringkasan p50/p95 jika sample memadai; jika tidak, laporkan per-job measurements. Targetkan penurunan latency secara terukur, bukan menjanjikan maksimal satu menit untuk semua model/provider.

## 7. Error and recovery rules


| Failure                    | Action                                    |
| -------------------------- | ----------------------------------------- |
| Planning JSON invalid      | Bounded planning correction               |
| Provider 429/transient     | Controlled retry with backoff             |
| Provider output incomplete | Safe continuation/correction if supported |
| CSS contract failure       | Targeted repair if safely applicable      |
| HTML irreparable           | Failed with specific internal category    |
| Preview capture failure    | Retry capture, not full AI generation     |
| Lease lost                 | Recovery/claim handling                   |
| Worker queued but busy     | Keep queue, no false "worker dead"        |
| One frame failed           | Preserve completed siblings               |


All retry actions must be idempotent. Explicitly protect billing/credit semantics from duplicate charges caused by retries.
