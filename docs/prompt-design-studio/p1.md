## Context

I am building EvVibe, specifically VibeDesign Studio, an AI-powered design workspace that generates standalone HTML/CSS prototypes for web and mobile, displays frames on a canvas, and supports AI-driven revisions.

The target experience is inspired by Google Stitch but deliberately limited to:

- Persistent AI chat workspace on the left.
- Canvas displaying generated web/mobile frames.
- Frame generation and incremental availability.
- Frame selection and prompt attachments.
- Adding or revising screens through conversation.
- Selecting individual HTML elements and asking AI to modify only that target.

Do NOT expand scope to voice, full Figma-style manual editing, external publishing integrations, or unrelated Stitch features.

The goal of this task is to investigate actual reference implementations and produce a technically grounded implementation plan. Do not start changing VibeDesign source code.

## 2. Reverse engineer Google Stitch using REA

Target: Google Stitch's publicly available, user-accessible product functionality.

Use REA's supported browser investigation tools as appropriate:

- `list_browser_targets`
- `inspect_web_page`
- `observe_web_session`
- `capture_web_screenshot`
- `compare_web_captures`
- `capture_browser_scenario`
- `analyze_web_bundle`
- `export_web_scripts`

Only use capabilities that are supported by the installed REA version.

Passive CDP observation does not perform clicks. For controlled browser interactions, use supported browser-scenario facilities or ask the user to perform the action while the observation window is active.

Do not bypass Google authentication, anti-bot measures, access controls, or usage restrictions. Do not reproduce proprietary code or protected design assets.

### Required investigation A — Initial prompt and chat handoff

Observe:

1. How a user starts a new design from the landing page.
2. What appears in the chat when the workspace opens.
3. Whether the original prompt becomes the first user message.
4. Whether the assistant's response is displayed before or after planning.
5. What kind of status or progress messages appear.
6. Whether the agent message is updated or followed by another message.
7. When the first frame becomes visible.
8. What happens when the chat panel is closed and reopened.
9. Whether messages and state survive reload.

Do not infer backend message storage from appearance alone.

### Required investigation B — Generation and concurrency

Investigate this scenario:

```
User: Generate 4 travel application screens
          |
          v
Initial generation starts
          |
          v
User: Add a Profile screen
          |
          v
Observe:
- Is second message accepted?
- Is it queued, rejected, or executed?
- Does initial generation continue?
- Are jobs serialized or overlapping from user perspective?
- Are existing frames preserved?
- When does Profile appear?
- What happens after reload?
```

Observe actual user-visible behavior and available evidence.

Do not claim that Stitch uses a particular queue/database/worker architecture without proof.

### Required investigation C — Frame selection and attachment

Test:

- Select one frame.
- Select several frames.
- Inspect their representation in the composer.
- Remove one attached target.
- Remove all targets if supported.
- Close and reopen chat.
- Switch selection and examine whether draft targets are preserved.
- Send a scoped revision.
- Determine how selected targets are represented to users.

### Required investigation D — Element-level editing

Investigate:

- How element selection is activated.
- How selected elements are highlighted.
- Whether an element is attached to chat.
- Whether the action affects only one frame.
- How edits are previewed or committed.
- What happens if selection becomes stale.
- Whether undo/version history is exposed.

Distinguish observed interface behavior from implementation guesses.

### Required investigation E — Error states and partial completion

Observe only normal, authorized scenarios:

- Generation still running.
- One frame ready while others are pending.
- Panel closed during generation.
- Reload during work.
- Valid cancellation/retry controls, if exposed.
- Preview unavailable or failed generation when naturally encountered.

Do not intentionally exhaust provider limits or abuse the service to manufacture failures.

## 5. Audit existing EvVibe implementation

Inspect both:

- `main`
- `feature/vibedesign-design-studio`

Also inspect the real local checkout, working tree, and relevant rules.

Read existing Studio services, routes, hooks, components, schemas, and tests.

Important previous findings to verify, not blindly assume:

- Studio already generates up to three initial frames concurrently.
- Frame-ready persistence happens independently.
- The worker's advisory lock intentionally caps aggregate concurrency.
- Extra frame enqueue may race with initial planning slot persistence.
- The composer already contains an `onRemoveFrame` control.
- Canvas currently displays captured frame images, not directly selectable DOM.
- Preview capture and AI generation are separate.
- Some latency fixes have already been implemented.

Read `docs/[studio-generation-latency.md](http://studio-generation-latency.md)` before making any performance recommendation.

Produce a code-grounded sequence:

```
Landing prompt
    -> project creation
    -> persisted job
    -> planning
    -> frame creation
    -> HTML validation
    -> persistence
    -> preview capture
    -> canvas display

Composer request
    -> intent resolution
    -> frame/project targeting
    -> enqueue
    -> worker
    -> revised frame

Future element selection
    -> element identity
    -> scoped chat target
    -> version-safe patch
    -> preview
    -> apply/revert
```

Map actual file paths and state ownership at each step.
