# P1 — Build and Integrate the Internal EvVibe Design Intelligence Skill

**Complexity: VERY COMPLEX**  
**Execution order: 01/11**  
**Scope: VibeDesign AI engine, design intelligence, prompt composition, and quality enforcement.**

## 1. Objective

Build a mandatory internal design skill named `evvibe-design` that governs how the AI engine inside VibeDesign Studio understands, plans, generates, and revises user interface designs.

IMPORTANT:

This is NOT a skill for Codex, Claude Code, Antigravity, or the coding agent implementing this task.

This skill must be consumed by VibeDesign's own AI engine at runtime.

Do not restore the previously removed user-facing design skill feature. Do not introduce another skill selector or bring back optional Frontend Design, Impeccable, Taste, or similar choices.

Every new design generated by VibeDesign must automatically benefit from this internal design intelligence.

## 2. Background and reported failures

Despite previous anti-slop improvements, generated UI still suffers from:

- Generic mobile app bars containing only page-title text.
- Back arrows appearing without appropriate navigation context.
- Web navbars with three generic links and an arbitrary colored CTA on the last link.
- Websites composed almost entirely of plain cards containing headings and paragraphs.
- Portfolio websites resembling administrative dashboards.
- Weak understanding of desktop versus mobile layout conventions.
- Decorative badges, dots, tinted alerts, and meaningless colored borders.
- Text overflowing cards.
- Awkward line breaks.
- Overlapping text and controls.
- Squashed mobile components.
- Inconsistent spacing between related screens.
- Product and travel images replaced with simplistic SVG/CSS illustrations.
- Weak visual storytelling and excessive text-heavy content.
- Unsupported statistics, testimonials, skill percentages, and professional claims.

Previous quality rules already address some of these problems. Do not simply duplicate those rules into a new markdown file.

The objective is to improve the design intelligence and its actual integration into the engine.

## 5. Mandatory design reasoning

The internal skill must teach the AI engine to reason about why an interface component is necessary.

Before making design decisions, the engine must consider:

- Product type and domain.
- Intended users.
- Primary user goals.
- Information architecture.
- Device and viewport.
- Primary versus secondary actions.
- Navigation depth.
- Content hierarchy.
- Visual identity.
- Interaction frequency.
- Accessibility.
- Relevant established UI patterns.

Do not use the same component composition for every product.

Examples:

- Travel application: destination imagery and trip discovery are important.
- Portfolio website: featured work and professional identity are important.
- Finance dashboard: readable financial data and efficient task completion are important.
- E-commerce application: product discovery, search, comparison, and checkout are important.
- E-book marketplace: book cover imagery, discovery, readability, and purchasing journey are important.

The skill must understand when NOT to use a card, badge, sidebar, navbar, table, carousel, modal, or CTA.

## 6. Website design intelligence

Teach the engine to distinguish:

- Public websites.
- Marketing landing pages.
- Portfolios.
- Editorial and content websites.
- E-commerce websites.
- Authenticated web applications.
- Administrative dashboards.

For public websites:

- Use purposeful navbar composition.
- Choose navigation destinations based on actual information architecture.
- Do not force exactly three navlinks.
- Do not automatically promote the last navlink into a solid button.
- CTA is optional and must represent an actual primary action.
- Use meaningful hero, editorial, showcase, gallery, and content-section compositions.
- Use images and visual assets when they contribute to the product.
- Avoid reducing every section to a bordered card.

Visual example:

```
BAD:

[Brand] [Beranda] [Tentang] [ KONTAK ]

[Card: About]
[Heading]
[Long paragraph]

[Card: Experience]
[Heading]
[Long paragraph]

[Card: Skills]
[Heading]
[Long paragraph]
```

```
GOOD:

[Brand]     Work   About   Contact

Large value proposition       Relevant visual

Featured projects
[ Project image ]             [ Project image ]
Project title                 Project title

Editorial about section
Selected experience
Meaningful closing action
```

Do not implement the good example as one universal portfolio template.

The examples must communicate design principles and alternatives.

## 7. Mobile design intelligence

Teach the engine that mobile design is not desktop layout compressed to a smaller width.

Distinguish:

A. Top-level destination screens.

B. Detail screens.

C. Search and discovery.

D. Transactional flows.

E. Profile/settings.

F. Modal or contextual task flows.

Top-level mobile screens should not automatically display a back arrow.

Detail screens may require back navigation and contextual actions.

App bars may contain:

- Brand or product identity.
- Current location.
- Search.
- Notification action.
- Profile/account access.
- Back navigation when justified.
- Save/share when relevant.
- Contextual action menus.

No screen should receive all of these automatically.

Visual example:

```
HOME / DISCOVERY

+--------------------------+
| Brand       Search  User |
|                          |
| Discover destinations    |
| [ Search destinations  ] |
|                          |
| [ Destination image   ] |
| [ Featured destination ] |
|                          |
| Explore   Trips   Saved  |
+--------------------------+
```

```
DETAIL SCREEN

+--------------------------+
| <  Detail Paket   Share  |
|                          |
| [ Destination photo    ] |
| Bali Escape              |
| Duration · Location      |
|                          |
| Itinerary                |
| Facilities               |
|                          |
| Price       [ Pesan ]    |
+--------------------------+
```

A back arrow is meaningful because the detail screen has a parent destination, not because every mobile screen requires a generic header.

## 8. Anti-slop policy

Establish explicit prohibitions against:

- Meaningless green/yellow/red dots.
- Decorative badges with no useful information.
- Arbitrary colored accent stripes on cards.
- Repeated semantic-color alerts for ordinary information.
- Excessive gradients, glow, glassmorphism, and decorative borders.
- Fake KPI cards.
- Unnecessary progress bars representing subjective skill proficiency.
- Generic "premium", "verified", or "live" labels.
- Excessive cards used as a substitute for proper content composition.
- Unnecessary headings and filler descriptions.
- Text clipping, overlap, and broken wrapping.
- Placeholder graphics pretending to be actual photographs.

Do not ban semantic badges, real alert states, charts, or cards when they are functionally justified.

The engine must understand the distinction between meaningful status communication and decoration.

## 9. Responsive quality rules

Include strong guidance and examples for:

- CSS flex and grid layout.
- Minimum and maximum widths.
- Intrinsic sizing.
- `min-width: 0` where appropriate.
- Intentional text wrapping.
- Atomic prices and short labels.
- Responsive media.
- Horizontal overflow and scrollable cards.
- Tap target sizing.
- Content reflow.
- Typography.
- Safe-area handling.
- Responsive navigation.

Examples:

```
BAD:
[ 3   ]
[ Item ]

GOOD:
[ 3 Item ]
```

```
BAD:
[ Oat M... ] [ Description... ] [ Price ]

GOOD:
[ Radio ] Oat Milk          +Rp8.000
          Plant-based milk
```

Do not use aggressive truncation to hide layout defects.

## 10. Real imagery requirement

If a design needs photos, the skill must require appropriate actual image assets obtained through the supported image asset system.

Examples:

- Travel destination photos.
- Food/product photography.
- Book covers provided or discovered through legitimate sources.
- Interior photos.
- Relevant visual project showcases.

Do not use AI-written CSS shapes, emojis, or geometric inline SVG as replacements for actual photography.

SVG remains acceptable for:

- Icons.
- Genuine vector logos.
- Charts.
- Explicitly requested illustrations.
- Appropriate visual diagrams.

Do not instruct the model to invent image URLs.

The actual image retrieval and delivery infrastructure will be implemented in P2. Define a clear asset contract now without inventing a working provider integration.

Also inspect existing EvVibe reusable components and HTML patterns.

Build a curated, component-aware reference collection for the AI engine.

Each applicable pattern should describe:

- Component purpose.
- When to use it.
- When not to use it.
- Required anatomy.
- Responsive behavior.
- Accessibility considerations.
- Compatible HTML/CSS implementation.
- Good and bad examples.
- Reference source and licensing.

Do not instruct an HTML-only model to import React components that cannot run in standalone HTML.

Use approved, compatible static implementations and patterns derived from mature components.

Do not copy paid or incompatible-license source without rights.

```
    |
    v

    |
    v

    |
    v

    |
    v
Canonical assembly
    |
    v

    |
    v

```

Use stage-specific context:

- Planning: product reasoning, user journey, navigation, content needs.
- Generation: relevant layout, media, and component patterns.
- Adding screens: project identity and the new screen's purpose.
- Revision: applicable design constraints and requested scope.
- Correction: narrowly relevant diagnostic rules.

Do not inject every reference file into every model request.

Consolidate competing instructions and avoid repeating existing baseline rules.

Maintain context/token budgets.

The skill must not become another cause of slow generation.

## 13. Quality enforcement

An instruction in [SKILL.md](http://SKILL.md) is not sufficient evidence of enforcement.

Integrate applicable checks into the existing validation/correction pipeline.

Distinguish:

- Hard structural/security defects.
- Deterministically repairable layout defects.
- Subjective visual concerns.

Do not treat every aesthetic preference as a mandatory full-document regeneration.

Keep bounded correction attempts.

Do not weaken safety validation or hide legitimate failures.

Preserve [DESIGN.md](http://DESIGN.md) and selected theme precedence for user-directed visual identity.
