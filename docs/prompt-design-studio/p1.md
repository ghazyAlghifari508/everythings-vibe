## 4. State Synchronization Requirements

Implement reliable synchronization between database, server, and React state.

Requirements:

- Use persisted database state as the source of truth.
- Reflect each frame transition independently.
- Reconcile project state, job state, and frame state.
- Avoid stale/out-of-order responses overwriting newer state.
- Prevent overlapping uncontrolled polling requests.
- Properly cancel requests or subscriptions on unmount.
- Distinguish network failure from actual generation failure.
- Avoid unnecessary full-canvas rerenders.
- Stop normal active-job polling when terminal state is confirmed.
- Resume appropriate synchronization after tab visibility changes and network reconnection.

Choose the synchronization strategy based on the current infrastructure.

Possible approaches:

- Correct, bounded polling with reliable status reconciliation.
- Server-Sent Events plus reconciliation fallback.
- Another existing infrastructure-supported mechanism.

Do not add WebSocket or Redis merely to make the implementation seem sophisticated.

### Mandatory proof

```
Frame A = ready
Frame B = generating
Frame C = queued

Frontend:
Frame A = preview visible
Frame B = shimmer
Frame C = shimmer
```

Then transition B to ready without remounting the entire workspace or refreshing the browser.

## 6. Durable Job Lifecycle

Audit whether Studio jobs remain reliable when:

- The HTTP request finishes.
- A browser tab closes.
- The user refreshes.
- A network connection is temporarily lost.
- The runtime restarts.
- A serverless invocation is terminated.
- The lease expires during a long model call.

Pay particular attention to:

```
void runStudioJobPipeline(...)
```

and the current job-lease implementation.

Do not assume fire-and-forget execution is durable across every deployment environment.

Use a deployment-compatible durable execution mechanism where necessary. Prefer the infrastructure already present in the repository.

Requirements:

- A persisted job must be recoverable.
- Job ownership must be explicit.
- Lease refresh must remain reliable during long-running work.
- Multiple workers must not overwrite each other's results.
- Expired jobs must be reclaimed safely.
- Reclaimed jobs must not unnecessarily regenerate completed frames.
- Recovery must have bounded attempts.
- No endless queued/generating state without recovery or terminal failure.
- Job completion and frame completion must be idempotent.

### Recovery example

```
Job running
    |
    +--> Frame A: ready (persisted)
    |
    +--> Frame B: generating
    |
    X Worker interrupted
    |
    v
Lease expires / recovery detects interruption
    |
    v
Reclaim job safely
    |
    +--> Frame A: KEEP existing ready result
    |
    +--> Frame B: resume/retry with bounded attempts
```

Never destroy successful frames just because another frame failed.
