# FIX 01 — Repair Studio Planning State, False Failure &amp; Retry Lifecycle

**Complexity: COMPLEX | Priority: P0 | Scope: VibeDesign Studio generation lifecycle**

Kerjakan task ini lebih dulu sebelum perbaikan UI atau quality pipeline.

## 1. Konteks masalah

Pada EvVibe VibeDesign Studio, user membuat proyek dari prompt, masuk ke canvas, lalu melihat:

- "Perencanaan layar gagal"
- "AI tidak dapat menyusun rencana layar untuk topik ini."
- Tombol "Coba lagi"

Namun beberapa detik kemudian frame justru berhasil digenerate. Ini sangat menyesatkan karena sistem memberitahu user bahwa AI gagal, padahal pekerjaan masih berjalan.

Berdasarkan audit sebelumnya, `src/features/studio/components/canvas/studio-canvas.tsx` menggunakan logika:

```
const sharedPlanningFailed =
  !project.designBlueprint &&
  frames.length > 0 &&
  frames.every((frame) => !frame.htmlCode);
```

Logika ini dapat menyimpulkan kegagalan hanya karena blueprint atau HTML belum tersedia, tanpa memeriksa apakah job masih `queued`, `planning`, atau `generating`.

Log runtime yang dilaporkan menunjukkan `planning-validation: VALID`, lalu `frame-context`, `first-token`, dan `frontend-ready`. Ini merupakan indikasi kuat bahwa error tersebut muncul sebelum job benar-benar gagal.

Jangan menyimpulkan bahwa pemakaian branch `main` adalah akar penyebab tanpa bukti. Kode Studio di kedua branch yang sebelumnya diperiksa sama.

## 3. Perbaikan yang wajib

### A. Gunakan status job sebagai sumber kebenaran

Jangan memakai `!designBlueprint` atau `!htmlCode` sebagai bukti tunggal kegagalan.

Bedakan dengan jelas:

- `queued`: menunggu worker.
- `planning`: AI sedang menyusun blueprint/screen plan.
- `generating`: AI sedang menghasilkan frame.
- `completed`: pekerjaan selesai.
- `partial`: sebagian hasil selesai, sebagian gagal.
- `failed`: pekerjaan benar-benar gagal.

Periksa status persisted job, hubungan antara project dan frame, serta data yang mungkin datang terlambat melalui polling.

Susun fungsi selector/state derivation yang teruji, bukan rangkaian boolean ambigu yang tersebar di komponen.

### B. Jangan tampilkan error sebelum status terminal

Error planning hanya ditampilkan ketika planning sungguh-sungguh gagal, bukan karena data sementara belum lengkap.

Pada status nonterminal, tampilkan indikator progress yang benar sesuai sinyal yang tersedia. Jangan membuat animasi tahap, persentase, atau estimasi waktu palsu.

Jika job sudah `completed`, tetapi blueprint atau frame hilang, perlakukan itu sebagai kemungkinan state tidak konsisten. Periksa dan tampilkan recovery yang sesuai, bukan menganggap setiap ketidaklengkapan data sebagai planning error.

### C. Perbaiki hubungan status polling dengan UI

Periksa apakah status dari respons lama bisa menimpa status terbaru.

Pastikan:

- Tidak ada flicker dari generating ke failed lalu ready.
- Pembaruan job dan frame tidak menghasilkan presentasi yang kontradiktif.
- Status stale tidak dianggap lebih baru.
- Transisi akibat reconnect atau halaman dibuka ulang tetap benar.
- Ketika sebagian frame berhasil dan yang lain gagal, hasil valid tetap tampil.
- Project yang sudah selesai tidak kembali ke state loading hanya karena data sementara tidak sinkron.

Jangan menyelesaikan masalah menggunakan delay arbitrer seperti `setTimeout` untuk menyembunyikan error.

### D. Perbaiki retry planning

Saat user menekan "Coba lagi", sistem hanya boleh mencoba ulang job yang memenuhi syarat.

Pertahankan guard backend yang sudah ada dan perkuat bila perlu:

- Job masih berjalan: tidak boleh membuat duplicate job.
- Job selesai: tidak boleh menimpa hasil valid.
- Job planning gagal: retry boleh dilakukan secara terkendali.
- Dua klik bersamaan: tidak boleh menghasilkan dua pekerjaan.
- Retry tidak boleh membuat project baru secara diam-diam.
- Retry tidak boleh menghapus frame yang sudah berhasil.
- Status backend wajib dikonfirmasi sebelum tombol retry tersedia.

Jika request retry ditolak karena job masih berjalan, UI tidak boleh menampilkan pesan ambigu yang menyiratkan AI gagal lagi.

### E. Error message dan UX

Gunakan copy yang manusiawi, spesifik, dan sesuai kondisi nyata.

Contoh:

**Saat planning:**  
"Menyusun struktur halaman..."

**Saat generation:**  
Frame menampilkan shimmer sesuai statusnya.

**Saat planning benar-benar gagal:**  
"Rencana halaman belum berhasil dibuat."  
"Periksa koneksi atau coba proses ini kembali."

Jangan menggunakan kalimat "AI tidak dapat menyusun rencana layar untuk topik ini" sebagai pesan universal untuk semua jenis kegagalan.

Tampilkan detail error teknis pada diagnostics/log yang relevan, bukan menumpahkan JSON atau pesan provider mentah ke UI.

## 5. Testing dan acceptance criteria

Tambah atau perbarui targeted tests untuk:

- Blueprint null + frame sementara + job planning = bukan error.
- Blueprint null + frame sementara + job generating = bukan error.
- Job failed saat planning = tampil recovery.
- Status completed + frame valid = tampil hasil.
- Job partial = frame sukses tetap tersedia.
- Status polling terlambat tidak menimpa hasil lebih baru.
- Retry saat running ditolak tanpa duplicate job.
- Retry setelah completed tidak merusak HTML.
- Retry setelah genuine failure mengikuti lifecycle benar.
- Double click retry tetap idempotent.
- Perubahan halaman, reload, dan reconnect tidak memalsukan status.

Jangan melemahkan assertions atau menghapus test untuk membuat hasil hijau.

**Jangan menjalankan browser QA, Playwright E2E, atau inspeksi browser otomatis untuk task ini.** Gunakan targeted unit/integration tests yang tidak membutuhkan browser dan typecheck seperlunya.

## 6. Batasan

Pertahankan architecture, database ownership, worker lease, credit rules, dan mekanisme concurrency yang sudah ada. Jangan membuat state machine baru secara berlebihan bila state derivation saat ini dapat diperbaiki dengan aman.

Jangan melakukan refactor unrelated atau mengubah UI Studio di luar konteks.

## 7. Laporan penyelesaian

Jelaskan:

1. Root cause aktual setelah membaca kode.
2. File yang diubah dan alasannya.
3. State transitions sebelum dan sesudah.
4. Penanganan retry dan concurrency.
5. Targeted tests yang dijalankan.
6. Hal yang belum diverifikasi.

Task hanya selesai apabila error palsu dan retry lifecycle sudah diperbaiki tanpa merusak generasi frame.
