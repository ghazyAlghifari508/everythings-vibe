## 1. Mission

Investigate and optimize VibeDesign Studio's AI generation performance.

The user reports that generating several UI frames still takes an unacceptably long time, even after enabling the standalone Studio worker.

The desired product experience is:

- Fast, responsive project creation.
- Minimal unnecessary queue waiting.
- Parallel generation where appropriate.
- First completed frame visible immediately.
- Other frames continue independently.
- High visual quality, functional HTML, and consistency maintained.
- No indefinite shimmer or silent stalled jobs.
- No unnecessary latency caused by oversized skill prompts, repeated work, excessive retries, or inefficient preview capture.

**Do not optimize for speed by sacrificing the actual purpose of VibeDesign Studio: generating excellent, consistent, usable interfaces.**

```
User Submits Prompt
         |
         v

         |
         v
Worker Acquires Job
         |
         v
Generate Shared Plan + Blueprint
         |
         v
      Parallel Frames
   +---------+---------+
   |         |         |
 Frame A   Frame B   Frame C

   |         |         |
```

Frames exceeding concurrency start when slots become available.

For example, with four requested frames and concurrency three, Frame D does not start immediately.

This is expected bounded behavior.

The task is to determine why real observed latency remains excessive.

## 5. Investigate Skill Prompt Overhead

The Studio design-skill system loads real upstream skill material through a manifest and registry.

Some guidance may be large.

Investigate whether every frame unnecessarily receives material that is:

- Irrelevant to the selected platform.
- Duplicated elsewhere in the prompt.
- Already captured in the shared blueprint.
- Applicable only to planning rather than per-frame HTML generation.
- Excessively large relative to the model's available context.

Compare:

```
WITHOUT SELECTED SKILL
User Brief + Blueprint + Screen Contract

WITH SELECTED SKILL
User Brief + Blueprint + Screen Contract
+ Upstream Skill Guidance
+ Reference Documents
+ Optional Dataset Lookup
```

### Requirements

- Preserve fidelity to the selected upstream skill.
- Do not delete original skill documents.
- Do not replace source guidance with improvised generic summaries.
- Preserve source provenance and manifest integrity.
- Avoid loading unrelated supporting documents without purpose.
- Consider stage-specific skill context where technically appropriate.
- Reuse a validated shared design plan rather than repeatedly asking the model to reinterpret the entire product identity.
- Investigate prompt caching if supported by the actual model/provider.

Any context-reduction strategy must be evaluated for correctness and output quality.

Do not claim smaller prompts automatically produce better or faster results.

## 6. Optimize Planning

The system currently produces a shared plan and blueprint before generating all frames.

This is important for consistency, so do not remove it merely to reduce latency.

Investigate:

- Whether the planning prompt is unnecessarily verbose.
- Whether response schema can be made easier for the selected model to satisfy.
- Whether JSON parsing failures cause repeated full planning calls.
- Whether valid planning data can be reused.
- Whether deterministic project metadata should be calculated outside the model.
- Whether the planner generates irrelevant details or duplicated content.
- Whether model routing for planning is appropriate.

Possible improvements:

- Structured-output contracts when genuinely supported.
- Reduced redundant instructions.
- Better schema validation and targeted correction.
- Appropriate model selection based on measured quality/latency.

Do not hardcode project-specific plans.

Do not let the planner ignore PRD, design reference, user requirements, or selected skill.

## 7. Optimize Parallel Frame Generation

Keep bounded parallelism unless evidence supports changing it.

### Expected scheduling

```
FRAME CONCURRENCY = 3

Time →

Frame A: [========== READY]
Frame B: [================== READY]
Frame C: [============ READY]
Frame D:             [========== READY]

A ready frame becomes available immediately.
```

The drawing is illustrative, not a promised duration.

Investigate:

- Whether `runWithConcurrency()` actually overlaps provider requests.
- Whether provider rate limits serialize or delay requests internally.
- Whether shared worker locks unnecessarily block independent jobs.
- Whether frame generation is accidentally awaited before persisting individual results.
- Whether single slow frames block final state updates.
- Whether concurrency settings are appropriate for the selected provider.
- Whether background worker configuration causes unnecessary queue delay.
- Whether one slow model call blocks cancellation or lease renewal.
- Whether preview generation competes with model generation for limited resources.

Do not blindly set concurrency to 5, 10, or unlimited.

Higher concurrency is not automatically better.

Consider provider throughput, rate limits, request limits, resource utilization, and observed latency.

Preserve deterministic frame ordering even if completion order differs.

## 8. Improve Time to First Frame

The user must not wait for every frame before seeing the first completed result.

Required lifecycle:

```
Frame A: READY      -> Preview visible
Frame B: GENERATING -> Shimmer
Frame C: GENERATING -> Shimmer
Frame D: QUEUED     -> Shimmer
```

When Frame C finishes:

```
Frame A: READY      -> Preview visible
Frame B: GENERATING -> Shimmer
Frame C: READY      -> Preview visible
Frame D: GENERATING -> Shimmer
```

Review project-status synchronization and preview loading.

Do not introduce new polling bugs.

Do not force a full workspace refresh when one frame changes.

Do not clear ready-frame previews while other frames are processing.

## 9. Validation and Correction Latency

The current frame pipeline validates generated HTML and allows a bounded corrective attempt.

This means a rejected frame may require another substantial AI generation.

Investigate:

- Which validation rules fail most often.
- Whether failures are genuine or false positives.
- Whether the generator prompt conflicts with validator expectations.
- Whether corrective prompts preserve enough valid work.
- Whether small deterministic repairs can safely resolve limited structural issues.
- Whether the system needlessly regenerates the entire document for a minor repair.

Do not disable important HTML safety or structure validation.

Do not mark invalid output as successful to improve benchmark numbers.

Use precise diagnostics to reduce unnecessary retries.
