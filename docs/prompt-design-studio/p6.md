# P6 — Establish a Shared Responsive HTML Renderer and Eliminate Frame Flickering

**Complexity: VERY COMPLEX**  
**Execution order: 06/11**

## 1. Objective

Repair the existing frame presentation architecture so VibeDesign can support:

- Responsive desktop/tablet/mobile viewport changes.
- Immediate element inspection.
- Stable hover and click selection.
- Later direct editing and AI editing.
- Interactive prototype presentation.
- No visible flickering when switching between canvas tools.

Do not introduce another unrelated rendering pipeline for every feature.

Build a shared HTML rendering foundation compatible with the existing canvas and persisted frame documents.

## 2. Current problem

The current canvas uses captured images for ordinary frame presentation.

When element inspection mode is activated, the frame can switch from its screenshot to `StudioElementSurface`, which fetches inspection HTML and mounts an iframe.

This transition can cause:

- Frame flashing.
- Content disappearing temporarily.
- An empty surface.
- Layout changing visibly.
- Delayed element availability.
- Inconsistent selection bounds.

The user does not want a frame to appear as if it becomes editable only after blinking.

A cosmetic animation does not solve the underlying renderer lifecycle.

## 4. Shared renderer contract

Create or consolidate a renderer abstraction that can represent the same persisted frame revision in several modes:

```
                       Persisted HTML
                             |
                     Responsive renderer
                             |
          +------------------+------------------+
          |                  |                  |
       Canvas            Inspection          Prototype
       surface             mode               mode
```

The representation should use:

- Frame ID.
- Persisted document revision.
- Viewport dimensions.
- Render mode.
- Asset/reference context.
- Readiness state.
- Controlled interaction/inspection capability.

Keep inspection overlays and prototype controls outside the canonical exported document or inject them only into ephemeral rendering documents.

Never persist editor-specific UI into the user's generated HTML.

## 5. Rendering strategy

Evaluate the best fit for current architecture:

A. Keep live HTML surfaces for visible/active frames.

B. Use screenshot virtualization for distant, offscreen, or inactive frames, with prewarmed live rendering for relevant frames.

Choose according to measured resource requirements.

Do not mount dozens of unnecessary active iframes when the project contains many screens.

However, the selected ready frame must have a usable live renderer before responsive device controls and element inspection require it.

Avoid making the user pay the full iframe initialization cost only after clicking Pencil.

Use bounded preloading and readiness management.

## 6. Eliminate flicker

Desired transition:

```
BEFORE:

Screenshot
    |
    v
Screenshot removed
    |
    v
Blank / loading iframe
    |
    v
Editable HTML
```

```
AFTER:

Existing frame remains visible
    |
    +--- Live document prepared
    |
    +--- Required styles/assets available
    |
    v
Ready surface activated
    |
    v
Inspection overlays become available
```

Prefer keeping the same live surface mounted while switching between ordinary frame selection and element inspection.

Changing tools must not recreate the iframe unnecessarily.

If an image-backed frame needs to transition to HTML, retain the existing visual until the replacement surface is ready.

Do not reveal a white or black blank iframe.

Do not display a generation shimmer for an already completed frame just because it is entering editing mode.

## 7. Responsive viewport support

The renderer must support multiple viewport dimensions using the same HTML revision:

```
Frame document / revision 7
            |
            +--- Desktop: 1440px
            +--- Tablet:   768px
            +--- Mobile:   390px
```

Dimensions are initial suggested presets; select and document final values compatible with the application.

The renderer must change the actual document viewport.

Do not stretch or shrink a static screenshot and call it responsive behavior.

CSS media queries and responsive layouts must respond to the new dimensions.

Viewport state is presentation metadata, not an HTML design revision.

Changing viewport must not:

- Call an LLM.
- Generate a new frame.
- Create a generation job.
- Deduct credits.
- Modify the stored design identity.
- Display generation shimmer.

For legacy documents with poor responsive CSS, report the actual limitations. Do not silently regenerate them.

## 8. Document geometry

Ensure renderer geometry remains correct for:

- Canvas zoom.
- Canvas pan.
- Different frame heights.
- Internal scrolling.
- Selection overlays.
- Device viewport changes.
- Frame labels.
- Future contextual toolbar placement.

Avoid mixing screen pixels, iframe document coordinates, and canvas world coordinates without an explicit transformation model.

Preserve stable artboard identity and layout.

Handle changed frame dimensions without overlapping unrelated artboards.

## 9. Iframe security

Generated HTML is untrusted.

Preserve or strengthen:

- Appropriate iframe sandboxing.
- HTML sanitization.
- Content security policy.
- Isolation from application credentials and storage.
- Restricted navigation and form behavior.
- Validated message protocols.
- Frame/project identity verification.

Do not allow arbitrary generated scripts merely to enable interaction.

For iframe messaging, account for sandboxed documents that may have an opaque origin. Validate the expected source window, session identity, message type, and allowed schema rather than pretending origin alone is sufficient.

Only trusted editor/prototype bridge code may receive the narrowly scoped privileges necessary for its function.

## 10. Renderer failures

Differentiate:

- Generated HTML not available.
- Live document initialization failure.
- Screenshot unavailable.
- Asset loading failure.
- Inspection bridge not ready.

If valid HTML and a last-good preview exist, retain available content.

Do not change a ready frame's generation status to failed just because an inspection surface could not initialize.

Use appropriate recovery without regeneration.

## 11. Component-first requirement

For any newly required renderer controls, use existing UI primitives and inspect relevant shadcn, HeroUI, Magic UI, React Bits, Thinking Orbs, affectUI, TUFFUI, CUI, and SakaniUI components.

Renderer lifecycle itself is infrastructure and should not be implemented using decorative UI libraries.

Do not introduce new unnecessary loading animations.

## 12. Targeted tests

Test:

- Same persisted HTML used in supported renderer modes.
- Mode changes do not create unnecessary document reloads.
- Ready preview retained before live surface readiness.
- Viewport changes do not generate AI requests.
- Viewport state is isolated from design revision state.
- Zoom/pan coordinate transformations.
- Asset and revision changes invalidate the correct renderer.
- Stale renderer results cannot overwrite newer revisions.
- Bounded live surface count.
- Offscreen resource cleanup.
- Frame isolation.
- Unauthorized bridge messages rejected.
- Editor overlays excluded from export.
- Old projects remain displayable.
- Failure in one live renderer does not corrupt sibling frames.

No browser QA, headless browser visual checks, or Playwright E2E in this phase.

## Definition of done

Report the confirmed flicker mechanism, renderer architecture, readiness contract, responsive viewport strategy, iframe isolation policy, resource-management tradeoffs, impacted files, and tests.

Do not claim flicker is visually eliminated until final browser QA verifies it.

Do not mark responsive rendering complete if the implementation only resizes JPEG images.
