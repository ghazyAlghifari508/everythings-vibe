# 5. Strict Markdown-Only Validation

## Allowed

`.md`

## Not allowed

- `.pdf`
- `.doc`
- `.docx`
- `.txt`
- `.rtf`
- `.html`
- `.markdown`
- archive formats
- executable files
- arbitrary renamed binary files

The `.md` extension requirement is explicit.

### Validation

Client:

- File extension.
- Size.
- Readability.
- Empty content.
- UTF-8 decoding.

Server:

- Revalidate all fields independently.
- Reject invalid extensions.
- Reject oversized payloads.
- Reject empty or invalid text.
- Reject invalid encoding/binary content.
- Enforce appropriate size limits.
- Do not trust the browser's MIME type alone.

Choose a sensible size limit consistent with existing application constraints and the AI context budget.

Declare it in a shared constant/schema rather than scattering hardcoded values.

Do not silently truncate the PRD.

If a document is too large, return a clear actionable validation error.

### Security

PRD content is untrusted user-provided reference data.

It must not be allowed to override:

- system prompts;
- authentication;
- output security;
- tool permissions;
- model/provider configuration;
- database rules.

Do not execute Markdown-embedded scripts.

Do not fetch arbitrary embedded remote references automatically.

Do not treat Markdown code fences as server-executable commands.

Preserve ownership and privacy.

# 6. Distinguish PRD From [DESIGN.md](http://DESIGN.md)

This is critical.

```
                   STUDIO COMPOSER
                          │
        ┌─────────────────┼──────────────────┐
        │                 │                  │
        ▼                 ▼                  ▼
    USER PROMPT        PRD.md             DESIGN.md
        │                 │                  │
        │          PRODUCT CONTEXT           │
        │                 │          VISUAL REFERENCE
        └─────────────────┼──────────────────┘
                          │
                          ▼
                    AI PLANNING
                          │
                          ▼
                 SHARED DESIGN BLUEPRINT
                          │
                          ▼
                  1–5 CONNECTED FRAMES
```

**PRD** describes:

- Product purpose.
- Target users.
- Core features.
- User journeys.
- Business rules.
- Functional requirements.
- Data and entities.
- Relevant constraints.
- Important application states.

[**DESIGN.md**](http://DESIGN.md) describes:

- Colors.
- Typography.
- Spacing.
- Component styling.
- Iconography.
- Visual identity.
- Design-system rules.

Do not merge these two concepts into one generic file reference.

The same project must be able to use:

- A user prompt.
- An uploaded PRD `.md`.
- A selected design skill.
- A selected theme or custom [DESIGN.md](http://DESIGN.md).
- A selected initial page count.

All must have clearly defined roles.

# 7. Backend Data Contract &amp; Persistence

Add an appropriate typed PRD attachment contract to Studio project creation.

Avoid overloading the existing short `prompt` field with potentially long PRD content.

For example, conceptually:

```
Studio Generate Request
├── prompt
├── designMode
├── initialPageCount
├── designSkillId
├── designReference
└── prdAttachment
    ├── filename
    └── validated Markdown content
```

The exact implementation should follow existing project schemas and file-upload conventions.

### Persistence requirements

The PRD must be associated with the created Studio project.

Preserve:

- User ownership.
- Original filename.
- Validated PRD content.
- Useful content hash/version metadata where appropriate.
- Availability when the project is reopened.
- Availability for future planning/revision context.
- Proper deletion alongside the owning project.

Do not store the document only in transient React component state.

Do not let a page refresh erase the project-associated PRD after successful creation.

If a Studio project is duplicated, inspect and define whether the copied project retains its PRD context.

Ensure existing projects without a PRD remain compatible.

### Idempotency

Inspect current project creation deduplication.

Two submissions with the same visible prompt but **different PRDs** must not accidentally resolve to the same existing project.

Include a suitable PRD identity/content hash in the creation identity logic when needed.

Avoid duplicate projects caused by repeated clicks or retries.

# 8. Real AI Planning Integration

This is the most important requirement.

The uploaded PRD must reach the actual model request.

Do not stop at persisting it.

### Required generation flow

```
User Prompt + Validated PRD
           │
           ▼
     Product Context
           │
           ▼
      AI Planning
           │
           ▼
Shared Design Blueprint
           │
           ▼
  N Requested Screens
           │
           ▼
 Frame-Specific Generation
```

Use the PRD as authoritative product-requirement context within appropriate precedence rules.

The AI should understand:

- Required features.
- Relevant user journeys.
- Product terminology.
- Roles/permissions.
- Data entities.
- Key interactions.
- Required screens and states.

Avoid generating generic pages that ignore the uploaded PRD.

### Page-count contract

If the PRD describes ten modules but the user selects four initial pages, the AI must plan exactly four initial screens while choosing sensible coverage of the most important user journeys.

Do not silently generate ten screens.

Do not discard essential PRD context merely because not all modules fit into four initial frames.

Planning should capture the intended coverage and reasonable limitations.

### Shared Blueprint integration

The blueprint should reflect domain terminology, navigation, important features, and platform requirements derived from the PRD.

Visual decisions should still follow the active design reference and selected skill.

Do not let PRD product requirements accidentally override unrelated security or design-system contracts.

### Revision support

Future project revisions should retain access to the project's PRD.

When a user requests changes, relevant PRD context should still be available without needing to upload it again.

Do not blindly inject the entire document into every frame request if a validated, sufficient planning context can provide the required information.

Preserve source accuracy while controlling token usage.

### Large-document handling

If the supported document size can exceed a practical model context budget:

- Use a deterministic and explainable context-preparation strategy.
- Preserve important feature requirements.
- Avoid arbitrary first-N-character truncation.
- Report unsupported sizes rather than hiding missing content.

Do not fabricate PRD requirements during summarization.

# 9. Attachment Lifecycle &amp; Error States

Support:

**No attachment**

Generation works as before.

**Valid attachment**

PRD is included in the real request.

**Invalid file extension**

Reject with clear guidance: only `.md` is supported.

**Empty document**

Reject.

**Oversized document**

Reject with stated limit.

**File read failure**

Show error; keep the prompt draft.

**Server validation failure**

Do not navigate as if a project was created.

**Generation failure after project creation**

Preserve persisted PRD context and appropriate retry behavior.

**Remove attachment**

Remove it from the pending composer draft without affecting unrelated project data.

**Replace attachment**

Use the new file content, not stale data from the previous file.

**Project deletion**

PRD data and related references must follow project deletion rules.
