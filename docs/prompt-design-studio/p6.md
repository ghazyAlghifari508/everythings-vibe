# PROMPT 06 — Enforce High-Quality Domain-Aware AI UI Generation and Remove AI Slop

\*\*Complexity: VERY COMPLEX\*\*
\*\*Execution order: 06 of 13\*\*

## Objective

Fix recurring low-quality outputs from VibeDesign Studio.

Users are seeing:

- Poor visual hierarchy.
- Generic layouts.
- Desktop websites resembling mobile applications.
- Inconsistent design between related frames.
- Product imagery cropped or partially displayed.
- Text escaping cards.
- Values such as "3 item" split awkwardly.
- Squashed form controls and milk-selection options.
- Mobile cards forced to shrink instead of using horizontal scrolling.
- Excessive decorative pills, colored dots, tinted status boxes, and accent stripes.
- Generic mobile app bars and website headers.
- Fake-looking or ungrounded metrics, testimonials, credentials, and statuses.

The task is NOT to make every design minimal or grayscale. It is to produce contextually appropriate and polished interfaces without meaningless decoration.

## 3. Improve the design planning model

The shared blueprint should provide a coherent identity across screens:

- Brand tone.
- Color and typography tokens.
- Content density.
- Spacing system.
- Layout family.
- Navigation behavior.
- Platform-specific conventions.
- Shared card/control patterns.
- Media usage.
- Screen-specific hierarchy.

Each screen should remain distinct based on its job.

Examples:

\*\*Coffee app:\*\* exploration, product details, customization, and order tracking should share identity but not use identical card grids.

\*\*Travel app:\*\* destination exploration, itineraries, trips, and profile should reflect relevant content priorities.

\*\*Portfolio website:\*\* navigation, hero, featured work, case studies, and contact should not be converted into a fake financial dashboard.

\*\*SaaS dashboard:\*\* denser controls and metrics are appropriate where actually useful.

Do not hardcode the names of sample projects into generic logic.

## 4. Enforce meaningful component composition

### A. Badge and dot policy

Allowed:

- Current selection.
- Stock availability.
- Real order/payment status.
- Valid error/success/warning state.
- Functional category labels.

Not allowed as generic decoration:

- Fake "live" dots.
- Unexplained green/yellow/red circles.
- Repeated "verified" pills.
- Random "premium" badges.
- Unnecessary colored dots alongside ordinary text.
- Semantic colors without semantic meaning.

Do not ban all badges. Ban gratuitous badge use.

### B. Status/error visual treatment

Avoid a single repetitive AI-generated alert style:

\`\`\`text
\[ GREEN DOT \] SUCCESS
\[ green tinted blurry background \]
\[ green border + green stripe \]
\`\`\`

Use established, accessible component patterns chosen for their actual severity and content.

Ordinary information does not need a success-colored panel.

Error/success/warning visual styles must not be generated automatically for every informational sentence.

### C. Card and border discipline

Avoid:

- Random colored left-edge stripes on cards.
- Nested border-on-border containers.
- Gratuitous glassmorphism.
- Repeated gradients and glowing backgrounds.
- Overabundant KPI cards.
- Excessively rounded chips everywhere.

Use visual accents only where they serve hierarchy, grouping, or user action.

### D. Media rules

For product media:

- Establish a suitable container ratio.
- Preserve the important visual subject.
- Match image fitting to intended use.
- Avoid clipping caused by global CSS.
- Provide appropriate fallback behavior.
- Do not leave half-empty media containers.

Audit example types such as Cascara and Aeropress, without hardcoding those names into production rules.

### E. Text and sizing

Prevent:

\`\`\`text
BAD:
\[ 3    \]
\[ item \]

GOOD:
\[ 3 item \]
\`\`\`

Also prevent:

- Broken currency labels.
- Button labels split into tiny stacked words.
- Essential titles truncated without user benefit.
- Information escaping card boundaries.
- Quantity buttons that are taller than intended.
- Option labels hidden behind prices.

Use correct \`min-width\`, flex behavior, wrapping, and component hierarchy.

### F. Mobile card strategy

Do not automatically shrink wide cards to fit a phone.

Choose intentionally among:

- Responsive reflow.
- Vertical list.
- Grid.
- Horizontal scroll/carousel.
- Expandable detail.

Travel cards and promotional cards may intentionally have fixed minimum width and horizontal scrolling.

Form options usually need readable full-width rows.

## 5. Prevent fabricated content

Prototype content may be illustrative, but unsupported claims must not be presented as verified facts.

Do not casually invent:

- Realistic professional testimonials attributed to identifiable people.
- Compliance certifications.
- Exact performance improvement metrics.
- Verified user satisfaction.
- Business qualifications not in the brief.

If a brief explicitly provides illustrative numbers, they may be rendered consistently as sample content.

If missing, use believable neutral placeholder content that does not masquerade as verified evidence.

Do not fill empty space with fake KPIs merely to make a design look complete.

## 6. Strengthen quality validation

Existing diagnostics differentiate hard failures and advisory findings.

Investigate whether significant quality problems are being emitted only as harmless warnings.

Define clear severity classes:

\*\*Hard failure\*\*
- Invalid/unsafe HTML.
- Broken essential structure.
- Critical inaccessible interaction.
- Confirmed severe layout violation.

\*\*Repairable structural defect\*\*
- Clearly clipped essential label.
- Known CSS ratio conflict.
- Invalid quantity/price grouping.
- Invalid component shrink behavior.
- Duplicated canonical navigation.
- Critical text hidden by overflow.

\*\*Advisory visual concern\*\*
- Potentially excessive badge use.
- Weak hierarchy.
- Minor spacing or aesthetic concern.

Only deterministic and strongly evidenced violations should force mandatory correction.

Do not turn subjective visual taste into an infinite LLM retry loop.

If actual pixel geometry is required to prove a defect, do not claim a source-only rule can guarantee it. Reserve full visual verification for the final browser QA phase.

## 7. Apply consistent quality to every generation mode

Quality controls must cover:

- Initial generation.
- Adding a new screen.
- Revising selected frames.
- Targeted editing when implemented later.
- With selected theme.
- With custom \`DESIGN.md\`.
- With VibeScrape design reference.
- Without any design reference.

A selected theme is not permission to discard quality rules.

Do not make generator quality dependent on optional design skills; they will be removed in Prompt 07.

## 9. Targeted tests

Test domain-aware planning contracts, blueprint consistency, component usage guidance, media rules, responsive intent, quality classification, safe correction bounds, and content grounding requirements.

Tests must not assert exact stochastic model prose.

Use representative fixtures without overfitting to one screenshot.

Do not bypass safety rules or force acceptance by weakening test assertions.

No browser QA or visual Playwright tests in this phase.

## Definition of done

Report:

1. Root causes across planning/generation/assembly/quality checks.
2. Component-first discovery evidence.
3. Actual reusable patterns adopted.
4. Rules eliminated or consolidated.
5. Hard vs repairable vs advisory checks.
6. Targeted tests.
7. Expected latency/cost tradeoffs.
8. Remaining visual concerns requiring final browser validation.

Do not claim the design quality issue is resolved merely because the system prompt became longer.

Do not commit/push/merge/deploy.
