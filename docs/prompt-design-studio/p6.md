# TASK 06 — Implement Context-Aware Default Visual Direction and Eliminate Repetitive Green Palette Bias

**Priority:** P1  
**Complexity:** MEDIUM–COMPLEX  
**Branch:** `feature/vibedesign-design-studio`

## Mission

Fix the tendency for Studio projects generated without a selected theme or [DESIGN.md](http://DESIGN.md) to repeatedly use green accents or highly similar visual compositions.

The user wants automatically selected design direction that fits the actual product context while remaining consistent across all screens in each project.

Do not solve this by randomly assigning one of the built-in themes.

## 1. Desired Behavior

```
USER PROJECT REQUEST
          |
          v
Understand product domain
          |
          v
Understand target audience
          |
          v
Identify visual personality
          |
          v
Choose intentional visual direction
          |
          v
Generate shared design tokens
          |
          v
Apply them to every screen
```

Illustrative examples:

```
Finance SaaS
  -> Navy / Indigo / controlled teal

Creative Portfolio
  -> Monochrome / violet / bold accent

Travel Booking
  -> Ocean / sky / natural tones

Healthcare
  -> Sage / blue / restrained green

Education
  -> Cobalt / indigo / warm accents
```

These are examples, not rigid rules.

Two products in the same industry may still deserve different visual directions.

## 2. Identify Sources of Repetitive Output

Audit:

- Planning prompt examples.
- Implicit default design tokens.
- System-prompt wording.
- Skill guidance.
- Canonical-shell defaults.
- Prompt shortcuts.
- Static palette fallback.
- Model sampling configuration.
- Product identity extraction.
- Reuse of previously generated blueprints.
- Cached project metadata.

Separate confirmed causes from hypotheses.

Do not introduce unnecessary randomness to conceal the issue.

## 3. Establish Design Direction at Planning Time

When no design reference exists, generate a coherent visual-direction object containing:

- Intended mood.
- Primary accent.
- Secondary accent.
- Canvas/background.
- Surface.
- Text/ink.
- Muted text.
- Borders.
- Typography direction.
- Radius and density.
- Reason grounded in the product brief.

Validate contrast, color syntax, and compatibility with Studio's canonical shell.

Keep the number of necessary tokens reasonable.

Use the existing blueprint schema where possible. Avoid another competing theme object.

## 4. Respect Explicit Preferences

Precedence must be:

```
Safety / Accessibility
          |
          v
Explicit user color or brand requirements
          |
          v
Validated DESIGN.md / selected theme
          |
          v
Shared project blueprint
          |
          v
Selected skill guidance
          |
          v
Context-aware automatic design direction
```

If a user selects Midnight, Studio must use Midnight rather than replacing it with context-aware colors.

If a user provides a valid custom [DESIGN.md](http://DESIGN.md), preserve its visual rules.

If the user explicitly requests green, green is correct.

Only apply automatic palette selection when no higher-priority design reference exists.

## 5. Preserve Identity Across Screens

Wrong:

```
Screen 1: Green
Screen 2: Blue
Screen 3: Purple
Screen 4: Green
```

Correct:

```
PROJECT DESIGN BLUEPRINT
        |
        +--> Screen 1
        |
        +--> Screen 2
        |
        +--> Screen 3
        |
        +--> Screen 4
```

Every screen receives the same approved color tokens and typography foundations.

When adding a fifth screen, reuse the existing project identity.

Do not reselect a new palette for every added frame.

Do not silently change the colors of previously completed screens.

## 6. Avoid Hardcoded Industry Templates

Do not create a giant mapping where every finance application must be blue, every travel application must be cyan, and every health application must be green.

Use product context and actual requirements.

A domain-aware recommendation can be a starting signal, not an unbreakable template.

Preserve creative variety without sacrificing consistency.

Avoid random colors that fail contrast or produce incoherent combinations.

- Repetitive palette behavior is investigated and addressed.
- Design direction matches project context.
- Explicit user references always take precedence.

- Additional screens preserve existing identity.
- No random per-frame palette generation.
