# P10 — Build a Dedicated Interactive Prototype Viewer With Device Mockups and Mock State

**Complexity: VERY COMPLEX**  
**Execution order: 10/11**

## 1. Objective

Build a dedicated prototype preview experience separate from the VibeDesign canvas.

Allow the user to try generated frontend prototypes through meaningful interactions.

Scope explicitly includes:

- Cross-page navigation.
- Buttons.
- Tabs.
- Accordions.
- Dialogs and modals.
- Form input and validation.
- Search and filters over mock data.
- UI state transitions.
- Simulated checkout and other requested workflows.
- Device switching.
- Refresh/reset.
- Right-side page navigation.
- Desktop, tablet, and mobile device presentation.

This is an interactive frontend prototype, not a full-stack production application or backend generator.

## 2. Existing architectural limitation

Generated Studio frames historically follow a static-artboard contract.

Some navigation links use `href="#"`.

Generated scripts and inline event handlers are restricted for security.

Merely displaying existing HTML inside another iframe does not make its controls functional.

Do not mark this feature complete if the prototype only looks interactive.

Introduce an explicit, validated interaction architecture.

## 4. Dedicated preview route

Add an authorized project/frame-aware preview route using existing routing conventions.

Possible route:

```
/design/$id/preview
```

The exact route may differ based on the existing architecture.

The preview must support selecting the initial frame through appropriate validated route state or parameters.

User flow:

```
Canvas workspace
       |
       v
Select frame
       |
       v
Click Preview icon
       |
       v
Dedicated prototype viewer
       |
       v
Try interaction / switch pages / switch device
       |
       v
Back returns to canvas
```

Preserve the workspace's prior camera position, selection, chat state, and draft where practical.

Enforce project ownership and authorization.

## 6. Device presentation

Provide visually appropriate device shells.

### Desktop

Use a clean browser-window presentation with suitable browser chrome/address indication.

### Tablet

Use an appropriate tablet-sized device shell with readable proportions.

### Mobile

Use a realistic mobile device frame/bezel.

Requirements:

- Actual HTML viewport matches the selected device.
- Presentation scales to available viewer space while preserving internal document viewport.
- Scrolling remains usable.
- Buttons and forms are interactive.
- Device shell does not obstruct prototype content.
- Browser/address decoration does not masquerade as editable browser chrome.
- No unnecessary mock operating-system controls.

The device mockup must add meaningful presentation context, not just another plain rectangle identical to a canvas frame.

Display all actual available project pages in a right-side sidebar.

Requirements:

- Clearly selected current page.
- Accurate page names.
- Actual route or meaningful route identifier.
- Scrollable for larger projects.
- Reflect newly added screens.
- Handle removed screens.
- Never invent pages that do not exist.
- On narrower viewports, adapt to a drawer or compact page switcher.

Clicking a page updates the central prototype without returning to the canvas.

## 8. Interaction contract

Introduce the minimum architecture needed for safe, meaningful prototype interactions.

Prefer:

- Native HTML behavior where sufficient.
- Declarative interaction attributes.
- Validated action manifests.
- Trusted EvVibe prototype runtime.
- Typed mock state.

Example conceptual contract:

```
Interaction:
  source element: detail-package CTA
  action: navigate
  target screen: pemesanan
```

```
Interaction:
  source element: checkout submit
  action: validate-and-transition
  required fields: name, email, participant
  success target: tiket-saya
  failure state: show validation
```

Define explicit supported action types rather than executing arbitrary JavaScript strings.

Possible interaction primitives:

- navigate
- back
- open_dialog
- close_dialog
- select_tab
- expand
- collapse
- set_mock_state
- filter_collection
- validate_form
- submit_mock_form
- toggle
- show_feedback

Choose exact contracts according to the existing architecture.

Do not use `eval`, dynamic code execution, or unrestricted AI-generated event handlers.

## 9. Multi-page prototype navigation

Example travel flow:

```
Jelajah
    |
    | Click destination
    v
Detail Paket
    |
    | Click Pesan
    v
Pemesanan
    |
    | Complete mock form/payment flow
    v
Tiket Saya
```

Connect real available screens by stable identity, not merely fragile display names.

Support a prototype-local navigation history for Back.

Keep the current route and sidebar selection synchronized.

Existing canonical navigation destinations should map to the appropriate generated screens.

Do not create a nonexistent route silently.

If a legacy document references a page that does not exist, provide an honest unavailable-state behavior rather than pretending the link succeeded.

## 10. Full mock state interactions

Use prototype-local state that can support requested workflows without a real backend.

Examples:

### Search and filtering

```
Search: Bali
Result: matching mock destinations

Filter: Pantai
Result: appropriate mock records
```

### Forms

```
User submits with empty required field
    -> Accessible validation shown

User enters valid example data
    -> Mock submission succeeds
    -> Relevant next state or page
```

### Modal

```
Click "Tolak Pengajuan"
    -> Dialog opens

Empty required rejection reason
    -> Validation error

Valid reason
    -> Mock status transitions
```

### Checkout

```
Choose mock payment method
    -> Validate mock checkout details
    -> Simulate outcome
    -> Navigate to confirmation screen
```

Do not perform actual payment, banking, email delivery, authentication, or production mutations.

Do not request users' real passwords, bank credentials, or payment details to exercise a prototype.

Use clearly fictional example data.

Maintain state across related prototype pages where the simulated workflow requires it.

## 11. Refresh and reset

The viewer's Refresh control must reload the latest committed frontend document without AI generation.

Reset prototype session state to its documented initial values where appropriate.

```
Refresh
    -> Latest saved HTML
    -> Initial mock state
    -> Same selected page/device
```

No model calls.

No generation job.

No extra credits.

No stored design revision.

No mutation of real application data.

## 12. Generation engine integration

Update relevant engine contracts so new frames contain meaningful interaction targets and supported mock behavior.

The internal `evvibe-design` intelligence must determine which controls need interaction.

Do not fake interactivity with decorative buttons that have no intended action.

For every core flow required in the brief, generate compatible interactions and appropriate visual states.

Integrate:

```
Adaptive planning
      |
      v
Screen identities + navigation relationships
      |
      v
Component and interaction requirements
      |
      v
Generated HTML + validated interaction metadata
      |
      v
Safe prototype runtime
```

If a frame later undergoes direct editing or AI revision, validate and reconcile affected interaction references.

Do not leave broken manifest targets after an element is deleted.

## 13. Legacy projects

Existing projects must remain openable and viewable.

Use deterministic mapping or native HTML behavior when supported.

Do not automatically regenerate every historic project to make it interactive.

For old frames with missing interaction metadata, retain available functionality and explain genuine unsupported interactions where needed.

Do not claim all historic static HTML has become fully interactive if the necessary behavior does not exist.

## 14. Security and isolation

Prototype HTML remains untrusted.

Requirements:

- Sandboxed renderer.
- Validated interaction manifest.
- No unrestricted external form submission.
- No real backend state mutation.
- No access to EvVibe credentials.
- No arbitrary generated script execution.
- No untrusted navigation of the parent application.
- No unvalidated postMessage commands.
- Strict project/frame ownership checks.
- Safe asset loading.
- Bounded mock data.

Separate prototype session state from production application state.

The prototype may demonstrate simulated UI behavior, but it must never impersonate an actual financial transaction or real account authentication.

Actually adopt compatible device mockup, segmented control, scroll area, sidebar, drawer, tooltip, and navigation primitives where available.

Do not use a large custom collection of CSS shapes if a mature suitable device presentation already exists.

Only implement specialized viewer/runtime infrastructure that cannot be satisfied by existing components.

Follow EvVibe's visual identity rather than introducing an unrelated purple or light theme just because the supplied reference uses those colors.

## 16. Export compatibility

Preserve existing standalone HTML/ZIP export.

Do not inject editor UI, unsafe code, or internal API credentials into exports.

If the trusted prototype runtime can be safely packaged with the existing export format, document its behavior and dependencies.

Otherwise clearly distinguish interactive viewer capabilities from standalone exported HTML functionality.

Do not silently promise that every exported HTML file supports all runtime mock interactions when that capability has not been implemented.
