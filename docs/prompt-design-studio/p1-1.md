# P1.1 — Refactor EvVibe Design Intelligence Into an Efficient, Flexible Runtime Skill

**Complexity: VERY COMPLEX**  
**Execution order: Immediately after completed P1, before P2**  
**Scope: Internal VibeDesign AI engine and prompt architecture**

## 1. Objective

Refactor the existing `evvibe-design` internal skill to improve its correctness, efficiency, flexibility, and actual contribution to design quality.

P1 has already been implemented. Do not restart it from scratch or restore the deprecated selectable design skills.

The target architecture is an AI design engine that understands UI/UX, applies consistent quality standards, and independently creates appropriate visual compositions based on the user's requirements.

The engine must not become a fixed-template generator that merely replaces colors, text, and images.

## 4. Distinguish skill, hardcoded prompt rules, and deterministic enforcement

The existing implementation contains three different mechanisms.

A. Static written design guidance.

B. Deterministic HTML/layout generation.

C. Deterministic validation and safety enforcement.

Do not confuse them.

### Static written design guidance is allowed

An internal skill necessarily contains written knowledge.

For example:

"Use back navigation when the user enters a nested screen. Choose relevant app-bar content according to the screen's purpose."

This is acceptable because the AI still makes the design decision.

### Fixed visual composition is not acceptable

For example:

- Every mobile frame receives the same title-only app bar.
- Every website receives three navlinks.
- The last navlink always becomes a filled CTA.
- Every portfolio receives a hero followed by three cards.
- Every detail page receives exactly the same content hierarchy.

These are visual decisions that should not be imposed universally by the engine.

### Deterministic safety and objective validation must remain

Examples:

- HTML sanitization.
- Unsafe script rejection.
- Valid document structure.
- Asset reference validation.
- Project ownership.
- Version-safe revision.
- Duplicate identifier detection.
- Clearly evidenced structural layout defects.

Do not delete or weaken these checks.

The intended principle is:

**Hardcode the quality and security boundaries, not the visual design decisions.**

## 7. Make guidance adaptive without creating fixed templates

The current context options expose:

```
viewport
layoutIntent
composition
```

Previous inspection showed that only `viewport` meaningfully controls reference filtering.

Use the existing layout intent and relevant screen composition information to select compact guidance where useful.

But do NOT introduce rigid mappings such as:

```
Portfolio → always Hero + 3 Project Cards + Testimonials
Travel → always Search + Carousel + 4 Cards
Dashboard → always 4 KPI Cards + Chart + Table
```

Those are precisely the repetitive outputs the user wants to eliminate.

The skill should instead communicate principles.

Examples:

- Portfolio: prioritize the actual work and professional identity.
- Travel: prioritize destination discovery, meaningful photography, and booking decisions.
- Dashboard: prioritize the tasks, records, and metrics the user genuinely needs.
- Mobile checkout: prioritize form clarity, progress, validation, and the primary action.

These examples describe design priorities, not mandatory layout templates.

Allow AI to determine:

- Number of sections.
- Information hierarchy.
- Navigation structure.
- Hero composition.
- Use of cards.
- Header appearance.
- Media positioning.
- Appropriate interaction controls.
- Visual density.

Use screen-specific guidance only when relevant and available.

Do not add another model request to classify or select skill references when the existing planning output provides sufficient context.

P2 will handle the actual canonical renderer ownership changes. This task must remove or reconcile conflicting design instructions without prematurely performing the entire P2 implementation.

Suggested separation:

```

    -> Non-negotiable generation and safety boundaries.

    -> Design reasoning and general UI/UX knowledge.

Platform/context addendum

```

Remove duplicated instructions after confirming their original meaning remains covered.

Do not delete valuable quality rules simply to reduce context size.

Do not retain parallel versions of the same rule unless they serve genuinely distinct purposes.

The component knowledge currently present in the skill may be retained as compact educational UI/UX guidance. It must not become a mandatory runtime component catalog.

## 9. Optimize stage context budgets

Current configured ceilings are measured in characters, not tokens.

Previous P1 values:

- Planning: 20,000 characters.
- Generation: 17,000 characters.
- Initial: 9,000 characters.
- Add-screen: 9,000 characters.
- Revision: 8,800 characters.
- Correction: 4,400 characters.

Previous source-based measurement showed approximately 13,729 characters of generation guidance plus 8,288 characters of initial guidance for an initial web frame.

That is approximately 22,017 characters of internal skill content alone, before the remaining prompt requirements.

This is unnecessarily concerning given VibeDesign's existing latency target.

Evaluate compact initial ceilings in these approximate ranges:

- Planning: 12,000–15,000.
- Generation: 6,000–9,000.
- Initial: 4,000–6,000.
- Add-screen: 4,000–6,000.
- Revision: 3,000–5,000.
- Correction: 1,000–2,000.

These are proposed evaluation ranges, not proven optimal values.

Do not blindly change numeric constants while leaving large references unchanged. That would cause important sections to be dropped without solving the underlying duplication.

Priorities:

1. Consolidate repeated instructions.
2. Rewrite verbose rules into concise, actionable guidance.
3. Preserve mandatory quality and security instructions.
4. Preserve relevant platform guidance.
5. Include examples selectively.
6. Measure the actual resulting context.

Remember that the total request includes both system and user messages.

A small individual stage budget does not guarantee a small total model input.

Report:

- Skill characters.
- Complete system prompt characters.
- Complete user prompt characters.
- Actual provider-reported input tokens where available.
- Estimated tokens separately when actual usage is unavailable.
- Included and omitted reference IDs.
- Before/after differences.

Do not confuse character ceilings with model context limits or output-token limits.
