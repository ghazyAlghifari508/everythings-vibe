# P3 — Remove Manual Page Count Selection and Implement Adaptive Screen Planning

**Complexity: COMPLEX**  
**Execution order: 03/11**

## Objective

Remove the manual page-count selector from VibeDesign Studio.

The AI engine must intelligently determine how many screens are necessary based on the user's requested product and scope.

Also fix project titles that are too short, generic, and uninformative.

Examples:

```
BAD:
Jelajahin
Metriq
Ruang Seduh

GOOD:
Jelajahin — Domestic Travel Booking App
Metriq SaaS Analytics Dashboard
Ruang Seduh — Mobile Coffee Ordering
```

## 1. Inspect current implementation

Audit:

- `studio-generation-options.ts`
- `studio-planning-prompt.ts`
- `studio-planning-parser.ts`
- `studio-planning.ts`
- `studio-project-title.ts`
- `studio-prompt-contracts.ts`
- `studio-project-enqueue.ts`
- `studio-landing-page.tsx`
- `studio-launch-composer.tsx`
- Generation API contracts.
- Studio project/job/frame schema.
- Billing and credit accounting.
- Tests related to initial page count and temporary frame slots.

Previous implementation uses fixed requested page counts, including default three pages, and requires the generated plan to return exactly that count.

Do not merely hide the UI and leave the same fixed behavior in the backend.

## 2. Remove manual page count feature

Target landing composer:

```
What will you design?

+--------------------------------------------------+
| Describe the application or website...           |
|                                                  |

|--------------------------------------------------|
| [ Web | Mobile ]             [Attach] [Theme] ↑  |

```

Remove the button displaying:

- 1 halaman

- 4 halaman
- Other manually selected initial page quantities.

Keep:

- Web/Mobile mode.
- Prompt.
- PRD/file attachments.
- Design reference selector.
- Theme selection.
- Submit action.

Update ready-made brief shortcuts so they no longer silently depend on the deleted page-count selection mechanism.

If an old preset explicitly describes multiple screens in natural-language content, preserve those requirements as part of the brief.

## 3. Adaptive planning

The new planner must determine the necessary screens based on:

- User's requested scope.
- Product intent.
- Navigation destinations.
- Essential user journey.
- Explicit page requests.
- Existing PRD requirements.
- Platform.
- Reasonable initial design coverage.

Examples:

```
Prompt:
"Design a mobile login page"

Plan:
1 screen.
```

```
Prompt:
"Design a coffee shop marketing website"

Plan:
A suitable single-page or multi-page website,
depending on the actual brief.
```

```
Prompt:
"Design a domestic travel booking application
with discovery, details, booking, and tickets"

Plan:
A coherent set of screens covering that journey.
```

Do not hardcode these examples as mappings.

If the user explicitly requests four pages in the prompt, respect that request within supported limits.

Keep an internal resource limit for workload, credits, and provider capacity.

When the requested scope exceeds that limit, communicate what can be generated in the initial batch and what remains to be added. Do not silently claim complete coverage or truncate an important user journey without explanation.

## 4. Correct initial job lifecycle

Target:

```
User submits prompt
        |
        v
Project and initial request persisted
        |
        v
Adaptive shared planning
        |
        v
Actual screen count determined
        |
        v
Plan validated and persisted
        |
        v
Create initial frame slots
        |
        v
Generate frames independently
```

Do not pre-create three fake initial screen placeholders when the actual count is unknown.

If planning fails, preserve the request and provide appropriate recovery.

Ensure accurate accounting and bounded workload when actual count becomes known.

Do not introduce unexpected credit deductions without the product's applicable authorization and accounting rules.

Preserve previous race-condition fixes.

If the user sends "Tambah halaman Profil" before initial planning finishes, the request must be handled through the existing dependency-aware queue rather than accidentally changing the initial plan slots.

## 5. Project naming

Separate concepts:

```
productName   = Brand identity used within generated UI.
projectTitle  = Informative workspace/history title.
screenName    = Individual frame name.
```

Example:

```
Product name: Jelajahin
Project title: Jelajahin — Domestic Travel Booking App

Screens:
- Jelajah
- Detail Paket
- Pemesanan
- Tiket Saya
```

Do not use the full descriptive workspace title as the product's navbar brand.

The title should:

- Identify the product when a name exists.
- Describe the application's purpose.
- Be concise enough for history.
- Follow the language/context naturally.
- Distinguish similar projects.

Avoid generic titles such as "Website Modern", "Aplikasi Mobile", or just the quoted brand.

Use the existing initial planning model call to produce the title where practical.

Do not introduce a separate expensive LLM request only to generate a title.

Preserve manual user renaming through existing `titleSource` or equivalent semantics.

Do not overwrite an explicitly renamed project during later screen generation.

## 6. Component-first frontend requirement

For the landing composer cleanup, reuse existing compatible components.

Inspect shadcn, HeroUI, TUFFUI, Magic UI, React Bits, Thinking Orbs, affectUI, CUI, and SakaniUI if replacement primitives are needed.

Do not redesign the entire existing landing page.

Preserve the appearance of unaffected controls.

## 7. Tests

Cover:

- Landing UI no longer has page-count selection.
- Simple prompt produces one justified screen.
- Complex prompt produces an adaptive plan.
- Explicit requested screen count is respected where supported.
- Internal resource limit is enforced.
- Actual planned count drives persisted frame slots and progress.
- No duplicate frame slots.
- Follow-up operations during planning remain safe.
- Billing remains correct.
- Retry and worker recovery remain correct.
- Informative project title.
- Product brand remains distinct.
- Manual rename is not overwritten.
- Existing projects created with fixed page counts still load and export.

Use targeted non-browser tests. No browser QA.

## Definition of done

Report removed dependencies, new planning contract, actual count lifecycle, legacy compatibility, title-generation strategy, resource/billing behavior, and test results.

Do not claim adaptive planning is implemented if the backend always creates three screens after removing the selector.
