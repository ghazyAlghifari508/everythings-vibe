# TASK 03 — Studio AI Generation Performance, Token Efficiency, and Intelligent Correction Pipeline

**Priority:** P0 / CRITICAL  
**Complexity:** COMPLEX  
**Branch:** `feature/vibedesign-design-studio`

## Mission

Investigate and substantially improve the end-to-end AI generation performance of VibeDesign Studio WITHOUT sacrificing output quality, design fidelity, security, or frame consistency.

Users report that generating three screens takes approximately six minutes and adding one more screen can take more than four minutes.

The generation system must be optimized using measured evidence, not arbitrary timeout or concurrency changes.

## 2. Audit Model Output Token Limits

The logs show reported completion tokens exceeding the requested `maxTokens=12000`.

Trace:

```
Studio configured output limit
          |
          v
AI orchestrator
          |
          v
Provider adapter / gateway
          |
          v
Actual request payload
          |
          v
Provider response usage
```

Check:

- Whether `maxTokens` maps to the correct provider parameter.
- Whether the gateway ignores or overrides the limit.
- Whether reported usage includes hidden reasoning tokens.
- Whether output-token accounting is cumulative or per attempt.
- Whether `finishReason` and `tokenLimitExceeded` are computed consistently.
- Whether a fallback provider behaves differently.

Do not conclude the provider violated the limit until these possibilities are checked.

Implement reliable diagnostic reporting.

## 3. Reduce Unnecessary Output Without Making UI Simplistic

Current frames can return 40–70 KB of generated markup.

Investigate whether the model repeatedly generates:

- Identical app shell and navigation.
- Repeated CSS tokens.
- Duplicate component styles.
- Large inline SVG structures.
- Repeated mock datasets.
- Unnecessary commentary or formatting.
- Entire documents when only body content is required.

The project already has canonical shell generation.

Prefer generating only meaningful screen content when the architecture supports it.

Reuse the canonical header, navigation, icon mapping, and tokens instead of asking the model to reproduce them for every frame.

However:

**Do not shorten output by deleting useful sections, forms, charts, tables, or information hierarchy.**

An efficient generation is not a half-finished UI.

## 5. Replace Wasteful Full Regeneration With Targeted Correction Where Safe

Observed example:

```
AI generates ~53 KB HTML
        |
        v
Validation:
2 missing accessible labels
        |
        v
Another lengthy AI request
with ~66 KB correction prompt
        |
        v
Additional ~210 seconds
```

This is inefficient.

Target:

```
Generated HTML
     |
     v
Validation
     |
     +--> VALID
     |      |
     |      v
     |    SAVE
     |
     +--> SMALL, SAFE, DETERMINISTIC ISSUE
     |      |
     |      v
     |   Narrow repair + revalidate
     |
     +--> STRUCTURAL OR AMBIGUOUS ISSUE
            |
            v
       Bounded AI correction
```

Investigate safe deterministic repairs for narrowly defined, unambiguous problems.

For example, some accessibility metadata can be repaired when the intended label is already explicitly present.

Do not fabricate labels for ambiguous controls.

Do not blindly strip security-sensitive code.

Do not bypass `UNSAFE_EVENT_HANDLER` or other security validation.

Do not automatically accept malformed HTML just because it looks close enough.

AI correction should focus on the failed contract rather than needlessly rebuilding the entire page.

## 6. Review Concurrent Generation

Current configuration includes:

```
STUDIO_FRAME_CONCURRENCY = 3
```

Verify this remains true in the latest branch.

Do not increase concurrency to 5, 10, or 20 without measuring provider quotas and contention.

Investigate:

- Whether three requests really overlap.
- Whether provider-side queuing serializes requests.
- Whether one slow frame blocks other ready frames from being persisted.
- Whether a failed frame delays project completion unnecessarily.
- Whether a correction monopolizes job resources.
- Whether operations for separate projects contend unexpectedly.
- Whether model selection is appropriate for planning vs HTML generation.

Persist and expose each completed frame independently.

Do not make frame A wait for frame C before displaying its result.

## 7. Define Performance Goals

Optimize these separately:

```
TIME TO FIRST FRAME
TIME TO EACH SUBSEQUENT FRAME
TIME TO ALL FRAMES
TIME TO VISIBLE PREVIEW
```

Target a substantial reduction from the current multi-minute baseline.

For common cases, work toward first useful output within approximately one minute, while reporting measured limitations honestly.

Do not promise every five-screen project will finish under one minute regardless of model, provider, or complexity.

Use configurable time budgets and controlled quality trade-offs rather than hiding latency.
