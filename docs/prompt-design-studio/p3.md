# TASK 03 — VibeDesign Studio: Design Skill Fidelity Audit, Real AI Integration &amp; Output Quality Improvements

## Mission

Repository: `ghazyAlghifari508/everythings-vibe`

Target branch: `feature/vibedesign-design-studio`

Audit and improve the actual implementation of VibeDesign Studio's selectable design skills.

The user reports that generated screens still contain poor visual hierarchy, inconsistent design decisions, and generic layouts even after selecting a specialist design skill.

The requirement is NOT to make the dropdown look functional.

The requirement is to ensure each selectable skill provides genuine, identifiable, source-grounded design guidance to the AI generation system and materially influences the appropriate design decisions.

**Important distinction:** Do not confuse successfully injecting a short text snippet with executing every capability of the original external agent skill.

Be precise about what the current Studio architecture can and cannot support.

### Previously observed implementation

The current system has a server-side skill registry and a function similar to:

`studioSkillSystemGuidance(skillId)`

Guidance is appended to AI system instructions during planning and HTML generation.

The existing registry currently contains abridged, curated guidance rather than the full original skill implementations.

This is evidence that the feature is not merely decorative, but it does not prove complete integration or quality improvement.

Reverify against current HEAD.

## 3. Build a Skill Fidelity Matrix

Before implementation, create an evidence-based audit table.

Example:


| Skill           | Current implementation    | Actual upstream capability | Missing integration |
| --------------- | ------------------------- | -------------------------- | ------------------- |
| Impeccable      | Short craft guidance      | Verify upstream            | Identify            |
| Frontend Design | Visual principles         | Verify upstream            | Identify            |
| UI UX Pro Max   | UX/accessibility summary  | Verify data/tools          | Identify            |
| Anti-Slop       | Anti-generic guidance     | Verify modules             | Identify            |
| Taste           | Typography/layout summary | Verify skill               | Identify            |


Do not fill this table from assumptions.

Separate three levels:

1. **Connected:** Skill ID reaches the AI request.
2. **Faithful:** Relevant, versioned skill guidance reflects its real source.
3. **Effective:** Its intended design decisions are observable in output.

These levels must not be treated as equivalent.

### Skill adapter quality

For each skill:

- Use source-grounded instructions.
- Preserve distinctive design principles.
- Avoid reducing every skill to the same generic advice.
- Keep guidance relevant to the actual project domain and platform.
- Avoid irrelevant landing-page rules on application dashboards.
- Avoid excessive prompt bloat and contradictions.
- Record meaningful source revision/version metadata.
- Respect licenses and attribution.

Do not blindly paste an entire upstream README or repository into the model's system prompt.

Where structured datasets genuinely benefit output, assess whether the current runtime can support a safe lookup/selection step.

Do not claim to run a searchable dataset if no lookup occurs.

If a feature requires a coding-agent tool that Studio cannot execute, either implement a compatible safe adapter or document the limitation.

Do not silently call the entire external skill "installed and executed" when only a short guidance summary is used.

## 5. Ensure Skill Guidance Reaches Every Relevant AI Path

Verify integration into:

- Initial planning.
- Shared design blueprint creation.
- Initial per-frame generation.
- Adding a new frame.
- Revising selected frames.
- Project-wide revisions.
- Targeted retry.
- Reopening an existing project.

The selected skill must remain tied to the correct persisted project.

Changing a skill should update subsequent generation behavior without silently rewriting existing finished frames.

The user's explicitly selected design system must remain authoritative.

### Instruction precedence

Preserve a deterministic hierarchy:

1. Security/output contracts and platform constraints.
2. Explicit user requirements.
3. Verified selected design reference / [DESIGN.md](http://DESIGN.md).
4. Shared project blueprint.
5. Selected design skill.
6. Generic defaults.

A skill must not override explicit brand colors, requested functionality, or selected project requirements.

A design skill also must not be allowed to inject executable instructions into untrusted HTML.

## 6. Validate Differences Between Skills

Build meaningful deterministic tests for skill guidance.

Do not test merely that the strings "Impeccable" and "Taste" appear in a prompt.

Test that:

- No Skill contributes no extra user-selected skill guidance.
- Each skill resolves to distinct, nonempty relevant instructions.
- Unsupported skill IDs are rejected.
- Correct versions are reported.
- Prompt assembly includes the selected guidance in planning and frame generation.
- Revision routes use the project's current skill.
- Design reference priority is not overridden.
- External guidance remains inside the intended trust boundary.

### Design-quality evaluation

Where an appropriate generation/test environment is available, evaluate multiple skills against the same controlled project brief.

Suggested evaluation dimensions:

- Visual hierarchy.
- Typography.
- Product specificity.
- Color consistency.
- Component consistency.
- Navigation consistency.
- Mobile layout discipline.
- Accessibility.
- Absence of decorative AI-slop patterns.

Record actual observations and methods.

Do not invent scores or claim one skill performs best without controlled evidence.

Do not require live provider generation if credentials, quotas, or environment access are unavailable. In that case, implement the deterministic evaluation harness and report the unexecuted live evaluation separately.

Do not use browser QA or screenshot-based manual comparisons.

## 7. Design Blueprint Compatibility

Review how skill guidance influences the existing shared project blueprint.

A selected skill should guide design decisions without creating independently conflicting visual systems for each frame.

Example:

```
One Project
  ├── Selected skill: Impeccable
  ├── Design tokens: shared
  ├── Typography: shared
  ├── Navigation: shared
  ├── Component geometry: shared
  │
  ├── Frame 1: follows contract
  ├── Frame 2: follows contract
  └── Frame 3: follows contract
```

Different skills may change design direction, but the same project must still follow one coherent blueprint.

Do not let each frame reinterpret the design skill independently without its shared specification.

## 8. Avoid Superficial Integration

Forbidden shortcuts:

- Changing only skill dropdown descriptions.
- Adding a skill label to the prompt and claiming success.
- Injecting generic "make beautiful UI" instructions.
- Blindly copying massive repositories into a prompt.
- Executing untrusted third-party scripts.
- Enabling external dynamic instructions on every request without version pinning.
- Inventing skill features not present upstream.
- Ignoring token budgets and instruction conflicts.
- Hardcoding coffee-shop or finance-project examples into production guidance.

Improve the actual implementation contract.

### UI component rule

If UI components need to be changed, first explore existing primitives and appropriate components from shadcn, HeroUI, Magic UI, React Bits, and Thinking Orbs.

Reuse fitting production-ready components.

This task is primarily a backend/AI integration audit; do not add unrelated UI merely to consume a library.
