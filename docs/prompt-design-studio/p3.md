# PROMPT 03 — Eliminate Known Studio Generation and Preview Failure Paths

**Complexity: COMPLEX**  
**Execution order: 03 of 13**

## Objective

Repair recurring VibeDesign failures where:

- AI-generated HTML is rejected.
- A frame remains unavailable even when other frames succeed.
- Canvas shows "Pratinjau belum tersedia" or "Halaman belum berhasil dimuat".
- Planning or generation is incorrectly shown as failed while work continues.
- Retry performs the wrong action or needlessly regenerates valid HTML.

User expects failures to be rare, clearly classified, and recoverable without destroying completed results.

Never promise zero possible errors. Eliminate confirmed causes, add regression coverage, and make unavoidable failures recoverable.

Earlier logs include:

```
UNSAFE_EVENT_HANDLER
STUDIO_CONTRACT_VIOLATION
INVALID_OUTPUT
```

These codes must be traced to the real validator and correction path. Do not assume every failed preview is an AI output failure.

## 2. Separate failure ownership

Implement or refine an error taxonomy that clearly separates:

A. Planning failure.

B. Provider/network/model failure.

C. HTML contract/validation failure.

D. HTML persistence failure.

E. Screenshot capture failure.

F. Preview asset delivery failure.

G. Browser image load/decode failure.

H. Queue/retry/lease interruption.

Each category should own an appropriate retry action and diagnostic code.

Never use one generic "Generate again" button for every failure.

## 3. Repair recoverable HTML violations safely

Investigate whether known defects can be corrected deterministically without another full LLM invocation.

Examples:

- Unsupported inline event handlers.
- Invalid or redundant attributes.
- Duplicated canonical styles.
- Known structural wrappers.
- Safe normalization of narrowly defined markup.

Do NOT remove security rules or blindly strip arbitrary HTML without analyzing semantics.

A deterministic repair must be:

- Scoped to a known violation.
- Predictable and idempotent.
- Followed by full validation.
- Covered by positive and negative tests.
- Rejected if it would alter essential content unexpectedly.

When deterministic repair is insufficient, use the existing bounded AI correction mechanism.

The previous latency work already reduced duplicate prompt context and bounded retries; do not regress it.

Never turn every aesthetic warning into an LLM retry.

## 4. Independent preview recovery

A valid persisted HTML frame must remain valid even when screenshot capture fails.

Target:

```
VALID FRAME HTML
       |
       +---- HTML remains READY and downloadable
       |
       v
Preview capture
       |
       +---- success -> image asset -> canvas
       |
       +---- failed  -> retry capture ONLY
                              |
                              v
                          image asset
```

If the image URL exists but loading fails, investigate asset authentication, HTTP response, cache, content type, size, and image decode.

A preview retry must not regenerate HTML or charge for a new AI generation.

If HTML is ready but preview is temporarily unavailable, show an accurate state and provide the appropriate recovery path.

Do not use infinite image retries or tight polling loops.

## 5. Prevent false failures

Planning failure must require actual failure evidence, not merely a null blueprint or empty HTML during ongoing work.

Check job/frame status, polling reconciliation, delayed updates, and stale responses.

Specifically verify that a running initial job cannot display a confirmed planning failure solely because provisional frames exist.

Preserve ready frames while other frames are pending or failed.

## 6. Honest error messages

Use copy that identifies what happened and what action is available.

Examples:

**HTML generation failed:**

"Halaman ini belum berhasil dibuat."

Action: "Coba buat ulang".

**HTML ready, preview unavailable:**

"Desain sudah dibuat, tetapi pratinjau belum dapat ditampilkan."

Action: "Muat ulang pratinjau".

**Initial job queued:**

Use real waiting status. Do not show an error.

**No recoverable action:**

Display useful guidance rather than a retry button that is guaranteed to be rejected.

Do not display raw provider payloads, stack traces, or internal job IDs in user-facing messages.

## 7. Preserve safety and existing architecture

- Do not weaken HTML sanitization or iframe isolation.
- Do not enable arbitrary generated JavaScript to bypass the existing contract.
- Keep security validation before persistence/public rendering.
- Keep deterministic retry limits and credit accounting.
- Keep frame-specific recovery isolated from unrelated frames.
- Never reset all screens because one screenshot failed.
- Preserve existing export and revision history.

## 8. Targeted regression tests

Cover:

- Invalid inline event handler that is safely repairable.
- Invalid handler that cannot be safely repaired.
- Valid output after one correction.
- Correction exhaustion with proper error.
- Ready HTML + capture failure.
- Ready HTML + asset load failure.
- Retry capture without new model call.
- Existing image asset cache hit.
- Partial frame success.
- Worker interruption while capture is pending.
- False planning error regression.
- Concurrent retry submissions.
- No duplicated credit deduction.
- User-facing error mapping for each category.

Use non-browser targeted tests for this task.

Do not run browser QA, Playwright E2E, or visual regression in this phase. Browser verification will occur only in the final QA phase.
