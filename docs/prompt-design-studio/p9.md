# P9 — Implement Contextual Frame Toolbar With Device Switching, Focus, Preview, and Refresh

**Complexity: COMPLEX**  
**Execution order: 09/11**

## 1. Objective

Add a contextual toolbar that appears alongside a selected frame in VibeDesign Studio.

This toolbar must contain six icon-only actions:

1. Desktop.
2. Tablet.
3. Mobile.
4. Focus.
5. Preview.
6. Refresh.

Reference interaction: a design canvas where selecting a frame reveals relevant presentation controls near that frame.

The user does not want permanent text labels or a large floating settings panel.

## 2. Inspect existing architecture

Read:

- `studio-frame.tsx`
- `studio-canvas.tsx`
- `studio-canvas-controls.tsx`
- `use-studio-canvas-view.ts`
- Existing canvas zoom/pan implementation.
- Frame selection state.
- Shared responsive renderer implemented in P6.
- Chat attachments and element selection behavior.

Reuse existing camera transforms, frame identity, and renderer contracts.

Do not implement a new canvas engine.

## 4. Toolbar behavior

The contextual toolbar appears when exactly one ready frame is selected.

For multiple selected frames, do not show several overlapping floating toolbars.

Hide or disable contextually unsupported actions while a frame is unavailable.

The toolbar must:

- Follow the frame position during canvas pan and zoom.
- Maintain a usable screen-space button size.
- Avoid scaling controls into tiny unreadable icons.
- Avoid overlap with the floating chat panel.
- Avoid covering important frame content.
- Reposition when approaching viewport boundaries.
- Remain accessible by keyboard.
- Provide tooltips for every icon.
- Communicate the selected device clearly.

Use concise state styling, not decorative colored badges.

## 5. Device switching

Desktop, Tablet, and Mobile must change the actual viewport of the existing HTML frame.

Suggested initial presets:

```
Desktop: 1440 × 900
Tablet:   768 × 1024
Mobile:   390 × 844
```

Finalize consistent viewport presets using the P6 renderer contract.

Behavior:

```
Click Mobile
      |
      v
Existing renderer viewport changes to mobile width
      |
      v
CSS responsive rules reflow content
      |
      v
Frame bounds update
```

STRICTLY FORBIDDEN:

```
Click Mobile
      |
      v
Create generation job
      |
      v
Show shimmer
      |
      v
Ask AI to regenerate
```

Viewport switching must not:

- Call an LLM.
- Deduct credits.
- Create a generation job.
- Create an HTML design revision.
- Replace or delete the existing frame.
- Display a generation shimmer.
- Stretch a JPEG image as fake responsive behavior.
- Lose the current project design reference.

For a ready live renderer, the size change should be immediate.

Ensure the relevant live surface is prepared before exposing device controls that require it.

If a legacy frame is not sufficiently responsive, do not quietly regenerate it. Preserve the existing HTML and report the actual responsive limitation through appropriate behavior.

## 6. Canvas layout after resize

When a frame changes width or presentation size:

- Recalculate artboard bounds.
- Preserve the same frame ID.
- Preserve current selection.
- Prevent overlap with sibling artboards.
- Avoid unexpected large camera jumps.
- Preserve selected viewport preference during the relevant workspace session.

Persist viewport preference only where appropriate as presentation metadata, not as a modification of generated HTML.

## 7. Focus action

When the user clicks Focus, move the canvas camera to the selected frame.

Example:

```
BEFORE:

[Frame 1] [Frame 2] [Frame 3] [Frame 4]

Canvas zoom: 35%
```

```
AFTER:

          +-------------------------+
          |        Frame 2          |
          |                         |
          |        Focused          |
          +-------------------------+
```

Use the existing canvas transforms to implement a `fitFrame(frameId)` capability or equivalent.

Account for:

- Actual viewport size.
- Floating chat panel.
- Workspace header.
- Context toolbar.
- Zoom controls.
- Frame dimensions.
- Current device preset.

Use a smooth camera transition.

For a very tall mobile screen, prioritize a readable width and useful top alignment rather than zooming so far out that the entire screen becomes unreadable.

Respect reduced-motion preferences.

Do not change the actual HTML or frame dimensions when focusing.

## 8. Preview action

Preview must open the separate prototype viewer implemented in P10.

It must not open another canvas or simply enlarge a static screenshot.

Pass:

- Authorized project ID.
- Selected frame ID or route.
- Current device viewport.
- Appropriate return context.

Do not introduce a temporary fake preview modal that will later need to be discarded.

If P10 is not yet implemented, prepare the real integration contract and keep the unavailable action honest. Do not claim navigation works until the route exists.

## 9. Refresh action

Refresh means render ulang HTML yang sudah tersedia.

```
Click Refresh
     |
     v
Resolve latest committed HTML revision
     |
     v
Refresh renderer and appropriate asset state
     |
     v
Display same design
```

Refresh must not:

- Request AI generation.
- Modify the design.
- Deduct credits.
- Create an unnecessary design revision.
- Reload the entire workspace.
- Reset unrelated frames.
- Clear the user's chat draft.

Keep the last successful visual visible until replacement content becomes available where practical.

Do not show regeneration shimmer.

If the current frame is up-to-date and no renderer refresh is required, use the appropriate lightweight reload/invalidation behavior.

## 10. Interaction conflicts

Handle correctly:

- Multi-select.
- Pencil mode.
- Active element menu.
- Frame drag.
- Canvas pan.
- Pending AI revision.
- Frame deletion.
- Changing device while a revision is finishing.

Do not accidentally trigger frame selections, chat submissions, or camera movement when interacting with toolbar buttons.
