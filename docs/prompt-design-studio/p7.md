## 1. Mission

Improve the visual consistency and overall quality of AI-generated UI frames in VibeDesign Studio.

The user expects the system to generate multiple screens that look like they belong to the SAME professionally designed application.

Currently, individual screens may be visually attractive in isolation, but their shared components and overall layouts can be inconsistent.

Observed problems:

1. Bottom navigation differs between frames.
2. Active navigation icons unexpectedly change size, shape, or decoration.
3. Some mobile screens include a simulated system clock/status bar, while others do not.
4. Header structure changes between screens without product justification.
5. Floating components appear in inappropriate locations.
6. Inconsistent spacing, padding, and alignment.
7. Some elements extend beyond the visible viewport.
8. Unnecessary visual artifacts appear, such as `|` after currency values.
9. Input controls and cards may have inconsistent proportions.
10. Some generated screens feel generic, messy, or overdecorated.
11. Cross-frame design differences undermine the experience of using Studio as an application design tool.

**Your goal is to implement genuine shared design-system enforcement.**

Do not attempt to solve every problem by adding more generic adjectives to AI prompts.

## 2. Critical Principle

The current architecture generates standalone HTML for individual frames.

A shared blueprint already exists, but many of its component specifications are natural-language strings.

Example:

```
sharedComponents: z.object({
  header: z.string(),
  navigation: z.string(),
  buttons: z.string(),
  inputs: z.string(),
  cards: z.string(),
  tabs: z.string(),
  icons: z.string(),
})
```

This is useful guidance, but it does not guarantee identical component geometry or markup.

Different model calls may still interpret the same instruction differently.

**Shared UI structure should be deterministic wherever practical. Screen-specific content should remain AI-generated and creative within validated constraints.**

Do not claim a purely probabilistic model can guarantee 100% aesthetic quality.

## 7. Component-First Requirement for GENERATED UI

The user strongly rejects generic AI-generated UI from scratch.

Research and explore production-ready design components/patterns from:

- [https://ui.shadcn.com/](https://ui.shadcn.com/)
- [https://www.heroui.com/](https://www.heroui.com/)
- [https://magicui.design/](https://magicui.design/)
- [https://reactbits.dev/](https://reactbits.dev/)
- [https://www.thinkingorbs.com/#orbs](https://www.thinkingorbs.com/#orbs)

Also inspect existing UI component packages and reusable assets already present in the repository.

### Mandatory workflow

1. Identify components appropriate to the product category and screen purpose.
2. Inspect their actual implementation and requirements.
3. Check whether they support the target output environment.
4. Reuse compatible components, implementations, patterns, or approved templates.
5. Only create a genuinely custom component when no suitable existing one meets the requirement.
6. Preserve licensing and provenance where applicable.
7. Keep visual quality high, even for custom fallback components.

### Important runtime compatibility constraint

Studio currently produces standalone HTML documents.

Some libraries, including shadcn/ui and HeroUI, primarily provide React components.

Do not simply place a React import statement inside standalone generated HTML and pretend it will work.

Instead:

- Reuse existing components directly where the rendering architecture supports them.
- Use approved static HTML/Tailwind equivalents or safely rendered shared fragments where appropriate.
- Reuse verified component patterns where direct React execution is not supported.
- Keep generated HTML self-contained and valid under Studio's actual renderer.
- Do not inject arbitrary third-party scripts into generated frames.
- Do not copy proprietary assets without appropriate rights.

**Component reuse must be real and technically compatible, not a decorative claim in the final report.**

## 9. Mobile System Status Bar Policy

Observed inconsistency:

```
FRAME A                  FRAME B

┌─────────────────┐      ┌─────────────────┐
│ 09:41     WiFi  │      │                 │
│                 │      │ App Header      │
│ App Header      │      │                 │
│                 │      │                 │
└─────────────────┘      └─────────────────┘
```

The Studio pipeline must decide whether device chrome belongs to the generated frame.

### Supported approaches

**Option A: Simulated status bar across all applicable mobile frames.**

Use one canonical shared status bar.

**Option B: No simulated status bar inside generated application HTML.**

Allow the canvas/device preview layer to represent device context separately if appropriate.

Choose the policy based on Studio's established platform design contract and rendering strategy.

Do not arbitrarily mix both approaches within a single project.

If a status bar is used, unify:

- Clock appearance.
- Clock position.
- Signal/WiFi/battery icon style.
- Height.
- Padding.
- Background.
- Foreground contrast.
- Safe-area behavior.

Do not hardcode inconsistent fake operating-system chrome independently in each frame.

## 10. Eliminate Unwanted Text and Caret Artifacts

The user reported a strange `|` after currency values, such as:

```
Rp 44.000|
```

Possible causes:

- Generated literal pipe character.
- Text cursor from a focused input.
- CSS pseudo-element.
- Decorative blinking cursor animation.
- Capture-time focus state.

**Investigate actual generated HTML before claiming the cause.**

Requirements:

- Avoid unrelated literal separators after amounts.
- Avoid unnecessary typing cursors in static presentation states.
- Prevent accidental `autofocus` from affecting preview capture unless the screen intentionally demonstrates focus.
- Avoid CSS animations that make static screenshots contain unintended artifacts.
- Preserve legitimate editable fields and intended focus interactions.
- Do not globally remove carets from functional inputs.

The system must distinguish an unintended visual artifact from a valid interactive control.

### Example

Wrong:

```
JUMLAH YANG DIKELUARKAN

Rp 44.000 |
```

Correct default presentation:

```
JUMLAH YANG DIKELUARKAN

Rp 44.000
```

If the product genuinely uses a numeric entry screen, an interactive input is allowed. However, the initial preview must not display accidental focus artifacts.

## 11. Avoid Floating and Misplaced Components

Generated UI should not contain arbitrary floating elements without a clear interaction purpose.

Examples of anti-patterns:

- Floating buttons that obscure content.
- Sticky controls overlapping bottom navigation.
- Icons positioned outside their parent card.
- Unnecessary fixed-position decorations.
- Giant action buttons with no clear hierarchy.
- Random floating badges.
- Misaligned status elements.
- Modal-like cards on ordinary screens without reason.

### Target

```
┌──────────────────────────────┐
│ App Header                   │
├──────────────────────────────┤
│                              │
│ Main Content                 │
│                              │
│ [Card]                       │
│ [Card]                       │
│ [Form]                       │
│                              │
├──────────────────────────────┤
│ Canonical Bottom Navigation  │
└──────────────────────────────┘
```

Do not force every application into this exact layout.

Use its spatial principles:

- Clear hierarchy.
- Bounded containers.
- Predictable navigation.
- Consistent alignment.
- No overlapping fixed/sticky elements.
- Correct content scrolling.

For web dashboards, use the appropriate desktop layout contract instead of a mobile bottom navigation.

Repair the specified violations.

Preserve valid screen content, product identity,

## 14. Preserve Visual Creativity

A design system must produce consistency, not sameness across unrelated products.

Two different projects should still look different.

Example:

```
PROJECT A: FINANCE

- Precise dashboard layout
- Dense but readable information
- Consistent financial typography
- Relevant data visualization
- Appropriate navigation


PROJECT B: TRAVEL

- Rich destination imagery
- Discovery-oriented layout
- Clear booking calls to action
- Appropriate search/filter patterns
- Different visual tone
```

Within each project, shared components must remain consistent.

Across unrelated projects, the AI should adapt its design to actual product requirements.

Do not make every generated application look like the same shadcn demo dashboard.

Do not allow unrelated design skills to overwrite an explicit [DESIGN.md](http://DESIGN.md) brand identity.
