## 1. Mission

Address the remaining quality problems in VibeDesign's AI-generated websites and mobile applications.

The user reports:

- Generic mobile app bars containing only text such as "Profil", "Tiket Saya", and "Detail Paket".
- Repetitive websites and mobile layouts.
- Excessive generic cards containing only headings and paragraphs.
- Weak or purposeless navigation.
- Unclear search and discovery flows.
- Missing or poorly justified destinations.
- Weak visual storytelling.
- Unclear relationships between screens.
- Artificial-looking SVG/CSS images replacing expected real photography.
- Incorrect or incoherent product data.
- Generated UI that looks structurally valid but is not genuinely useful.

Do not implement a fixed template system in response to these complaints.

The goal is to improve the AI's product reasoning and output, not force every app into the same visual formula.

## 2. Critical design philosophy

### Keep deterministic boundaries for:

- Safety.
- Valid HTML.
- Authorization.
- Consistent project identity.
- Valid navigation targets.
- Required project constraints.
- Stable screen identifiers.
- Reliable media references.
- Objective structural defects.
- Revision preservation.

### Let the AI decide:

- Visual composition.
- Navigation presentation.
- Appropriate header contents.
- Number and type of sections.
- Hero arrangement.
- Information hierarchy.
- Whether cards are needed.
- Whether a sidebar or bottom navigation is justified.
- Image layout and density.
- Whether a separate Home destination is useful.
- Whether a separate search destination is useful.

Do NOT create rules such as:

```
All mobile apps must have Home.
All Detail pages must have a back-arrow title bar.
All websites must have a hero.
All portfolios must have a project-card grid.
All travel websites must show a huge photo.
All dashboards must use KPI cards.
All app headers must contain exactly two actions.
```

These are not universally valid design rules.

Design decisions must be grounded in product goals and user journeys.

## 6. Product-specific mobile navigation

The user asked why Jelajahin has no Home/Beranda destination and what the search control is for.

Do not interpret that as a universal requirement for all mobile applications.

Mobile design should have a coherent information architecture.

### Example 1 — Discovery is the entry point

```
Jelajahin
    |
    +-- Jelajah
    +-- Tiket
    +-- Profil

Jelajah -> Detail Paket -> Pemesanan -> Confirmation
```

Here, "Jelajah" can function as the primary starting destination.

A separate "Beranda" may be redundant.

### Example 2 — Home and search serve different tasks

```
Jelajahin
    |
    +-- Beranda
    +-- Cari
    +-- Tiket
    +-- Profil

Beranda -> Recommendations
Cari    -> Destination/package search
```

Here, a separate Home can be justified.

Neither structure is universally mandatory.

The planner must determine which information architecture serves the requested product.

### Navigation requirements

- Every presented navigation action must have a clear purpose.
- Top-level destinations should not be confused with nested screens.
- Detail screens should have an understandable way to return.
- Back actions should match actual screen hierarchy.
- Search controls should lead to real search functionality or an honest prototype state.
- Tabs should reflect real sections, not arbitrary labels.
- Destination identifiers should be valid and consistent across frames.
- Mobile top bars should be contextual, not mechanically identical.
- Bottom navigation should be used only when justified by actual destinations.

Do not solve generic app bars by enforcing a different universal app bar.

## 7. Improve UI composition reasoning

The current output often uses repeated bordered cards for unrelated content.

Examples of weak output:

```
Generic Header

+----------------------+
| Title                |
| Paragraph            |
+----------------------+

+----------------------+
| Title                |
| Paragraph            |
+----------------------+

+----------------------+
| Title                |
| Paragraph            |
+----------------------+
```

The issue is not that cards exist.

The issue is that the layout fails to express content priority or product purpose.

Consider more appropriate structures where relevant:

- Editorial reading sections.
- Image-led content.
- Filterable collections.
- Rich product details.
- Split list/detail layouts.
- Real forms.
- Data tables.
- Comparison views.
- Timelines.
- Maps.
- Galleries.
- Compact settings rows.
- Purposeful controls.

These are possible design patterns, not mandatory templates.

The AI must choose based on user tasks.

Do not add an unconditional component quota.

Do not hardcode "at least one gallery", "no more than three cards", or similar arbitrary rules.

Keep the existing narrow card-wall validator as an objective heuristic where justified.

Do not treat it as a complete visual quality evaluator.

## 8. Ensure content supports actual user tasks

A frame is not useful solely because it has a navbar and attractive typography.

Use product-specific reasoning.

For a travel application:

- Can users discover destinations?
- Can they compare a package?
- Can they understand dates, duration, and price?
- Can they proceed to booking?
- Can they find their tickets?
- Are profile details related to booking where appropriate?
- Are status labels consistent?
- Are buttons meaningful?

For a publisher payout workspace:

- Are statuses clear?
- Can the operator understand what needs manual action?
- Does the design distinguish mock UI from real money transfer?
- Are validation and rejection states represented accurately?
- Does it avoid claiming actual bank execution?

For a developer portfolio:

- Are actual works/projects prioritized?
- Does the design represent the creator rather than a generic admin dashboard?
- Are links and contact actions appropriate?

Do not invent metrics, verified reviews, transactions, or official account information merely to fill empty sections.

Use clearly labeled sample data when operating in a prototype context.

Ensure dates, labels, currency, and workflow states are internally consistent.

Example issue to investigate from the user's screenshot:

- A travel flow presents references to 2025 and 2026 within related booking/ticket content.

Avoid inconsistent fake data across connected screens.

- Planner did not request a photo.
- Photo request was not appropriate.

- Asset exists but did not render in the isolated iframe.
- Image was cropped or styled incorrectly.

Record actual evidence.

## 10. Image-source policy

The user approves relevant legal image sources such as:

- Openverse.
- Pexels.
- Unsplash.

Use approved sources according to availability and current usage terms.

Verify actual provider licensing, API requirements, attribution, hotlinking, download tracking, caching and redistribution obligations before adopting a new source.

Do not simply scrape random image URLs.

Do not fabricate URLs.

Do not expose provider credentials.

Do not treat all online images as freely reusable.

Maintain:

- Relevance.
- Appropriate image size.
- Provider timeouts.
- Safe fetching.
- SSRF protection.
- MIME checks.
- Asset size limits.
- Attribution metadata where required.
- Valid export behavior.
- Caching permitted by provider terms.

User-provided imagery should remain usable.

## 11. No fake photographic substitutes

For image-led travel content, a geometric SVG sunset must not be presented as a real Uluwatu photograph.

If the design requires actual photography:

- Resolve genuine approved photography when available.
- Place the actual image into the intended layout.
- Preserve correct aspect ratio and cropping.
- Avoid model-invented image URLs.
- Report unavailable assets truthfully.

Do not fake success by generating CSS scenery.

SVG remains appropriate for:

- Icons.
- Genuine illustrative graphics.
- Logos.
- Diagrams.
- Charts.
- Explicitly requested illustration styles.

Do not make photography mandatory for every product or screen.
