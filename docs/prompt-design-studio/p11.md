# P11 FIX 04 — Replace Generic Conversation Templates With Meaningful Design Explanations and Rich Frame Results

**Complexity: VERY COMPLEX**  
**Execution order: 4 of 6 P11 fixes**  
**Prerequisites: P11 Fix 01–03**  
**Followed by: P11 Fix 05**

## 1. Mission

Improve VibeDesign Studio's AI conversation so that it behaves like a genuinely useful design assistant rather than a job-status reporting interface.

The user reports repetitive, generic, short responses such as:

- "Rencana layar: Profil."
- "Rencana layar: Jelajah."
- "4 halaman selesai diproses."
- "Revisi diterapkan."

The result component also shows only:

```
1 halaman dibuat
Profil
```

This is insufficient to help users understand what was designed.

The required outcome is:

- Contextually meaningful design explanations.
- Correct and readable Markdown.
- Honest reporting of actual implementation.
- Rich frame result summaries with real previews.
- Navigation from result summaries to the corresponding canvas frames.
- Clear separation between job status and assistant explanation.

Do not solve this by hardcoding a longer generic essay.

## 3. Distinguish three conversation layers

A design assistant needs three distinct layers.

### A. Operational status

Examples:

```
Preparing design
Generating 3 of 4 frames
One frame needs retry
```

These should remain short, accurate, and derived from actual jobs.

They are not the main assistant explanation.

### B. Design explanation

Explain what was created and why the composition serves the requested user flow.

This requires grounded information from:

- User request.
- PRD / [DESIGN.md](http://DESIGN.md).
- Approved blueprint.
- Screen plan.
- Implemented screen relationships.
- Actual committed HTML and available verified metadata.

### C. Result presentation

Show the actual created frames, their identity and preview, and how to open them.

Do not collapse all three into one template such as "4 halaman dibuat."

## 4. Desired assistant response quality

Use the user's example from Google Stitch as a reference for explanation richness and readable hierarchy.

However, do not copy its claims.

The assistant response should adapt its depth to the complexity of the request.

### Simple request

User:

"Tambahkan layar Profil."

A suitable response would summarize:

- New screen and its purpose.
- Important actual UI areas implemented.
- Its relationship to existing navigation.
- Relevant next-step limitations.

It should not output ten paragraphs of unrelated generic design advice.

### Complex request

User requests a publisher payout operations workspace.

A suitable response may explain:

- Operational context.
- The requested payout workflow.
- Status organization.
- List/detail structure.
- Bank details and validation areas.
- Proof-of-transfer interaction.
- Rejection state.
- Desktop/mobile adaptation.
- Mock prototype limitations.
- What was actually generated and what was not.

Only include claims grounded in the generated result and accepted requirements.

## 5. Never fabricate research or implementation success

The user's sample Stitch response mentions Stripe, Wise, Zoho Books, published interfaces, official banking records, and end-to-end integrations.

These are examples of presentation richness, NOT permission to invent facts.

Do not claim:

- Industry research was performed if it was not.
- External competitors were consulted without evidence.
- A website was published if it was not.
- Payment integration is complete when only a mock UI exists.
- Bank transfers were executed by the prototype.
- Emails were sent.
- Authentication or database writes work in a frontend-only prototype.
- A generated screen contains controls not actually present.
- Every requested scenario is implemented when some are missing.

Prefer accurate, specific descriptions over impressive-sounding unsupported claims.

## 6. Architecture for grounded explanations

Preferred workflow:

```
User request
    |
    v
Existing planning/model output
    |
    +--> Structured screen rationale
    +--> Intended user flow
    +--> Significant decisions
    |
    v
Actual validated frame generation
    |
    v
Grounded design summary
    |
    v
Markdown assistant message
    +
Real frame result component
```

Reuse design rationale already produced by the existing planning and generation process.

Where necessary, extend the existing planning schema to return a bounded, useful design rationale, provided this does not destabilize planning or inflate the request unreasonably.

Do not add a second autonomous design agent.

Do not create one extra LLM request for every status update or frame completion.

Avoid new model calls where existing validated planning and frame data are sufficient.

If a genuinely optional narrative generation call is needed for complex requests, isolate and measure it separately, make it bounded, and ensure it cannot block first-frame readiness or fabricate evidence. Prefer no extra call on the normal path.

## 7. Response content guidelines

Design assistant messages should:

- Address the actual user's requested task.
- Name the real product/screens.
- Explain important navigation relationships.
- Explain the purpose of major UI areas.
- Distinguish generated UI from backend functionality.
- Mention actual constraints when relevant.
- Reference meaningful changes when revising.
- Avoid generic filler.
- Avoid repetitive grandiose introductions.
- Use Markdown headings and lists when warranted.
- Remain readable in a narrow chat panel.

Do not force every message into the same number of bullets or fixed headings.

Do not force a mandatory word count.

Do not hardcode one identical introduction for every domain.

Do not expose implementation internals such as database IDs, model retries, service names, or internal pipeline tags in ordinary assistant copy unless the user specifically requests technical details.

### Example structure — illustration only

```
**Layar Profil berhasil ditambahkan**

Layar ini difokuskan pada informasi wisatawan yang
digunakan dalam proses pemesanan.

**Bagian yang dibuat**
- Data pemesan dan kontak.
- Pengelolaan peserta.
- Akses informasi akun yang relevan.

**Hubungan antarlayar**
...
```

The exact sections and their claims must be derived from the real generated frame.

If a feature is not actually in the HTML, do not claim it exists.

## 8. Separate progress from conversation copy

Progress should remain visible but unobtrusive.

Bad:

```
Rencana layar: Profil. 1 halaman selesai diproses.
```

Better concept:

```
Assistant:
[Meaningful explanation of Profile design]

Result:
[Frame thumbnail + name + metadata]

Small status:
Completed
```

Do not produce repeated assistant paragraphs every time the worker changes from queued to generating to validating.

Persist stable messages appropriately.

Allow background progress updates without overwriting already-authored meaningful content with a shorter generic template.

Do not lose messages after workspace reopen.

Replace the current bare-name result list.

Desired composition:

```
┌──────────────────────────────────────────┐
│ 2 screens created                     ˄  │
├──────────────────────────────────────────┤
│ ┌─────────┐  Kelola Pencairan — Desktop  │
│ │ ACTUAL  │  Web UI                     │
│ │ THUMB   │  Open on canvas             │
│ └─────────┘                             │
│                                          │
│ ┌─────────┐  Kelola Pencairan — Mobile   │
│ │ ACTUAL  │  Mobile UI                  │
│ │ THUMB   │  Open on canvas             │
│ └─────────┘                             │
└──────────────────────────────────────────┘
```

Requirements:

- Show the actual result count.
- Use actual frame names or meaningful derived descriptions.
- Display a thumbnail derived from the real committed HTML.
- Clearly identify device/platform if useful.
- Allow click to select and focus the matching canvas frame.
- Correct project/frame ownership.
- Correct status for ready, failed, and pending frames.
- Collapse/expand behavior.
- Keyboard and screen-reader accessibility.
- Proper long-title truncation with accessible full title.
- Responsive to narrow chat width.

Do not use invented illustrative thumbnails in real result cards.

The main canvas remains HTML-first. A small thumbnail is acceptable as derived presentation data, but must never be used as the authoritative artboard.

If a preview asset is unavailable, show honest metadata rather than fake generated imagery.

Do not depend on screenshot capture to declare the generated HTML frame ready.

## 10. Product naming and terminology

Preserve the distinction between:

- Product name/brand.
- Project/workspace title.
- Screen/frame name.

Example:

```
Brand:
Jelajahin

Project title:
Jelajahin — Domestic Travel Booking App

Frame:
Profil
```

Do not show meaningless concatenations or duplicated project names.

Prefer copy such as "1 layar dibuat" or "2 layar dibuat" consistently in Indonesian, unless the surrounding product locale specifies another language.

Do not mechanically copy English from Google Stitch while the rest of EvVibe uses Indonesian.

## 11. Markdown and visual quality

Ensure safe rendering of:

- Paragraphs.
- Bulleted and numbered lists.
- Bold text.
- Headings with sensible hierarchy.
- Inline code.
- Links when appropriate.
- Longer messages with natural line wrapping.

Protect against unsafe HTML in model-produced Markdown.

Avoid giant headings, excessive separators, colored callouts, repeated badges, and narrow-column typography that becomes unreadable.

Support long messages without pushing the composer out of view.

Keep the existing collapsible user-message behavior and preserve original prompt text.

Do not replace real content with raw status logs.

## 12. Persistence and concurrency

Ensure:

- A queued message is not silently overwritten by unrelated frame progress.
- Add-screen operations attach the correct new result.
- Multiple submitted operations retain correct message-to-job association.
- Frame results do not duplicate after reload.
- Retry updates remain scoped to the correct operation.
- Revisions show truthful changed-frame results.
- Failed operations have honest failure status.
- Stale worker updates cannot replace a newer completed explanation.
- The user can continue writing while jobs run.
- No additional credit charge for simply displaying explanations.

Use existing job/message identifiers and persistence mechanisms.
