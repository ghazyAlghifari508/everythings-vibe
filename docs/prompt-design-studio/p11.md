# P11 — Final VibeDesign Acceptance, Real Browser QA, Design Diversity, and Performance Verification

**Complexity: VERY COMPLEX**  
**Execution order: FINAL — after P1.1 and P2–P10**  
**Replaces the previous P11**

## 1. Mission

Perform comprehensive end-to-end verification of VibeDesign Studio using its actual application, generation engine, worker, renderer, database, and browser interface.

The goal is not simply to obtain passing tests.

The goal is to establish that the product genuinely satisfies all user requirements and that previously reported problems have been resolved without introducing regressions.

Evaluate from the perspective of a real EvVibe user.

## 2. Non-negotiable testing integrity

Do not manipulate the application or test environment to fabricate successful outcomes.

STRICTLY FORBIDDEN:

- Manually setting database job status to completed.
- Manually setting frames to ready.
- Inserting generated HTML directly into the database to bypass generation.
- Changing timestamps to fake faster generation.
- Editing messages to simulate successful AI responses.
- Creating fake revisions to demonstrate Undo.
- Changing credit balances to hide billing defects.
- Deleting failed generation records to conceal failures.
- Using pre-generated screenshots as evidence of a new generation.
- Claiming mocked provider responses are real AI results.
- Hardcoding successful output to bypass a broken feature.
- Adding fake loading, success, or progress states.
- Hiding error components without fixing their cause.
- Weakening assertions merely to pass tests.
- Removing failing tests.
- Adding skips to avoid known regressions.
- Silently suppressing genuine exceptions.
- Ignoring newly discovered bugs.
- Cherry-picking successful model runs.
- Excluding failures from performance reports.
- Redefining performance metrics after seeing results.
- Claiming tests were executed when they were not.
- Reporting NOT VERIFIED functionality as PASS.

Normal migrations, documented isolated test fixtures, and legitimate unit-test mocks are allowed.

However, they cannot substitute for real end-to-end evidence.

Use normal application flows for acceptance scenarios.

Do not manually repair production or acceptance-test database state to get through a broken user journey.

## 7. Evaluate design diversity honestly

Compare unrelated generated projects.

Bad result:

```
Portfolio:
Navbar + generic hero + three text cards

Restaurant:
Same navbar + same hero + three text cards

E-commerce:
Same navbar + same hero + three text cards
```

Desired result:

```
Portfolio:
Composition justified by work and professional identity.

Restaurant:
Composition justified by food, atmosphere, and customer needs.

E-commerce:
Composition justified by discovery, comparison, and purchase.
```

Check:

- Information architecture.
- Section composition.
- Navigation hierarchy.
- Media treatment.
- Visual density.
- Primary action placement.
- Product-specific content priorities.

Do not consider different colors alone evidence of design diversity.

Also do not force every design to be visually different just to satisfy a comparison metric.

Two products may legitimately share common patterns.

The requirement is to avoid mechanically imposed template repetition while retaining coherent UI/UX.

Related screens inside one project should maintain consistent design identity.

## 9. Suite D — Performance and correction reliability

Measure Time to First Usable Frame.

```
t0  User submits prompt
t1  Request accepted
t2  Planning completed
t3  Frame HTML produced
t4  HTML validated and committed
t5  First complete usable frame visible
```

Mandatory target:

```
t5 - t0 < 60 seconds
```

The frame must be complete, valid, and visually usable.

Do not count:

- Skeleton.
- Shimmer.
- Partial HTML.
- Empty iframe.
- Unrelated cached frame.
- Invalid design.
- Database-ready status without a visible result.

Record:

- Queue wait.
- Planning TTFT and duration.
- Full model input characters.
- Actual input tokens where available.
- Output tokens.
- Cached input telemetry where available.
- Frame generation TTFT.
- Total generation duration.
- Image retrieval duration.
- Correction duration.
- Validation duration.
- Persistence duration.
- Preview/renderer visibility duration.
- First usable frame duration.
- All-frame completion duration.
- Request count.
- Failed attempts.

Compare against appropriate pre-P1.1 or existing equivalent baselines where feasible.

Keep model configuration, brief, workload, and test conditions comparable.

Record cold and warm/cache-hit results separately.

Do not claim caching occurred merely because the system prompt was identical.

If a valid before/after baseline cannot be established, report that limitation rather than inventing a performance improvement.

Report every run, including slow and failed results.

Do not claim statistical reliability from a tiny sample.
