# P11 — Comprehensive VibeDesign Browser QA, Regression Testing, and Final Product Acceptance

**Complexity: VERY COMPLEX**  
**Execution order: 11/11 — FINAL PHASE**

## 1. Mission

Perform comprehensive real-browser validation of VibeDesign Studio after P1–P10 have been implemented.

Evaluate the product as an actual user would use it.

The objective is not to make test reports look successful. The objective is to discover, reproduce, fix, and verify actual product defects.

Do not declare the implementation complete until the mandatory acceptance criteria are satisfied or remaining blockers are explicitly documented.

## 2. Mandatory testing integrity

THIS SECTION IS NON-NEGOTIABLE.

The coding agent must never manipulate the application or test results to fabricate successful outcomes.

Strictly forbidden:

- Manually inserting successful generation results into the database.
- Updating failed job records to completed.
- Manually setting frame status to ready.
- Inserting generated HTML directly into database records to bypass generation.
- Changing timestamps to fake latency improvements.
- Editing conversation records to fake successful AI responses.
- Manually inserting revisions to make Undo appear functional.
- Altering credit balances or billing records to hide bugs.
- Deleting failed jobs or records to hide evidence.
- Modifying existing valid designs solely to make comparison tests pass.
- Using mocked provider responses while claiming real AI generation succeeded.
- Using pre-generated screenshots while claiming a new frame was generated.
- Replacing failing runtime behavior with hardcoded demo results.
- Hiding error components with CSS without fixing the root cause.
- Marking a broken feature as passed because the UI contains a button.
- Weakening assertions.
- Deleting failing tests.
- Adding test skips to avoid known problems.
- Catching and suppressing genuine exceptions merely to obtain green tests.
- Ignoring console errors, network failures, or newly discovered bugs.
- Cherry-picking only successful generation runs.
- Changing the definition of latency after seeing results.
- Claiming tests were executed when they were not.

Normal migration execution and explicitly documented test fixtures are allowed in appropriate isolated test environments.

However, synthetic fixtures or mocked failures must never substitute for real end-to-end acceptance evidence.

Do not manually repair database records to get through the user journey.

If the test environment itself is broken, repair the legitimate application/setup issue or report the blocker.

## 4. Acceptance objectives

The final product must prove that:

1. Generated web and mobile designs are appropriate to their platforms.
2. The internal `evvibe-design` skill genuinely affects runtime generation.
3. Real, relevant image assets are used where photography is necessary.
4. The first complete usable frame appears within the target of less than 60 seconds.
5. Previously reported generation and preview failures are resolved or correctly recoverable.
6. The user can submit prompts, add screens, and revise designs through the AI workspace.
7. The floating chat panel is polished, contextual, and persistent.
8. Screen planning is adaptive.
9. Project naming is informative.
10. Pencil selection works without frame flicker.
11. Edit Text, Delete, and Edit with AI work.
12. AI revisions automatically apply after validation and support Undo.
13. Device resizing is immediate and does not invoke AI.
14. Frame Focus and Refresh work correctly.
15. The interactive prototype viewer genuinely supports frontend mock interactions.
16. Theme, [DESIGN.md](http://DESIGN.md), and existing design references affect the generated result.
17. Existing projects, exports, histories, and revision data remain usable.

## 8. Test suite D — Performance and reliability

Measure Time to First Usable Frame from the user's perspective.

```
t0: User presses Submit

t1: Request accepted

t2: Planning completes

t3: First-frame model generation finishes

t4: HTML validated and persisted

t5: Usable frame actually visible
```

Target:

```
t5 - t0 < 60 seconds
```

The measured first frame must be:

- Complete.
- Valid.
- Visually usable.
- Actually displayed.
- Not a loading skeleton.
- Not a partially streamed document.
- Not a previously cached unrelated frame.

Record:

- Queue wait.
- Planning latency.
- Model first-token time.
- Model total generation time.
- Input/output token usage when available.
- Image search/load time.
- Correction attempts.
- Validation time.
- Preview/render latency.
- Total first-frame time.
- All-frame completion time.
- Generation failure count.
- Preview failure count.

Use comparable real scenarios and report every measured run, including slow or failed runs.

Separate cold and warm/cache-hit measurements.

Use meaningful sample counts before making percentile or SLA claims.

Do not reduce output quality merely to get a faster time.

If the target is not achieved, identify actual bottlenecks and continue focused optimization within scope.

Never manipulate timestamps or redefine the start/end measurement.

## 18. New defect handling policy

Every newly discovered issue must be recorded even if it was not explicitly listed in the original task.

For each issue:

```
Defect ID:
Discovery scenario:
Expected:
Actual:
Severity:
Reproduction steps:
Screenshot/trace:
Console/network evidence:
Confirmed cause or hypothesis:
Affected files:
Fix:
Retest result:
Remaining limitation:
```

If severity is high or critical, it must not be ignored simply because the original acceptance checklist did not mention it.

Fix defects within the legitimate feature scope.

If a defect cannot be safely fixed without a significant architectural change, document the blocker and avoid an uncontrolled rewrite.

After fixing:

1. Reproduce the original failure.
2. Retest the affected behavior.
3. Test related regression paths.
4. Run appropriate unit/integration tests.
5. Revalidate relevant browser scenarios.

Do not test only the corrected happy path.
