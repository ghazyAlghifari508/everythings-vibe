## 3. Problem A — Unsafe oversized correction fallback

### 3.1 Confirmed current behavior

The current correction builder uses logic equivalent to:

```
const fitsWithDocument =
    html.length <= STUDIO_PREVIOUS_HTML_MAX_CHARS &&
    fullDocument.length <= STUDIO_CORRECTION_PROMPT_MAX_CHARS;

const prompt = fitsWithDocument
    ? fullDocument
    : documentOmitted;
```

When the HTML cannot fit, the previous document is omitted completely and the model receives an instruction to regenerate the entire screen using the approved blueprint and product context.

This addresses the previous correction-budget exception, but introduces a preservation risk.

The correction pipeline is shared by initial generation, added screens, revisions, and retry operations.

`ValidatedFrameInput` currently does not contain a sufficiently explicit operation/preservation policy that distinguishes these cases.

### 3.2 Why this is dangerous

Consider an existing portfolio website:

```
Committed revision 5
+-----------------------------------+
| Navbar                            |
| Hero                              |
| Featured projects                 |
| About                             |
| Contact                           |
| Footer                            |
+-----------------------------------+
```

The user submits:

"Change the contact button color to dark green."

The model returns a revised document, but the candidate contains one structural defect.

If the candidate exceeds the correction budget, the current implementation can omit the entire candidate and regenerate the screen from the blueprint.

```
Original revision 5
        |
        v
Small requested modification
        |
        v
Invalid candidate HTML
        |
        v
Correction budget exceeded
        |
        v
Previous candidate omitted
        |
        v
Full screen regeneration
        |
        v
Structurally valid but visually different
revision 6 may be committed
```

The resulting document may satisfy structural validation while changing the hero, project cards, navigation, imagery, typography, or content that the user never requested to change.

Database revision checks do not prevent this problem. They protect against stale writes, but do not guarantee that a valid model response preserves unaffected design content.

### 3.3 Required operation-aware correction policy

Explicitly distinguish whether an operation is creating a new frame or modifying a frame that already has a committed design.

Use the actual job type, persisted revision state, and available committed HTML.

Do not infer this distinction from the wording of the user's prompt.

Required behavior:


| Operation                                               | Full regeneration without previous HTML |
| ------------------------------------------------------- | --------------------------------------- |
| Initial generation of a new frame                       | Allowed as a bounded fallback           |
| Adding a new frame                                      | Allowed if no committed design exists   |
| Retry of a frame that has never produced valid HTML     | Allowed                                 |
| Revision of an existing frame                           | Not allowed automatically               |
| Retry of a failed revision with existing committed HTML | Not allowed automatically               |
| Selected-element revision                               | Not allowed                             |


An explicitly requested complete redesign may be handled differently, but must not be inferred merely because a correction request exceeds its budget.

Introduce a small typed operation context or preservation policy within the existing architecture.

An illustrative interface:

```
type StudioFramePreservationPolicy =
    | "new-frame"
    | "preserve-existing";
```

This is an illustrative contract, not a mandatory naming convention.

Prefer an existing equivalent type if the repository already provides one.

Propagate the required information through the actual generation and correction call sites.

Cover legacy projects that have committed HTML even when historical metadata is incomplete.

Never classify an existing design as disposable solely because its current frame status is `failed` or `generating`.

### 3.4 Desired correction lifecycle

```
Candidate fails validation
            |
            v
Can existing deterministic repair
safely resolve the defect?
      /                 \
    YES                  NO
     |                    |
     v                    v
Revalidate          Full-document correction
                        fits budget?
                      /             \
                    YES              NO
                     |                |
                     v                v
              Bounded repair     Check preservation
                                 policy
                                  /          \
                             NEW FRAME     EXISTING FRAME
                                 |                |
                                 v                v
                          Bounded fresh     Safe scoped repair
                          regeneration      if supported
                                                 |
                                                 v
                                       Otherwise retain last
                                       committed valid HTML
```

Do not add an unbounded correction chain.

Reuse existing deterministic repair mechanisms where appropriate.

Do not attempt blind string replacements against arbitrary HTML.

If safe scoped repair is not supported for a particular structural defect, fail the requested revision transparently rather than silently redesigning the entire frame.

A graceful, honest failure is preferable to an unauthorized destructive redesign.

### 3.5 Preserve the last-known-good revision

When an existing-frame revision or correction fails:

- Preserve the original committed HTML.
- Preserve the original revision history.
- Preserve the previously valid visual representation.
- Preserve unaffected frames.
- Do not overwrite the existing design with an invalid or unrelated regenerated candidate.
- Do not increment the committed revision number.
- Do not create a successful revision record.
- Do not incorrectly report that the user's requested change was completed.
- Preserve existing authorization and concurrency guarantees.
- Follow the existing billing and failure-recovery policy.

Separate the failed operation from the previously successful design.

A failed revision must not make previously valid user work inaccessible.

For example:

```
Frame revision 5: valid and retained

Revision operation:
Failed to safely apply the requested change.

Available actions:
Retry / submit a more specific instruction
```

Use existing application feedback patterns. Do not create unnecessary new UI.

### 3.6 Preserve original request semantics

The correction request must remain aware of the user's actual modification instruction.

Preserving the product brief and blueprint alone is insufficient.

For existing frames, retain the distinction between:

- Original committed HTML.
- User-requested modification.
- Invalid candidate HTML.
- Reported validation defects.

When performing correction, the engine must repair the candidate while continuing to respect the original modification scope.

Do not let a generic instruction such as "regenerate the screen" replace a narrow user request.

## 4. Problem B — Silent truncation of existing HTML

### 4.1 Confirmed current behavior

The audited `studio-screen-prompts.ts` implementation contains:

```
opts.previousHtml
    .trim()
    .slice(0, STUDIO_PREVIOUS_HTML_MAX_CHARS)
```

The same underlying truncation behavior exists in both frame-level and single-shot revision prompt construction.

The configured limit is:

```
STUDIO_PREVIOUS_HTML_MAX_CHARS = 60000;
```

Despite sending only part of the existing document, the model is instructed to return a complete revised HTML document.

This is unsafe.

### 4.2 Example failure scenario

```
Existing HTML: 80,000 characters

+--------------------------+-------------+
| First 60,000 characters  | Last 20,000 |
| Sent to model            | Discarded   |
+--------------------------+-------------+
```

The discarded section could contain:

- CSS rules.
- Closing HTML tags.
- Footer.
- Important application content.
- Product imagery.
- Navigation.
- Accessibility attributes.
- Previously completed user modifications.

The model cannot reliably preserve information it never received.

This risks losing valid design content even before the correction pipeline begins.

### 4.3 Required fix

Eliminate silent arbitrary character truncation of HTML documents that must be preserved.

Search for all production occurrences of:

- `.slice()` applied to existing HTML.
- `.substring()` applied to existing HTML.
- Other raw HTML clipping mechanisms.
- `STUDIO_PREVIOUS_HTML_MAX_CHARS` consumers.
- Full-document revision instructions that follow truncated input.

Determine which callers actually require a complete document.

Do not remove unrelated safe limits used for previews, diagnostics, or intentionally non-authoritative summaries.

For revision operations, use a preservation-safe approach.

### 4.4 Preferred handling order

#### Option A — Complete document fits

Send the complete existing document with compact relevant instructions.

Continue through normal validation and revision persistence.

```
Complete existing HTML
          +
Requested modification
          +
Compact revision guidance
          |
          v
Complete validated revision
```

#### Option B — Complete document does not fit

First remove genuinely unnecessary duplicate context.

Evaluate whether safe document preparation can reduce the input without changing its meaning or visual behavior.

Any normalization or compaction must preserve:

- HTML structure.
- Relevant styles.
- Text content.
- Asset references.
- Accessibility attributes.
- Design tokens.
- Stable element identifiers.
- Existing interaction metadata.
- The ability to reconstruct the complete document without information loss.

Do not indiscriminately remove comments, whitespace, CSS, or attributes where doing so could change semantics or rendering.

#### Option C — Scoped modification

Where an existing safe scoped-edit mechanism can represent the requested change, reuse it.

For example:

```
Existing HTML: retained server-side
                 |
                 v
Extract relevant target context
                 |
                 v
Generate or apply scoped patch
                 |
                 v
Apply patch to complete original HTML
                 |
                 v
Validate reconstructed full document
```

The existing element-patch infrastructure may provide reusable mechanisms.

Do not prematurely implement the entire P8 editor during this task.

Do not create a second incompatible revision architecture.

Use scoped editing only when the target and requested modification can be reliably identified.

#### Option D — No safe representation available

Reject the requested revision with an appropriate recoverable error.

Retain the last committed valid document.

Do not:

- Silently truncate.
- Silently regenerate the full existing screen.
- Return a fabricated successful result.
- Delete old content.
- Raise all limits indiscriminately.

### 4.5 Context limit accounting

Consider the complete request, not merely the existing HTML length.

Account for:

- System prompt.
- User instructions.
- Existing HTML.
- Blueprint.
- [DESIGN.md](http://DESIGN.md) and theme information.
- PRD context.
- Correction instructions.
- Output capacity.

Character limits are approximate engineering guards, not exact model-token limits.

Where reliable provider context limits or tokenizer information are available, use them appropriately.

Do not invent tokenizer measurements.

Avoid unlimited context expansion.

### 4.6 Required outcome

```
BEFORE

Original document
       |
       v
Raw character truncation
       |
       v
Model generates full document
from incomplete information
       |
       v
Potential content loss
```

```
AFTER

Original document
       |
       v
Preservation-aware context evaluation
       |
       +--> Complete-document revision
       |
       +--> Safely scoped revision
       |
       +--> Recoverable failure
            with original design retained
```

Merely replacing truncation with automatic document omission does NOT solve the problem.

## 5. Problem C — CARD_ONLY_COMPOSITION false positives

### 5.1 Existing improvement

P1.1 improved `CARD_ONLY_COMPOSITION` to inspect the direct children of the content region.

It now recognizes generic text-card walls built from ordinary `div` elements, rather than only `section`, `article`, or `[data-card]`.

Preserve that improvement.

However, its detection criteria include computed:

- Border.
- Background color.
- Box shadow.

A non-transparent background alone does not necessarily make a section a card.

### 5.2 Potential false-positive example

A valid editorial website might use three full-width sections with different backgrounds.

```
+--------------------------------------+
| Dark background                      |
| Large editorial introduction        |
|                                      |
+--------------------------------------+
| Light background                     |
| Long-form narrative                  |
|                                      |
+--------------------------------------+
| Accent background                    |
| Closing statement                    |
|                                      |
+--------------------------------------+
```

This can be an intentional and legitimate visual composition.

It should not automatically be treated as a wall of generic cards simply because all three sections contain text and have backgrounds.

### 5.3 Genuine card-wall example

```
+--------------------------------------+
| +----------------------------------+ |
| | Heading                          | |
| | Generic paragraph                | |
| +----------------------------------+ |
|                                      |
| +----------------------------------+ |
| | Heading                          | |
| | Generic paragraph                | |
| +----------------------------------+ |
|                                      |
| +----------------------------------+ |
| | Heading                          | |
| | Generic paragraph                | |
| +----------------------------------+ |
+--------------------------------------+
```

The current validator should continue detecting high-confidence repetitive boxed compositions where supported by reliable structural evidence.

### 5.4 Required refinement

Review the use of computed background color as an independent card-detection signal.

Improve the distinction between:

- Ordinary full-width page sections.
- Editorial color-block compositions.
- Repeated contained card-like surfaces.

Use combined structural and styling evidence when available.

Do not assume JSDOM provides accurate browser layout geometry.

Do not rely on unsupported computed layout measurements.

Do not introduce a mandatory visual-quality model call.

If a particular aesthetic judgment cannot be made with sufficiently high confidence from available DOM/CSS evidence, report it as advisory rather than forcing regeneration.

Retain bounded correction for genuine high-confidence structural defects.

### 5.5 Avoid new rigid design rules

Do not require every public website to contain:

- Photography.
- A hero.
- A CTA.
- A gallery.
- A predefined section count.
- A particular card style.
- A particular color scheme.

A genuinely text-oriented page can be valid.

The validator must not undermine the creative freedom established in P1.1 and the planned P2 canonical-renderer refactor.

## 8. Required regression tests

### A. Correction policy

Test that:

1. New-frame correction with a document inside the budget preserves the complete candidate.
2. Oversized initial-frame correction may use bounded regeneration.
3. Oversized add-screen correction may regenerate a genuinely new frame.
4. Retry of a never-successful frame follows new-frame policy.
5. Existing-frame correction cannot omit all candidate HTML and silently perform destructive regeneration.
6. Retry of a failed revision retains the existing-design preservation policy.
7. Existing committed HTML is recognized even if the current operation status is failed.
8. Invalid corrected output never replaces valid committed content.
9. No additional correction attempts are introduced.
10. A successful fresh-frame fallback still undergoes all mandatory validation.

### B. Large-document revision

Use realistic valid HTML fixtures, not only repeated arbitrary characters.

Test documents around the current supported boundary, including:

- Below 60,000 characters.
- Exactly at the configured boundary.
- Above 60,000 characters.
- Documents whose HTML fits individually but whose complete request exceeds the available budget.

Include distinctive content at the end of each document:

```
<section id="preserve-this-section">
    Important existing user content
</section>

<footer id="original-footer">
    Original footer
</footer>
```

Verify that a small modification near the beginning does not silently remove these elements.

Test:

- Complete-document revision.
- Safe scoped revision, where supported.
- Explicit failure when neither approach is safe.
- Last-known-good HTML preservation.
- Revision history integrity.
- No silent raw truncation.

### C. Persistence and concurrency

Verify:

- No committed revision increment after failed correction.
- No successful revision history entry for a failed operation.
- Previous visual content remains accessible.
- No unrelated frame modification.
- Stale revision protection remains effective.
- Existing ownership and authorization checks remain intact.
- Successful writes remain atomic.
- Existing billing behavior remains consistent with the actual operation result.

### D. Card-wall validator

Positive cases:

- Three or more genuinely repetitive boxed text-only card blocks.
- Relevant `section`-based card walls.
- Relevant plain `div`-based card walls.
- Explicit card structure with sufficient supporting evidence.

Negative cases:

- Plain text-oriented editorial website.
- Multiple full-width sections with different backgrounds.
- A legitimate article or long-form narrative.
- An intentional typography-led website.
- A public website with meaningful media or interaction.
- A web application legitimately using data cards.
- A valid layout with a small number of ordinary cards.

Ensure uncertain aesthetic findings do not trigger unnecessary model regeneration.

- Platform-specific planning.

- Prompt-size bounds.
- No duplicated correction guidance.
- Element-level skill boundary.
- [DESIGN.md](http://DESIGN.md) precedence.
