## 3. Finding A — HTML compaction is not genuinely lossless

### Confirmed root cause

`studio-html-preservation.ts` removes whitespace between tags globally:

```
const BETWEEN_TAGS = />\s+</g;
```

The compaction logic applies:

```
chunk.replace(COMMENT, "").replace(BETWEEN_TAGS, "><");
```

However, whitespace between HTML elements can affect visible content, layout, and accessibility.

Example:

```
<span>Total</span> <span>Rp150.000</span>
```

After compaction:

```
<span>Total</span><span>Rp150.000</span>
```

Visual difference:

```
Expected: Total Rp150.000
Actual:   TotalRp150.000
```

This also affects:

- Inline-block spacing.
- Mixed text and inline elements.
- Typography.
- Whitespace-sensitive CSS.
- Content with inherited white-space properties.
- Text surrounding links, icons, and emphasized words.

The existing equivalence check does not reliably detect these changes because it uses:

```
text: element.children.length === 0 ? text : ""
```

Text nodes belonging to elements that also contain child elements are therefore excluded from the comparison.

Furthermore, whitespace normalization through `.replace(/\s+/g, " ").trim()` can conceal meaningful text differences.

### Required fix

Remove unsafe global inter-tag whitespace removal.

Do not assume whitespace between elements is decorative simply because it appears between closing and opening tags.

If compaction remains supported, it must be conservative and demonstrably preservation-safe.

Prefer retaining exact text nodes over achieving maximum compression.

Do not continue using regular expressions to remove arbitrary markup without understanding its DOM context.

If removing non-semantic comments is retained as an optimization, use context-aware removal and preserve meaningful comments, conditional comments, and any existing runtime or interaction metadata.

If compaction cannot be proven safe, reject the revision using the existing `STUDIO_REVISION_TOO_LARGE` mechanism.

### Strengthen document equivalence

Replace the current incomplete element-shape comparison with a comparison that preserves meaningful document information.

Account for:

- Node types.
- Element hierarchy.
- Ordered child nodes.
- Exact text-node values.
- Mixed content.
- Element attributes and namespaces.
- Document type and compatibility mode.
- SVG content.
- Whitespace-sensitive elements.
- CSS and style content.
- Template content where present.
- Existing interaction metadata.

Do not compare only leaf-element text.

Do not normalize away whitespace differences to make the comparison pass.

Close JSDOM instances appropriately after use.

The equivalence check should establish structural and semantic preservation within its supported boundaries. Do not claim it proves complete visual equivalence in every browser.

### Desired behavior

```
Existing HTML exceeds supported budget
                  |
                  v
Attempt conservative compaction
                  |
                  v
Compare complete meaningful DOM structure
       /                         \
 Equivalent                  Different
     |                            |
     v                            v
Check size again            Reject compaction
     |
 Fits?
  /     \
YES      NO
 |        |
 v        v
Send    STUDIO_REVISION_TOO_LARGE
HTML    Preserve committed design
```

Do not silently truncate or regenerate existing user work.

## 4. Finding B — Committed HTML must take precedence over job type

### Confirmed root cause

The current policy in `studio-frame-operation.ts` uses:

```
return jobType === "add" || !frame.htmlCode
    ? "new-frame"
    : "preserve-existing";
```

This means an `add` operation receives `new-frame` even if it unexpectedly already owns committed HTML.

That contradicts the preservation contract.

Although this is not a confirmed failure in the normal add-screen workflow, the implementation should fail safely when encountering recovered, resumed, inconsistent, or legacy operation state.

### Required fix

Committed HTML must always take precedence when determining preservation requirements.

Expected policy:


| Job type | Committed HTML | Policy                                                     |
| -------- | -------------- | ---------------------------------------------------------- |
| Initial  | No             | new-frame                                                  |
| Add      | No             | new-frame                                                  |
| Add      | Yes            | preserve-existing, or safely reject inconsistent operation |
| Revision | Yes            | preserve-existing                                          |
| Retry    | No             | new-frame                                                  |
| Retry    | Yes            | preserve-existing                                          |


Do not use frame status to determine whether existing user work is disposable.

Also inspect the related prompt-construction behavior:

```
previousHtml:
    job.jobType === "add"
        ? undefined
        : frame.htmlCode ?? undefined
```

Changing the preservation policy alone is insufficient if another branch continues discarding committed HTML from the generation context.

Ensure prompt construction and correction policy remain consistent.

If an add operation unexpectedly owns committed HTML, either:

- Safely retain and use the committed document when resuming the operation; or
- Reject the inconsistent operation without modifying existing user work.

Choose the approach that aligns with the existing job-resumption and idempotency architecture.

Do not create a new job architecture for this fix.

## 5. Finding C — Preservation policy must be explicit

### Confirmed root cause

`ValidatedFrameInput` declares:

```
preservation?: StudioFramePreservationPolicy;
```

The correction builder then uses:

```
const preservation = input.preservation ?? "new-frame";
```

This creates a fail-open default.

A future production caller could forget to supply the preservation policy, unintentionally allowing destructive regeneration of an existing frame.

### Required fix

Make the preservation policy mandatory:

```
preservation: StudioFramePreservationPolicy;
```

Remove the implicit `new-frame` fallback.

Every production caller must explicitly establish whether it is operating on a new frame or preserving committed user work.

Update relevant:

- Initial generation callers.
- Project creation callers.
- Frame operations.
- Retry operations.
- Legacy revision services.
- Test fixtures and helper functions.

Do not bulk-assign `new-frame` to every caller just to satisfy TypeScript.

Determine the correct policy from actual operation semantics.

Where runtime input is unexpectedly invalid, fail conservatively rather than enabling document-free regeneration.
