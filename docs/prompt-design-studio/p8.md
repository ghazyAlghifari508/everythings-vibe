# FIX 08 — Professional Delete Project Confirmation Copy

**Severity:** P2  
**Complexity:** SMALL  
**Target:** `feature/vibedesign-design-studio`  
**Execution order:** 08/08. This is the last task.

## Problem

The current project deletion modal uses wording similar to:

"Project 'CatatDompet - Manajemen Keuangan Pribadi' akan dihapus permanen beserta seluruh layar, riwayat revisi, dan asetnya. Tindakan ini tidak dapat dibatalkan."

The information is broadly accurate but the sentence feels unnecessarily long, procedural, and robotic.

Improve the UX copy without weakening the warning.

## Verify existing behavior

Inspect:

- `src/features/studio/components/workspace/studio-delete-project-dialog.tsx`
- `studio-project-lifecycle.ts`
- existing `Dialog`, `DialogHeader`, `DialogDescription`, and `Button` primitives.

Verify which data is actually deleted. Do not invent deletion consequences.

```
┌─────────────────────────────────────────────┐
│                                             │

```

The project name must be dynamic.

### Preferred copy

**Title:**

Hapus project "{projectName}"?

**Description:**

Semua halaman, riwayat perubahan, dan aset dalam project ini akan dihapus permanen. Project yang dihapus tidak bisa dipulihkan.

**Buttons:**

- Batal
- Hapus project

Maintain consistent spelling with the existing product language. Avoid em dashes in the copy.

## UI requirements

1. Reuse existing dialog/button components.
2. Before modifying any UI, inspect available shadcn/ui, HeroUI, Magic UI, React Bits, Thinking Orbs, and affectUI components for a suitable confirmation pattern.
3. Keep the current reusable dialog architecture if it already fits. Do not rebuild from zero.
4. Use an appropriate delete icon if consistent with the design system.
5. Do not add an excessive warning card, decorative red gradient, or extra badges.
6. The destructive action should be clearly distinguishable.
7. Long project names must wrap safely without breaking the modal.
8. Cancellation must remain easy.
9. During deletion, prevent duplicate destructive requests.
10. Errors must be understandable.
11. Preserve correct focus management and accessible dialog semantics.
12. Do not change project deletion logic, cascading delete semantics, or ownership checks unless a genuine bug is discovered and documented.

## Tests

- Correct title with dynamic name.
- Long project name.
- Warning content.
- Cancel closes dialog.
- Confirm calls existing delete handler once.
- Pending state prevents duplicates.
- Deletion failure displays error.
- No em dash in the new user-facing copy.

No browser QA or browser-based E2E.

The confirmation modal is concise, clear, professional, accessible, and consistent with the existing UI.

Report changed files, actual reused components, and test outcomes.
