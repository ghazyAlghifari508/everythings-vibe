# P8 — Complete Element Editing: Direct Text, Instant Delete, AI Auto Apply, and Undo

**Complexity: VERY COMPLEX**  
**Execution order: 08/11**

## 1. Objective

Make all three Edit Element actions genuinely functional.

- Edit Text: direct local text editing without AI.
- Delete: immediate deterministic deletion without AI.
- Edit with AI: scoped AI revision through the floating chat, automatically applied after validation.

Every successful design change must support Undo.

Do not implement a comprehensive manual property inspector, freeform drag-and-drop layout editor, or Figma clone.

Use existing element revision and patch infrastructure whenever possible.

## 3. Edit Text

Desired experience:

```
Select heading
       |
       v
Edit Element -> Edit Text
       |
       v
Text becomes editable in place
       |
       v
User changes text
       |
       v
Commit change
       |
       v
New persisted revision
```

Example:

```
Before: Ulasan Pembeli

After: Ulasan Pelanggan
```

Requirements:

- Direct text editing at the selected element.
- No LLM request.
- No new generation job.
- No credit deduction.
- Preserve element typography and styles.
- Preserve sibling elements.
- Handle Enter, multiline editing, blur, and Escape through documented semantics.
- Do not save a change if content is unchanged.
- Cancel restores the original displayed text.
- Persist valid committed changes.

For complex text containing inline markup or nested icons, patch the intended text node or supported editable range.

Do not overwrite the entire container with `textContent` if that would accidentally delete child icons, links, or formatting.

Sanitize input and treat it as text rather than executable HTML.

## 4. Delete

Desired behavior:

```
Select product card
        |
        v
Edit Element -> Delete
        |
        v
Only selected card disappears immediately
        |
        v
Revision persisted
        |
        v
Undo available
```

No AI call.

No regeneration of the frame.

No full-frame shimmer.

No unnecessary confirmation modal for ordinary reversible element deletion.

Do not permit deletion of protected document/runtime infrastructure.

If deleting a structural element affects references needed by the prototype runtime, handle the resulting relationship safely.

Do not silently remove unrelated sections.

If deletion cannot be persisted because the target is stale or a request fails, reconcile the visual state to the last valid revision.

## 5. Edit with AI

Target workflow:

```
User selects a card
        |
        v
Edit Element -> Edit with AI
        |
        v
Floating chat opens if closed
        |
        v
Element attachment enters composer
        |
        v
User types instruction
        |
        v
Submit scoped AI revision
        |
        v
Validate candidate + scope + version
        |
        v
Automatically apply valid result
        |
        v
Undo available
```

Example composer:

```
[ Detail Paket / Promo Card × ]

Ganti desain card ini agar lebih minimalis
dan gunakan foto destinasi yang sesuai.

[ Send ]
```

Clicking Edit with AI must not itself submit the request.

The user must be able to inspect the target, remove the attachment, and write/edit instructions before submitting.

The submitted target must be snapshotted with the operation.

Later canvas selection must not mutate an already-submitted revision.

## 6. Auto Apply

The previous Preview → Apply workflow is no longer the desired interaction.

After the AI produces a valid scoped revision, automatically persist and display it.

Remove obsolete confirmation steps from the new editing flow.

Preserve any existing saved history and handle previously created pending revisions safely. Do not silently apply an old unapproved candidate created under the previous preview-confirmation behavior.

Auto Apply does NOT mean bypassing validation.

Required sequence:

```
Candidate patch
      |
      v
HTML/security validation
      |
      v
Scope preservation check
      |
      v
Current document version check
      |
      v
Atomic revision persistence
      |
      v
Renderer update
```

If any step fails, retain the previous valid frame.

Do not show success if persistence fails.

## 7. Scoped editing guarantees

If user selects Section A, only Section A and necessary scoped dependencies should change.

Example:

```
Before:
Navbar + Hero + Statistics + Projects + Contact

Instruction:
Hapus Statistics

After:
Navbar + Hero + Projects + Contact
```

Do not regenerate the entire website merely to remove a section.

Prefer deterministic operations for well-defined removal and text changes.

For complex AI edits, provide only relevant context:

- Selected element.
- Relevant ancestors/siblings.
- Shared design tokens.
- Current document version.
- User instruction.
- Allowed modification boundaries.

Reject unrelated global redesign unless explicitly requested by the user.

## 8. Concurrent revision safety

A revision generated from version 5 must not overwrite version 6 that was committed by another operation.

```
AI starts from version 5
        |
User directly edits text -> version 6
        |
AI candidate finishes
        |
Version check
        |
Conflict detected
```

Use the existing concurrency architecture and optimistic version checks.

Define a safe policy for queued revisions, stale targets, and conflicts.

Do not silently discard the user's more recent work.

## 9. Undo

Every committed element change must have a reversible revision.

Support Undo for:

- Edit Text.
- Delete.
- AI Auto Apply.

Undo must restore the relevant previous valid state through revision-safe behavior.

Do not implement Undo by deleting arbitrary database records or blindly overwriting newer unrelated work.

Use existing revision history where possible.

If multiple operations have occurred since the selected change, apply a documented safe undo policy.

Do not claim undo of one operation succeeded while unrelated later edits were unintentionally lost.

Provide concise contextual feedback and an Undo action using existing toast/action components.

No excessive green badges or large success panels.

## 10. Fix element revision history failure

Investigate the error shown when opening the workspace:

"Riwayat revisi elemen belum dapat dimuat."

Inspect:

- Endpoint response.
- Authentication and project ownership.
- DB migrations/schema.
- Empty history representation.
- Response validation.
- Stale request reconciliation.
- Error handling.

An empty revision history must be represented as a valid empty result.

If the history request fails, normal chat and frame generation must remain usable.

Place relevant recovery in the editor/history area rather than cluttering ordinary conversation.

Do not modify the database manually to remove evidence of the failure.

Use proper migrations or application fixes where required.
