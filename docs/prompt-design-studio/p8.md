# PROMPT 08 — Build the Stitch-Style Persistent Chat and Canvas Workspace

**Complexity: VERY COMPLEX**  
**Execution order: 08 of 13**

## Objective

Transform VibeDesign Studio from a canvas with a bottom floating composer into a coherent AI design workspace inspired by the observed core behavior of Google Stitch.

This is NOT a visual mockup task.

Build a real conversation experience connected to existing Studio jobs, frames, projects, and revisions.

Scope:

- Left-side collapsible chat panel.
- Persistent user/assistant messages.
- Initial landing prompt handoff.
- Genuine agent planning/generation updates.
- Canvas displaying frames independently.
- User can send follow-up prompts and requests.
- Selected frame/element context can later be attached to the chat.
- Panel can close/reopen without losing state.

Do not add voice, manual visual editing, or unrelated Stitch capabilities.

## 3. Component-first implementation is mandatory

Explore:

- Existing EvVibe components.
- shadcn/ui (ScrollArea, Sheet, Resizable, Button, InputGroup, where available).
- HeroUI (appropriate chat/drawer/button primitives).
- TUFFUI (chat/composer/prompt suggestions if compatible).
- affectUI.
- Magic UI, React Bits, Thinking Orbs, CUI, SakaniUI where genuinely relevant.

Inspect current official docs and actual available components. Never invent API exports.

Actually adopt suitable existing/installable primitives.

Do not rebuild a textarea, resizable panel, modal, or scroll container entirely from scratch when mature compatible primitives exist.

Do not install all catalogs blindly or make chat visually noisy with animations.

## 4. Persistence and data ownership

Design durable conversation entities associated with a Studio project.

Represent the minimal necessary information:

- Message ID.
- Project/conversation ID.
- User or assistant role.
- Message content.
- Creation ordering.
- Related operation/job ID.
- Message status.
- Attached frame/element references when applicable.
- Error/recovery metadata where needed.

Avoid persisting sensitive provider internals in user-readable records.

Use database migrations compatible with existing projects.

Messages must survive:

- Page reload.
- Workspace history reopen.
- Panel collapse.
- Client reconnect.
- Temporary job interruption.

Do not create duplicate initial messages when the workspace loader runs twice.

## 5. Initial landing prompt handoff

When user submits a prompt from `/design`:

1. Create or resolve the project.
2. Persist the user's original prompt as a conversation message.
3. Link the initial generation job.
4. Navigate to the workspace.
5. Display the original prompt in chat.
6. Show a genuine assistant response derived from the actual plan when available.
7. Show frame progress driven by persisted job/frame events.

Never fabricate a finished-plan message before planning has completed.

Do not call a separate LLM merely to produce decorative acknowledgment if the existing blueprint can supply accurate response content.

## 6. Assistant responses

Assistant messages must answer what the system actually did.

Examples:

**After planning:**

"Aku akan membuat empat halaman: Eksplorasi, Detail Destinasi, Perjalanan, dan Profil."

Only use those names if they match the actual persisted plan.

**During generation:**

"1 dari 4 halaman tersedia."

Only use verified frame readiness.

**After completion:**

"Empat halaman selesai dibuat."

Only if all four are truly successful.

**Partial completion:**

"3 halaman tersedia. 1 halaman belum berhasil dibuat."

Include appropriate recovery action.

No simulated typing, fabricated percentages, fake countdowns, or misleading success responses.

## 7. Chat during generation

The composer must remain useful while jobs are running.

Use the queue guarantees implemented previously.

User can type and submit another valid request. The resulting message and operation should show an honest status such as accepted/queued, not imply immediate generation if dependencies are pending.

Maintain:

- Draft when submit fails.
- No duplicate messages on retry.
- No duplicate job creation.
- Correct ordering.
- Clear operation targeting.
- No unintended cancellation of initial generation.

Do not copy OpenDesign's exact UI or all of its capabilities; adapt its verified interaction concepts.

## 8. Synchronization with the canvas

Chat and canvas are two views of the same project state.

On frame-ready events:

- Canvas updates the matching frame.
- Chat progress updates.
- Existing ready frames remain visible.
- No unrelated screen jumps are forced.
- Selection context stays stable where possible.

When panel collapses, generation continues.

When reopened, conversation and current statuses remain correct.

Do not rely on the chat component remaining mounted to complete backend work.

## 9. Attachments and suggestions boundaries

Provide clear integration points for frame attachments and contextual shortcuts.

Full attachment behavior will be refined in Prompt 09.

Element-level editing will be introduced in Prompt 10.

Do not implement an incomplete independent targeting model now.

Avoid old large suggestion cards blocking the canvas.

## 10. Tests

Cover:

- Initial prompt creates exactly one durable message.
- Reload retains messages.
- Opening existing history retains conversation.
- Panel collapse preserves draft and progress.
- Queued user message survives reload.
- Assistant progress reflects actual job state.
- Failed submission preserves draft.
- No duplicate messages.
- No cross-project or cross-user message access.
- Ready/partial/failed statuses reconcile correctly.
- Existing frame revision endpoints still work.
- Mobile panel state is controlled.

Do not run browser QA or Playwright E2E in this phase.

Report architecture, persistence model, component sources used, state/event flow, migration, targeted tests, and known limitations.

The task is incomplete if it only moves the old composer into a new sidebar.
