# P8 — Complete Element Editing With Compact Design Intelligence, Auto Apply, and Undo

**Complexity: VERY COMPLEX**  
**Execution order: After P7, before P9**  
**Replaces the previous P8**

## 1. Objective

Complete VibeDesign's visual element editing experience using the existing renderer and Pencil selection infrastructure.

Required actions:

- Edit Text.
- Delete.
- Edit with AI.

Edit Text and Delete must be deterministic and immediate.

Edit with AI must automatically apply valid scoped changes after validation.

Every successful operation must support Undo.

Do not restore the old mandatory Preview → Apply confirmation flow.

Do not implement a full manual Figma-style property editor.

## 4. Edit Text

Desired workflow:

```
Select text
    |
    v
Edit Text
    |
    v
Inline editing at the selected location
    |
    v
Commit valid text
    |
    v
Persist revision and offer Undo
```

Requirements:

- Direct editing without LLM requests.
- No credit deduction.
- No generation job.
- No full-frame regeneration.
- Preserve typography.
- Preserve surrounding layout.
- Preserve sibling elements.
- Preserve supported inline formatting and icons.
- Appropriate Enter, multiline, blur, and Escape behavior.
- No new revision if text is unchanged.
- Safe cancellation.

Treat user-entered text as text, not executable HTML.

Do not replace a complex element's entire `textContent` when doing so would delete children, icons, links, or formatting.

Use a supported text node/range or other deterministic targeted patch.

If a target cannot be safely edited as text, do not falsely advertise direct support.

## 5. Delete

Desired workflow:

```
Select card or section
        |
        v
Click Delete
        |
        v
Only selected target disappears immediately
        |
        v
Persist revision
        |
        v
Undo available
```

Delete must not:

- Call an LLM.
- Deduct credits.
- Create a generation job.
- Show generation shimmer.
- Delete unrelated elements.
- Modify unrelated frames.

Do not require an unnecessary confirmation dialog for an ordinary reversible element deletion.

Protect essential document/runtime infrastructure.

If deletion affects navigation or interaction metadata, reconcile the affected references safely.

For a rejected or failed persistence operation, restore/reconcile the previous valid visual state.

Never report a successful deletion if the operation did not persist.

## 6. Edit with AI

Desired workflow:

```
Pencil selection
      |
      v
Edit Element -> Edit with AI
      |
      v
Floating chat opens
      |
      v
Selected element attached to composer
      |
      v
User writes instruction
      |
      v
Submit scoped AI revision
```

Example:

```
[ Detail Paket / Promo Card × ]

Buat card ini lebih minimalis dan perbaiki
hierarki harga tanpa mengubah bagian lain.

[ Send ]
```

Requirements:

- Open chat automatically when needed.
- Attach the exact selected target.
- Preserve frame identity and base revision.
- Allow attachment removal.
- Preserve the user's draft.
- Do not auto-submit when the menu item is clicked.
- Snapshot the submitted target.
- Prevent later selection changes from mutating submitted requests.
- Preserve existing multi-frame attachment behavior.

## 7. Integrate the internal evvibe-design skill

Previous source inspection found that `studio-element-generation.ts` uses a separate scoped editing system prompt.

It did not use `evvibe-design`.

Integrate the compact element-revision guidance established in P1.1.

Target:

```
User element-edit instruction
            +
Selected element and relevant context
            +
Compact evvibe-design revision guidance
            +
Project design tokens
            |
            v
Scoped AI patch
```

The skill should help the model maintain:

- Visual hierarchy.
- Typography.
- Layout quality.
- Responsive behavior.
- Semantic clarity.
- Anti-slop standards.
- Existing design identity.

Use relevant guidance only.

Do not send the full website/mobile planning skill.

Do not send a complete component catalog.

Do not add a component browsing stage.

Do not add another LLM request solely to select design guidance.

Do not perform a full-document redesign for a localized edit.

The user's requested scope must remain more specific than general design guidance.

An instruction such as "change this heading color" must not cause the AI to improve unrelated sections merely because the skill suggests better general composition.

## 8. Preserve scoped patch guarantees

Prefer deterministic operations for simple text changes and removal.

For complex AI changes, provide only the required context:

- Target element ID.
- Base HTML revision.
- Target fragment.
- Relevant parent and sibling structure.
- Existing styles/tokens.
- User instruction.
- Allowed patch schema.

Restrict generated patches to the selected target and explicitly authorized changes.

Do not permit arbitrary generated JavaScript, unsafe HTML, editor overlays, or unauthorized global styles.

When the target uses a shared design token or shared class, ensure a local edit does not unintentionally modify every other element using that token or class.

Use a safely scoped style or appropriate existing mechanism.

## 9. Auto Apply

Remove the requirement for the user to review a separate candidate modal and click Apply.

The new sequence is:

```
AI returns candidate
        |
        v
Validate patch schema
        |
        v
Validate HTML/security
        |
        v
Validate target and scope
        |
        v
Verify current revision
        |
        v
Atomically persist valid change
        |
        v
Update live renderer
        |
        v
Offer Undo
```

Auto Apply does not mean applying unvalidated model output.

If any validation fails, retain the previous design.

Do not publish a broken intermediate frame.

Do not show a whole-frame loading shimmer for a small element revision.

Use contextual progress feedback and keep existing design visible until the valid change is ready.

Handle historical pending candidates safely. Do not automatically apply previously unapproved candidates created under the old workflow.

## 10. Concurrent revision safety

Use the existing durable operation and revision architecture.

Example:

```
AI reads frame version 5
          |
Direct text edit creates version 6
          |
AI finishes candidate based on version 5
          |
Version conflict detected
```

Do not allow the stale candidate to overwrite version 6.

Use optimistic revision checks, atomic persistence, or equivalent existing safeguards.

If safe rebasing is supported, validate it rigorously.

Otherwise reject/recover transparently.

Never discard user's newer modifications silently.

## 11. Undo

All successful operations must be reversible:

- Direct text edit.
- Direct deletion.
- AI Auto Apply.

Undo must restore the relevant previous valid state through proper revision operations.

Do not implement Undo by manually deleting database history or blindly restoring an old full document over newer unrelated edits.

Define an explicit policy for multiple sequential revisions.

Use the existing revision architecture where possible.

Provide concise feedback:

```
Perubahan diterapkan                      Undo
```

Avoid excessive success badges or large notification panels.

Undo must remain coherent after:

- Reload.
- Renderer refresh.
- Device switching.
- Other completed revisions.
- Workspace history reopening.

Do not misrepresent unsupported historical undo behavior.

## 12. Fix the revision history failure

Investigate the reported message:

"Riwayat revisi elemen belum dapat dimuat."

Verify:

- Endpoint response.
- Project authorization.
- Required migrations.
- Schema and response validation.
- Empty history representation.
- Stale asynchronous requests.
- Error-state lifecycle.

An empty revision history should be a valid empty result.

An actual history failure should be recoverable without breaking ordinary chat or frame generation.

Do not merely hide the error.

Do not manually alter database records to make the history request return success.

## 13. Renderer consistency

Use P6's shared responsive renderer.

Ensure:

- Direct editing does not remount the entire iframe unnecessarily.
- Undo does not recreate unrelated frames.
- Selected viewport is retained.
- Hover overlays remain aligned.
- Editor-specific metadata is not accidentally exported.
- Updated element identities are reconciled.
- Stale renderer responses cannot overwrite newer revisions.

The frame must remain a single coherent design across desktop, tablet, and mobile presentation.
