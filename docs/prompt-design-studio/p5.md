# TASK 05 — Keep Shared Navigation Consistent When Adding Screens Through the Canvas Composer

**Priority:** P1  
**Complexity:** COMPLEX  
**Branch:** `feature/vibedesign-design-studio`

## Mission

Fix navigation inconsistencies when users add screens to an existing Studio project through the canvas composer or context-aware prompt suggestions.

Current behavior:

A project begins with three screens and a shared navigation structure.

The user then requests:

"Tambahkan halaman baru untuk Catat Transaksi."

The new frame may be created successfully, but the generated application's navigation can still contain only the original three destinations.

The new screen must be integrated appropriately into the application's structure without unnecessarily regenerating all previously completed screens.

## 1. Understand the Current Issue

Current:

```
INITIAL PROJECT

Screens:
[A: Ikhtisar]
[B: Pelanggan]
[C: Laporan]

Navigation:
Ikhtisar | Pelanggan | Laporan
```

User adds a new screen:

```
Screens:
[A: Ikhtisar]
[B: Pelanggan]
[C: Laporan]
[D: Catat Transaksi]

Navigation:
Ikhtisar | Pelanggan | Laporan

PROBLEM:
D exists, but is absent from navigation.
```

## 2. Define Explicit Screen Roles

Not every newly created screen needs to become a global navigation item.

Examples:


**Primary destination**

- Dashboard.
- Transactions.
- Customers.
- Reports.

**Contextual screen**

- Customer details.
- Edit transaction.
- Checkout step.
- Confirmation page.

Desired architecture:

```
PROJECT SCREEN STRUCTURE

PRIMARY NAVIGATION
├── Ikhtisar
├── Catat Transaksi
├── Pelanggan
└── Laporan

CONTEXTUAL SCREENS
├── Detail Pelanggan
├── Edit Transaksi
└── Konfirmasi Pembayaran
```

Define a reliable classification mechanism using:

- Explicit user instructions.
- Existing navigation contract.
- Project blueprint.
- Product context.
- New screen role.

Avoid assuming that every new screen must become an additional sidebar or bottom-nav tab.

When the intent is ambiguous and would materially change navigation, use a safe, explicit decision policy or request clarification rather than silently redesigning the whole app.

## 3. Extend the Shared Blueprint Safely

Current architectural elements include:

```
designBlueprint
  ├── productIdentity
  ├── designTokens
  ├── sharedComponents
  ├── navigationContract
  ├── canonicalShell
  └── screenPlan
```

When a primary screen is added, update the appropriate shared blueprint metadata.

Ensure:

- Navigation destination ID remains stable.
- Navigation labels are consistent.
- Navigation ordering is intentional.
- Icon mapping is valid.
- Newly added screen receives correct active state.
- Existing screens retain correct active states.
- Screen plan includes the new screen.
- Existing brand/theme tokens remain unchanged.
- Blueprint updates are validated and persisted.

Do not create duplicate destinations for semantically equivalent screens.

Do not use the human-readable screen name as an unstable identifier without a normalization strategy.

## 4. Preserve Existing Generated Screens

This is a critical constraint.

Wrong:

```
User adds D

[A READY] [B READY] [C READY]
     |
     v
[A REGENERATE] [B REGENERATE] [C REGENERATE]
                             [D GENERATE]
```

Correct:

```
User adds D

[A READY] [B READY] [C READY]
                             |
                             v
                        [D SHIMMER]
                             |
                             v
                        [D READY]

Existing screen bodies stay intact.
```

If shared navigation needs to be updated across older frames, investigate reassembling or projecting the deterministic canonical shell using updated blueprint metadata.

Do not send unchanged screen bodies through another expensive AI generation request.

Do not mutate the content of existing screens merely to change a navigation label.

If preview assets must be refreshed because the shared shell changed, only regenerate derived previews, not the AI-produced page content.

Preserve recoverable last-good previews and avoid showing unrelated frames as generating.

## 5. Resolve Static HTML vs Shared Navigation

The system currently saves generated HTML.

Inspect whether navigation is already embedded into the persisted HTML during canonical assembly.

If yes, avoid a naive database-only blueprint update.

Otherwise, old screens will retain old navigation inside stored HTML or previews.

Implement an appropriate, version-aware strategy:

```
Existing Screen Body
        +
Updated Shared Blueprint
        |
        v
Canonical Shell Assembly
        |
        v
Correct HTML / Preview / Export
```

Ensure source-of-truth consistency between:

- Project blueprint.
- Frame HTML.
- Canvas preview.
- Exported HTML/ZIP.
- Revision operations.

Do not create multiple conflicting navigation sources of truth.

## 6. Add-Screen Flow

Expected:

```
Canvas composer:
"Tambahkan halaman Catat Transaksi"

        |
        v
Intent = ADD_SCREEN
        |
        v
Classify screen role
        |
        v
Persist new screen metadata
        |
        v
Extend shared blueprint if required
        |
        v
Generate only new screen body
        |
        v
Render new frame
        |
        v
Shared navigation remains coherent
```

Existing screens should not unexpectedly lose their ready status.
