# PHASE 5 — Refine VibeDesign Landing Page to Match Google Stitch's Layout Quality

**Priority: P2 — MEDIUM**  
**Complexity: MEDIUM**  
**Branch:** `feature/vibedesign-design-studio`  
**Primary route:** `/design/studio` (verify the actual route implementation)

## 1. Objective

Refine the existing VibeDesign Studio landing page.

The current design has several problems:

1. Excessive horizontal distance between the history sidebar and the main composer.
2. History sidebar shrinks vertically when projects are deleted.
3. The visual composition still feels substantially different from Google Stitch.
4. Heading typography is inconsistent with the application's established design language.
5. Supporting copy exposes technical implementation details instead of explaining user value.
6. The PRD attachment control is not sufficiently understandable.
7. The textarea placeholder is static for Web and Mobile.
8. Prompt shortcuts contain excessive implementation-oriented instructions.
9. The horizontal shortcut carousel has clipping/alignment issues.

The objective is a polished, cohesive layout that follows Google Stitch's proven composition while preserving VibeEverything's identity.

**Do not rebuild the landing page from zero. Refactor the actual existing components.**

## 4. Fix Excessive Sidebar-to-Content Gap

Investigate the current relationship between:

- Sidebar width.
- Main flex container.
- Main max-width.
- `mx-auto`.
- Main horizontal padding.
- Responsive breakpoints.
- Hero/composer width.

Existing code uses a centered main content wrapper similar to:

```
mx-auto ... max-w-3xl
```

This may center content too far away from the sidebar inside the remaining main area.

Refactor the layout constraints intentionally.

Do not solve the gap using fragile negative margins, arbitrary absolute positioning, or numerous hardcoded breakpoint offsets.

Keep the composition balanced on wide monitors.

## 5. Stable History Sidebar Height

The sidebar must NOT shrink when:

- All projects are deleted.
- Only one project remains.
- Search returns no results.
- The history list changes.
- Loading finishes.

Target:

```
BEFORE DELETE              AFTER DELETE

┌──────────────┐             ┌──────────────┐
│ My Projects  │             │ My Projects  │
│ Search       │             │ Search       │
│ Project A    │             │              │
│ Project B    │             │ No projects  │
│ Project C    │             │              │
│              │             │              │
│              │             │              │
│              │             │              │
└──────────────┘             └──────────────┘

SAME OUTER HEIGHT
```

Requirements:

- Stable sidebar height based on available viewport space.
- Responsive max/min constraints.
- Internal scrolling for long history.
- No full-page overflow caused by the sidebar.
- Pleasant empty state without enlarging the empty-state text.
- No unnecessary skeleton or fake project entries.

Preserve deletion, project navigation, search, and existing history behavior.

## 7. Dynamic Platform-Specific Placeholder

The textarea placeholder must change according to selected mode.

Example:

```
[ Mobile selected ]

Contoh: Aplikasi pesan kopi dengan pilihan menu,
kustomisasi minuman, checkout, dan pelacakan pesanan.
```

```
[ Web selected ]

Contoh: Dashboard bisnis dengan laporan penjualan,
grafik performa, tabel transaksi, dan manajemen tim.
```

The placeholder should use a tasteful typing animation.

Requirements:

- Animate only when the input is empty.
- Never modify the actual textarea value.
- Never interfere with typing or IME composition.
- Pause or stop animation on focus.
- Respect `prefers-reduced-motion`.
- Clean up animation resources correctly.
- Avoid layout shifts.
- Restart appropriately when Web/Mobile changes.
- Keep examples meaningful and reasonably concise.

Prefer an existing appropriate typewriter component if compatible with a textarea placeholder.

Explore ready-made solutions before implementing custom animation logic.

Do not use an oversized cursor, blinking banners, or typewriter effects on user-entered text.

## 9. Horizontal Shortcut Carousel

Shortcuts must remain horizontally arranged.

Example:

```
Mulai dari brief siap pakai                        [←] [→]

┌────────────────┐ ┌────────────────┐ ┌────────────────┐
│ Coffee App     │ │ Finance App    │ │ Travel Booking │ →
```

Requirements:

- Never wrap into a multi-row grid.
- Support left/right navigation.
- Prevent partially clipped text that cannot be reached.
- Correct first/last item alignment.
- Correct disabled arrow states.
- Preserve horizontal touch/trackpad scrolling where appropriate.
- Maintain keyboard accessibility.
- Avoid unintended horizontal page overflow.
- Keep cards compact and readable.

Inspect the existing carousel instead of replacing it unnecessarily.

## 10. Clean Shortcut Prompt Content

Current shortcut prompts include explicit instructions such as:

"Layar yang direncanakan (5 halaman, saling terhubung)"

This duplicates system-level page-count configuration.

Separate user product requirements from generation mechanics.

Target architecture:

```
Shortcut Selection
       |
       +--> Product brief text
       |
       +--> Recommended platform (Web/Mobile)
       |
       +--> Recommended page count
       |
       v
Composer State
       |
       v
Submit
       |
       +--> User brief
       +--> Selected platform
       +--> Selected page count
```

A user changing page count after choosing a shortcut must not encounter conflicting instructions inside the prompt.

Shortcut content should describe:

- Product purpose.
- Target audience.
- Real features.
- Important user workflows.
- Relevant sample content/data.
- Meaningful UI states.
- Functional requirements.

Do not include:

- AI execution instructions.
- Hardcoded page-count commands.
- Internal generation rules.
- "Make all pages connected" directives.
- Generic design-quality slogans.

The system prompt and planning contract should handle the technical rules.

Keep shortcut prompts detailed and genuinely useful. Do not overcorrect into one-line examples.
