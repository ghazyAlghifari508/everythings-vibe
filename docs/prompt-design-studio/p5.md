# P5 — Replace Generic Shortcut Pills With Contextual Horizontal Action Cards

**Complexity: MEDIUM**  
**Execution order: 05/11**

## Objective

Improve both the presentation and intelligence of VibeDesign's suggested follow-up prompts.

The current shortcut system produces labels that are too short and generic, such as:

- Buat Profil.
- Buat Beranda.
- Atur Jadwal.
- Selesaikan Pembayaran.

These suggestions do not sufficiently explain what the user could improve or create next.

## 1. Inspect current implementation

Read:

- `studio-screen-suggestions.ts`
- `studio-screen-recipes.ts`
- `studio-suggestion-row.tsx`
- `use-studio-screen-suggestions.ts`
- Current chat panel and composer.
- Composer intent resolution.
- Existing shortcut tests.

Previous inspection found that the suggestion contract was centered on `add_screen`.

Verify the current supported intent types.

## 2. New shortcut UI

Use horizontally scrollable action cards, not tiny single-line pills and not a vertical stack.

```
+-------------------------------------------+
| Assistant response                        |
|                                           |
| Suggested next actions                    |
|                                           |
| +---------------------+ +---------------+ |
| | ↪ Uji validasi      | | ↪ Simulasikan | |
| | tanggal perjalanan  | | paket habis...| |
| +---------------------+ +---------------+ |
|                    Horizontal scrolling  |
|                                           |
| +---------------------------------------+ |
| | Mau buat atau ubah apa?             ↑ | |
| +---------------------------------------+ |
+-------------------------------------------+
```

Requirements:

- Rounded action cards.
- Meaningful sentence-length copy.
- Two or three lines when necessary.
- Readable typography.
- Appropriate icon.
- Horizontal scrolling.
- Comfortable interaction target.
- No tall vertical list that consumes the chat.
- No decorative badge, dot, or gradient.
- No unnecessary section heading if the recommendations are self-explanatory.

Place cards above the composer or in the latest appropriate assistant result context while maintaining one clear recommendation surface.

## 3. Contextual intelligence

Suggestions must consider:

- Original user request.
- Current project.
- Actual existing screens.
- Latest conversation.
- Design blueprint.
- User journey.
- Selected frame or element where relevant.
- Missing pages.
- Unrepresented UI states.
- Interaction gaps.
- Latest completed changes.

Support useful categories beyond adding pages:

- Add screen.
- Create an alternative UI state.
- Improve an existing component or screen.
- Complete a missing interaction flow.
- Add a relevant validation scenario.
- Refine an existing design based on the user's domain.

Do not suggest actions the current engine cannot understand or safely execute.

If a suggestion concerns prototype interaction, connect it to the mock interaction capability established in P10, or treat it as a request to design a specific visual state until that runtime is available.

## 5. Full prompt behavior

The displayed card must correspond to a complete contextual instruction.

Example:

Displayed:

"Simulasikan paket wisata yang kehabisan kuota"

Internal prompt:

"Tambahkan atau revisi state pada halaman Detail Paket ketika kuota keberangkatan sudah habis. Tampilkan alternatif jadwal yang masih tersedia, nonaktifkan pemesanan untuk jadwal penuh, dan pertahankan design system serta navigasi proyek Jelajahin. Jangan mengubah halaman lain yang tidak terkait."

Clicking a suggestion should:

1. Fill the composer with the full instruction.
2. Attach the intended target when safe and explicitly available.
3. Let the user edit the instruction.
4. Not automatically submit.
5. Not charge credits until the user actually submits.

Avoid attaching or mutating an unrelated frame.

## 6. Recommendation generation policy

Generate recommendations after relevant work has completed or enough verified context exists.

Do not call a model whenever the canvas is panned, zoomed, or rerendered.

Reuse the existing planning/result context where practical.

Cache suggestions by meaningful project, conversation, or revision changes.

Filter duplicate suggestions using actual screen and intent semantics, not just exact string matching.

Keep deterministic recipes as a fallback, but improve domain-specific detail.

If no useful suggestion is available, it is better to show none than to display three low-quality generic actions.

## 7. Mandatory component-first adoption

Inspect existing UI and available components from:

- TUFFUI prompt suggestions.
- shadcn/ui Button, Card, ScrollArea.
- HeroUI.
- Magic UI.
- React Bits.
- Thinking Orbs.
- affectUI.
- CUI.
- SakaniUI.

Actually adopt a suitable card/button and horizontal-scroll pattern.

Use existing iconography, theme tokens, and interaction primitives.

Do not implement a custom carousel from scratch if a suitable accessible component already exists.

Do not add auto-playing motion.

## 8. Tests

Cover:

- Context-specific suggestion labels and payloads.
- Existing-screen duplicate detection.
- Multiple supported intent categories.
- Full prompt prefilling.
- Intended target attachment.
- No generation on click alone.
- No accidental credit deduction.
- Composer draft preserved safely.
- No unnecessary model calls.
- Suggestions invalidate appropriately after relevant changes.
- Horizontal layout contract.
- Keyboard and scroll accessibility.

No browser QA in this phase.
