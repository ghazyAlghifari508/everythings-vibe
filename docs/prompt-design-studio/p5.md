# PROMPT 05 — Fix Platform-Aware Navigation, App Shell, Responsive HTML, and Export Fidelity

**Complexity: VERY COMPLEX**  
**Execution order: 05 of 13**

## Objective

Generated websites should look like real websites. Generated mobile applications should look like well-designed mobile applications.

Current defects include:

- A web portfolio navbar resembles oversized mobile tabs.
- Header branding and navigation feel disconnected.
- Generic app bars and headings are repeatedly generated.
- The first screen sometimes has excessive side whitespace while sibling screens have reasonable widths.
- HTML export may look worse than the canvas preview.
- Global Studio CSS can interfere with local component styles, gutters, image ratios, and controls.

Fix the structural causes, not only individual example pages.

## 2. Define product-aware layout categories

`web` and `mobile` are not sufficient to choose an appropriate navigation shell.

Model the minimal additional layout intent needed to distinguish:

**Public marketing/portfolio website**

- Conventional horizontal desktop navbar.
- Brand and navigation aligned.
- Suitable CTA and hero.
- Responsive mobile menu behavior.
- No giant equal-width navigation tabs.

**Web application/dashboard**

- Sidebar, top bar, or contextual navigation chosen according to information architecture.
- Appropriate page title and controls.
- Dense layouts where tasks require them.
- Do not force a landing-page navbar everywhere.

**Mobile application**

- App bar appropriate to current screen.
- Back button on nested flows where needed.
- Bottom navigation for genuine top-level destinations.
- No duplicated generic headers.
- Correct handling of safe areas and content spacing.

Do not hardcode a portfolio-only solution as the default for every web project.

Preserve support for legacy blueprints that currently contain only `designMode` and navigation contracts.

## 4. Canonical CSS must respect component ownership

Audit deterministic injected styles for:

- `--app-gutter`
- Header and navigation sizing
- Global button/input/select/textarea sizing
- Product images
- Media aspect ratios
- Container max widths
- Text wrapping
- Overflow
- Positioning
- Responsive breakpoints

Previous HTML inspection revealed:

- Gutter overrides.
- Quantity controls whose CSS dimensions were altered by global min-height/padding.
- Image ratio conflicts such as a 16:10 container with a 16:9 global image rule.
- Mobile-width content aligned left on a wide desktop viewport.

Correct the global/local styling boundary.

Global shell styling should own shell structure and shared tokens, not force every button or image into one rigid size.

Avoid broad `!important`, aggressive `overflow:hidden`, and arbitrary fixed widths.

## 5. Responsive layout contracts

Use consistent project-level tokens while allowing screen-specific composition.

Correct:

- Web content widths and gutters.
- Mobile screen widths.
- Header and navigation alignment.
- Card grid vs horizontal scroller behavior.
- Overflow and shrink rules.
- Text/price grouping.
- Mobile sticky action areas.
- Media ratios and cropping behavior.

A horizontal product/travel carousel should be allowed to scroll instead of shrinking all cards into unreadable miniatures.

For product imagery, distinguish `cover` and `contain` based on actual content intent.

Do not apply a universal ratio to every image.

## 6. HTML preview/export consistency

Ensure the same finalized, validated HTML is the source of truth for both canvas preview capture and ZIP export.

```
Generated HTML
       |
       v
Canonical assembly + validation
       |
       v
Final persisted HTML
       |
       +---- Screenshot capture
       |
       +---- Standalone HTML export
```

At equal viewport sizes and equivalent assets, they must preserve the same layout.

Preserve:

- Existing asset collection/packaging.
- Standalone HTML format.
- Correct font and image dependencies.
- Revision history.
- Web/mobile mode.
- Project-specific [DESIGN.md](http://DESIGN.md) styling.

For mobile output opened on desktop, center the mobile shell instead of unintentionally placing it on the far left.

For web output, do not constrain content to a 390–440px mobile shell.

No duplicate canonical header, duplicated CSS, or repeated navigation after revision/export.

## 7. Mandatory component-first research and adoption

Before building any UI pattern, review:

- Existing Studio patterns and shared UI.
- shadcn/ui.
- HeroUI.
- Magic UI.
- React Bits.
- Thinking Orbs.
- affectUI.
- TUFFUI.
- CUI.
- SakaniUI.

Review the official docs/registries and actual licenses.

For a relevant need, identify a mature compatible component or pattern and **actually adopt it**.

Examples: navigation, responsive cards, form controls, carousel, app headers, action groups.

Studio generated documents are standalone HTML/CSS. React-only components cannot simply be imported into the exported HTML. Reuse compatible structural/CSS patterns or existing static component templates instead.

Do not install unnecessary component libraries or add visual effects that have no UX purpose.

Document every chosen component and source. If none fits, justify a narrowly scoped custom implementation.

## 8. Tests without browser QA

Create/update targeted tests for:

- Public website navbar layout contract.
- Web dashboard navigation.
- Mobile top-level and nested navigation.
- No equal-width tab behavior forced on public web navbar.
- Consistent canonical project tokens.
- No duplicated headers or nav.
- Gutter and CSS override safety.
- Button/quantity controls not globally distorted.
- Different image ratio contracts.
- Intentional horizontal scrolling not globally suppressed.
- Mobile shell centering.
- Web export not mobile constrained.
- HTML assembly idempotency.
- Export preserving CSS and assets.
- Legacy blueprint compatibility.

Use CSS/source-level assertions where meaningful, without falsely claiming visual pixel-perfect guarantees.

Do not run browser QA, headless Playwright, or browser-based screenshot regression in this phase.

Do not conclude that all generated websites are now beautiful based solely on a successful TypeScript build.
