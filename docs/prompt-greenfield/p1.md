# P1 — Fix PRD Live Streaming, Output Routing, and Generation Lifecycle

**Kompleksitas:** COMPLEX / HIGH · **Prioritas:** P0 (critical regression)  
**Urutan:** 1 dari 8 — kerjakan sebelum P2.  
**Repository:** `ghazyAlghifari508/everythings-vibe` · **Target branch:** `feature/vibeplan-greenfield`

## 1. Konteks dan masalah yang dilaporkan

Setelah migrasi Greenfield ke Nested Layout Routes (`/vibeplan/$id/ask`, `/fitur`, `/prd`, `/ac`, `/task`, `/kanban`), ada regresi saat initial PRD generation. Di sisi kiri/tengah (document canvas) loading “Menyusun PRD” tetap muncul; sementara Markdown PRD, heading FR-01, requirements, dan paragraf dokumen justru terus mengalir sebagai bubble di panel Chat sebelah kanan. Setelah generation selesai, baru seluruh PRD muncul di document canvas. Sebelum perubahan routing, pengguna mengharapkan PRD muncul dan bertambah secara live di canvas tengah.

Ini bukan permintaan redesign dan bukan masalah yang boleh diselesaikan dengan menyembunyikan bubble Chat. Perbaiki kontrak penyaluran output, lifecycle request, dan rendering live PRD secara benar. Pertahankan Nested Routes dan data existing. P2 akan menangani CTA/progress; P3 menangani interaksi Chat/composer; P5 menangani desain loading. Jangan mendahului ketiga scope itu.

**Kandidat root cause yang kuat dari audit source sebelumnya:** `use-chat-stream.ts` memiliki `activeChatMode` dengan nilai awal `"chat"`. `useChatStreamBuffer({ chatMode: activeChatMode })` dibentuk pada render tersebut. Jika initial request mode `generate` masih memakai callback buffer mode `chat`, `use-chat-stream-buffer.ts` memasukkan Markdown ke `setStreamingContent` (bubble) alih-alih `setStreamingPRDContent` (canvas). Ini masuk akal tetapi belum dibuktikan runtime; jangan menganggap pasti hanya ada satu penyebab.

Verifikasi apakah ada reset store/activeProjectId, overlay predicate, hydration, loader revalidation, atau completion handler yang juga menyebabkan/memperparah masalah. Bedakan data dokumen, natural-language chat output, section progress, dan thinking events. Dokumentasi relevan: [https://react.dev/learn/state-as-a-snapshot](https://react.dev/learn/state-as-a-snapshot) dan [https://react.dev/learn/referencing-values-with-refs](https://react.dev/learn/referencing-values-with-refs) .

## 4. Implementasi wajib

### 4.1 Request-scoped stream routing

Jadikan mode request yang sedang berjalan sebagai input eksplisit terhadap pengolahan delta, accumulation, RAF/throttled flush, final flush, error, resume dan completion. Gunakan tipe mode aktual SDK/domain (`generate`, `resume`, `revise`, `chat` atau tipe ekuivalen); jangan gunakan string bebas bila tipe yang tepat sudah ada. Mode tidak boleh bergantung pada waktu render ulang React.

```
mode snapshot pada start request + projectId + request identity
                     ↓
               SSE event handler
                     ↓
             request-owned buffer
          ┌──────────┴──────────┐
 generate/resume           chat / revise
          ↓                     ↓
 document store         natural-language output (chat)
                        + patch dokumen (revise saja)
```

- `generate`: delta PRD mengisi canvas dari token dokumen pertama; jangan echo raw Markdown sebagai pesan Chat.
- `resume`: gabungkan partial prefix + delta baru tepat satu kali; canvas terus diperbarui, tanpa kehilangan/duplikasi bagian.
- `revise`: pertahankan aturan existing patch/section revision, tampilkan perubahan dokumen di canvas, hanya penjelasan revisi yang pantas di Chat. Jangan merusak format parser/contract existing.
- `chat`: jawaban percakapan masuk panel Chat, bukan mengotori dokumen.
- Thinking events dan progress section tidak boleh dianggap sebagai document delta. Jangan mengekspose raw document sebagai fallback Chat hanya karena mode belum diketahui.

Pilih desain minimal yang secara struktural mencegah stale closure: misalnya buffer menerima immutably captured context per request atau flush eksplisit menerima mode/request context. Jika memakai ref, pastikan identitas request terikat pada buffer/pending callback agar request lama tidak membaca mode request baru. Jangan hanya menambah `setTimeout`, efek sinkronisasi yang berlomba dengan delta, atau global flag yang menyembunyikan gejala.

### 4.2 Buffer lifetime, ownership, dan completion

Audit urutan onDelta → scheduled flush → onDone/onError → cleanup. Final flush harus memproses seluruh delta terakhir sebelum menandai request selesai. Batalkan RAF/timer yang sudah tidak valid. Late events dari request lama atau project sebelumnya tidak boleh menimpa store, progress, draft, atau document pane lain. Hindari reset global yang menyingkirkan stream aktif pada rerender parent yang sama.

Pada keberhasilan, pertahankan konten live sampai persisted PRD/version loader yang benar siap (tidak ada blank flash). Pastikan server benar-benar mengonfirmasi persistensi sebelum UI menganggap versi final tersedia; jangan mengubah outcome error menjadi success. Cek `use-prd-detail.ts` termasuk typewriter reveal, live source, `latestVersion`, revalidation dan pemilihan versi. Overlay pre-token boleh hilang segera ketika ada delta dokumen; jangan menunggu `done`. Jangan menghilangkan fungsi typewriter/Markdown/Mermaid/TOC yang existing jika tidak terkait bug.

### 4.3 Recovery, cancellation, dan project boundary

Pertahankan satu owner untuk satu generation request. Pastikan initial autosubmit sekali per proyek sesuai contract, tidak ada duplicate generation karena route remount, cache invalidation, resize, atau perubahan visibility Chat. Gunakan guard yang sudah ada untuk navigasi yang tidak aman; jangan memperkenalkan background job/queue baru tanpa bukti kebutuhan. Refresh/disconnect/abort mengikuti recovery yang existing; partial/error tidak boleh disimpan sebagai versi sukses. Stop harus benar-benar membatalkan request sesuai contract existing, membersihkan state/lock dan credit sesuai server policy. Jangan memotong kredit ganda atau memodifikasi billing untuk menyamarkan kegagalan UI.

Jika sedang memproses PRD dan pengguna hanya menutup panel Chat (P3), generation harus tetap memiliki owner yang stabil. Siapkan boundary/fungsi yang memungkinkan P3 mengubah visibility tanpa menghancurkan owner request. Jangan membuat beberapa ChatPanel/controller aktif atau mengubah seluruh responsive layout di P1.

## 5. Test yang HARUS membuktikan perbaikan

Gunakan framework test repo (Vitest/unit/integration hook, deterministic SSE fixtures). Tambahkan test yang gagal pada implementasi lama apabila memungkinkan, lalu lulus pada implementasi baru. Jangan sekadar assert bahwa fungsi dipanggil; assert tujuan dan isi output.

1. Initial hook mode `chat`, start `generate`, delta tiba sebelum render berikutnya: canvas menerima Markdown, Chat tidak menerima dokumen, progress sesuai heading aktual.
2. Multiple delta, RAF flush, final delta dan `done` pada frame sama: konten lengkap tanpa teks hilang/duplikasi.
3. `resume` dengan prefix partial: konsisten, prefix sekali, canvas live.
4. `revise`: mempertahankan patch serta natural-language bubble yang sah. `chat`: tidak mengubah PRD.
5. Request failure/aborted stream: tidak memalsukan status selesai, tidak hilang draft/recovery yang seharusnya dipertahankan.
6. Project switch dan late callbacks: tidak ada cross-project leakage. Membuka kembali proyek dengan saved PRD tidak memicu generate baru.
7. Generation complete: versi tersimpan tersedia, canvas tidak kosong saat revalidation, lock/credit mengikuti behavior existing.
8. Existing auto-submit, version selection, PRD share/export dan guard regression tetap lulus. Test parent layout/rehydration yang relevan jika terdampak.

Gunakan test doubles yang transparan di test terisolasi, bukan mock yang menonaktifkan fungsi yang justru sedang diverifikasi. Jangan mengedit database manual, memaksa status `completed`, memalsukan SSE/done dalam aplikasi, atau mengabaikan test yang gagal. Jangan menghapus assertions valid. Tidak boleh menjalankan browser QA/Playwright pada fase ini; gunakan targeted tests, typecheck, lint sesuai skrip nyata repo.
