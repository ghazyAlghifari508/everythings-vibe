## 1. Tujuan Utama

Refactor arsitektur routing VibePlan Greenfield agar seluruh proses perencanaan produk berjalan dalam satu workspace yang konsisten menggunakan **TanStack Router Nested Layout Routes (Opsi 2)**.

Saat ini enam tahapan Greenfield menggunakan route terpisah:

```
/ask/:id
/fitur/:id
/prd/:id
/ac/:id
/task/:id
/kanban/:id
```

Migrasikan menjadi:

```
/vibeplan/:id
├── /ask
├── /fitur
├── /prd
├── /ac
├── /task
└── /kanban
```

Tujuan perubahan bukan hanya mengganti struktur URL. Hasil akhir harus memberikan pengalaman sebuah aplikasi workspace yang terintegrasi, mempertahankan shared layout, identitas proyek, navigasi, dan seluruh workflow Greenfield.

**Batasan paling penting:**

- Semua fitur Greenfield yang sudah berfungsi wajib dipertahankan.
- Tidak boleh kehilangan PRD, Acceptance Criteria, Feature Tree, Task, Kanban, riwayat versi, maupun progres pengguna.
- Tidak boleh mengubah cara AI menghasilkan dokumen kecuali diperlukan untuk memperbaiki kompatibilitas routing.
- Tidak boleh terjadi duplicate generation, duplicate credit deduction, stale state, atau cross-project data leakage akibat navigasi.
- Jangan membangun ulang sistem Greenfield dari nol.
- Jangan mengganti Nested Routes dengan search-param wizard.
- Jangan menggunakan solusi sementara yang hanya menyembunyikan error.
- Jangan menganggap pekerjaan selesai hanya karena URL baru berhasil dibuka.

Fokus pada **architectural correctness, feature preservation, lifecycle safety, maintainability, dan regression prevention**.

## 3. Target Arsitektur: Nested Layout Routes

Gunakan file-based nested routing TanStack Router.

Target struktur konseptual:

```
src/
├── routes/
│   ├── vibeplan/
│   │   └── $id/
│   │       ├── route.tsx       # Persistent parent workspace
│   │       ├── index.tsx       # Default/resume route
│   │       ├── ask.tsx
│   │       ├── fitur.tsx
│   │       ├── prd.tsx
│   │       ├── ac.tsx
│   │       ├── task.tsx
│   │       └── kanban.tsx
│   │
│   ├── ask/$id.tsx            # Legacy redirects
│   ├── fitur/$id.tsx
│   ├── prd/$id.tsx
│   ├── ac/$id.tsx
│   ├── task/$id.tsx
│   └── kanban/$id.tsx
│
└── features/
    └── greenfield/
        ├── components/
        ├── hooks/
        ├── services/
        ├── types/
        └── utils/
```

Struktur ini merupakan target logis. Pastikan penamaan `route.tsx`, `index.tsx`, `$id`, serta parent-child registration kompatibel dengan konfigurasi TanStack Router aktual.

Gunakan typed file routes, `createFileRoute`, dan `Outlet` sesuai dokumentasi.

Jangan memodifikasi `src/routeTree.gen.ts` secara manual. Biarkan generator resmi TanStack mengelolanya.

### 3.1 URL akhir

```
/vibeplan/abc123
/vibeplan/abc123/ask
/vibeplan/abc123/fitur
/vibeplan/abc123/prd
/vibeplan/abc123/ac
/vibeplan/abc123/task
/vibeplan/abc123/kanban
```

`abc123` merupakan contoh identitas proyek.

URL `/vibeplan/:id` berfungsi sebagai **workspace entry/resume**, bukan halaman kosong baru yang mengharuskan pengguna memilih tahap lagi.

URL ini harus menentukan tujuan berdasarkan state proyek yang valid, artefak yang tersedia, dan informasi resume yang aman.

Jangan hanya mempercayai `projects.step`, sebab proyek Greenfield baru atau legacy dapat memiliki nilai step default meskipun artefak tahap tersebut belum tersedia.

Jika tersedia last visited route yang valid dan masih dapat diakses, gunakan sesuai kebijakan resume yang sudah berjalan. Jika tidak, tentukan tahap paling tepat menggunakan data proyek yang telah diverifikasi.

Hindari redirect loop, stale resume, dan akses ke tahap yang belum tersedia.

### 3.2 Route state vs workflow state

Pisahkan konsep berikut:

- **Route/view:** Tahap UI yang sedang dilihat pengguna.
- **Workflow progress:** Tahap tertinggi yang benar-benar telah diselesaikan.
- **Artifact availability:** Apakah Feature Tree, PRD, AC, atau Task sudah tersedia.
- **Generation status:** Pending, generating, completed, atau failed sesuai state aktual.

Jangan menganggap pengguna yang membuka URL `/prd` otomatis telah menyelesaikan PRD.

Jangan menurunkan workflow progress hanya karena pengguna kembali melihat tahap sebelumnya.

Kanban tetap menjadi view tersendiri, tetapi jangan otomatis menambahkan step database keenam. Periksa dan pertahankan kontrak workflow saat ini, termasuk hubungan Kanban dengan Task.

Buat shared parent layout yang benar-benar menjadi container seluruh tahapan Greenfield.

Visualisasi konseptual:

```
┌──────────────────────────────────────────────────────────────────┐
│ EvVibe / VibePlan                  Project actions / Profile     │
├──────────────────────────────────────────────────────────────────┤
│ Project: HalamanUMKM                                           │
│                                                                  │
│   Ask ── Fitur ── PRD ── AC ── Task ── Kanban                  │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│                   DYNAMIC WORKSPACE OUTLET                       │
│                                                                  │
│   Jika route = /prd                                              │
│   ┌────────────────────────────┬───────────────────────────┐    │
│   │                            │                           │    │
│   │     PRD Document           │      AI Revision Chat     │    │
│   │                            │                           │    │

│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

Diagram ini menunjukkan hierarki konseptual, bukan instruksi membuat desain UI baru dari nol.

### Persyaratan shared shell

- Workspace shell tidak boleh unmount hanya karena child route berubah dalam proyek yang sama.
- Header proyek dan identitas proyek harus konsisten.
- Step indicator harus menunjukkan tahap aktif dan progres aktual.
- Pending/error UI tahap tertentu tidak boleh otomatis menggantikan seluruh workspace shell.
- Parent tidak boleh mengunduh seluruh data PRD, AC, Task, dan Kanban sekaligus.
- Shared project metadata boleh dimuat sekali pada parent dan digunakan oleh child bila benar-benar diperlukan.
- Pertahankan viewport dan scroll ownership yang kompatibel dengan `AppLayout`.
- Tidak boleh ada nested scroll container yang tidak diperlukan atau konflik `overflow` dan `h-dvh`.
- Tidak boleh terjadi duplicate Navbar, duplicate project header, atau duplicate progress indicator.

### Penting: existing global layout

Repository sudah mempunyai `AppLayout` dan `Navbar` global.

Inspeksi terlebih dahulu apakah workspace shell baru seharusnya:

1. Mengintegrasikan komponen global yang sudah ada, atau
2. Menggunakan komposisi layout khusus yang benar-benar diperlukan.

Jangan membuat Navbar baru dengan markup dan behavior yang menyalin Navbar lama.

Utamakan reuse, composition, dan perbaikan komponen existing.

### Responsive design

Pertahankan layout responsif yang sudah tersedia. Perubahan routing tidak boleh merusak tampilan mobile/tablet.

Khusus PRD, jangan menghilangkan document/chat toggle, drawer, atau panel resize yang telah ada.

Jangan menambahkan animasi, shimmer, skeleton, atau elemen visual baru hanya untuk menyamarkan transisi routing.

## 6. AI Streaming dan State Lifecycle Safety

Ini merupakan **critical regression area**.

Saat ini PRD streaming menggunakan beberapa bagian seperti:

```
use-chat-stream.ts
chat-panel.tsx
prd-detail.tsx
prd-chat-stream.server.ts
generation-stream.server.ts
```

Inspeksi hubungan antara component lifecycle, AbortController, Zustand, SSE, persistensi server, dan navigasi.

### Masalah yang harus dicegah

```
User generates PRD
        │
        ▼
AI streaming started
        │
        ▼
User navigates to another step
        │
        ▼
PRD component unmounts
        │
        ▼
Potential stream/state loss
```

Implementasi tidak boleh membiarkan kasus ini menghasilkan:

- Generasi yang dibatalkan diam-diam.
- Output parsial dianggap berhasil.
- Kredit terpotong padahal operasi gagal tanpa settlement benar.
- Proses generasi duplikat.
- Status generating yang stuck.
- Isi PRD hilang dari UI tanpa recovery.
- SSE tetap berjalan tanpa lifecycle ownership yang jelas.
- Konten dari proyek sebelumnya muncul pada proyek lain.

### Strategi yang diwajibkan

Pisahkan secara jelas:

1. Long-running server generation.
2. Client SSE connection.
3. Stream UI state.
4. Persisted artifact state.
5. Navigation lifecycle.

Evaluasi apakah state streaming harus tetap dikelola oleh komponen PRD, dipindahkan ke provider/controller tingkat workspace, atau ditangani melalui existing durable/recovery mechanism.

**Jangan otomatis menambah sistem job queue, worker, atau infrastruktur baru.** Gunakan mekanisme existing apabila sudah mampu memenuhi kebutuhan.

Jika navigasi akan menyebabkan kehilangan stream atau unsaved state, gunakan mekanisme navigasi yang aman dan terverifikasi. Navigation blocking yang jelas lebih baik daripada silently aborting generation.

Jika stream memang dapat dipertahankan atau di-reattach dengan aman, pastikan implementasinya didukung lifecycle dan server contract yang nyata.

Jangan sekadar menyimpan `isGenerating = true` di global store tanpa menjaga koneksi atau recovery aktual.

### Expected behavior

```
PRD generation active
        │
        ├── Generation completed
        │      └── Persist result → Update UI → Navigate safely
        │
        ├── User navigates away
        │      └── Preserve safely / block with clear explanation
        │
        ├── Connection interrupted
        │      └── Existing recovery behavior remains functional
        │
        └── Explicit user cancellation
               └── Correct abort + consistent credit/status cleanup
```

Seluruh perubahan harus menghormati idempotency, reservation, settlement, dan generation status yang sudah diterapkan.

## 8. Backward Compatibility untuk URL Lama

Semua URL lama harus tetap dapat digunakan sebagai entry point dan diarahkan ke URL canonical.


| Legacy URL    | Canonical URL          |
| ------------- | ---------------------- |
| `/ask/:id`    | `/vibeplan/:id/ask`    |
| `/fitur/:id`  | `/vibeplan/:id/fitur`  |
| `/prd/:id`    | `/vibeplan/:id/prd`    |
| `/ac/:id`     | `/vibeplan/:id/ac`     |
| `/task/:id`   | `/vibeplan/:id/task`   |
| `/kanban/:id` | `/vibeplan/:id/kanban` |


Gunakan TanStack Router redirects sesuai API aktual.

Persyaratan:

- Tidak ada redirect loops.
- Pertahankan project ID.
- Pertahankan search params yang memang didukung destination, termasuk callback billing/payment yang relevan.
- Jangan membawa parameter tidak terpercaya secara buta.
- Preserve exact destination stage, jangan selalu diarahkan ke PRD hanya karena itu tahap default.
- Jika user belum login, pertahankan existing login redirect behavior secara aman.
- Jika proyek tidak ditemukan, tampilkan error yang benar.
- Jika proyek milik user lain, jangan bocorkan metadata.
- Jika tahap tidak tersedia atau plan tidak memenuhi syarat, gunakan existing flow guard atau paywall behavior.
- Jangan mengubah `/prd/share/$token`.
- Jangan merusak route Existing Codebase.

Legacy route sebaiknya menjadi redirect compatibility layer yang tipis. Jangan mempertahankan dua implementasi UI Greenfield aktif secara paralel.

## 16. Engineering Constraints

1. **No unnecessary rewrite.** Pertahankan existing implementation patterns.
2. **No fake fixes.** Jangan menyembunyikan error dengan fallback generik atau catch yang mengabaikan masalah.
3. **No type bypass.** Hindari `as any`, `as never`, `@ts-ignore`, dan unsafe cast untuk memaksa router types.
4. **No feature removal.** Jangan membuang fitur lama hanya karena mempersulit migrasi.
5. **No scope creep.** Jangan merombak AI prompt, database, billing, atau UI di luar kebutuhan migrasi.
6. **No duplicate implementation.** Setiap fitur cukup memiliki satu sumber implementasi aktif.
7. **No invented APIs.** Gunakan dokumentasi TanStack dan SDK yang sesuai versi repository.
8. **Feature-driven architecture.** Pertahankan pemisahan routes, components, hooks, services, types, dan tests.
9. **No monster files.** Ikuti batas panjang file dan aturan modularisasi proyek.
10. **No silent behavior changes.** Semua perubahan perilaku harus dijustifikasi dan diuji.
11. **No unrelated modifications.** Jangan memperluas pekerjaan ke domain lain.
12. **No unauthorized Git operations.** Jangan commit, push, merge, atau publish tanpa izin eksplisit. Pertahankan perubahan working tree milik pengguna.
13. **No premature completion.** Jangan menutup task hanya karena sebagian route berhasil dimigrasi.

Bila menemukan masalah existing yang tidak terkait, catat secara terpisah. Jangan diam-diam memperluas refactor.

Jika ada conflicting implementation details, gunakan source code terbaru, existing behavioral contracts, dan dokumentasi resmi sebagai dasar keputusan.
