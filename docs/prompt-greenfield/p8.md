# P8 — Final Browser QA: Full Greenfield Workflow, Visual Regression, and Real User Acceptance

**Kompleksitas:** COMPLEX / HIGH · **Prioritas:** Final acceptance gate  
**Urutan:** 8 dari 8 — jalankan hanya setelah P1–P7 selesai dan pengguna meminta browser QA.  
**Repository:** `ghazyAlghifari508/everythings-vibe` · **Target branch:** `feature/vibeplan-greenfield`

## 1. Tujuan akhir QA

Verifikasi pengalaman nyata pengguna Greenfield setelah seluruh perbaikan. Target bukan sekadar halaman terbuka atau screenshot terlihat bagus. Targetnya adalah pengguna dapat membuat rencana produk dari awal sampai Kanban melalui Nested Routes, melihat dokumen PRD/AC terbentuk pada lokasi yang benar, melanjutkan tahap berikutnya, berinteraksi dengan Chat/composer, dan melihat UI yang bersih tanpa tambahan copy/status yang redundan. Data, versi, progres, auth, entitlement, dan kredit harus konsisten.

Browser QA ini harus dilakukan **secara nyata** menggunakan browser environment yang tersedia dan diotorisasi. Automation Playwright/browser tools boleh digunakan pada fase ini saja bila tersedia; gunakan browser nyata, jangan menggantinya dengan sekadar membaca source, unit tests, screenshot statis, atau laporan fabricated. Jika tool browser, app server, login, database test, AI provider atau akun test eligible tidak tersedia, laporkan blocker dan bagian Not Verified. Jangan memalsukan hasil atau meminta pengguna menonaktifkan keamanan.

## 2. Setup dan aturan integritas yang tidak boleh dilanggar

- Periksa branch, HEAD, working tree, aturan repo, hasil P1–P7, dan environment test. Gunakan local/staging yang diotorisasi, bukan production tanpa izin. Jangan deploy atau melakukan pembayaran riil. Gunakan akun test yang memang berhak menggunakan Greenfield dan eligible untuk AC/Task sesuai kebijakan paket normal, dengan kredit/AI usage yang diotorisasi.
- Baca konfigurasi dev start/browser tooling aktual; gunakan URL local/staging yang benar. Jangan mengarang port, kredensial, API key, atau akun.
- Buat test project melalui UI normal (satu project utama yang utuh). Contoh ide aman: dashboard inventory dan laporan penjualan UMKM dengan export PDF; jangan memasukkan data pribadi nyata atau secrets. Simpan project ID dan route yang benar, tanpa membocorkan credential/session token.
- Untuk menguji proyek lama/resume gunakan proyek test existing yang diperoleh melalui flow sah atau buat proyek melalui UI. Jangan menyiapkan hasil generasi dengan injecting artifact atau manually editing database. Jika tidak tersedia legacy data, verifikasi legacy route terhadap proyek sah dan tandai persisted legacy-row test Not Verified bila memang tidak tersedia.

### Larangan keras: tidak ada kecurangan QA

**Dilarang** membuat test terlihat berhasil dengan:

- Mengedit DB (SQL/ORM/admin scripts), memaksa `projects.step`, `hasPrd`, `hasAc`, `taskStatus`, `credits`, entitlement, atau generation status; membuat PRD/AC/Task palsu atau memalsukan `lastUrl` agar skenario lulus.
- Langsung menggunakan API mutasi untuk berpura-pura user sudah menekan CTA/generate/save melalui UI; melewati Ask/Fitur/PRD/AC/Task karena satu tahap gagal; memilih pre-completed project lalu mengklaim full generation pipeline lulus.
- Mencegat/modifikasi network response, menyuntikkan fake SSE `done`, hardcode UI state, disable route guard/error reporting, hide overlay/element via DevTools atau CSS injection demi screenshot bagus.
- Memakai mock/fake model output sebagai bukti real E2E. Unit fixtures terisolasi boleh ada di P7, bukan substitusi full real generation di P8.
- Mengubah paket akun, kredit, akses atau auth demi bypass. Jika akun tidak eligible atau provider tidak merespons, laporkan blocker; jangan membeli paket/credit riil atau menggunakan akun orang lain tanpa izin.
- Menghapus screenshot failure, crop bagian yang bermasalah untuk menyembunyikan error, menekan tombol lewat programmatic DOM handler apabila klik pengguna nyata tidak bekerja lalu mengklaim klik lulus. Gunakan browser interaction yang representatif (click/tap/keyboard). Debugging boleh, tetapi hasil debug tidak dihitung acceptance sampai user-like interaction lulus tanpa manipulasi.
- Mengabaikan console error, failed network request, stale UI, timing/lifecycle bug, atau temuan baru hanya karena tidak tercantum dalam laporan awal. Bedakan expected 4xx (auth/gate/failure test), warning existing, dan unexpected failures dengan evidence, bukan menyatakan semuanya baik.

Read-only inspection terhadap request/response metadata, app logs, dan data test yang diotorisasi boleh digunakan sebagai supporting evidence; jangan memodifikasi data atau mengungkap rahasia. Jangan menggunakan arbitrary sleeps sebagai bukti completion: tunggu kondisi UI/response yang benar dengan timeout masuk akal. Jika timeout, tangkap bukti dan laporkan. Jangan menjanjikan tidak ada bug sama sekali; laporkan cakupan dan hasil nyata.

## 4. Skenario browser QA — jalankan sesuai urutan

### B1 — Initial entry dan Ask (happy path)

1. Login via supported flow dengan akun test yang diotorisasi, buka Home/Plan New.
2. Isi ide produk valid, platform/opsi existing, buat proyek melalui UI. Pastikan satu project dibuat dan canonical `/vibeplan/<id>/ask` dibuka.
3. Periksa navbar: tepat 5 tahap, tidak ada `Kanban` sebagai step 6 dan bar `VibePlan [nama proyek]`. Completed/current/pending neutral dan dapat dibedakan; title/copy Ask lama yang fungsional tetap ada.
4. Jawab pertanyaan sesi 1 dan sesi 2 sesuai UI; uji sebagian recover/refresh pada state aman (setelah autosave) dan pastikan jawaban kembali benar. Uji opsi Skip sesuai existing policy. Jangan mengubah DB untuk memenuhi jawaban.
5. Lanjut ke Fitur lewat CTA normal. Catat ID sama dan URL benar; jika gagal, stop happy path dan perbaiki/diagnose, bukan melompati tahap.

### B2 — Feature Tree generation dan transisi PRD

1. Observasi loading nyata sejak request dimulai: topbar `Feature Tree` statis; dotted canvas + existing skeleton nodes; satu status `Menyusun daftar fitur...` dengan spinner, tanpa dua/lebih copy generation, timer/thinking card, atau state UI hardcoded.
2. Disabled forward CTA adalah action yang konsisten, tidak menduplikasi loading text. Pastikan klik berulang selama generation tidak memicu duplicate request.
3. Tunggu sampai actual tree tersimpan dan terlihat, bukan hanya animation berhenti. Periksa node asli, subfitur, zoom/pan, dan CTA `Generate PRD` yang benar. Reopen/refresh setelah sukses tidak membuat generation baru.
4. Klik Generate PRD melalui UI. Pastikan konteks Ask/Fitur tetap dibawa dan project ID tidak berubah.

### B3 — PRD live generation (critical)

Capture bukti tiga fase yang berbeda: pre-token, saat actual document streaming (sebelum done), dan persisted completion. Rekam/catat timestamp relatif yang benar jika diperlukan; jangan membuat angka simulasi.

- Pre-token: panel kanan menampilkan section checklist dengan spinner section aktif, tanpa card “Menyusun PRD / Menganalisis kebutuhan / Menulis dokumen” pada center dan tanpa typing dots/raw reasoning duplikat. Tidak ada bar project title.
- Saat token dokumen tiba, center canvas mulai terisi Markdown ter-render dan bertambah secara nyata **sebelum generation selesai**. Raw PRD tidak mengalir sebagai bubble Chat. Heading/TOC sesuai konten live; later sections muncul seiring actual content. Jangan menganggap screenshot setelah done sebagai bukti streaming.
- Checkmarks completed netral, current spinner informatif, pending muted; tidak semua section hijau. Jangan semua bagian marked complete saat stream masih aktif.
- PRD selesai: dokumen tetap ada, versi tersimpan, no blank flash yang mengganggu, step/availability sinkron. Periksa CTA `Generate AC` untuk akun eligible (bukan `Kembali ke Fitur >`). Pada v1 tidak ada toolbar/tab Pratinjau atau gap kosong pengganti.
- Periksa browser console dan relevant network events (sanitized): tidak ada duplicate generation, route/hydration errors, unexpected API failure atau leaked data. Jangan memalsukan `done` atau response.

### B4 — Chat toggle dan composer (runtime evidence wajib)

Lakukan pada PRD, baik saat idle maupun streaming pada operasi yang telah diotorisasi. Tidak perlu mengulang generation hanya untuk tampilan jika dapat diuji saat B3 atau B5.

1. Klik `Chat` di Navbar: panel kanan tutup, dokumen melebar, TOC tetap ada, tidak ada ghost width/border/overlay. Klik lagi: panel kembali dengan ukuran dan chat history/draft yang benar.
2. Toggle saat stream aktif: stream tetap berjalan, tidak abort/restart. Ketika Chat tertutup sebelum first delta (jika kondisi nyata dapat diamati), satu fallback status tersedia di center; setelah konten ada, fallback hilang. Jangan memaksa state via DOM untuk mensimulasikan kondisi. Jika terlalu cepat, catat kondisi tidak teramati, jangan mark Passed tanpa evidence.
3. Saat idle, klik area teks dan padding kosong bawah/kiri composer: textarea mendapat focus. Ketik teks dan cek draft. Click Send/Stop tidak memicu event wrapper yang salah atau submit ganda. Tab/focus/keyboard input dapat digunakan.
4. Send/Stop berada di kanan bawah yang sama, bukan kiri. Uji tombol Stop dengan klik sungguhan saat request active. Periksa area hit target, overlay (termasuk devtools bila relevan), z-index, scroll/resize handle. Stop tidak terhalang oleh disabled textarea. Periksa cancellation dan recovery behavior tanpa memaksa server success; jangan menganggap partial content adalah persisted PRD.
5. Jika stop test memerlukan membatalkan request yang masih berjalan, gunakan test project/operasi terpisah yang diotorisasi atau revisi yang aman, sehingga full happy path proyek utama tidak rusak. Verifikasi akun/kredit/release behavior melalui mekanisme yang sah. Jika environment/limit menghalangi, tandai scenario Not Verified.

**Catatan:** pengguna belum yakin apakah hit-testing bug ada pada Stop atau area kosong composer. Laporkan hasil kedua pengujian secara terpisah, termasuk akar masalah jika ditemukan. Jangan mengaku bug lama sudah diketahui pasti hanya dari CSS/source.

### B5 — PRD version history dan Diff

Sebelum maju ke AC (PRD mungkin terkunci setelahnya), lakukan revisi nyata melalui Chat yang diotorisasi, misalnya mengubah format laporan dari harian menjadi mingguan. Pastikan revision benar-benar selesai serta disimpan sebagai versi baru. Jangan menyuntikkan v2 melalui DB.

- Saat initial v1: document langsung tampil tanpa Pratinjau/tab redundant.
- Setelah v2 nyata: satu kontrol `Versi 2 ▾` di area document, pilihan previous/latest dan `Bandingkan perubahan` dalam menu yang sama. Jangan ada standalone tab Diff/Pratinjau permanen.
- Pilih versi lama: document/TOC sesuai konten actual, current version label benar. Latest bisa dipilih kembali. Compare menunjukkan pasangan/arah yang benar; highlight addition/deletion sesuai data dan keluar compare kembali ke dokumen. Tidak berubah project step/menambah versi karena memilih view.
- Chat toggle, panel resize, dan revision lifecycle tetap bekerja. Bila entitlement history terbatas, verifikasi gating yang benar dengan akun sah atau tandai skenario blocked; jangan bypass.

### B6 — Generate AC dan flow setelah PRD (critical)

1. Pastikan saved PRD dan plan valid. Klik `Generate AC` normal; cek route `/vibeplan/<id>/ac`, project ID sama, tidak ada route loop/premature backward CTA. Tidak ada step/progress yang dipalsukan.
2. Observe AC generation: satu pre-token loader ringkas, bukan verbose thinking panel atau multi-animated TOC placeholders. Saat actual content muncul, TOC terisi dari heading nyata dan dokumen bertambah di canvas; spinner berhenti sesuai lifecycle.
3. Inspect persisted acceptance criteria dan format yang benar; tidak ada tambahan bar project, step 6, status UI redundant. Verify retry/save failure behavior bila failure terjadi atau skenario aman yang diotorisasi tersedia; jangan sengaja merusak DB untuk memicu failure. Upgrade/paywall error tetap informatif.
4. Pastikan AC selesai membuka `Generate Task` yang benar untuk eligible. Klik via UI normal, bukan direct API.

### B7 — Task Breakdown dan Kanban

1. Saat Task generation: header `Task Breakdown` statis, satu compact status, dotted canvas + skeleton existing, tanpa raw thinking title/animasi titik/paragraph berulang. CTA/controls sesuai prerequisites, tidak menambah fake progress.
2. Setelah structured result valid, skeleton diganti task sebenarnya, hierarchy/dependencies sesuai data, zoom/pan dan actual task detail bisa digunakan. Implementation options/handoff tidak hilang.
3. Buka Kanban menggunakan kontrol UI normal. URL `/vibeplan/<id>/kanban` benar, stepper tetap lima tahap dengan Task sebagai representasi view. Tidak boleh muncul Kanban step 6.
4. Ubah status task test lewat UI sesuai role; refresh/reopen dan pastikan status/progres masih ada. Jika test reset tersedia dan memang dibutuhkan, lakukan hanya pada test project dengan konfirmasi normal. Jangan mengubah data pengguna nyata.

### B8 — History, deep link, compatibility, dan responsive/theme check

- Tinggalkan workspace secara aman, buka melalui History dan History Drawer; resume route benar dan saved Feature Tree/PRD/AC/Task/Kanban tidak hilang. Buka saved project langsung pada masing-masing child yang valid; browser Back/Forward dan reload tidak duplicate generate atau mengubah step mundur.
- Coba legacy URLs yang valid (`/ask/<id>`, `/fitur/<id>`, `/prd/<id>`, `/ac/<id>`, `/task/<id>`, `/kanban/<id>`) dengan project test dan stage yang tersedia; canonical redirect sesuai guard, tidak loop. Public PRD share yang sah tetap terpisah dan tidak membocorkan data; test hanya jika fitur/entitlement tersedia. Jangan membuka proyek milik pihak lain; authorization negative test hanya akun/proyek test yang diotorisasi.
- Periksa desktop (mis. 1440 px), tablet (~768–1024 px), mobile (~360–430 px), dan light/dark mode yang tersedia. Ukuran tersebut contoh, sesuaikan target responsive repo. Periksa content clipping, horizontal overflow yang tidak seharusnya, scroll ownership, composer/Stop reachable, TOC/Chat drawer/tab, resize handles, contrast, focus-visible/menu keyboard behavior. Pada desktop, panel kiri–tengah–kanan tetap terasa konsisten; mobile mengikuti responsive existing, bukan memaksakan desktop tiga kolom.
- Periksa loading/status hanya satu sumber primary per view, progress neutral, tidak ada UI baru yang tidak punya fungsi. Error/retry/paywall tetap ada jika dibutuhkan. Smoke-check shared consumers (Existing Codebase, PRD share/export) yang relevan dan authorized, jangan merusak fitur lain.

## 5. Bug triage dan loop perbaikan

Untuk setiap temuan, catat ID, severity, steps to reproduce, actual vs expected, route/project anonymized, viewport/state, screenshot/video/log yang relevan, dan source hypothesis yang dibedakan dari temuan terverifikasi. Prioritaskan critical functional regression (streaming salah lokasi, CTA buntu, data bisa hilang, duplicate generation/charge, access leak) sebelum UI polish.

Jika bug berkaitan langsung dengan P1–P8 dan dapat diperbaiki, perbaiki root cause, tambahkan targeted regression test, jalankan non-browser checks terkait, dan ulangi skenario browser yang gagal serta skenario downstream yang terpengaruh. Jangan mengabaikan temuan baru. Jika bug di luar scope atau membutuhkan akses/budget/keputusan tambahan, laporkan blocker/severity secara transparan; jangan memperluas pekerjaan tanpa batas atau mengklaim lulus. Jangan skip langkah awal yang gagal lalu menandai happy path selesai.

Bila fix perlu perubahan frontend, eksplorasi dan **wajib reuse komponen siap pakai yang sesuai** dari existing UI, HeroUI, shadcn/ui, Magic UI, React Bits, [https://www.thinkingorbs.com/#orbs](https://www.thinkingorbs.com/#orbs), [https://www.affectui.com/components](https://www.affectui.com/components), [https://tuffui.com/](https://tuffui.com/), [https://yappologistic.github.io/CUI/](https://yappologistic.github.io/CUI/), [https://www.sakaniui.com/](https://www.sakaniui.com/) dan library relevan. Jangan menambah animasi/copy/dekorasi hanya untuk memberi kesan fix. Custom minimal hanya jika tidak ada yang cocok, dengan alasan terdokumentasi. Pertahankan keputusan final user: skeleton Fitur/Task, single status, version history + Diff satu kontrol, no extra workspace header, five-step flow, neutral progress.

## 6. Final report (wajib evidence-based)

Buat QA report dengan tabel seperti:


| ID  | Scenario             | Expected                        | Actual | Result                                   | Evidence                 |
| --- | -------------------- | ------------------------------- | ------ | ---------------------------------------- | ------------------------ |
| B3  | PRD live first delta | Markdown di canvas sebelum done | ...    | Passed / Failed / Blocked / Not Verified | screenshot/log/test path |
| B4  | Stop hit-test        | click cancel once               | ...    | ...                                      | ...                      |


Jangan mengisi Passed otomatis. Sertakan:

- Branch/commit, environment, browser/tool yang benar-benar dipakai, test account role/plan tanpa credential, viewport, batas akses dan AI usage.
- Happy path lengkap atau titik berhenti nyata. URL route yang diuji, screenshot pre-token/live/persisted PRD, Fitur/Task skeleton loading, PRD v1 dan dropdown/diff, Chat open/closed dan composer Send/Stop, AC dan Kanban views bila telah diuji. Mask secrets/private data; jangan cantumkan token/session IDs.
- Reproduction dan status semua issue awal (termasuk composer yang sebelumnya belum jelas), hasil perbaikan dan rerun, bug baru, baseline errors, remaining blockers.
- Unit/integration/typecheck/lint/build commands setelah perbaikan QA, actual exit codes. Browser evidence tidak boleh digantikan dengan test pass.
- TODO verification update berdasarkan hasil nyata. Jangan centang QA seluruhnya jika skenario wajib belum bisa dilakukan.

**Final acceptance:** P8 lulus hanya jika happy path nyata dari project creation hingga Kanban dapat dijalankan tanpa known blocking regression, semua revisi visual yang disetujui terpenuhi berdasarkan pengamatan, dan skenario yang belum diverifikasi dicatat jujur (jangan menganggap blocked sebagai passed). Target adalah tidak ada regresi yang diketahui dalam cakupan yang benar-benar diuji, bukan klaim absolut “100% bug-free”. Jangan deploy, publish, push, merge, atau melakukan tindakan berbiaya tanpa otorisasi.
