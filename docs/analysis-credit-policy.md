# Existing Codebase: initial analysis entitlement

One successful initial repository analysis is included per account for its lifetime. This is not an allocation per repository name, Git remote, project, subscription period, or payment. Accounts with a ready analysis or a historically settled/refunded codebase-analysis operation before rollout have already used the entitlement. A synced repository whose initial analysis never succeeded remains eligible if its account has no successful analysis. Failed attempts release the entitlement; ready results remain reusable without a charge.

`users.initial_analysis_used_at` retains the consumed entitlement across repository deletion and subscription renewal. The migration backfills only that entitlement marker; it neither refunds nor rewrites historical charges or ledger entries. Apply `0040_initial_analysis_allowance.sql` before deploying the application. Its additions and backfill are idempotent. The migration is tested in an isolated PostgreSQL schema. Development migration uses `pnpm db:migrate`; it adds columns/index and backfills entitlement metadata without removing data.

Allowance attempts use the existing `credit_operations` lifecycle with `initial_analysis_allowance = true`, zero reservation, and zero final charge. No zero-amount financial ledger entries are inserted because the ledger forbids them. A user-scoped transaction advisory lock and partial unique index permit only one active allowance operation per account. The entitlement is consumed in the same transaction as analysis persistence and settlement. Rename, duplicate records, deletion, refresh, and subscription renewal do not reset it. Creating another account remains an account-abuse concern, not repository identity verification.

Paid analysis uses the existing adaptive pricing version and snapshot metrics, capped by its configured maximum (currently 12 credits). Pricing, Billing, and the sync prompt disclose this rate. Routine sync and analysis do not require session-local approval metadata or client consent. No pricing version or maximum is changed by removing that gate. A future material billing-policy change belongs to the account billing flow, not sync onboarding. First-analysis allowance and verified billing exemptions remain server-owned; paid operations reserve and settle through the existing atomic lifecycle.

Preflight reuses `GET /api/codebases?preflight=analysis`; the final quote reuses analysis POST with `preflight: true`. Preflight, repository creation, session recovery, and analysis share eligibility. They neither create subscriptions nor charge for opening a page or issuing credentials. Missing subscription data or failed billing reads produce `BILLING_UNAVAILABLE`, never free access or an insufficient-balance diagnosis. Ready analysis remains reusable without charge.

The onboarding entry derives one mutually exclusive state from server eligibility and a schema-validated session payload: checking eligibility, creating a session, prompt ready, credit blocked, or session creation failed. A valid payload always wins over a previously read credit status, so stale eligibility can never replace a live prompt with the lock, and the "connecting" progress line is only rendered while a request is genuinely in flight. There is no approval state to transition through.

Onboarding requires a UUID `requestId`, retained in the current browser history entry across refresh and retry. A new connection navigation receives a new identity. The repository primary key is SHA-256 of `[authenticatedUserId, requestId]`; the existing database primary key and transaction advisory lock enforce one repository and one initial session even for concurrent requests. An immutable create-input fingerprint rejects incompatible key reuse with `CODEBASE_ATTEMPT_CONFLICT`, survives rename, and occupies one hash per repository until explicit deletion. No repository-name deduplication or automatic cleanup occurs.

Only the initial successful create returns a cryptographically random sync credential. Database persistence contains its SHA-256 hash only; no credential can be reproduced from a secret or hash. Replayed creation returns the original repository and latest session identity with `CODEBASE_SESSION_RECOVERY_REQUIRED`, never another initial session or raw token. Recovery is metadata-only. Lost/malformed responses retain the attempt key and may be retried safely. Explicit replacement names the current session, invalidates its old credential, and creates one replacement under the same repository. A concurrent replacement loser receives metadata, not a replayed token. The handshake lock and in-transaction credential revalidation protect against stale prevalidated CLI requests. Active usable CLI sessions and uploaded snapshots cannot be replaced by onboarding retry. Expired incomplete uploads can be replaced. Explicit workspace re-sync remains a separate action. Credential responses use `no-store`; raw tokens are never persisted in browser storage or History.

Home Existing Codebase now navigates to the canonical onboarding flow rather than creating a second repository itself or passing raw credentials through sessionStorage. Sufficient credits automatically show the prompt; stale eligibility cannot mask a valid prompt. Missing one-time credentials show recovery on the same repository with an explicit replacement action, not another create. Routine create/recovery does not reserve or deduct analysis credits. Apply `0045_codebase_onboarding_idempotency.sql` before deploying this code. The additive nullable column preserves legacy records; old attempts without a verifiable fingerprint must resume through their existing repository identity, not be merged or recreated automatically.

A status `404` clears only stale onboarding pointers, finishes recovery loading before pointer invalidation, then rechecks eligibility. Temporary status failures retain recoverable identity and expose retry. Responses arriving after unmount or a different onboarding attempt cannot replace the active repository pointer or prompt.

Validated analysis output is currently retained only by the request until finalization commits. A rolled-back finalization cannot recover that output: retry uses the existing verified snapshot but invokes generation again. No output is exposed through logs or client storage. Avoiding regeneration requires a separately authorized, versioned server-side checkpoint with retention; the current analysis row has no checkpoint lifecycle.

Expiry comparisons must use Drizzle column operators such as `lte(expiresAt, now)`, not raw SQL interpolation of a JavaScript Date. The schema uses timestamp without timezone; raw Date parameters can be interpreted in the PostgreSQL session timezone and release a future reservation prematurely. Non-UTC PostgreSQL integration tests cover this boundary.

Provider calls have a bounded timeout. Analysis reservations expire after ten minutes and are reconciled on preflight, trigger, and sync-status reads. Expired linked pending analyses become failed and their holds are released; late settlement is rejected. A disconnected browser does not itself release a running operation. With no traffic, reconciliation happens on the next read rather than a separate scheduler. Existing size, upload validation, authentication, and rate limits still apply. Paused subscriptions cannot start analysis, including the allowance; legacy paid subscriptions without an end date remain valid.
