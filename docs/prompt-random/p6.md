# TASK 06 — Admin Transactions Pagination &amp; Financial Metrics Integrity

**Repository:** `ghazyAlghifari508/everythings-vibe`  
**Complexity:** CRITICAL  
**Scope:** `/admin/transactions`

## Objective

Implement scalable transaction management with accurate financial statistics.

Current problems:

1. Route initially loads only up to 100 transactions.
2. No pagination UI.
3. Search, status filter, and plan filter operate on loaded rows.
4. KPI counts are calculated from the limited array.
5. `Total Penerimaan` is derived from the loaded transactions rather than a full database aggregation.
6. A transaction outside the initial 100 cannot be reached through the current interface.

These issues must be fixed without modifying payment processing or billing ledger integrity.

## 3. Server-Side Pagination

Implement:

- Default 20 transactions per page.
- Bounded limit, maximum 100.
- Stable ordering: `createdAt DESC, id DESC`.
- Server-side search.
- Server-side payment status filter.
- Server-side plan filter.
- Accurate filtered total count.

Ensure filtering happens BEFORE pagination.

Use Drizzle parameterized queries.

Validate input:

- Page/offset cannot be negative.
- Limit cannot be unbounded.
- Search input is length-bounded.
- Status values are whitelisted.
- Plan values are verified against actual supported plans.

If query parameters are persisted in the URL, use the existing TanStack Router validation conventions.

Search and filter changes reset pagination to page 1.

Prevent stale responses from overriding newer filtered queries.

## 4. Preserve Existing Payment Status Semantics

The frontend currently groups several gateway statuses.

Audit the actual implementation carefully.

Known distinctions may include:

- `success`
- `settlement`
- `capture`
- `pending`
- `failed`
- `expire`
- `cancel`
- refund-related statuses where supported.

Do not use simple string equality in the backend if the UI's filter represents a group of equivalent business statuses.

For example:

`Berhasil`

must map to the actual accepted set of successful payment states.

`Gagal`

must map only to verified terminal unsuccessful states.

Do not treat pending payments as failed.

Use one consistent status-mapping policy across:

- Filtering.
- KPI counts.
- Table labels.
- Revenue calculations.

Preserve statuses that matter to reconciliation.

## 5. Fix Financial KPIs

Current Admin Transactions view calculates:

- `Total Transaksi` using `transactions.length`.
- Success count from the loaded array.
- Pending count from the loaded array.
- Total revenue by summing loaded successful transactions.

This is incorrect when more transactions exist than the initial result limit.

Replace with database-level aggregate queries.

Required:

- Total Transaksi.
- Transaksi Sukses.
- Menunggu Pembayaran.
- Total Penerimaan.

Aggregates must cover the intended complete dataset and follow explicit period/status semantics.

Financial requirements:

1. Do not include failed payments in successful revenue.
2. Do not double-count multiple representations of the same payment.
3. Use canonical financial status policy verified from billing services.
4. Avoid summing JavaScript floats for currency when the database already stores exact integer/minor-unit amounts.
5. Preserve currency formatting in Rupiah.
6. Confirm whether metric labels mean all-time or current-month totals.
7. Keep the Admin Dashboard and Transactions definitions consistent where they represent the same KPI.

If total transaction count is global while the table is filtered, keep that distinction clear.

Do not silently make KPI values depend on the current page.

## 6. Data Integrity &amp; Deletion Policy

The user wants cleaner tables, not destruction of payment history.

**Do not add hard-delete transactions in Admin.**

Preserve:

- Payment record history.
- Order IDs.
- Midtrans reconciliation.
- Webhook idempotency.
- Credit grants.
- Subscription state.
- Refunds and adjustments.
- Financial auditability.

For older failed, cancelled, or refunded records:

- Provide filtering and pagination.
- Retain valid transaction records.
- Do not automatically purge them.

If a record is under a separate documented retention policy, that policy is outside this pagination task.
