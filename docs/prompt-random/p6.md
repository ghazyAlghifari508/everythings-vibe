# TASK 06: Extend Existing Credit Ledger into a Universal Multi-Product Billing Architecture

**Complexity:** CRITICAL  
**Priority:** P0  
**Scope:** Billing domain, database schema, credit contracts, compatibility

## 1. Objective

Extend the existing credit system to support all billable EVVIBE product families:

- VibePlan Greenfield.
- VibePlan Codebase Existing.
- VibeDesign Studio.
- VibeScrape.

The platform must use a shared credit balance for paid plans.

Do not create separate recurring credit balances for Studio and Scrape.

VibeTemplate remains free.

Manual editing, viewing previous results, and non-generative workspace interactions remain free.

This task creates architectural support only. No unapproved Studio or Scrape charge may be activated.

## 3. Current Architectural Limitation

Previous source inspection identified:

- Existing operation types primarily cover codebase analysis, PRD, AC, and Task generation.
- `creditOperations.projectId` references the VibePlan project model.
- Studio and Scrape use their own resource and job models.
- They therefore cannot be safely represented by the existing mandatory project reference alone.

Reverify these observations against the current local checkout.

## 5. Resource Identity and Ownership

Design a typed, database-safe way for credit operations to reference resources beyond the VibePlan `projects` table.

Potential resource families:

- Existing plan project.
- Studio project/frame/job.
- Scrape resource/job.

Use an explicit, internally validated relationship model.

Evaluate:

- Nullable typed foreign keys with consistency constraints.
- Dedicated resource associations.
- Existing domain operation references.

Choose the smallest appropriate schema design that preserves referential integrity and existing query contracts.

Do not store arbitrary unvalidated strings as a substitute for ownership validation.

Do not create fake VibePlan projects merely to store Studio/Scrape credit operations.

Every operation must retain:

- User ownership.
- Product family.
- Operation identity.
- Relevant resource/job reference.
- Idempotency identity.
- Existing accounting linkage.

## 8. Shared Credit Accounting

Retain the existing credit source and allocation policy.

Required invariants:

- A reservation cannot exceed spendable capacity.
- Simultaneous operations cannot overspend the balance.
- A reservation must be tied to one logical operation.
- Retries cannot produce duplicate charges.
- Settlement cannot silently exceed the authorized/reserved maximum.
- Genuinely unused reservations are released.
- Refunds preserve accounting history rather than deleting operations.
- Failed work follows the verified failure policy.
- Billing exemptions remain authoritative.
- Historical subscription periods are not silently rewritten.

Respect period rollover while jobs are running.

Do not accidentally release credits from the wrong period or source bucket.

## 9. Trial Compatibility Foundation

The future entitlement system will support:

- One Studio trial per Free account.
- One Scrape trial per Free account.
- No recurring trial reset.
- Separate trial consumption tracking.

Prepare extensibility for identifying operation funding source:

- Existing paid allocation.
- Existing top-up allocation.
- Trial.
- Exempt operation, where supported.

Trial is not a fake monetary payment or fabricated paid credit balance.

Detailed trial behavior is implemented in TASK 10.

Do not activate trial restrictions here.

## 10. Safe Migration Strategy

Use additive, reviewed Drizzle migrations where practical.

Plan:

```
Existing schema
      |
Add compatible fields/associations
      |
Backfill only evidence-supported metadata
      |
Verify old and new readers
      |
Retain legacy compatibility
```

Requirements:

- No destructive reset.
- No truncation.
- No unsafe cascade deletion.
- No mutation of real user balances.
- No direct production migration.
- No historical charge recomputation.
- Preserve accounting-linked tombstones when required.

Generate and inspect migration output.

Test migrations against a disposable isolated database or representative test fixtures.

Report deployment steps that remain pending.

## 11. Transaction and Concurrency Safety

Verify:

- Atomic reservation.
- Concurrent spending across feature families.
- Duplicate submission handling.
- Worker retries.
- Conflicting settlement attempts.
- Cancellation.
- Crash recovery.
- Stale reservation reconciliation.
- Idempotent refund/release behavior.

Do not introduce a generic distributed architecture if existing database transaction primitives can safely solve the problem.

Do not weaken ownership or authorization.
