# TASK 06 — Refocus API Keys Settings on Integration Access Management

**Repository:** `ghazyAlghifari508/everythings-vibe`  
**Complexity:** MEDIUM  
**Scope:** Settings API Keys UI and access management experience

## Objective

Improve the `/settings/api-keys` page to reflect how everythings-vibe actually works.

Most ordinary users should not need to manually create an API key before using Greenfield or Codebase Existing AI Agent handoff.

The existing system already automates key/token provisioning through its respective workflows.

Therefore, transform the page into a clear access-management interface rather than presenting manual credential generation as the primary action.

Do not remove existing credential management or break power-user integrations.

## 1. Mandatory Investigation

Read all applicable agent/design rules and inspect:

- `src/features/auth-settings/components/settings/api-keys-client.tsx`
- `src/routes/settings/api-keys.tsx`
- Shared `SettingsContentPanel`
- API key listing and revocation endpoints
- Automatic key generation endpoint
- Relevant tests
- Existing manual API key consumers

Verify which credentials can reliably be identified as automatic versus manual.

Do not assume naming prefixes alone are an authoritative security boundary.

## 2. Desired Information Hierarchy

Current:

```
API Keys                         [+ Buat API Key Baru]

Existing keys / empty state
Create manual key modal
```

Target:

```
┌────────────────────────────────────────────────────┐
```

The UI should use the actual API fields available.

Do not invent labels, lifecycle states, or activity timestamps that the backend cannot support.

## 3. Primary Experience

The main section should communicate:

- Which integrations have access.
- When credentials were created.
- Their last use, when known.
- Their expiration, when applicable.
- Their permissions.
- How to revoke access.

Use clear Indonesian product copy.

Example description:

`Akses untuk AI Agent dan CLI dibuat otomatis saat kamu menghubungkan integrasi. Kamu bisa memeriksa dan mencabut akses di sini.`

Refine wording based on the verified behavior.

Do not make promises that are not true for Codebase Existing sync tokens.

## 4. Manual API Key Creation

Move manual API key generation into a secondary advanced section.

Recommended label:

`Pengaturan lanjutan`

Inside, provide the existing manual creation flow for users who explicitly need custom integrations.

Do not permanently delete the manual API key endpoint unless an independent consumer audit establishes that it is unnecessary.

Preserve:

- Key naming.
- Scope selection.
- One-time raw-key visibility.
- Copy action.
- Validation.
- Error states.

Do not expose the raw key again after the creation flow closes.

## 5. Empty State

Avoid the current empty-state approach that heavily emphasizes:

`Buat API Key`

Instead, explain that access is created automatically through supported handoff flows.

Provide an understated explanation.

Do not add random product navigation links or fake CTA buttons.

Keep advanced manual creation discoverable for users who need it.

## 6. Revocation

Revoking an access token is a security-sensitive action.

Maintain:

- Confirmation before revocation.
- Clear naming of the credential being revoked.
- Correct backend authorization.
- Accurate success/error feedback.
- Updated list after successful revocation.

Explain that revoking a credential may stop an existing CLI/agent integration.

Do not disable all credentials when a user revokes one.

## 7. Mandatory Component-First UI

Before coding, inspect the existing Settings component system.

Explore suitable ready-made components from:

- shadcn/ui
- HeroUI
- MagicUI
- ReactBits
- Thinking Orbs
- AffectUI

**Reuse existing or approved prebuilt components wherever appropriate.**

Suitable primitives may include:

- Table.
- Dialog.
- Button.
- Disclosure/Accordion.
- Tooltip.
- Badge.
- Empty state.

Do not build a table, dialog, or accordion from scratch when a suitable ready-made component exists.

Keep the design restrained and consistent with other Settings pages.

No decorative gradients, fake security badges, unnecessary card nesting, or oversized headings.

Do not install libraries solely for visual decoration.

## 8. Responsive &amp; Accessibility

- Clear content hierarchy.
- Keyboard-accessible disclosure and dialogs.
- Responsive credential list.
- Safe truncation of identifiers.
- Accessible revoke controls.
- No exposed full secrets in lists.
- Proper disabled/loading states.
- Consistent light/dark tokens.

## 9. Testing

Update tests for:

- Auto-generated credential listing.
- Manual creation in advanced section.
- Empty state.
- Expired/revoked states where available.
- One-time secret display.
- Revocation confirmation.
- Keyboard accessibility.
- No regression in existing Settings layout.

Run focused Vitest, TypeScript, and Biome.

No browser QA, Playwright browsers, or screenshot automation.

## Definition of Done

The page primarily manages integrations instead of encouraging unnecessary manual credential creation.

Manual creation is secondary but available where supported.

Automatic handoff continues functioning.

No credential security regression.

Update tracked TODO items only after verification and report completed work.
