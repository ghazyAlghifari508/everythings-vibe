# TASK 09: Calibrate Real Credit Pricing from Verified Operational Benchmarks

**Complexity:** HIGH  
**Prerequisites:** TASK 06, TASK 07, TASK 08  
**Scope:** Pricing registry, unit economics, trial limits, pricing approval

## 1. Objective

Determine defensible proposed credit tariffs for Studio and Scrape using actual benchmark evidence.

The owner explicitly selected benchmark-based pricing and allocation evaluation.

Do not derive production prices from arbitrary AI recommendations.

Do not treat illustrative prices from earlier discussions as approved prices.

## 2. Current Plan Baseline

Verify the current production configuration.

Previously audited packages:

- Free: 2 credits per 30 days for the existing VibePlan entitlement.
- Pro: Rp49.000, 30 credits.
- Hengker: Rp149.000, 105 credits.

Keep current package prices and allocations unchanged unless a revised proposal is explicitly approved.

## 3. Pricing Models

Develop a proposal using the agreed hybrid strategy.


| Operation                              | Intended model                        |
| -------------------------------------- | ------------------------------------- |
| Studio Generate                        | Adaptive                              |
| Studio Add Frame                       | Fixed/adaptive based on size          |
| Studio AI Revision                     | Adaptive                              |

| Scrape HTML                            | Fixed within verified resource limits |
| Scrape Images                          | Fixed within verified resource limits |
| Generate [DESIGN.md](http://DESIGN.md) | Adaptive                              |


Map these to actual implemented operations.

Do not charge for nonexistent or unsupported features.

## 4. Calibration Inputs

Use actual evidence from shadow metering:

- AI provider usage and cost.
- Browser execution.
- Worker CPU/RAM where measurable.
- Storage and bandwidth.
- Success rate.
- Retry overhead.
- Failed-operation overhead.
- Partial completion.
- Expected job frequency.
- Subscription revenue assumptions.

Distinguish measured costs from business assumptions.

Do not use current free-provider access to conclude long-term service cost is zero.

Use verified paid-provider scenarios separately where useful.

## 5. Produce Financial Scenarios

Compare at least:

A. Existing plan allocations with calibrated operation prices.

B. Existing subscriptions with increased credit allocations.

C. Alternative bounded operation pricing where the initial model is unsustainable or excessively expensive for users.

For each scenario report:

- Effective credits per operation.
- How many ordinary operations a Pro user can perform.
- How many ordinary operations a Hengker user can perform.
- Cost exposure for high-usage accounts.
- Trial cost exposure.
- Assumptions and uncertainties.

Do not claim profit margins are guaranteed without complete cost data.

## 6. Trial Policy Calibration

Previously agreed:

- One Studio trial per Free account.
- One Scrape trial per Free account.
- Studio trial targets one generated frame.
- Scrape trial targets one bounded extraction job.
- No monthly trial reset.
- Failed system operation should not consume the trial permanently.

Determine proposed Scrape trial limits based on measured costs.

Include:

- Allowed modes.
- Maximum completed/requested pages.
- Image or byte limits.
- Browser runtime limits.
- Supported [DESIGN.md](http://DESIGN.md) configuration.
- Retry handling.

Define treatment for partial success and cancellation before activation.

A trial cannot be consumed twice through retries, deletion, or subscription changes.

## 7. Pricing Registry and Quote Contract

Prepare an explicitly versioned tariff proposal.

```
Operation + Input Metrics
          |
          v
Versioned pricing policy
          |
          +--> Estimate
          +--> Maximum charge
          +--> Settlement calculation
```

A new operation must pin its pricing version.

An already accepted operation must not be repriced using a later registry version.

For adaptive operations:

- Define measurable billing units.
- Define minimum/maximum.
- Define rounding.
- Define partial-success settlement.
- Prevent final charges exceeding the authorized maximum.

For fixed operations:

- Verify resource limits.
- Avoid permitting unlimited resource use at a fixed nominal price.

## 8. User Experience Decision

The pricing policy must support inline estimates.

Do NOT design a permission or confirmation popup for normal credit consumption.

If credits/trial are sufficient:

- User clicks the existing operation button.
- Backend validates and reserves.
- Work starts directly.

If credits are insufficient:

- Use the existing Credit Exhausted Modal.

For large jobs:

- Display the maximum possible charge inline.
- Do not impose another confirmation popup.

## 9. Mandatory Approval Gate

Produce a complete proposal for owner review.

Do not activate production pricing until the owner has approved:

- Exact tariff values.
- Trial limits.
- Allocation changes, if any.
- Partial/cancellation settlement policy.
- Deployment/rollout strategy.

If benchmark evidence is insufficient:

- Clearly identify missing measurements.
- Keep new charging disabled.
- Keep the pricing calibration item pending.
- Provide the appropriate next benchmark action.

Do not make up cost data to unblock implementation.

## 10. Verification

Test any prepared pricing-policy implementation using explicitly labelled synthetic test tariffs.

Test:

- Deterministic quotes.
- Fixed/adaptive boundaries.
- Version pinning.
- Rounding.
- Maximum cap.
- Partial settlement policy.

Synthetic test values are not production tariffs.

No browser QA.

## Definition of Done

A reproducible, evidence-backed pricing proposal exists.

Any approved configuration is versioned and testable.

Unapproved tariffs remain inactive.

Report the measured data, proposed rates, plan comparison, trial limits, assumptions, and unresolved decisions.

Do not mark pricing approval complete without actual approval.
