## 2. KNOWN MEASUREMENTS FROM THE USER

The user previously ran the following commands on Windows PowerShell while the development server was running.

### IPv4 loopback

Command:

curl.exe -s -o NUL -w "Connect: %{time_connect}s | TTFB: %{time_starttransfer}s | Total: %{time_total}s\\n" [http://127.0.0.1:3000/](http://127.0.0.1:3000/)

### localhost

Command:

curl.exe -s -o NUL -w "Connect: %{time_connect}s | TTFB: %{time_starttransfer}s | Total: %{time_total}s\\n" [http://localhost:3000/](http://localhost:3000/)

Results:

Run 1:

- Connect: 0.206111s
- TTFB: 0.229513s

- Connect: 0.207948s
- TTFB: 0.232214s
- Total: 0.232768s

### Initial Interpretation

These results indicate:

1. The already-running local server can return HTML very quickly over direct IPv4.
2. `localhost` exhibits approximately 200ms of additional connection latency.
3. This discrepancy could involve IPv4/IPv6 selection, proxy configuration, local networking, or another hostname-dependent factor.
4. The measurements DO NOT prove that this 200ms delay explains the user's much longer browser startup experience.
5. These measurements DO NOT cover development server cold startup, initial module compilation, JavaScript loading, React hydration, or post-load API requests.

**Do not incorrectly conclude that the problem is solved or caused exclusively by localhost DNS resolution.**

The main user complaint concerns the complete cold-start experience.

## 3. INVESTIGATION PHASE A — IDENTIFY EXACTLY WHERE TIME IS SPENT

Decompose the development startup process into measurable stages.

### Stage A: Command Initialization

Measure the time spent between invoking the development command and beginning the actual Vite process.

Inspect:

- Package manager startup overhead.
- Pre-development scripts.
- Studio skill asset generation.
- File validation or hashing operations.
- Synchronous filesystem operations.
- Unnecessary repeated preparation work.

The repository previously used a development command resembling:

pnpm studio &amp;&amp; node --dns-result-order=ipv4first node_modules/vite/bin/vite.js dev --port 3000

Verify whether this is still accurate.

Measure the duration of `studio:assets` independently.

Determine whether its generated assets actually need to be recreated on every server startup.

If checks are unnecessary or expensive, investigate safe caching, incremental generation, or change detection.

Do not remove required asset generation or silently introduce stale generated files.

### Stage B: Vite Server Initialization

Measure:

- Time until Vite starts.
- Plugin initialization.
- Time until the server reports Ready.
- Dependency scanning.
- Route generation.
- TanStack Start integration.
- Tailwind processing.
- Filesystem scanning.

Identify unusually expensive plugins or initialization hooks.

Do not assume every Vite plugin is responsible merely because it appears in the configuration.

### Stage C: First HTTP Request

After Vite reports Ready, measure:

- First HTML request latency.
- First-route SSR time.
- Module transformation time.
- Warmed request latency.
- Server-side import/evaluation overhead.

Compare first request against subsequent requests.

Determine whether the slow startup happens before the server is ready or after the first browser request begins.

### Stage D: Client Application Initialization

Investigate:

- Initial JavaScript module loading.
- Hydration workload.
- Large synchronous computations.
- React providers mounted globally.
- Heavy components included in the initial route.
- Client-side data fetching.
- Blocking loading states.
- Initial font/CSS loading.

Distinguish an actually slow server from a page that has received its HTML but remains visually blocked by client initialization.

Terminal HTTP timing alone cannot establish browser rendering time.

Do not claim to have measured hydration or visual readiness without appropriate evidence.

## 4. INVESTIGATION PHASE B — EXAMINE SPECIFIC HYPOTHESES

The following hypotheses were identified during a preliminary source audit.

Investigate each one, but do not treat it as necessarily true.

### Hypothesis 1 — Expensive Vite Cold Compilation

The application uses TanStack Start, React, TypeScript, Vite, and multiple feature modules.

Investigate:

- First-request module transformation overhead.
- Dependency optimization.
- Lazy loading.
- Initial import graph size.
- Excessive route/component eager imports.
- Vite cache invalidation.
- Unnecessary dependency pre-bundling.

Check whether slow startup occurs only after cache invalidation or on every clean server restart.

Avoid clearing caches before establishing baseline measurements.

### Hypothesis 2 — Studio Asset Generation

Investigate the pre-start asset pipeline.

Measure its execution time and inspect whether:

- Files are regenerated unnecessarily.
- Large directories are scanned repeatedly.
- Hashing is excessive.
- Files are rewritten despite unchanged contents.
- The script creates avoidable downstream invalidation.

Optimize only if measured overhead justifies the change.

### Hypothesis 3 — Development Tooling Overhead

The root application previously mounted:

- TanStack Devtools.
- TanStack Router Devtools.
- TanStack Query Devtools.

Determine whether these increase cold transformation or initial client bundle workload.

Investigate safe development-only lazy loading or isolation if they contribute meaningfully.

Preserve useful debugging functionality.

Do not disable development tools blindly.

### Hypothesis 4 — Initial Authentication, Billing, or Database Requests

Inspect initialization of:

- Better Auth session.
- Navbar user session.
- User plan/credit queries.
- Subscription status.
- Global data loaders.
- PostgreSQL connections.

Check for:

- Slow database connection establishment.
- Network connection timeouts.
- Blocking server-side data fetching.
- Redundant requests.
- Duplicate session queries.
- Sequential requests that could safely be independent.
- Query waterfall.
- Excessive retry behavior.
- Poorly configured connection pools.

Do not bypass authentication or authorization to improve performance.

Do not cache private user data globally.

### Hypothesis 5 — CSS, Tailwind, and External Fonts

Inspect all CSS entrypoints and external font loading.

Investigate:

- Duplicate global stylesheet processing.
- Excessive CSS compilation.
- Redundant Tailwind directives.
- Blocking font requests.
- Unnecessary font weights/styles.
- Large style dependencies.

Do not remove styles or fonts without checking affected components.

### Hypothesis 6 — localhost / IPv4 / IPv6 Behavior

The recorded timings show:

- `127.0.0.1` connects in approximately 1ms.
- `localhost` connects in approximately 207ms.

Investigate:

- IPv4 vs IPv6 resolution.
- IPv6 loopback listener availability.
- Local proxy configuration.
- Relevant Windows host resolution behavior.
- Security software interference, where observable.
- Vite host binding configuration.
- HTTP keep-alive/connection reuse.

Use safe terminal tests, such as:

curl.exe -4 -s -o NUL -w "Connect: %{time_connect}s | Total: %{time_total}s\\n" [http://localhost:3000/](http://localhost:3000/)

curl.exe -6 --max-time 5 -s -o NUL -w "Connect: %{time_connect}s | Total: %{time_total}s\\n" [http://localhost:3000/](http://localhost:3000/)

curl.exe --noproxy "*" -v [http://localhost:3000/](http://localhost:3000/) -o NUL

Do not alter Windows networking configuration, disable firewall protection, or edit the hosts file without verified necessity and explicit authorization.

Do not assume the browser and curl resolve `localhost` identically.
