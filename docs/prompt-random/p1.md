# TASK 01 — Payment History Integrity &amp; Safe Retention

**Repository:** `ghazyAlghifari508/everythings-vibe`  
**Branch:** current working branch  
**Complexity:** CRITICAL  
**Scope:** Billing backend, payment history deletion, transaction integrity

## Objective

Replace the unsafe payment-history deletion behavior with a reliable transaction-record retention policy.

Currently, `src/features/billing/services/billing-settings.functions.ts` exports a `deletePayment` server function that physically deletes payment records when their status is not `success`.

The Billing UI also exposes a delete button for non-successful payments.

This creates unnecessary risks because payment records participate in payment reconciliation, callback processing, auditability, and customer support.

**The user wants a clean payment history UI, not the destruction of financial records.**

Implement the safest reasonable solution while preserving payment functionality.

## 2. Correct Data Retention Policy

Implement these principles:


| Payment status    | User history                      | Database record      |
| ----------------- | --------------------------------- | -------------------- |
| Successful        | Visible                           | Retained             |
| Failed            | Available through history/filter  | Retained             |
| Cancelled/expired | Available through history/filter  | Retained             |
| Pending           | Follow existing visibility policy | Retained as required |
| Refunded/disputed | Accurately represented            | Retained             |


Do not add a hard-delete button for successful transactions.

Do not retain the existing hard-delete action for failed transactions merely because it is already implemented.

Prefer filtering and compact presentation to destructive cleanup.

Any actual retention/deletion policy must be explicitly defined, justified, and compliant with applicable obligations; do not invent a universal legal retention period.

## 3. Remove Unsafe User-Facing Deletion

- Remove the obsolete delete confirmation dialog.
- Remove the unused `deleteId` state.
- Remove the unused `handleDelete` logic.

From the server:

**Important:** Do not introduce a new archive database column merely to solve this UI issue.
