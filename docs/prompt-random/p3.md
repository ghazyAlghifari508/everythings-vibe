# TASK 03 — Server-Side Credit Usage History Pagination

**Repository:** `ghazyAlghifari508/everythings-vibe`  
**Complexity:** HIGH  
**Scope:** Settings Billing, credit operation queries, pagination and filters

## Objective

Make `Riwayat Penggunaan Kredit` scalable, readable, and accurate when a user has hundreds or thousands of credit operations.

Currently:

- `billing-settings.functions.ts` loads the latest 50 credit operations.
- `credit-usage.tsx` filters the loaded array locally.
- All matching rows are rendered without pagination.
- The table can become excessively long.
- Filtering cannot discover older records beyond the initial 50.

This must be corrected at both the database/query and UI layers.

## 3. Server-Side Query Contract

Move stage and status filtering to the database query.

The query MUST:

- Require the authenticated user.
- Filter by `creditOperations.userId`.
- Apply the requested stage/status filters before pagination.
- Enforce a safe maximum page size.
- Use stable newest-first ordering.
- Resolve project names only from authorized user-owned projects.
- Return only the fields required by the UI.
- Handle invalid filters safely.

Recommended initial page size: 10 or 20 operations.

Prefer cursor pagination for high-volume event histories when supported by the current architecture.

For a cursor scheme, use a deterministic compound ordering such as:

`createdAt DESC, id DESC`

This avoids unstable ordering when events share timestamps.

If implementing offset pagination instead, justify the decision and ensure correctness with stable ordering.

Do not fetch the entire history into memory.

## 4. Pagination State

Support:

- Next page.
- Previous page where feasible.
- End-of-results indication.
- Loading state.
- Empty state.
- Filtered-empty state.
- Query error/retry state.
- Filter changes resetting pagination to the first page.

Keep pagination state consistent with established TanStack Router/Query conventions.

Avoid using arbitrary local state that gets out of sync with server data.

Do not generate fake totals.

Only show an exact total count if the server calculates one correctly.

## 6. Credit Ledger Integrity

DO NOT introduce user-facing hard deletion of credit operations.

These records are required for:

- Billing explanations.
- Reservation/settlement reconciliation.
- Failed-operation investigations.
- Credit refund/release tracking.
- Duplicate charge investigations.

Do not modify:

- Credit charging.
- Credit settlement.
- Reservation idempotency.
- Ledger balance.
- Refund logic.

Pagination is a reading-layer change, not a financial-state change.
