# TASK 03 — Modularize Oversized Drizzle Schema Without Database Changes

Repository: ghazyAlghifari508/everythings-vibe  
Target: Remaining high-risk refactoring work.

## Objective

Refactor `src/db/schema.ts`, currently approximately 1,393 lines, into cohesive schema modules.

**This is source-code modularization, NOT a database schema migration.**

The resulting database model must be behaviorally and structurally identical.

## 1. Mandatory Deep Audit

Read [AGENTS.md](http://AGENTS.md), architecture rules, no-type-bypass rules, and current Drizzle configuration.

Inspect:

- `src/db/schema.ts` completely.
- `src/db/index.ts` or current database client.
- `drizzle.config.ts`.
- Existing migrations and snapshots.
- All schema imports.
- SQL constraints, foreign keys, indexes, and relation declarations.
- Services depending on schema types.

Capture the current database schema metadata BEFORE editing.

Inspect the dependency graph between tables.

Do not begin by moving arbitrary groups of lines.

## 2. Target Structure

Organize by cohesive schema responsibility.

Illustrative structure:

src/db/  
├── schema.ts # Stable public re-export facade  
└── schema/  
├── auth.ts  
├── billing.ts  
├── projects.ts  
├── codebase.ts  
├── scrape.ts  
├── studio.ts  
├── feedback.ts  
└── shared-types.ts

Names and module boundaries must follow actual FK dependencies and import relationships.

The target is not to create an excessive number of tiny files.

Move table definitions and tightly coupled types together.

Preserve the current public imports from `@/db/schema`.

## 3. Non-Negotiable Schema Invariants

Preserve EXACTLY:

- SQL table names.
- Column names.
- Column types.
- Nullability.
- Default values.
- Primary keys.
- Foreign keys.
- Foreign key actions.
- Check constraints.
- Unique constraints.
- Indexes.
- Enum-like values.
- Table relations.
- Existing inferred TypeScript types.

Do not rename tables, reorder business contracts, or change generated SQL semantics.

Avoid accidental circular dependencies caused by cross-domain foreign keys.

If a clean split would require dangerous circular imports, identify and solve the dependency design before moving the relevant tables.

## 4. Migration-Neutral Verification

Before and after refactoring:

- Compare schema exports.
- Compare Drizzle table metadata.
- Compare generated schema/migration output using safe, non-mutating inspection.
- Verify migration snapshots remain semantically unchanged.
- Verify the ORM still resolves all relationships.
- Verify type inference for existing services.

DO NOT:

- Run `db:push`.
- Run `db:migrate`.
- Reset any database.
- Delete migrations.
- Introduce new migration files for source-only restructuring.

If generated SQL changes unexpectedly, stop and investigate instead of accepting it.

## 5. Architecture Quality

The root `schema.ts` should become a stable, thin facade.

Individual schema modules should respect the repository's 400-line maximum where practical without harming FK integrity.

Keep pure utility functions away from unrelated schema declarations where a cohesive extraction is possible.

Maintain strict typing.

No behavior changes, database contract changes, or unrelated refactors.

## 6. Verification

Run:

- Targeted database schema tests.
- TypeScript validation.
- Relevant Drizzle schema validation.
- Targeted tests for auth, credits, project persistence, codebase, scrape, and studio schema consumers.
- Biome checks.

Use safe mocks or an explicitly configured test database for integration tests.

Never mutate production data.

No browser QA or Playwright browser execution.

## 7. Completion Criteria

- Schema source is modular and maintainable.
- Existing import contracts continue working.
- No unintended SQL schema difference.
- No missing or duplicated exports.
- No circular dependency regression.
- All relevant checks pass.

Commit atomically, push to the working branch according to repository rules, and report:

- Modules created.
- Export compatibility.
- Before/after schema comparison.
- Tests.
- Any unresolved risk.

Do not claim completion if schema equivalence is unverified.
