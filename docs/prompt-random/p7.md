# TASK 07 — Paginate Admin Feedback &amp; Error Reports with Accurate Metrics

**Repository:** `ghazyAlghifari508/everythings-vibe`  
**Complexity:** HIGH  
**Scope:** `/admin/feedback`, Feedback and Error Report read/query layer

## Objective

Make the Admin Ticket page scalable when the platform receives hundreds or thousands of feedback submissions and system error reports.

Currently, the page loads both complete lists:

- `listFeedback()`
- `listErrorReports()`

Then filters and renders them in the browser without pagination.

This can cause:

- Very large server responses.
- Slow page loading.
- Increasing rendering cost.
- Extremely long tables.
- Difficult navigation.
- Poor administrative usability.

Fix the query and pagination layers.

**The separate status/archive workflow will be implemented in TASK 08. Do not duplicate that work here.**

## 2. Server-Side Pagination

Implement independent pagination for the two data sources.

### Feedback

Backend should support:

- Page or offset.
- Page size.
- Type filter.
- Search.
- Stable order.
- Total filtered count.

### Error Reports

Backend should support:

- Page or offset.
- Page size.
- Search.
- Stable order.
- Total filtered count.

Recommended defaults:

- 20 rows per page.
- Bounded maximum 100.
- `createdAt DESC, id DESC`.

Do not load all records and slice the array in the browser.

Keep `requireAdmin` on every endpoint.

## 3. Preserve Tab Independence

The Feedback and Error Reports tabs represent different datasets.

Recommended behavior:

- Switching tabs loads the correct dataset.
- Each tab can maintain its own page/filter state.
- Searching resets pagination for the relevant tab.
- No stale previous-tab results.
- No unnecessary repeated full-database fetch.
- Accurate empty/loading/error states.

Use existing TanStack Router/Query conventions.

Do not accidentally search error records using only feedback-specific fields.

## 4. Server-Side Filters

Feedback:

- Type: Semua, Bug, Feature, General.
- Search message.
- Search sender name/email where available.

Error Reports:

- Search error message.
- Search context.
- Search associated user name/email where available.

For both:

- Trim and bound search input.
- Use safe parameterized Drizzle queries.
- Apply filters BEFORE pagination.
- Escape literal wildcard input where appropriate.
- Support combined filters correctly.

No client-only filtering over the first page.

## 5. Accurate KPI Aggregates

Current UI calculates:

- Total Masukan.
- Feedback Umum.
- Permintaan Fitur.
- Bug &amp; Crash.

It currently does so using the loaded arrays.

When pagination is introduced, this calculation would become incorrect unless moved to database aggregation.

Required:

- Total Masukan = verified feedback total + error report total, according to the existing label definition.
- Feedback Umum = full relevant dataset.
- Permintaan Fitur = full relevant dataset.
- Bug &amp; Crash = feedback type Bug plus system error reports, according to the current definition.

Do not double-count a record.

Use the actual schema and establish clear counting semantics.

Counts should not change just because the admin moves between pages.

Keep the existing KPI card layout unless a small consistency fix is required.

## 8. Performance

- Query only page-sized results.
- Avoid N+1 queries for user information.
- Apply proper DB filters.
- Use stable ordering.
- Calculate counts via aggregation.
- Handle network race conditions.
- Avoid unnecessary refetch loops.

Inspect existing DB indexes and add narrowly justified indexes only if needed.

## 9. Security &amp; Data Integrity

- Admin-only authorization.
- No endpoint exposing private feedback data to ordinary users.
- No arbitrary deletion of feedback/error reports.
- No change to user feedback submission behavior.
- Do not expose new sensitive fields from error context.
- Preserve current report text.

This task is read/query/pagination only.
