# TASK 02 — Billing Layout Consistency &amp; Scalable Payment History

**Repository:** `ghazyAlghifari508/everythings-vibe`  
**Complexity:** MEDIUM–HIGH  
**Scope:** `/settings/billing`, payment history presentation and navigation

## Objective

Fix the Billing UI so it remains clean and compact regardless of the number of payment transactions.

The current desktop layout places two cards side by side:

1. `Billing & Kredit`
2. `Riwayat Pembayaran`

The payment card becomes tall as more transactions appear, and the subscription card visually stretches to the same height, creating excessive empty space.

The server currently limits payment history to 10 latest non-pending records. That prevents unlimited initial loading, but older history is not accessible through proper pagination.

Deliver a coherent, scalable design.

Read [`AGENTS.md`](http://AGENTS.md), applicable `.agents/rules/`, and existing layout conventions.

Inspect:

- `src/features/billing/components/billing-page.tsx`

- `src/routes/settings/billing.tsx`
- Settings shared content shell.
- Existing pagination, dialog, popover, and table components.
- Relevant billing tests.

Compare at least two sibling Settings pages before changing the layout.

Do not implement a new visual style unrelated to existing Settings design.

Requirements:

- Independent natural card heights.
- No forced excessive minimum height.
- Keep subscription information concise.
- Maintain consistent panel padding and heading scale.
- Ensure actions do not overflow on smaller viewports.
- Preserve the established Settings container and tokens.

Do not shrink important information merely to make both cards visually identical.

## 3. Payment History Preview

Show approximately 4–5 latest transactions in the summary card.

Keep:

- Amount.
- Timestamp.
- Accurate payment status.

Use appropriately compact rows.

Avoid one large bordered card nested inside another for every payment if a simple divided list is clearer.

Never display raw order secrets or gateway tokens.

Provide a clear `Lihat semua transaksi` action when full history is available.

## 4. Full Payment History

Implement access to complete payment history without creating an unnecessary global navigation link.

Preferred UX:

- An expandable/full-history section within Settings Billing, or
- An existing suitable dialog/drawer pattern if that provides better usability.

Avoid introducing a new route unless existing routing conventions clearly justify it.

For the complete history:

- Server-side pagination.
- Stable newest-first ordering.
- Bounded page size (approximately 10–20 records).
- Clear next/previous behavior.
- Loading, empty, error, and end-of-results states.
- Optional relevant status/date filtering if supported cleanly.

Do not implement pagination by fetching all payment records and slicing them in the browser.

The server must enforce:

- Authentication.
- Ownership filtering.
- Input validation.
- Bounded page size.
- Deterministic ordering.

Use cursor pagination if appropriate; otherwise use properly bounded offset pagination consistent with existing patterns.

## 5. Payment Status Presentation

Do not collapse every non-success state into `Gagal` without checking the actual status model.

Preserve the distinction between:

- Successful.
- Failed.
- Cancelled.
- Expired.
- Refunded/disputed, if supported.
- Pending, according to the verified visibility policy.

Do not invent status labels unsupported by the current backend.

Remove payment deletion actions if the preceding integrity task has already retired them.

## 6. Mandatory Component-First UI Workflow

Before authoring any JSX:

1. Inspect existing Billing and Settings components.
2. Search `src/components/ui` for suitable Card, Button, Dialog, ScrollArea, Pagination, Select, and Table primitives.
3. Explore appropriate ready-made patterns from:
   - shadcn/ui
   - HeroUI
   - MagicUI
   - ReactBits
   - Thinking Orbs
   - AffectUI
4. Reuse existing or approved ready-made components whenever suitable.

**Building a replacement component from scratch is a last resort.**

Use visual/animated libraries only when appropriate. A financial history table does not need decorative orb animations.

If a needed component does not exist, implement the smallest cohesive custom component consistent with the established design system, and explain the choice.

No AI-slop:

- No unnecessary gradient.
- No oversized card padding.
- No nested decorative cards.
- No meaningless badges.
- No giant heading.
- No visual inconsistency with Profile or other Settings pages.
- No extra navigation that was not requested.

## 7. Responsive Requirements

Desktop: two columns, independent heights.

Tablet: preserve readable contents and actions.

Mobile:

- Stack panels vertically.
- Avoid clipped buttons.
- Preserve accessible controls.
- No horizontal overflow.
- No nested scrolling that traps touch/keyboard users.

Prefer paginated full history over an oversized internal-scroll widget.
