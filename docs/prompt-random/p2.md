## 3. Preserve Existing Payment Flow

The current implementation uses:

POST `/api/payments/create`

with a payload containing:

- `planId`
- `returnUrl`
- `projectId`

Its response may contain:

- `redirect_url`
- `error`

The existing behavior includes:

1. Ignore selection of the free plan.
2. Persist resume intent.
3. Create the checkout request.
4. Handle authentication failure.
5. Show a meaningful server error.
6. Navigate to the returned checkout URL.
7. Reset loading state.

Preserve each step.

Do not change:

- API endpoint contracts.
- Request payload semantics.
- Subscription eligibility rules.
- Top-up prices.
- Credit amounts.
- Pricing versions.
- Midtrans checkout behavior.
- Redirect authorization.
- Credit accounting.
- User authentication.

Do not introduce new client-side payment calculations as the source of truth.

Server validation remains authoritative.
