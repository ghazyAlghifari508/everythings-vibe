## Objective

Implement a proper lifecycle for Admin Feedback and Error Reports so large amounts of historical reports do not clutter the active Ticket management interface.

The current system has two types of records:

1. User-submitted feedback.
2. System-generated error reports.

Both are currently represented mainly as chronological lists.

There is no persistent handling status or archive capability in the audited schema.

The user specifically wants a practical way to manage accumulated reports without having to permanently delete everything.

## 3. Database Design

Current database tables:

- `feedback`
- `error_reports`

The current schema does not provide persistent processing status or archive metadata.

Implement the smallest safe schema extension.

Recommended separation:

### Handling State

A field such as:

`handlingStatus`

Allowed values:

- `new`
- `in_progress`
- `resolved`

### Archive State

A separate nullable timestamp:

`archivedAt`

This is preferable to treating archive as a destructive or terminal record status.

Why?

- Archiving a resolved report should not erase the fact that it was resolved.
- Restoring an archived report should not arbitrarily change its original handling state.
- Archive and handling status represent different concerns.

Visible UI may still show:

`Diarsipkan`

when `archivedAt` is non-null.

Apply this to both Feedback and Error Reports where supported.

## 4. Safe Migration

Requirements:

- Existing rows remain intact.
- Existing rows receive a safe default handling state such as `new`.
- Existing rows are not automatically archived.
- No historical messages are modified.
- No user association is lost.
- No report is deleted.
- Migration is additive and reversible at the schema level where practical.
- New indexes must be justified by actual filtering/query needs.

Use the repository's Drizzle migration conventions.

Generate and review the necessary migration files.

Do not run production migrations automatically.

Do not reset or truncate the database.

## 5. Admin Mutation Endpoints

Implement secure Admin-only operations.

Required actions:

### Change Handling Status

`Baru → Diproses`

`Diproses → Selesai`

Allow appropriate corrections when an admin changes a status accidentally.

### Archive

Set `archivedAt` when the admin archives a record.

### Unarchive

Clear `archivedAt` while preserving the underlying handling status.

For all mutations:

- Require Admin authorization.
- Validate record type and ID.
- Validate requested status.
- Handle missing records.
- Ensure proper user feedback.
- Return safe responses.
- Prevent arbitrary writes to unrelated records.

If audit metadata is already supported in the project, record who changed a report's status and when.

Do not add an overengineered generic event-sourcing system solely for these actions.

## 8. Archive Versus Delete Policy

**Critical: Archiving is not hard deletion.**

Required behavior:

- Archived reports remain in the database.
- They do not appear in the default active queue.
- Admin can search/filter archived reports.
- Admin can unarchive them.
- Historical contents remain available for legitimate review.
- Pagination works in both active and archived views.

The user also asked whether old reports should be permanently deletable.

Recommended decision:

**Do not provide unrestricted hard deletion of all feedback and error reports.**

For legitimate spam or duplicate cleanup, a future limited deletion policy may be introduced with:

- Admin authorization.
- Explicit confirmation.
- Retention assessment.
- Audit evidence.
- Safeguards against accidental bulk deletion.

Do not implement a new mass-delete feature in this task without an established retention/security policy.

No automatic purge based solely on age.
