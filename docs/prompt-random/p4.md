# TASK 04 — Scalable Admin Users: Pagination, Search, Filters &amp; Accurate KPIs

**Repository:** `ghazyAlghifari508/everythings-vibe`  
**Complexity:** HIGH  
**Scope:** `/admin/users`

## Objective

Refactor halaman Admin Pengguna supaya mampu mengelola ribuan akun dengan:

1. Server-side pagination.
2. Server-side search dan filter paket.
3. Statistik global yang akurat.
4. UI tabel yang rapi dan konsisten.
5. Semua fitur administrasi pengguna tetap berfungsi.

User mengeluhkan tabel Admin yang tidak memiliki pagination dan berpotensi menumpuk ketika jumlah pengguna semakin besar.

**Jangan menyelesaikan ini menggunakan client-side pagination terhadap 100 data pertama.**

## 3. Server-Side Pagination

Refactor kontrak `listUsers` agar menyediakan:

- Rows untuk halaman saat ini.
- Total hasil sesuai filter.
- Page/pageSize atau offset/limit terverifikasi.
- Metadata yang diperlukan untuk kontrol pagination.

Rekomendasi:

- Default 20 row per halaman.
- Maksimal 100.
- Pilihan 10/20/50 jika sesuai UI existing.
- Urutan `createdAt DESC, id DESC`.

Gunakan stable ordering supaya pengguna dengan timestamp sama tidak menimbulkan duplikasi atau lompatan antarhalaman.

Validasi parameter di server.

Jangan memberi client akses ke query tanpa batas.

## 4. Search &amp; Filtering

Pindahkan filter dari browser ke database.

Dukung:

- Search berdasarkan nama.
- Search berdasarkan email.
- Filter Free.
- Filter Pro.
- Filter Hengker.
- Semua paket.

Gunakan query parameterized via Drizzle.

Pertahankan proteksi terhadap wildcard LIKE yang saat ini sudah ada pada pencarian.

Pastikan:

- Search mencakup semua akun, bukan 100 pertama.
- Filter dilakukan SEBELUM pagination.
- `totalCount` mengikuti kombinasi filter.
- Halaman kembali ke 1 ketika search/filter berubah.
- Search di-debounce secukupnya, sekitar 300ms bila diperlukan.
- Request lama tidak boleh menimpa hasil query terbaru.
- Pagination tidak kehilangan filter yang sedang aktif.

Ikuti state dan routing conventions TanStack Router/Query.

Jika filter disimpan di URL search params, validasi dan normalisasi parameternya.

## 5. Accurate Statistics

Jangan hitung KPI dari `rows.length`.

Ambil agregasi database terpisah untuk:

- Total Pengguna.
- Free.
- Pro.
- Hengker.
- Administrator.

Hasil harus merepresentasikan seluruh dataset sesuai definisi label, bukan satu halaman.

Periksa kondisi akun tanpa subscription.

Hindari join yang menggandakan user dalam perhitungan.

Jika ada subscription history, gunakan kontrak subscription aktif yang benar.

Jangan menambahkan KPI baru yang tidak diminta.

## 6. Preserve Admin Actions

Fitur existing harus tetap tersedia:

- Ubah paket pengguna.
- Reset kredit.
- Ban/unban.
- Berikan/cabut role Admin.
- Billing exemption.
- Proteksi terhadap perubahan privilege akun sendiri.

Saat aksi berhasil:

- Refresh row yang relevan.
- Perbarui KPI jika terdampak.
- Jangan otomatis mengembalikan pengguna ke halaman pertama tanpa alasan.
- Tangani item yang tidak lagi cocok dengan filter aktif.

Pertahankan aturan backend `requireAdmin`.

Jangan melemahkan authorization atau menampilkan data sensitif tambahan.

## 7. User Deletion Policy

**Jangan menambahkan tombol hard-delete akun sebagai solusi mengurangi jumlah baris.**

Ban/unban tetap menjadi alat pengendalian akses yang tersedia.

Jika dibutuhkan penghapusan akun permanen, itu harus melalui workflow khusus yang mempertimbangkan:

- Data pribadi.
- Sesi.
- Proyek.
- Transaksi.
- Ledger kredit.
- Kewajiban retensi dan permintaan penghapusan data.

Workflow itu bukan scope task ini.

## 8. Mandatory Component-First UI

Sebelum membuat pagination:

1. Baca [`AGENTS.md`](http://AGENTS.md), `.agents/rules/`, dan desain Admin saat ini.
2. Periksa shared UI, terutama Button, Table, Select, Pagination, Dialog, dan Tooltip.
3. Explore komponen/pola relevan dari shadcn/ui, HeroUI, MagicUI, ReactBits, Thinking Orbs, dan AffectUI.
4. Gunakan komponen siap pakai yang cocok, bukan menciptakan pagination primitive sendiri bila sudah tersedia.

Jika belum ada shared Admin Pagination, buat SATU primitive kecil berdasarkan komponen siap pakai yang bisa dipakai lagi di Proyek, Transaksi, dan Tiket.

Jangan membuat empat desain pagination berbeda.

No AI-slop:

- Tidak ada hero besar.
- Tidak ada card per pengguna.
- Tidak ada badge dekoratif baru.
- Tidak ada nested pagination panel.
- Jangan menambahkan animasi tidak relevan.
- Gunakan Hugeicons existing.

Tetap support mobile, tablet, desktop dengan strategi tabel responsif existing.

## 9. Tests

Wajib menguji:

- Lebih dari 100 user.
- Pagination halaman awal/tengah/akhir.
- Search menemukan user lama.
- Filter paket pada dataset lengkap.
- Gabungan search + filter.
- Akurasi global KPI.
- Akun tanpa subscription.
- Stable ordering.
- Unauthorized non-admin.
- Action mutation dan data refresh.
- Invalid pagination parameters.

Jalankan targeted Vitest, TypeScript, Biome, dan test query database bila tersedia.

No browser QA, Playwright browser execution, atau screenshot automation.
