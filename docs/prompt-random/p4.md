# TASK 04: Redesign Global Badge and Status Components

**Complexity:** HIGH  
**Priority:** P1 Design System  
**Scope:** All developer-owned badge and status interfaces

## 1. Objective

Eliminate repetitive AI-slop badge styling across everythings-vibe.

The user specifically dislikes the pattern that repeatedly combines:

- Rectangular badge container.
- Colored border.
- Text using the same saturated color.
- Transparent background derived from that same color.

Examples from the audited source resemble:

`bg-emerald-500/10 text-emerald-400 border-emerald-500/20`

`bg-amber-500/10 text-amber-400 border-amber-500/20`

This pattern appears across transactions, project categories, subscription plans, credit history, Admin tables, and other interfaces.

Do not solve this by merely changing the color palette.

Establish a semantic, reusable visual system.

## 5. Semantic Component Families

Do not treat all labels as the same kind of badge.

### A. StatusIndicator

Use for ordinary operational states.

Recommended:

```
[check-circle] Berhasil
[clock]        Menunggu
[activity]     Diproses
[circle-x]     Gagal
[undo]         Dilepas
```

Visual contract:

- No surrounding border by default.
- No colored background by default.
- Compact Hugeicons icon.
- Neutral readable text.
- Muted semantic color primarily on the icon.
- Text can be emphasized for genuine error/warning states.

Use existing semantic icon equivalents from Hugeicons.

### B. Badge

Use for categories and identities.

Examples:

```
[ Pro ]  [ Hengker ]  [ PRD ]  [ AC ]  [ Task ]
```

Visual contract:

- Neutral subtle background where a container is useful.
- No unnecessary colored border.
- No uppercase unless the original abbreviation requires it.
- Compact padding.
- Consistent typography and corner radius.

Do not treat premium plan identity as a warning state.

### C. StatusBadge

Use only when stronger visual emphasis is justified.

Examples:

- An important account restriction.
- A failed process requiring attention.
- A critical payment issue.

Avoid automatically applying container-based status badges to every status.

### D. Numeric Badge

Preserve a distinct existing pattern for counts, such as unread notifications.

Do not remove functional counters.

## 7. Domain Status Semantics

Payment and credit operations are different domains.

Do not merge their business status logic.

Maintain independent verified mappings for:

- Payment status.
- Credit operation status.
- Background job status.
- Ticket lifecycle.
- Project lifecycle.
- Account status.

Examples:

- Payment pending is not payment failed.
- Credit released is not a paid charge.
- Project draft is a lifecycle state.
- Pro is a subscription identity, not a success indicator.

Use shared visual primitives and domain-specific mappings.

Never alter backend status enums solely for UI redesign.

## 8. Design Tokens and Accessibility

Use shared theme tokens for:

- Neutral text.
- Muted text.
- Success.
- Warning.
- Danger.
- Neutral tag surfaces.

Support both light and dark mode.

Requirements:

- Meaning is understandable without color.
- Icons and labels remain visible.
- Text remains readable.
- No unnecessary animation.
- No new random hex colors across individual components.
- No glowing borders or gradients.
- No repetitive nested pills.

Preserve accessibility labels and tooltips where necessary.

## 9. Global Migration

Migrate all relevant user-facing badge/status implementations to the shared system.

Remove redundant hand-written Tailwind color combinations.

Update relevant component variants while preserving valid public APIs where practical.

Do not modify third-party embedded UI or user-generated Studio output.

Do not rewrite unrelated screens.

## 10. Prevent Recurrence

Extend the active design rules/skills with:

- Badge versus status distinction.
- Approved shared primitives.
- Mandatory component reuse.
- Restrained semantic color.
- Prohibition against repeated colored-border + tinted-background + colored-text patterns for all statuses.
- Mandatory inspection of existing sibling interfaces.

Do not recreate obsolete rules folders.
