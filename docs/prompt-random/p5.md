# TASK 05 — Secure Automatic AI Agent API Key Lifecycle

**Repository:** `ghazyAlghifari508/everythings-vibe`  
**Complexity:** CRITICAL  
**Scope:** API key lifecycle, automatic handoff credentials, security

## Objective

Improve the security, lifecycle management, and reliability of API keys generated automatically during AI Agent handoff.

The existing application uses different integration mechanisms:

**Greenfield**

- Generates API keys automatically via `/api/settings/api-keys/auto`.
- Uses these credentials during AI Agent handoff.

**Codebase Existing**

- Uses CLI synchronization tokens and related authorization flows.

Do not assume both integrations use interchangeable credentials.

The main problems to investigate and fix are:

1. Automatic keys can accumulate with repeated handoffs.
2. Newly created automatic keys do not currently receive an explicit expiry in the minting flow.
3. Their permissions and lifecycle may be broader than necessary.
4. Secrets must be protected when passed to CLI/agent handoff workflows.
5. Users need reliable ways to identify and revoke obsolete access.

## 2. Existing Credential Flow

Current conceptual architecture:

```
GREENFIELD HANDOFF

User requests AI Agent handoff
             |
             v
POST /api/settings/api-keys/auto
             |
             v
Mint raw API key
             |
             v
Store SHA-256 hash in database
             |
             v
Return one-time raw key
             |
             v
Agent/CLI uses credential
```

Current risk:

```
Handoff 1 -> Key A
Handoff 2 -> Key B
Handoff 3 -> Key C
Handoff 4 -> Key D
...
No explicit expiry assigned on creation.
```

The goal is controlled access, not an unlimited accumulation of long-lived credentials.

## 3. Expiry &amp; Revocation Policy

Define and implement a clear policy for automatic handoff credentials.

Requirements:

- New automatic keys must have explicit expiration.
- Expiration duration must reflect real workflow requirements.
- Do not select an arbitrary very short TTL that breaks long-running agent tasks.
- Use a documented, configurable policy with safe bounds.
- Preserve in-flight authorized work where compatible with security expectations.
- Expired or revoked keys must fail authentication.
- Never silently extend expired credentials.
- Existing keys must not be unexpectedly invalidated by a migration.

The application already checks `expiresAt` during bearer authentication.

Verify that this remains correct and that the creation path actually sets the expiry.

Design a safe renewal/re-handoff process if the selected expiry policy requires one.

Do not generate an unlimited stream of active credentials through automatic retries.

Avoid unsafe deletion of potentially active keys.

## 4. Least Privilege

Current automatic scopes include:

- `read:project`
- `write:task:status`
- `write:subtask:status`

Audit which scopes are genuinely needed.

Requirements:

1. Preserve operations required by current CLI handoff.
2. Avoid adding broad admin or wildcard scopes.
3. Do not automatically grant unnecessary future permissions.
4. Verify project ownership on every relevant operation.
5. Investigate whether credentials should be restricted to their associated project.

If project-scoping would require a significant API/schema redesign, document the dependency and implement only what can be done safely within the current architecture.

Never fake project-level authorization using a client-side label alone.

## 5. One-Time Secret Handling

The raw credential must remain available only when needed for the intended handoff.

Do not:

- Return raw keys in list APIs.
- Log raw tokens.
- Put credentials in URLs or query strings.
- Persist raw tokens in browser localStorage.
- Include secrets in telemetry.
- Expose credentials in unrelated error messages.

Set appropriate no-store response headers for secret-bearing responses.

Audit the handoff prompt/copy workflow.

If the current handoff necessarily embeds a bearer token in text copied to an external agent, explicitly evaluate the exposure and minimize it.

Do not silently break the handoff feature.

Prefer a verified secure provisioning pattern where compatible with the CLI architecture.

Do not implement a speculative authentication redesign without proving compatibility.

## 6. Control Key Accumulation

Introduce lifecycle controls appropriate to the actual data model.

Consider:

- Expiry-aware listing.
- Safe cleanup of truly expired credentials.
- Per-user active-key limits where justified.
- Clear identification of automatic versus manually created credentials.
- Revocation of obsolete access.

Do not revoke a credential simply because a user opens handoff again.

Do not delete credentials tied to active operations without a deliberate compatibility policy.

Keep cleanup simple, testable, and idempotent.

## 7. Preserve Existing Integrations

Do not break:

- Greenfield handoff.
- CLI task updates.
- Subtask updates.
- Project reads.
- Codebase Existing sync tokens.
- Existing valid manual API keys.
- Existing authorization boundaries.

Do not merge API keys and Codebase sync tokens into one credential format without a separate architectural requirement.
