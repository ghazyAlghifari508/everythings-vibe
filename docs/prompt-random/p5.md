# TASK 05: Implement Adaptive Credit Capacity Meter

**Complexity:** MEDIUM  
**Scope:** Billing credit meter and reusable credit capacity presentation

## Objective

Improve the current monochrome credit bar so its color communicates the user's remaining usable capacity.

The user requests:

- Green when sufficient credits remain.
- Yellow around half usage.
- Red when credits approach exhaustion.

Do not use a permanently white bar.

## 1. Inspect Current Implementation

Read:

- Current repository rules.
- `src/features/billing/components/billing-page.tsx`
- `use-user-plan` and credit entitlement services.
- Reservation, settlement, and available-balance calculations.
- Existing Progress/Meter components.
- Shared theme tokens.

Verify the real behavior of:

- Total allocation.
- Credits used.
- Credits reserved.
- Remaining available credits.
- Top-up balance, where applicable.
- Subscription reset period.
- Billing exemptions.

Do not derive entitlement from presentation-only values.

## 2. Threshold Contract

Use the previously agreed thresholds:


| Effective utilization      | Visual state                |
| -------------------------- | --------------------------- |
| 0% to below 50%            | Muted green                 |
| 50% to below 85%           | Muted yellow                |
| 85% to below 100%          | Red                         |
| 100% or no usable capacity | Red with exhaustion message |


These thresholds describe usage, not remaining percentage.

When applicable, utilization includes both used and currently reserved credits.

Use the canonical billing service to calculate actual available capacity.

Do not assume simple subtraction is correct for every entitlement, top-up, or billing period.

## 3. Represent Reservations Correctly

Example:

```
Allocation:       105
Used:              80
Reserved:          20
Available:          5

[ USED ################### ][ RESERVED ###### ][ 5 ]

Kredit hampir habis. Tersisa 5 kredit.
```

Requirements:

- Reserved credits reduce spendable availability.
- Reserved credits must not be described as permanently charged.
- Distinguish reservations visually using a neutral segment.
- Accessible text explains both values.
- Release immediately updates available capacity.

Where different credit buckets exist, respect actual consumption and expiry policies.

## 4. UX

Target:

```
Kredit digunakan                       98 / 105

[ RED ===================================     ]

Kredit hampir habis. Tersisa 7 kredit.
```

Avoid:

- Rainbow gradients.
- Pulsing warning animations.
- New decorative badges.
- Excessive alert cards.
- Red warnings when plenty of credits remain.
- Intrusive “buy credits” popups.
- Arbitrary fake usage values.

The color changes with usage; the bar is not a gradient from green to red.

Retain accurate reset-period copy.

## 5. Component-First Requirement

Inspect existing Progress/Meter primitives and reusable patterns.

Explore compatible components from shadcn/ui, HeroUI, MagicUI, ReactBits, Thinking Orbs, AffectUI, TuffUI, CUI, and SakaniUI.

Reuse a suitable ready-made component or existing primitive.

If existing Progress semantics are inappropriate, use a compatible accessible meter implementation rather than rebuilding a decorative bar without semantics.

Prefer shared `CreditMeter` behavior if multiple consumers need it.

## 6. Accessibility and Edge Cases

Handle:

- Zero allocation.
- Zero usage.
- Missing/loading values.
- Fully used quota.
- Negative or inconsistent input safely.
- Usage above allocation.
- Active reservations.
- Exempt users.
- Expired subscription.
- Both themes.

Clamp presentation width safely without hiding underlying data inconsistencies.

Use appropriate meter semantics and readable labels.

Do not rely exclusively on color.

## 7. Verification

Test exact boundaries around 50% and 85%, exhaustion, reservations, releases, and quota changes.

Use canonical available-credit values.

Do not adjust database balances to make tests pass.

Run focused tests, TypeScript, and Biome.

No browser QA until the final integration task.

## Done

The Billing credit meter is adaptive, accurate, accessible, and consistent with the global design system.

No change to actual charging logic.

Commit atomically and report thresholds, edge cases, and tests.
