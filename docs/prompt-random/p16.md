## 3. APPROVED PRODUCT CONTRACT

The following product decisions are authoritative and must not be changed during QA.

### Credit System

- Pro and Hengker use one shared credit balance across supported billable product families.
- Greenfield and Codebase Existing retain existing billing compatibility.
- Studio AI generation consumes credits under the approved pricing policy.
- All AI-driven Studio revisions consume credits.
- Manual Studio editing remains free.
- Scrape operations consume credits according to their approved fixed/adaptive pricing policies.
- VibeTemplate remains free.
- Opening existing results remains free.
- Routine preview, navigation, copying, and exporting existing artifacts remain free.

### Free Trial

- One Studio trial per Free account.
- One Scrape trial per Free account.
- Trials are independent.
- Trials do not renew monthly.
- Deleting a project does not restore a consumed trial.
- Upgrade/downgrade does not grant additional trials.
- Complete system failure releases an unused trial reservation.
- Partial success and cancellation follow the explicitly approved policy.

### Pricing

- Hybrid fixed and adaptive pricing.
- Actual tariffs are based on verified operational benchmarks.
- Pro/Hengker allocation changes require approval.
- No charging using unapproved placeholder tariffs.
- No retroactive charging of historical activity.

### UX

- Inline credit estimates.
- One-click operation execution when credit or trial is sufficient.
- No routine credit-confirmation popup.
- Existing Credit Exhausted Modal is reused when actual limits prevent execution.

If implementation conflicts with any of these decisions, treat the conflict as a bug.

Do not reinterpret product decisions to make existing code easier to pass.

The owner explicitly prohibits deceptive testing practices.

All testing must exercise the actual intended application behavior.

### 4.1 Forbidden Practices

STRICTLY DO NOT:

- Manually increase real user credit balances to make an operation succeed.
- Modify database subscription records to bypass plan restrictions.
- Change payment statuses directly in the database to simulate successful transactions.
- Edit credit operation statuses to simulate successful settlement.

- Change timestamps to conceal expiry or period-reset problems.
- Delete historical records to make incorrect totals appear correct.
- Manually mark worker jobs completed when their actual execution failed.
- Replace failed API responses with fake success responses.
- Insert hardcoded data into production components.
- Disable authentication or authorization temporarily to pass tests.
- Remove input validation.
- Skip problematic test cases.
- Weaken assertions merely to obtain passing results.
- Disable console errors or warnings to hide regressions.
- Modify production behavior exclusively to accommodate a test.
- Claim an operation was tested when it was only inspected in source code.
- Fabricate screenshots, measurements, logs, or results.

### 4.2 Legitimate Test Fixtures

Controlled test fixtures are allowed only within a verified isolated testing environment.

Examples:

- Existing automated test database.
- Disposable test users.

- Authorized payment sandbox.
- Controlled scraping fixtures.
- Deterministic failure injection in dedicated automated tests.

However:

- Document which tests use mocks.
- Document which tests use actual application endpoints.
- Clearly distinguish simulated and real provider execution.
- Never present mocked results as production verification.
- Never manipulate real business records.
