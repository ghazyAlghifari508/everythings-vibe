## RULE A — Interaction Pattern Minimalism

Add an enforceable rule:

**Do not introduce additional interaction modes when a direct, established interaction pattern can accomplish the same user goal with fewer steps.**

Examples:

### PROHIBITED

```
[Pilih]
   ↓
Selection Mode
   ↓
☐ Item A
☐ Item B
   ↓
[Hapus] [Selesai memilih]
```

When not materially necessary, this is unnecessary UI complexity.

### PREFERRED

```
☐ Item A
☐ Item B
☐ Item C

User selects A and B
        ↓
[2 dipilih] [Batal] [Hapus]
```

Mandatory principles:

- Favor direct checkbox selection for ordinary bulk-select lists.
- Contextual bulk actions appear only when relevant.
- Do not require an entry/exit mode for simple actions unless justified by actual product needs.
- Avoid additional confirmation/interaction steps without a real safety or usability benefit.
- Preserve keyboard, screen-reader and touch accessibility.
- Do not prohibit genuine modes used for complex editing where mode separation prevents mistakes.

## RULE B — Internal Diagnostics Are Not Product Copy

Add an enforceable rule:

**Never expose implementation details, AI schema validation messages, model/provider failures, internal fallback names, or developer-oriented pipeline statuses directly as primary end-user content.**

Examples of prohibited public messages:

```
AI tidak memenuhi kontrak sintesis design system.
Enrichment unavailable.
Schema validation failed.
Measurement-only fallback.
```

Instead:

- Fix the underlying error when possible.
- Assess whether the failure materially affects the user result.
- If the result is usable and internal diagnostics have no meaningful user consequence, omit technical status from primary UI.
- If the result is incomplete, explain its actual impact in natural Indonesian.
- Offer a recovery action only if it really works and is appropriate.
- Preserve technical diagnostics in logs/internal metadata.

Never hide materially incomplete or failed output merely to make UI cleaner.

## RULE C — Information Necessity Gate

Before showing ANY:

- Status label.
- Banner.
- Informational paragraph.
- Tooltip.
- Warning.
- Technical note.
- Recovery button.

The agent must evaluate:

```
       INFORMATION TO DISPLAY
                  │
                  ▼
        Relevant to user goal?
                  │
               ┌──┴──┐
               NO   YES
               │     │
             OMIT    ▼
               Is it understandable?
                     │
                  ┌──┴──┐
                  NO   YES
                  │     │
              REWRITE   ▼
                 Does user need it?
                         │
                      ┌──┴──┐
                      NO   YES
                      │     │
                    OMIT   SHOW
```

Additional checks:

- Is the information already visible elsewhere?
- Does it tell the user what happened?
- Is it actionable, safety-relevant, or necessary for informed decisions?
- Can it be placed in appropriate diagnostic detail instead?

Do not create new UI surfaces just to show internal metadata.

## RULE D — No Duplicate Status Disclosure

Examples:

### WRONG

```
DESIGN.md [Analisis AI belum lengkap]

[Rendered | Source]

Analisis AI belum lengkap: schema ...
```

### CORRECT

```
DESIGN.md

[Rendered | Source]

[Actual document]
```

For materially degraded output, show ONE clear, contextual indication of the consequence.

Do not repeat the same technical status in:

- Header.
- Panel subtitle.
- Banner.
- Toast.
- Result body.

unless each location serves a distinct and necessary purpose.

## RULE E — Prevent Cosmetic Error Fixes

Add a mandatory engineering principle:

**Removing a confusing error message does not count as fixing the underlying failure.**

Required behavior:

- Trace the actual error to its source.
- Verify whether the state represents incomplete, failed, or usable output.
- Correct the backend problem when within scope and feasible.
- Preserve accurate internal diagnostics.
- Improve UI copy without falsifying system status.
- Never change backend status to success solely to hide a warning.
