# PHASE 2 — SCRAPE ERROR DIAGNOSTICS &amp; RECOVERY

## Objective

Tingkatkan keandalan error handling untuk seluruh mode Scrape: Crawl, [DESIGN.md](http://DESIGN.md), HTML, dan Images.

Prioritas adalah root-cause classification, observability, dan actionable UI. Jangan sekadar mengganti error copy lalu menganggap masalah selesai.

User pernah menerima "Website terlalu lama merespons" ketika scraping Gemini dan tidak tahu apakah website yang bermasalah atau sistem VibeEverything yang gagal.

Sistem harus bisa menjelaskan kegagalan sesuai bukti yang benar-benar tersedia.

## Mandatory Preparation

- Baca [`AGENTS.md`](http://AGENTS.md) dan seluruh rules yang relevan sampai EOF.
- Periksa branch dan working tree.
- Trace dari `/api/scrape` → service/worker → `renderPage`/fetcher → persisted metadata → status polling → error UI.
- Fokus inspeksi `render-page.ts`, `scrape-service.ts`, `scrape-extraction-service.ts`, `scrape-worker.ts`, `scrape-error-presentation.ts`, `scrape-error-card.tsx`, `scrape-progress.tsx`, dan error contracts.
- Periksa error codes existing dan semua consumer. Jangan membuat error model paralel jika model existing bisa diperluas.
- Cari reusable components terlebih dahulu.
- Pertahankan SSRF restrictions, access controls, worker safety, rate limits, retry policies, serta website access restrictions.

## TASK A — Root-Cause Classification

Klasifikasikan kegagalan berdasarkan evidence nyata, setidaknya:

1. Website HTTP 429 / rate limited.
2. Website HTTP 401/403 / restricted access.
3. Website HTTP 404/410.
4. Website HTTP 5xx.
5. Navigation timeout.
6. Resource loading timeout.
7. Browser initialization/capture failure.
8. Worker timeout atau worker unavailable.
9. Asset-fetch failure.
10. Empty/unusable result.
11. Internal application/storage failure.

Pisahkan kegagalan website dari kegagalan internal jika evidence mendukung. Jangan otomatis menyebut seluruh kegagalan sebagai masalah website.

HTTP status dan Retry-After hanya boleh ditampilkan jika benar-benar diperoleh dari respons.

## TASK B — Diagnostic Metadata

Audit dan perbaiki metadata agar sistem dapat menjawab:

- Pada tahap mana proses berhenti?
- Apakah HTTP response pernah diterima?
- Apakah ada URL final setelah redirect?
- Apa error code dan stage sebenarnya?
- Bagian mana yang berhasil?
- Apakah ada partial result?
- Apakah retry aman dan diperbolehkan?
- Apakah error berasal dari capture website, asset, worker, atau storage?

Gunakan typed schema, size limits, dan data minimization. Jangan menyimpan secrets, cookies, authorization headers, atau sensitive browser context ke log maupun UI.

Jangan membuat metrics yang tidak benar-benar diukur.

## TASK C — Error UI Redesign

### TARGET VISUAL — TIMEOUT

```
Scrape Images / gemini.google.com

┌──────────────────────────────────────────────────┐
│ ⚠ Halaman belum berhasil diambil                 │
│                                                  │
│ Proses terhenti saat membuka halaman website.    │
│                                                  │
│ Yang bisa kamu lakukan                           │
│ Coba lagi nanti atau gunakan halaman lain.       │
│                                                  │
│ [Coba lagi]      [Gunakan URL lain]               │
│                                                  │
│ Detail teknis                                ˅    │
└──────────────────────────────────────────────────┘
```

Jangan selalu menggunakan copy di atas secara literal. Teks harus berubah berdasarkan actual error classification.

### TARGET VISUAL — RATE LIMIT

```
⚠ Website membatasi permintaan

Website mengembalikan HTTP 429.
Permintaan baru belum dapat dilakukan.

[Coba lagi jika tersedia]   [Gunakan URL lain]

Detail teknis ˅
```

Retry disabled ketika sistem masih berada dalam Retry-After cooldown yang valid. Jangan mengarang countdown jika server tidak memberi informasi tersebut.

### TARGET VISUAL — PARTIAL RESULT

```
⚠ Sebagian proses tidak selesai

24 gambar tersedia
6 resource gagal diambil

[Lihat hasil tersedia]    [Detail kegagalan ˅]
```

Partial results tidak boleh hilang hanya karena terdapat error di satu tahap.

## TASK D — Recovery Actions

- Retry hanya untuk kegagalan yang benar-benar retryable.
- Jangan retry otomatis tanpa batas.
- Jangan mem-bypass login, CAPTCHA, anti-bot, atau pembatasan website.
- Pertahankan data parsial dan state job dengan benar.
- Retry harus memperhatikan idempotency, stale worker lease, ownership, credits jika berlaku, dan rate limits.
- Tombol "Gunakan URL lain" harus benar-benar membuka form yang sesuai, bukan inert button.
- Technical details bersifat disclosure; user-friendly explanation tetap prioritas.
- Jangan menampilkan raw server exception pada UI publik.

## TASK E — Progress / Failure Continuity

Saat status berubah dari processing ke failed, jangan mengganti layout menjadi halaman error yang tidak berkaitan sama sekali.

Gunakan visual hierarchy yang tetap koheren dengan sistem progress existing. Tampilkan tahap gagal jika tersedia.

Jangan mengembalikan dot berkedip atau fake percentage.

## Automated Verification

Buat deterministic tests untuk error mapping, Retry-After, timeout classification, retry eligibility, partial result handling, owner authorization, dan recovery state.

Gunakan stub/fake HTTP responses dan mock service dependencies seperlunya; jangan bergantung pada website eksternal sungguhan dalam automated tests.

Run relevant tests, typecheck, lint, build.

Browser QA dan screenshot QA dikecualikan.

## Delivery

Atomic commit, push current branch, verify clean tree dan upstream sync. Laporkan diagnosis yang terbukti, kasus yang belum bisa dipastikan tanpa runtime network evidence, dan tes yang dijalankan.

## Acceptance Criteria

- Timeout website dan internal timeout tidak diperlakukan sebagai error identik tanpa bukti.
- User tahu apa yang terjadi dan apa yang bisa dilakukan.
- HTTP 429 diperlakukan benar.
- Partial results tidak hilang.
- Retry benar-benar aman dan efektif.
- Tidak ada klaim bahwa situs tertentu bermasalah tanpa verifikasi.
- Kontrak dan behavior keempat mode tetap kompatibel.
