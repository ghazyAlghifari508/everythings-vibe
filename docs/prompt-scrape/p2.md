## 3. Masalah nyata dari output Notion

### A. AI synthesis tidak berhasil tetapi scope terlihat complete

Dokumen berisi:

`Analysis scope: complete; depth: detailed; code reference: both.`

Namun bagian keterbatasan menyatakan:

`The AI synthesis step did not produce a narrative for this capture. AI synthesis is unavailable or did not run.`

Itu menimbulkan kesenjangan ekspektasi.

User mengaktifkan detailed analysis, tetapi hasil ternyata berupa measurement-only fallback.

**Jangan menyembunyikan kegagalan enrichment dan jangan mengaku AI synthesis telah berhasil.**

Perbaiki status, metadata, dan cara dokumen menjelaskan hasil supaya user atau agent dapat membedakan:

- extraction/pengukuran berhasil;
- synthesis/interpretasi berhasil;
- synthesis gagal tetapi pengukuran masih tersedia;
- informasi belum dapat diverifikasi.

Jika retry AI enrichment sudah ada, pertahankan dan perbaiki hanya bila ditemukan bug. Jangan membuat retry pipeline paralel tanpa kebutuhan.

### B. Token CSS bertabrakan antar-capture

Contoh nyata:

Base:

`--color-measured-1: rgba(0, 0, 0, 0.898);`

Mobile override:

`--color-measured-1: #ffdec4;`

Nilai tersebut mempunyai karakteristik dan kemungkinan peran yang sangat berbeda, tetapi mendapat identitas variable yang sama.

Ini menunjukkan bahwa pencocokan token antar-capture harus diperiksa.

**Jangan menggabungkan dua token hanya karena nomor urutan, posisi array, atau nama sementara sama.**

### C. Dark CSS dihasilkan tanpa dark appearance terverifikasi

Pada Notion, empat capture yang tercatat:

```
Capture 1 | Desktop | requested light | observed light
Capture 2 | Desktop | requested dark  | observed light
Capture 3 | Mobile  | requested light | observed light
Capture 4 | Mobile  | requested dark  | observed light
```

Namun hasil CSS mempunyai override `@media (prefers-color-scheme: dark)`.

Perbaiki generator agar **preferensi browser tidak otomatis dianggap sebagai bukti dukungan dark mode**.

Jangan mengeluarkan dark theme token yang tidak tervalidasi hanya karena user memilih parameter Light + Dark.

### D. Komponen dan pengukuran terlalu banyak berulang

Document saat ini mengulang treatment Navigation, Buttons/CTA, typography, spacing, dan border radius per capture.

Pengulangan tersebut menyebabkan agent sulit menemukan aturan yang benar-benar penting untuk implementasi.

Pertahankan data pembuktiannya, tetapi lakukan normalisasi dan pengelompokan dengan benar.

### E. Raw measurement mendominasi arahan desain

Dokumen masih terasa seperti dump hasil pengukuran browser, bukan panduan desain yang memprioritaskan keputusan implementasi.

Agent harus mendapat informasi utama lebih dahulu, baru rincian measurement ketika dibutuhkan.

### F. CSS dan Tailwind dapat menghasilkan instruksi yang menyesatkan

Jangan menganggap semua computed style adalah semantic design token.

Contoh:

- elemen dengan radius 0px tidak otomatis berarti semua navigation harus memiliki radius 0px;
- warna teks berulang tidak otomatis berarti brand palette;
- satu nilai max-width pada elemen kecil tidak otomatis berarti container utama;
- nilai pengukuran satu elemen tidak boleh menjadi global variable tanpa dasar;
- perubahan mobile tidak otomatis membuktikan lokasi breakpoint asli;
- varian minor tidak otomatis menjadi design system component.

### Implementation Brief wajib actionable

Contoh kualitas arahan:

**Typography**

- Gunakan keluarga font yang benar-benar teramati.
- Pertahankan hierarchy antara display, heading, dan body.
- Gunakan perbedaan ukuran desktop/mobile yang memiliki bukti.

**Colors**

- Gunakan warna berdasarkan peran, bukan sekadar daftar hex.
- Pisahkan brand/primary, text, surface, border, dan decorative colors.
- Jangan mengubah aksen minor menjadi warna utama global.

**Components**

- Petakan treatment ke komponen yang relevan.
- Jelaskan perbedaan variant bila memang terbukti.
- Jangan memaksa seluruh button atau navigation memakai satu radius global apabila evidence menunjukkan perbedaan.

**Responsive**

- Jelaskan perubahan yang terukur.
- Jangan mengarang intermediate breakpoints atau hidden layouts.

**Application context**

- Gunakan referensi desain untuk styling aplikasi pengguna.
- Jangan menyalin logo, isi teks, gambar, link, maupun brand assets website sumber.
- Jangan membuat halaman Color Palette, Typography Specimen, atau UI Documentation kecuali secara eksplisit diminta user.

Panduan harus membantu agent mengambil keputusan visual, bukan memaksanya mengikuti ribuan baris angka tanpa konteks.

## 5. Normalisasi dan deduplikasi

### A. Canonical token identity

Bangun atau perbaiki proses canonicalization berdasarkan:

- nilai CSS yang sudah dinormalisasi;
- semantic role yang didukung evidence;
- capture context;
- jumlah observasi;
- source token apabila valid;
- tingkat keyakinan.

Warna ekuivalen boleh dikelompokkan dengan hati-hati, tetapi jangan kehilangan informasi penting seperti alpha atau perbedaan role.

Dua nilai berbeda tidak boleh digabung hanya karena terlihat mirip. Dua role berbeda tidak otomatis harus digabung hanya karena value-nya identik.

### B. Shared vs context-specific

Aturan target:

```
Semua capture memverifikasi nilai sama
               |
               v
           Shared token

Nilai berbeda pada viewport tertentu
               |
               v
       Scoped viewport override

Nilai berbeda hanya pada verified theme
               |
               v
         Theme-specific token

Context tidak terverifikasi
               |
               v
   Tidak boleh mengarang override
```

Tidak boleh terjadi numeric alias collision seperti contoh `--color-measured-1`.

### C. Variants dan components

Jangan mengeluarkan variant baru untuk setiap elemen hasil sampling.

Kelompokkan treatment yang ekuivalen, tampilkan varian representatif, jelaskan sifat yang membedakannya, dan simpan jumlah sampel sebagai evidence.

Jangan melakukan deduplikasi secara agresif hingga varian yang benar-benar berbeda hilang.

Kalau jumlah varian harus dibatasi, jelaskan cakupan dan keterbatasan data secara jujur.

### D. Do's and Don'ts

Hasilkan aturan yang benar-benar berguna dan didukung pengamatan.

Hindari:

- aturan sama yang diulang pada empat capture;
- Do/Don't generik yang tidak berkaitan dengan website;
- larangan absolut dari observasi yang lemah;
- claim tentang states, responsive behavior, atau dark mode yang tidak terverifikasi.

Gunakan shared rules untuk pola yang konsisten, dan scoped rules hanya untuk perbedaan nyata.

## 6. CSS &amp; Tailwind output correctness

Audit seluruh output CSS custom properties dan Tailwind v4.

Pastikan:

- tidak ada duplicate/conflicting custom-property identity;
- semantic token tidak berganti arti antar-capture;
- media queries hanya memakai scope yang didukung evidence;
- CSS dark mode tidak dihasilkan sebagai desain terverifikasi apabila semua hasil capture tetap light;
- generated CSS valid secara sintaks dan semantik;
- penamaan variable konsisten dan dapat dipakai agent;
- value dengan confidence rendah tidak dipromosikan menjadi global design decision;
- fallback/unknown memiliki penjelasan dan tidak menghasilkan value palsu.

Jika satu measurement tidak cukup untuk menghasilkan semantic token, pertahankan sebagai evidence, bukan memaksanya ke CSS.

Jangan mengubah nilai aktual hasil pengukuran agar output sekadar terlihat lebih rapi. Perbaiki pemetaan dan interpretasinya.
