## 3. Critical Finding: SVG Rejected Unconditionally

Periksa `validateStoredImage()`.

Temuan awal: implementasi saat ini menolak file dengan MIME `image/svg+xml` atau signature SVG dan mengeluarkan `UNSAFE_SVG` tanpa membedakan SVG aman dan berbahaya.

**Tugas:** tentukan pendekatan penanganan SVG yang aman, praktis, dan dapat diaudit.

Pilih arsitektur terbaik berdasarkan codebase:

A. Sanitasi SVG dengan mekanisme tepercaya dan whitelist ketat; atau

B. Konversi SVG menjadi format raster aman dalam lingkungan terisolasi; atau

C. Jika kedua pendekatan tidak layak, pertahankan penolakan tetapi klasifikasikan sebagai format yang belum didukung dan tampilkan penjelasan yang akurat.

Jangan sekadar menghapus validator keamanan atau memasukkan raw SVG yang tidak tepercaya ke DOM.

Security requirements:

- Tidak ada eksekusi script, event handlers, embedded active content, atau unsafe references.
- Proteksi terhadap external resource fetching dan SSRF.
- Batas ukuran, kompleksitas, dan waktu pemrosesan.
- Validasi content type terhadap isi aktual.
- Asset delivery dengan content type dan security headers yang sesuai.
- Jangan membuat image proxy terbuka untuk URL sembarang.
- Pertahankan isolasi data per user/scrape.

Jika mendukung SVG, tulis automated security regression tests untuk konten SVG yang aman maupun tidak aman.

## 4. Accurate Asset Outcome

Sistem harus membedakan:

```
IMAGE FOUND
    │
    ├── FETCH FAILED
    │     ├── Timeout
    │     ├── HTTP 403/429
    │     ├── HTTP 5xx

          ├── INVALID CONTENT
          ├── UNSUPPORTED FORMAT
          ├── SECURITY REJECTED
          ├── STORAGE FAILED
          └── SAVED SUCCESSFULLY
```

Pastikan penyebab final berasal dari typed errors / metadata, bukan parsing pesan teks.

Jangan menyebut satu gambar berhasil tersimpan jika hanya URL-nya yang ditemukan atau baru diverifikasi sebagian.

Audit konsistensi angka:

- Discovered.
- Saved.
- Verified external links.
- Failed.
- Pending.
- Duplicate candidates.
- Partial outcome.

Total per kategori harus konsisten dengan model penyimpanan, termasuk deduplication dan retries.

## 5. Retry Policy

Pertahankan retry hanya pada kegagalan yang layak dicoba lagi.

Contoh:

- Temporary network timeout: boleh retry terbatas.
- HTTP 5xx: dapat retry terbatas sesuai policy.
- HTTP 429: hormati `Retry-After`; hindari agresif retry.
- Invalid image content: jangan loop tanpa akhir.
- Security rejection: jangan bypass dengan retry.
- Storage quota: jangan terus mengunduh jika batas sudah tercapai.

Periksa apakah retry terhadap satu asset menyebabkan duplikasi data, status salah, atau hitungan gagal membengkak.
