# TASK: Fix VibeScrape HTML First-Load Empty Preview and Retry Dependency

**Kompleksitas: COMPLEX**

## Problem statement

Saya menemukan bug serius pada VibeScrape HTML.

Contoh kasus: scrape [`https://t3.codes/`](https://t3.codes/).

Ketika pertama kali membuka hasil HTML, preview DOM terkadang menampilkan:

> Preview tidak berisi konten

Namun setelah user menekan tombol `Coba lagi`, preview dapat berhasil ditampilkan.

Ini merupakan UX yang buruk. User tidak seharusnya diwajibkan retry untuk melihat preview yang sebenarnya bisa dimuat oleh aplikasi.

**Objective:** menemukan akar masalah mengapa initial preview gagal/empty sementara retry berhasil, kemudian memperbaikinya secara menyeluruh.

Jangan hanya menghilangkan pesan error atau melakukan retry tanpa batas.

## 2. Area penyebab yang wajib diperiksa

### A. Readiness detection

Cari apakah:

- Empty detection dievaluasi sebelum halaman selesai memuat.
- Beberapa laporan `empty` menyebabkan status final terlalu cepat.
- Halaman sudah punya konten tetapi observer tidak mendeteksinya.
- Perubahan `preparing → ready` diabaikan karena race condition.
- State lama tertinggal pada initial mount atau retry.

Periksa `reducePreviewReport`, `previewDisplayReport`, dan fungsi terkait.

### B. Iframe lifecycle

Periksa:

- Urutan pemasangan iframe.
- Kapan `srcDoc` tersedia.
- Kapan listener `postMessage` terpasang.
- Apakah event load terjadi sebelum listener siap.
- Apakah `frameLoaded` tersinkron dengan dokumen yang benar.
- Apakah retry menciptakan iframe/document baru secara berbeda dari initial load.
- Apakah perubahan `srcDoc`/`active` men-trigger reset yang tidak perlu.
- Apakah cleanup timer menyebabkan initial attempt terputus.
- Apakah callback lama menerima pesan dari attempt baru.

### C. Timing and resource readiness

Periksa:

- Browser load versus DOM content readiness.
- External CSS, font, gambar, dan script.
- Website dengan JavaScript-heavy rendering.
- Konten yang muncul terlambat.
- Iframe yang masih mempersiapkan konten tetapi dianggap kosong.
- Perbedaan timing initial attempt dengan manual retry.

### D. Security and preview transformation

Periksa apakah:

- CSP terlalu membatasi resource yang sebenarnya aman.
- Sanitization menghapus root content.
- Asset rewriting menghasilkan URL salah.
- Sandbox menyebabkan halaman tidak dapat dipresentasikan.
- Readiness reporter salah menafsirkan resource error minor sebagai fatal.

**Jangan menyelesaikan bug dengan menonaktifkan seluruh sandbox atau CSP.**

## 4. Reliability requirements

Implementasikan perbaikan yang terbukti diperlukan.

- `ready` harus memiliki prioritas ketika konten valid sudah terdeteksi.
- `empty` harus berarti benar-benar tidak ada konten yang berguna, bukan sekadar masih loading.
- `failed` harus mencerminkan kegagalan yang nyata.
- Jangan menampilkan error hanya karena sebuah asset tambahan gagal dimuat jika halaman utama tetap berguna.
- Ketika dokumen baru dimulai, reset state dengan benar.
- Gunakan attempt identity/generation jika diperlukan untuk menghindari stale callbacks.
- Cleanup event listener dan polling timer harus benar.
- Hindari loop `postMessage` tanpa batas.
- Retry harus melakukan recovery nyata, bukan sekadar menghilangkan overlay.
- Jangan membuat UI menampilkan screenshot fallback secara prematur.
- Jika fallback diperlukan, pertahankan desain dan toolbar yang sudah ada.

Jika akar masalahnya berasal dari capture HTML atau penyimpanan, perbaiki di sana, bukan dengan menambah workaround di frontend.

## Definition of Done

- Akar masalah initial-empty ditemukan dan dijelaskan.
- Initial preview tidak lagi salah dinyatakan kosong pada kondisi yang dapat dipulihkan.
- Retry tidak lagi menjadi keharusan pada initial load yang sehat.
- Lifecycle iframe dan cleanup aman.
- Error state jujur dan tidak premature.
- Tidak ada retry loop tak terbatas.

- UI viewer tidak di-redesign.
