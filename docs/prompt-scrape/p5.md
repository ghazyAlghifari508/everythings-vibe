# PHASE 5 — SCRAPE HTML RELIABILITY, PREVIEW &amp; PERFORMANCE

## Objective

Improve Scrape HTML so users can reliably inspect the captured DOM, view a faithful visual reference when available, and access source code without severe UI lag.

Reported issues:

1. Google Stitch HTML preview fails or appears blank.
2. Downloaded HTML opens as an empty dark page.
3. "index.html mulai diunduh" is misleading and unnecessary.
4. Switching Asli/Terformat freezes or delays the UI.
5. User expects captured UI reference, not merely raw HTML that cannot reproduce the observed visual.

Do not promise a fully functional clone of a third-party application. The scope is reliable capture, accurate preview, honest export semantics, and fast source inspection.

## TASK A — Investigate Blank HTML &amp; Preview

The implementation captures rendered DOM using Playwright `page.content()`.

The current visual snapshot pipeline strips original scripts and uses restricted resource loading.

This can produce a valid HTML source but an incomplete visual representation for JavaScript-heavy applications.

Investigate separately:

1. Did browser capture reach meaningful rendered content?
2. Is persisted HTML complete or just a shell?
3. Are stylesheets, fonts and images captured or resolvable?
4. Are redirects/login restrictions involved?
5. Did resource rewriting cause breakage?
6. Did preview CSP/iframe sandbox intentionally disable required execution?
7. Is the source HTML usable, but not self-contained offline?
8. Is the preview-readiness detector classifying the document correctly?

Do not assume Stitch is failing for only one reason based on the screenshot.

## TASK B — Separate HTML Source and Visual Reference

Improve the output model so users understand what is available.

Recommended architecture:

- HTML Source: captured DOM source.
- Visual Preview: safe view of captured page.
- Visual Screenshot: browser-captured image fallback/reference where available.

Do not execute arbitrary third-party application scripts inside the main app to obtain visual fidelity.

If interactive/safe DOM preview cannot reproduce the page but an actual screenshot exists, show the screenshot instead of a giant blank/error area.

If no visual evidence exists, show a concise truthful empty/error state.

Only use the screenshot when captured successfully by the trusted server browser. Never fabricate a screenshot or reuse unrelated visuals.

## TASK C — Honest Export Behavior

The downloaded `.html` currently contains DOM source but may require the original website's JavaScript, CSS, images and other resources.

Define and communicate real export types instead of treating all exports as portable offline websites.

At minimum:

- Export captured HTML source faithfully.
- Export visual screenshot if generated.
- If providing a self-contained visual HTML export, implement proper resource handling; do not merely rename raw DOM to "offline clone".
- Do not promise working interactions without real support.
- Avoid embedding secrets, cookies, private session tokens, or executable unsafe website scripts.
- Maintain original source integrity and transparent export semantics.

Consider source filenames based on domain/path and ensure UI labels match the actual file downloaded.

Remove the redundant persistent message:  
`index.html mulai diunduh.`

Use appropriate error feedback only when needed.

## TASK D — Fix Asli/Terformat Performance

Current code path:  
`CodebaseSourcePreview` → `buildSourceViewRows` → `formatMarkupSource` + `highlight.js` + React row rendering.

The formatter may run redundantly while determining format availability.

### TARGET INTERACTION

```
HTML Source

[ Asli | Terformat ]

Mode switch:
click → selection changes immediately
      → formatted view becomes available
      → source viewer remains responsive
```

Requirements:

- Measure and identify time spent in formatting, highlighting and rendering.
- Avoid calling formatting functions twice for equivalent content.
- Cache stable formatted results.
- Avoid repeating expensive work on every tab switch.
- For large HTML, investigate worker-based formatting and syntax highlighting.
- Evaluate virtualization/windowing or a more suitable code viewer for large documents.
- Keep main-thread interaction responsive.
- Never drop content silently or truncate exported files.
- Preserve original source for copy/download.
- Preserve safe escaping of displayed HTML.
- Handle malformed HTML gracefully with an appropriate fallback.
- If processing needs time, show a subtle truthful preparation state without blocking the entire application.

Do not apply an arbitrary debounce as a substitute for performance improvements.

## TASK E — Security Boundary

Important constraints:

- Do not weaken SSRF protections.
- Do not bypass website authentication, CAPTCHA or anti-bot systems.
- Keep preview sandbox and CSP safety intact.
- Do not execute hostile scripts in the top-level application.
- Preserve signed asset access and owner authorization.
- Bounded downloads, resource usage, timeouts and memory.
- No use of browser cookies/credentials from private user sessions.

If browser-safe replay is not possible for a website, use actual visual evidence rather than relaxing security indiscriminately.

## TASK F — Error/Loading States

Distinguish:

- Capture failed.
- Captured source exists, visual preview failed.
- Source captured but offline resources unavailable.
- Screenshot available.
- Partial visual fidelity.
- Source file empty/invalid.

Do not report "Scrape berhasil" when the requested output has no meaningful content.

Do not discard captured source because the preview alone failed.

## Automated Verification

Tests should cover:

- HTML capture acceptance criteria.
- Empty document rejection.
- Source/preview separation.
- Asset rewriting.
- Preview CSP/sandbox invariants.
- Missing assets and degraded visuals.
- Screenshot fallback state.
- Export content and filenames.

- Large synthetic HTML performance regression.

Use deterministic fixtures, not live scraping of Stitch.

Run tests, typecheck, lint and production build.

Do not run browser QA, browser automation QA, or screenshot-based QA. Existing Playwright code used for actual capture remains permitted.
