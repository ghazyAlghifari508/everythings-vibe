# PHASE 6 — SCRAPE IMAGES RELIABILITY &amp; ASSET AVAILABILITY

## Objective

Fix the mismatch between verified image extraction and the actual availability of those images inside Images Explorer.

Observed example:

- 174 images discovered.
- 174 marked as saved/completed.
- Many thumbnails display "Gambar tidak dapat dimuat".

This undermines trust in result accuracy.

The system must not equate "a URL returned image bytes once" with "the image is permanently saved and can be rendered later".

## Mandatory Preparation

- Read [`AGENTS.md`](http://AGENTS.md) and applicable `.opencode/rules/*`.
- Verify current branch and clean ownership of changes.
- Trace:  
browser image discovery → candidate normalization → asset verification → DB persistence → signed asset URL → asset proxy → gallery rendering → download.
- Inspect `render-page.ts`, `scrape-extraction-service.ts`, `scrape-images.ts`, `scrape-service.ts`, `preview-capabilities.ts`, `scrape.asset.ts`, `images-result.tsx`, and related image schemas.
- Inspect existing object storage integrations, cleanup jobs, URL signing, quota/credit systems, file security, and retention policies.
- Reuse existing storage and UI infrastructure when applicable.
- Do not create an incompatible independent storage layer merely for this feature.

## TASK A — Fix Result Semantics

Current processing verifies resources and persists result metadata/URLs, while the gallery fetches images again through an authenticated proxy.

This can produce a completed job whose images cannot be displayed later.

Define accurate states such as:

- discovered;
- fetched/verified;
- persisted (if actual bytes are stored);
- unavailable/failed;
- rendering failure (separate from extraction failure).

Adapt these to existing schemas without breaking compatibility.

User-facing counts must represent actual capabilities.

For example, do not use "174 tersimpan" if 174 URLs were merely checked once and are not actually stored.

## TASK B — Durable Asset Strategy

Evaluate actual persistence requirements and existing storage capabilities.

Preferred target for saved scrape results:

- Save successfully fetched image bytes in controlled object storage where feasible.
- Persist asset metadata and storage reference.
- Serve images through authorized, stable access.
- Apply byte limits, file type validation, content sniffing, file-size caps, and quota.
- Handle duplicates efficiently.
- Respect data retention, copyright, permissions, and website restrictions.
- Avoid unbounded image storage costs.
- Support cleanup when a scrape result is deleted.

If the product intentionally keeps only source URLs, then clearly distinguish linked assets from locally stored assets and never promise long-term availability.

Decide based on repository architecture and actual product contract.

Do not fake persistence by saving only a remote URL.

## TASK D — Diagnose Proxy Failures

Inspect `/api/scrape/asset` and determine conditions where a previously verified image becomes unavailable.

Consider:

- Source URL expired.
- Remote CDN blocks subsequent requests.
- Proxy rate limit.
- Expired signed capability.
- Authentication/ownership mismatch.
- Unsupported or mismatched MIME.
- SVG rendering issues.
- Redirect restrictions.
- Resource fetch timeout.
- Image bytes unavailable.

Do not label every failure as an external website error.

Use exact diagnostics where possible, without exposing secrets.

Handle:

- Partial success.
- Proxy expired.

- Large gallery.

## TASK F — Storage &amp; Security

- Preserve authenticated ownership and signed asset access.
- Prevent SSRF through image redirects.
- Verify allowed content types and safe response headers.
- Enforce resource size limits.
- Avoid arbitrary SVG/script execution.
- Follow robots/site restrictions where applicable.
- Do not circumvent remote access controls.
- Do not create permanent public links for private user results without an explicit safe product design.
- Respect existing quota and cleanup rules.

## Automated Verification

Create deterministic tests for:

- Successfully fetched image persisted according to chosen strategy.
- Stored image renders without remote re-fetch.
- Failed resource classification.
- Signed asset validity.
- Expired capability.
- Ownership restrictions.
- MIME and size validation.
- Partial results and consistent counts.
- Correct cleanup after deletion.
- Legacy records.
- Retry/cooldown behavior.
- Gallery fallback rendering states.

Run relevant tests, typecheck, lint and production build.

No browser QA or screenshot QA.

## Delivery

Atomic commits for storage/data contract, proxy behavior, and gallery UX as appropriate.

Push correct branch, verify clean working tree and upstream sync.

Report data migration needs, storage cost implications, existing asset compatibility, actual tests, and unresolved remote-site limitations.

## Acceptance Criteria

- A verified and truly stored image does not depend on re-fetching the remote URL to appear in the gallery.
- User-facing saved counts are accurate.
- Broken image placeholder is replaced with useful UX.
- Errors are classified honestly.
- Download and preview work from the appropriate source.
- No security, quota, or cleanup regressions.
- Large results remain usable.

Implement this phase only.
