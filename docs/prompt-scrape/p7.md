## 2. Hal-hal yang wajib diselidiki

### Discovery

- Apakah seluruh URL yang ditemukan benar-benar mengarah ke gambar?
- Apakah URL relatif dinormalisasi dengan benar?
- Apakah URL yang sama dihitung berkali-kali?
- Apakah `srcset`, lazy-loading, dan URL hasil redirect ditangani dengan benar?
- Apakah gambar terdeteksi tetapi URL aslinya sudah kedaluwarsa?

### Fetch

- Apakah target mengembalikan HTTP 403, 404, 429, 5xx, atau timeout?
- Apakah redirect ditangani dengan benar?
- Apakah ada kesalahan pada request headers yang secara normal diperlukan untuk mengakses aset publik?
- Apakah request dilakukan terhadap URL yang tepat?
- Apakah concurrency terlalu tinggi sehingga memicu rate limit?
- Apakah batas waktu terlalu agresif?
- Apakah klasifikasi "akses dibatasi" memang sesuai respons nyata?

### Validasi

- Apakah server mengembalikan HTML error page tetapi pipeline menganggapnya file gambar?
- Apakah MIME type diverifikasi?
- Apakah file melebihi batas ukuran yang valid?
- Apakah SVG ditolak karena validasi keamanan?
- Jika SVG ditolak, apakah penolakan memang diperlukan atau validator terlalu ketat?
- Apakah aset valid gagal disimpan karena kesalahan parsing?

### Penyimpanan

- Apakah fetch berhasil tetapi upload ke storage gagal?
- Apakah koneksi Cloudflare R2 atau konfigurasi penyimpanan bermasalah?
- Apakah file sudah tersimpan tetapi database tidak mencatatnya?
- Apakah ada mismatch antara status persisted, verified, linked, dan failed?
- Apakah kegagalan sebagian menyebabkan hasil lain dibatalkan?

## 3. Jangan memalsukan keberhasilan

Jangan:

- Menandai gambar berhasil jika belum benar-benar tersimpan.
- Mengubah 403 menjadi completed.
- Menyimpan URL remote lalu mengklaim file sudah tersimpan permanen.
- Menyembunyikan kegagalan dari statistik.
- Menonaktifkan pembatasan keamanan.
- Melewati robots/access policy.
- Membypass autentikasi atau proteksi situs.
- Menganggap semua kegagalan sebagai kesalahan website tanpa bukti.

Jika server sumber benar-benar membatasi akses, laporkan secara tepat.

Jika yang gagal hanya penyimpanan internal, perbaiki penyimpanannya.

Jika masalah disebabkan bug aplikasi, selesaikan pada komponen pipeline yang relevan.

## 4. Penanganan retry

Klasifikasikan kegagalan berdasarkan penyebab:

```
IMAGE REQUEST
      │
      ▼
Berhasil?
   ├── Ya → Validasi & simpan
   │
   └── Tidak
          │
          ▼
     Jenis kegagalan?
          │
          ├── Temporary timeout
          │       └── Retry terbatas
          │
          ├── Rate limit
          │       └── Hormati Retry-After
          │
          ├── Permanent 404
          │       └── Catat kegagalan
          │
          ├── Access denied
          │       └── Hormati pembatasan
          │
          └── Internal storage error
                  └── Perbaiki pipeline
                      tanpa mengulang fetch
                      secara sia-sia
```

Retry harus dibatasi, menggunakan backoff yang sesuai, dan tidak menghasilkan request loop.

Jangan mencoba mengakali access control website sumber.

## 5. Correctness dan data integrity

Pastikan:

- Hasil sukses disimpan meskipun ada gambar lain yang gagal.

- Retry aman terhadap duplicate job.
- Tidak ada perubahan yang mengganggu Crawl, HTML, atau [DESIGN.md](http://DESIGN.md).
