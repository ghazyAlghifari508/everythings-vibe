# PHASE 7 — SCRAPE HISTORY PROFESSIONAL REDESIGN

## Objective

Redesign the Scrape History page into a professional, fast, usable workspace for managing website extraction results.

The current History uses a simple vertical list of repeated cards and has no meaningful searching, mode filters or pagination.

User requirements:

1. Quick filter by extraction mode.
2. Search websites/domain names.
3. Professional visual layout with strong information hierarchy.
4. Pagination.
5. Preserve view/delete result functionality.
6. Responsive design.
7. Consistent light/dark appearance.
8. Avoid generic AI UI, excessive cards, and monotonous layouts.

This task includes server-side data retrieval changes, not just frontend styling.

## Mandatory Preparation

- Read [`AGENTS.md`](http://AGENTS.md) and relevant `.opencode/rules/*` fully.
- Inspect branch/upstream/status.
- Read `scrap.history.tsx`, `scrape-history-list.tsx`, `scrape-service.ts`, DB schema, and current route search/query conventions.
- Check how history deletion works and which related records/assets are removed.
- Inspect existing pagination, search, filter, list/table, and modal components in the repository.
- Reuse mature library components where appropriate; prefer existing shadcn/HeroUI design primitives if compatible.
- Do not implement duplicate UI primitives or hardcode result samples.

## TASK B — Mode Filter

Provide quick filtering:

- Semua.
- Crawl.
- [DESIGN.md](http://DESIGN.md).
- HTML.
- Images.

Active filter must be clearly differentiated using existing design tokens.

Support combined filters, e.g.:

Mode = HTML  
Status = Gagal  
Search = stitch

Filter should affect server results and total count, not merely the currently fetched first 50 rows.

## TASK C — Search &amp; Sorting

Search by:

- Domain.
- Website/project display name when available.
- Potentially page title where meaningful.

Sort:

- Newest.
- Oldest.

Optional additional sorting only if a real use case and query support are established.

Use parameterized database queries and preserve tenant/owner boundaries.

If search uses debouncing, use a sensible short interval without delaying visible input changes.

## TASK D — Server-Side Pagination

Current `listScrapes()` loads up to 50 latest rows.

Do not implement pagination by loading those 50 and slicing them client-side.

Implement real server-side pagination with accurate filtered count.

Requirements:

- Bounded page size: e.g. 10, 20, 50.
- Stable ordering and deterministic tie-breaker.
- Proper limit/offset or cursor-based design based on existing data layer.
- Accurate total result count when supported.
- Handle invalid/out-of-range pages.
- Reset page appropriately when filter/search changes.
- Avoid unnecessary data over-fetching.
- Retain search/filter state while paging.
- Preserve selection and query state after returning from detail.
- After deletion, refresh counts and handle an empty last page.
- Avoid N+1 requests.

### TARGET PAGE CONTROL

```
Showing 11–20 of 33 results

Rows per page [ 10 ˅ ]         [‹] [1] [2] [3] [4] [›]
```

All displayed numbers must come from actual query results.

## TASK E — Row Information Architecture

Each history row should show:

- Website display name.
- Domain.
- Extraction mode.
- Result status.
- Creation date/time, with useful human-readable formatting.
- Open detail action.
- Secondary delete action.

Do not repeat full URLs unnecessarily.

Don't call a failed job "Selesai".

Do not mark jobs as complete because the list row exists.

Suggested visual state treatment:

```
[✓ Selesai]       Neutral/subtle success
[◌ Diproses]      Spinner only while processing
[! Gagal]         Clear warning/error
[⊘ Dilewati]      Only if supported by real state
```

Avoid colorful badges everywhere; use restrained status cues.

## TASK G — Empty, Loading &amp; Error States

Handle:

- First-time user with no history.
- Search with no matches.
- Filter with no matches.
- Failed fetch.
- Slow pagination request.
- Deleting one result.
- Last row deleted.
- Concurrent updates/newly created history.
- Result still processing.

Differentiate "Belum ada riwayat" from "Tidak ada hasil sesuai filter".

Never show fake loading percentages.

## TASK H — Delete Interaction

Preserve working deletion flow.

Improve if needed:

- Prefer existing confirmation/dialog components.
- Show exact website/result context.
- Clarify irreversible behavior.
- Keep user on the correct filtered page after deletion.
- Avoid nested interactive elements.
- Ensure owner authorization at service layer.
- If later phases introduced locally stored image assets, deletion must follow the established storage cleanup contract.

## TASK I — Performance &amp; Accessibility

- Semantic search and list structure.
- Keyboard-operable filters, row links, menus, pagination.
- Screen-reader labels for icon-only actions.
- Good focus visibility.
- Responsive result count.
- Light/dark contrast.
- Avoid unnecessary animation.
- No giant lists rendered all at once.
- Correct loading and route navigation.
- URL search parameters should represent useful sharable/restorable filter state when consistent with router conventions.
