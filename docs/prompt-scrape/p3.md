# TASK: Redesign the Generated [DESIGN.md](http://DESIGN.md) Structure for AI Coding Agent Usability

**Priority:** P1  
**Complexity:** Complex  
**Branch:** `feature/vibedesign-scrape`

## 1. Objective

Perbaiki struktur, isi, dan kualitas dokumen [`DESIGN.md`](http://DESIGN.md) yang dihasilkan VibeScrape agar benar-benar berfungsi sebagai **design reference dan implementation guide untuk AI coding agent**.

Hasil harus mempertahankan fakta pengukuran yang valid, tetapi menghilangkan pengulangan tidak perlu, token noise, raw measurements yang tidak actionable, dan panduan generik.

**Jangan mengubah desain website VibeEverything dalam task ini. Fokus pada output generator [DESIGN.md](http://DESIGN.md).**

Task ini mengonsumsi hasil canonical token model yang sudah diperbaiki pada task token identity dan verified themes. Jangan mengimplementasikan duplikasi algoritma canonicalization di Markdown renderer.

## 2. Konteks user dan hasil yang dilaporkan

User melakukan analisis Notion dengan:

- Desktop + Mobile.
- Light + Dark.
- Analisis mendalam.
- CSS + Tailwind.

Output menjadi sekitar 2.123 baris.

Masalah yang ditemukan:

1. Komponen Navigation berulang pada setiap capture.
2. Buttons and CTAs, Body copy, Header, dan beberapa komponen lain juga berulang.
3. Satu kelompok warna tampil berkali-kali karena ditangkap pada empat konteks.
4. Banyak warna biru tampak berulang dan tidak jelas makna setiap variasinya.
5. Do/Don't ditulis ulang pada capture berbeda.
6. Typography, radius, spacing, dan component styles memuat data granular yang tidak selalu membantu agent.
7. Dokumen cenderung seperti database pengukuran dibanding instruksi desain.
8. Sebagian metadata teknis lebih dominan daripada insight yang dapat digunakan.
9. Output harus dapat digunakan coding agent tanpa membuat agent membangun halaman dokumentasi design system alih-alih aplikasi sesungguhnya.

## 6. Semantic deduplication warna

Perhatikan tiga kasus berbeda.

### Case A: Nilai sama, role sama, banyak capture

```
Capture 1: brand accent #097fe8
Capture 2: brand accent #097fe8
Capture 3: brand accent #097fe8
Capture 4: brand accent #097fe8
```

Output utama cukup satu canonical token.

Catat bahwa token tersebut teramati pada beberapa capture melalui metadata atau cakupan, bukan empat entry yang tampak sebagai warna berbeda.

### Case B: Nilai berbeda, role berbeda

```
Brand accent    #097fe8
Primary action  #0075de
Text accent     #005bab
```

Jangan otomatis merge hanya karena semuanya biru.

Pertahankan perbedaan jika benar-benar berpengaruh terhadap desain.

### Case C: Nilai sama, role berbeda

Satu base color boleh memiliki beberapa alias, sehingga keputusan semantiknya tetap terpelihara.

Jangan menghapus role atau usage penting.

Periksa pula apakah warna-warna yang diklasifikasikan sebagai Surface, Text, Border, Brand, atau Accent benar-benar memiliki dasar evidence.

Jangan menjadikan semua warna unik pada website sebagai warna brand utama.

## 7. Ringkas komponen tanpa kehilangan variasi valid

Hindari format:

```
Navigation - Desktop Light
  20 aturan

Navigation - Desktop Dark
  20 aturan yang sama

Navigation - Mobile Light
  20 aturan

Navigation - Mobile Dark
  20 aturan yang sama
```

Ubah menjadi format semantik:

```
NAVIGATION

Base style
  Font family
  Typography
  Colors
  Spacing
  Component layout

Desktop differences
  Only values that change

Mobile differences
  Only values that change

Verified theme differences
  Only when a real difference exists

Notes
  Relevant implementation constraints
```

Bila Navigation memiliki beberapa treatment yang benar-benar berbeda, tetap tampilkan beberapa variant, tetapi berdasarkan karakteristik dan fungsi nyata, bukan sekadar urutan penemuan DOM.

Jangan menghilangkan variant valid secara agresif.

Jangan membentuk variant baru berdasarkan noise DOM.

## 8. Do's &amp; Don'ts berkualitas

Masalah saat ini: aturan seperti mempertahankan type contrast dan tidak menyamakan radius tertentu diulang untuk setiap capture.

Aturan umum cukup satu kali.

Gunakan Do/Don't yang:

- Spesifik pada desain website.
- Dapat dilaksanakan AI agent.
- Memiliki evidence.
- Tidak bertentangan.
- Tidak mengulang hal sama dengan parafrase.
- Tidak mempromosikan inferensi menjadi fakta.

Contoh ilustratif:

```
DO
- Gunakan NotionInter untuk typography UI
  sesuai role yang teramati.
- Pertahankan perbedaan typography desktop
  dan mobile yang terverifikasi.
- Gunakan radius tombol berdasarkan
  variant komponen yang bersangkutan.

DON'T
- Jangan mengasumsikan website memiliki
  dark theme jika belum terverifikasi.
- Jangan menyamaratakan semua tombol ke
  satu radius apabila variant-nya berbeda.
- Jangan mengganti hierarchy typography
  hanya untuk menyeragamkan ukuran.
```

Ini hanya contoh gaya penulisan, bukan hardcoded rules yang harus muncul di setiap website.

## 9. Konten untuk coding agent

Bagian Agent Implementation Guide harus operasional.

Perintah implementasi harus memandu agent untuk:

1. Memahami kebutuhan produk yang akan dibangun.
2. Menggunakan [DESIGN.md](http://DESIGN.md) sebagai referensi gaya, bukan spesifikasi fitur.
3. Memetakan style ke existing components.
4. Mempertahankan visual hierarchy dan semantic roles.
5. Menggunakan responsive differences yang terbukti.
6. Tidak membuat varian yang tidak diobservasi.
7. Tidak menyalin konten, logo, atau aset proprietary website sumber.
8. Tidak membangun halaman design documentation kecuali memang diminta user.
9. Melaporkan bagian yang belum bisa disimpulkan dari evidence.

Jangan membuat agent memprioritaskan reproduksi semua data raw CSS daripada kualitas aplikasi.

## 10. Output CSS dan Tailwind

Tetap dukung parameter pilihan user:

- CSS.
- Tailwind.

Jangan mengganti pilihan user secara sepihak.

## 11. Deduplikasi limitations

Buat bagian coverage/limitations singkat dan relevan.

Masalah yang sama cukup dilaporkan satu kali, kecuali benar-benar berbeda antar-capture.

Misalnya, jangan mengulang "requested dark but observed light" untuk empat section jika satu penjelasan bersama sudah mencakupnya.

Data diagnostik internal yang tidak membantu implementasi jangan mendominasi hasil akhir.

Namun jangan menyembunyikan keterbatasan yang dapat menyebabkan agent memakai data secara keliru.

## 12. Testing

Tambahkan tests untuk:

- Single capture.
- Four captures.
- Shared color.
- Different color roles.
- Shared and different component variants.
- Desktop/mobile typography.
- Verified and unverified dark theme.
- Duplicate guidelines.
- Repeatable deterministic output.
- CSS/Tailwind references.
- No loss of relevant evidence.
- No contradictory shared/scoped declarations.

Bandingkan output sebelum/sesudah secara struktural.

Jangan menetapkan batas baris sewenang-wenang. Targetnya **information density dan kegunaan**, bukan sekadar memotong file menjadi jumlah baris tertentu.

Jika sample [DESIGN.md](http://DESIGN.md) Notion yang dilaporkan user tersedia dalam workspace, gunakan sebagai regression fixture. Jika tidak, buat fixtures kecil yang mereproduksi kasusnya. Jangan mengarang bahwa file upload tersedia di filesystem agent.

## 13. Scope and UI rules

- Tidak boleh membuat ulang Style Inspector.
- Tidak boleh mengubah loading progress.
- Tidak boleh menambah page/route/navlink baru.
- Tidak boleh menambahkan UI dokumentasi baru.
- Tidak boleh browser QA.
- Tidak boleh menghapus measured values yang valid.
- Tidak boleh hardcode aturan khusus domain Notion.
- Tidak boleh menambah frontend custom yang tidak dibutuhkan.

Jika perubahan membutuhkan komponen UI, eksplorasi komponen existing dan library Magic UI, HeroUI, shadcn/ui, React Bits, Thinking Orbs, dan Affect UI terlebih dahulu; gunakan komponen yang sesuai, jangan membangun UI dari nol.

## 14. Acceptance criteria

- [DESIGN.md](http://DESIGN.md) tetap satu dokumen kanonis.
- Token yang sama tidak diulang sebagai beberapa token independen.
- Warna berbeda yang memiliki fungsi berbeda tetap dipertahankan.
- Komponen shared diringkas tanpa kehilangan variant valid.
- Desktop/mobile differences jelas.
- Dark theme tidak dikarang.
- Do/Don't spesifik, berguna, dan tidak repetitif.
- Panduan AI agent operasional.
- CSS/Tailwind sesuai pilihan parameter.
- Limitations singkat dan jujur.
- Tests dan static checks lulus.
- Tidak ada browser QA.
- Tidak ada UI regression yang sengaja diperkenalkan.
- Todos dicentang dan goal ditutup berdasarkan pekerjaan yang telah diverifikasi.

Setelah implementasi, berikan ringkasan perubahan struktur dokumen, contoh before/after, hasil tests, serta apa saja yang masih belum dapat diverifikasi.
