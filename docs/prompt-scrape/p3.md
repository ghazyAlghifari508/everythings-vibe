# TASK 3 — ENFORCE PUBLIC UI INFORMATION BOUNDARY &amp; ELIMINATE TECHNICAL SLOP

## Objective

Perketat aturan desain dan engineering VibeEverything agar AI coding agents tidak sembarangan menampilkan informasi teknis, metadata internal, diagnostic status, implementational details, atau pesan generik kepada pengguna akhir.

Target utama:  
`.agents/rules/[anti-ai-slop.md](http://anti-ai-slop.md)`

This is a permanent rule improvement task, not a feature implementation.

## 1. Problem Background

Beberapa contoh pelanggaran pada VibeScrape:

### Crawl Website

"robots.txt dihormati."

"Crawler membaca HTML statis tanpa eksekusi JavaScript."

"Jumlah ditemukan adalah halaman yang teramati dalam batas crawl, bukan jumlah seluruh halaman website."

"Cakupan: max 10 pages · depth 2."

### [DESIGN.md](http://DESIGN.md)

"Analisis AI belum lengkap."

"Panduan desain belum sepenuhnya selesai." (ditampilkan hanya berdasarkan state internal tanpa evaluasi dampak).

"Melengkapi..." (aksi pemulihan internal tanpa tujuan jelas).

### Scrape HTML

"Tangkapan Layar Browser — Referensi visual asli dari browser saat capture."

Redundant "Lihat HTML Source" dan "Coba lagi preview" controls.

Masalah utamanya adalah kebiasaan coding agent:

**Internal implementation knowledge is being mistaken for useful product information.**

Agent membuat UI untuk menjelaskan kode, bukan untuk membantu user mencapai tujuannya.

## 3. RULE A — PUBLIC UI INFORMATION NECESSITY GATE

Introduce an enforceable policy:

> Every piece of user-facing information must serve a specific user need. Information that is merely true, technically accurate, available in system state, or easy for developers to expose is not automatically appropriate for public UI.

Before rendering any informational content, the agent MUST evaluate:

1. **Relevance:** Does it help the user understand or use the feature?
2. **Consequence:** Does it explain a meaningful limitation, failure, risk or result?
3. **Clarity:** Can a non-technical user understand it?
4. **Actionability:** Does it guide a useful decision or action, if action is required?
5. **Uniqueness:** Is this information already visible elsewhere?
6. **Context:** Is this the right place and moment to show it?

### DECISION FLOW

```
       PROPOSED USER-FACING INFORMATION
                        │
                        ▼
           Is it relevant to user?
                        │
                ┌───────┴────────┐
                │                │
               NO               YES
                │                │
                ▼                ▼
              OMIT         Does it explain
                           meaningful value,
                           impact or limitation?
                                │
                         ┌──────┴──────┐
                         │             │
                        NO            YES
                         │             │
                         ▼             ▼
                       OMIT       Is it clear?
                                      │
                               ┌──────┴──────┐
                               │             │
                              NO            YES
                               │             │
                               ▼             ▼
                            REWRITE    Already shown?
                                             │
                                       ┌─────┴─────┐
                                       │           │
                                      YES         NO
                                       │           │
                                       ▼           ▼
                                   DEDUPLICATE    SHOW
```

Important exception:  
Safety-critical, legally required, privacy-relevant, materially incomplete, or decision-critical information must remain accessible even when it is technical or not immediately actionable. Translate it appropriately rather than suppressing it.

## 4. RULE B — NO INTERNAL IMPLEMENTATION NARRATION

Do not expose internal implementation descriptions as default user-facing copy.

Examples:

- robots.txt implementation.
- HTTP parser strategy.
- DOM extraction method.
- Browser capture architecture.
- Model-provider mechanics.
- AI schema validation.
- AI synthesis contracts.
- Worker queue/lease/heartbeat state.
- Internal retry stages.
- Cache implementation.
- Database persistence details.
- Debug/instrumentation metadata.

Technical information may exist in:

- Developer documentation.
- Diagnostic logs.
- Support tooling.
- Appropriate advanced technical views.
- Downloaded engineering artifacts when the information is useful to the document's purpose.

Do not indiscriminately place such information in:

- Main dashboard.
- Result summary.
- Card subtitle.
- Section heading.
- Generic accordion.
- Success banner.
- Primary navigation.
- Public-facing toast.

**Technical accuracy is not sufficient justification for UI visibility.**

## 5. RULE C — NO GENERIC INFORMATION COMPONENTS

Prohibit information components whose content is:

- Static for every result.
- Generic.
- Self-evident.
- Unrelated to the current task.
- Not actionable or decision-relevant.
- Repeated elsewhere.
- Written like internal documentation.

### BAD

```
┌──────────────────────────────────────────┐
│ ▼ Tentang analisis                       │
│                                          │
│ Analisis berdasarkan tampilan website    │
│ yang berhasil diperiksa.                 │
└──────────────────────────────────────────┘
```

### GOOD

```
Website Style Reference

Colors
Typography
Spacing
Components
Guidelines
```

Remove the unnecessary informational surface entirely.

Do not relocate meaningless text into a tooltip or accordion merely to make the primary UI look cleaner.

## 6. RULE D — BACKEND STATES ARE NOT AUTOMATIC UI STATES

A backend enum or metadata flag does NOT automatically justify:

- A new badge.
- A banner.
- A status label.
- A retry button.
- A loading message.
- An accordion.
- A warning card.

Before exposing internal states, map them to actual user-visible consequences.

### WRONG

```
enrichment = unavailable
         │
         ▼
Show "Analisis AI belum lengkap"
Show "Melengkapi..."
Show technical diagnostic
```

### CORRECT

```
INTERNAL STATE
      │
      ▼
ASSESS USER-FACING CONSEQUENCE
      │
      ├── Result usable
      │       └── Show result normally
      │
      ├── Materially incomplete
      │       └── Explain specific limitation
      │
      └── Failed/unavailable
              └── Show useful recovery when possible
```

Backend failure must still be logged and handled.

Never change failure to success merely to hide an inconvenient status.

---

## 7. RULE E — NO REDUNDANT RECOVERY UI

Retry, Refresh, Recheck, Regenerate, and Repair actions must satisfy:

- There is a real need for user intervention.
- The action has a distinct purpose.
- It is not already available in the same context.
- It works.
- It is appropriate for the current state.
- It has an understandable name.

Examples of prohibited UI:

- Retry Preview when screenshot is already available and no relevant failure remains.
- Duplicate "Lihat HTML Source" beside an existing HTML Source tab.
- "Lengkapi analisis" shown only because an internal AI enum is unavailable.
- Multiple banners describing the same failure.

Do not remove important recovery functionality. Move routine safe automatic recovery to backend only when technically appropriate and bounded.

---

## 8. RULE F — HUMAN-CENTERED LANGUAGE

Public-facing language must describe:

- The user's result.
- What is available.
- What is missing, if important.
- What they can do next, when necessary.

Do not describe the internal algorithm unless the user specifically needs that information.

### Examples


| Bad                                  | Better                                              |
| ------------------------------------ | --------------------------------------------------- |
| `robots.txt dihormati`               | Omit from default Crawl summary                     |
| `max 10 pages`                       | `Pencarian dibatasi hingga 10 halaman`              |
| `AI tidak memenuhi kontrak sintesis` | Internal diagnostics only                           |
| `Schema validation failed`           | Describe the actual user-visible failure            |
| `Enrichment unavailable`             | Omit unless a material result is missing            |
| `Measurement-only fallback`          | Explain which guidance is unavailable, if important |


Avoid robotic, generic, repetitive, verbose, self-congratulatory or pseudo-technical copy.

No filler phrases added just to populate empty sections.

## 10. RULE H — REDUNDANCY AUDIT BEFORE ADDING UI

Before creating new:

- Buttons.
- Menus.
- Tabs.
- Toolbars.
- Banners.
- Info panels.
- Accordion sections.
- Status labels.
- Input fields.
- Retry controls.

The agent must answer:

1. Does an existing control already accomplish this?
2. Is the new control actually needed?
3. Will it be relevant in the default state?
4. Would removing/reusing UI achieve a better result?
5. Does it compete with the primary task?
6. Can this be achieved with existing components?

If not justified, omit.

### UI DESIGN PRINCIPLE

**When an interface feels cluttered, the first solution should be an audit of unnecessary elements, not the introduction of new components.**

## 11. RULE I — MANDATORY USER-FACING COPY AUDIT

For every UI-related task, agent must review all NEW or MODIFIED user-facing copy.

This includes:

- Headings.
- Descriptions.
- Buttons.
- Dropdown options.
- Empty states.
- Error states.
- Loading states.
- Toasts.
- Tooltips.
- Result summaries.
- Information banners.
- Accordions.

Each new string must have a purpose.

Do not only inspect the main screenshot or the component being edited; trace related states that may become visible.

Before finalizing, ask:

```
Would a normal user understand why
this information is displayed?

Does removing it make the feature
less understandable or less usable?

If no, remove it.
```
