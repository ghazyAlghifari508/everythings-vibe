# PHASE 3 — PROFESSIONAL CRAWL SITEMAP REDESIGN

## Objective

Redesign Visual Sitemap pada Crawl Website agar menjadi visualisasi struktur website yang benar-benar berguna dan profesional.

Masalah saat ini:

- Node di depth yang sama ditumpuk vertikal tanpa mempertimbangkan hubungan.
- Homepage memiliki terlalu banyak garis lurus menuju setiap node.
- Garis melintang dan bersilangan sehingga terlihat seperti kabel kusut.
- Layout tidak menyesuaikan banyaknya child dan kelompok halaman.
- Node terlihat terlalu kecil akibat fit-to-view pada graph tinggi.
- Hubungan antarhalaman sulit dibaca.

Ini bukan sekadar masalah styling. Perbaiki algoritma layout dan graph interaction.

## Repository Inspection

- Inspeksi `crawl-result.tsx`, `crawl-sitemap-graph.tsx`, `crawl-graph.ts`, `crawl-website.ts`, `crawl-blueprint.ts`, dan type/schema scrape pages.

- Jangan membuat algoritma layout bespoke baru secara otomatis jika solusi yang sudah teruji tersedia.

## TASK A — Correct Graph Semantics

Penting: jangan mengarang website hierarchy.

Crawl mempunyai:

- Root URL.
- Discovery depth.
- Parent/discovery relationship.
- Observed outgoing links.
- Status per page.

Bangun graph dengan membedakan:

1. Primary discovery edges.
2. Secondary observed links.
3. Self-links.
4. Cross-links.
5. Duplicate links.
6. Unavailable/failed/skipped pages.

Primary discovery edges digunakan untuk menyusun struktur visual.

Secondary links boleh ditampilkan secara selektif, misalnya ketika node dipilih atau melalui toggle "Tampilkan semua relasi".

Jangan tampilkan semua edge sebagai kabel utama sekaligus.

## TASK B — Automated Layout

### CURRENT (INCORRECT UX)

```
[ Home ] ---------------------- [ Page A ]
      \----------------------- [ Page B ]
       \---------------------- [ Page C ]
        \--------------------- [ Page D ]
         \-------------------- [ Page E ]
          \------------------- [ Page F ]
```

### TARGET — CLEAN HIERARCHICAL GRAPH

```
                        ┌────────────┐
                        │  Homepage  │
                        └──────┬─────┘
                               │
                ┌──────────────┼──────────────┐
                │              │              │
          ┌─────▼─────┐  ┌─────▼─────┐  ┌─────▼─────┐
          │ Features  │  │ Pricing   │  │ Resources │
          └─────┬─────┘  └───────────┘  └─────┬─────┘
                │                            │
          ┌─────┴─────┐                ┌──────┴──────┐
          │           │                │             │
      [Feature A] [Feature B]       [Docs]        [Blog]
```

Above layout is illustrative only.

Requirements:

- Automatic layered/tree-aware layout.
- Parent and child clustered naturally.
- Spacing adaptive to node size and density.
- Edges routed around nodes, preferably with clean orthogonal/rounded connections if library supports them.
- Stable layout when new pages arrive.
- Reasonable fit-to-view and readable initial zoom.
- Avoid node overlaps and unnecessary edge crossings.
- Do not force the entire graph into one tiny visible cluster.
- Appropriate behavior for a root with 1, 10, or 50 discovered pages.
- No fabricated child relationship for pages without valid discovery evidence.

┌──────────────────────────────────────────────────┐
│ Visual Sitemap                                   │

│ Search...       │          │ Selected page      │

Requirements:

- Click node selects the same page in Page Inventory / Page Explorer.
- Selecting inventory page highlights or focuses corresponding graph node.
- Zoom and pan remain usable.
- Fit-to-view and reset controls work.
- Default graph is understandable without zooming excessively.
- Node status is visible but not visually noisy.
- Tooltips/detail interaction shows full page title and URL.
- Responsive mobile behavior.
- Keyboard accessibility and visible focus.
- Large graphs should not stall the UI.

## TASK D — Information Architecture

Avoid excessive status legends and developer-oriented descriptions.

"Relasi tautan teramati, bukan hierarki situs yang disimpulkan" is technically careful but too awkward as primary product copy.

Prefer short user-facing language such as:

"Peta halaman berdasarkan link yang ditemukan saat crawl."

If deeper explanation is required, provide accessible secondary help.

Do not hide important limitations or present discovered links as a fully verified information architecture.

## TASK E — Empty/Partial/Failed States

Handle:

- Root page only.
- No outgoing links.
- Many pages at the same depth.
- Cycles.
- Cross-links.
- Multiple pages linking to one page.
- Failed child page.
- Skipped URL.
- Depth limit reached.
- Paginated/filtered inventory.
- Partial crawl results.

Graph must show truthful results even when full crawl does not succeed.

## Tests &amp; Verification

Add deterministic tests for:

- Node/edge creation.
- Parent-child relationship correctness.
- Cycles and duplicate edges.
- Dense graph layout without collisions.
- Root-only and wide graphs.
- Selected page synchronization.
- Stable graph behavior after receiving more pages.
- Compatibility with saved crawl results.

Run tests, typecheck, lint, and production build.

No browser QA, Playwright UI automation, or screenshot tests.

## Delivery

Follow atomic commit and push rules. Report chosen layout technology, reuse decisions, data correctness, automated tests, and limitations.

## Acceptance Criteria

- Sitemap does not resemble a single vertical stack of cards.
- No spaghetti graph by default.
- Branching and grouping follow verified crawl relationships.
- Diagram is readable and interactive.
- Inventory and graph remain synchronized.
- No fake hierarchy.
- Light/dark contrast and responsive layout remain polished.

Only implement this phase.
