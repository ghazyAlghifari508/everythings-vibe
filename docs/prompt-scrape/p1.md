# TASK — ESTABLISH ANTI-FUNCTIONAL-SLOP RULES

## Context

Repository: `ghazyAlghifari508/everythings-vibe`  
Branch target: `feature/vibedesign-scrape`

User menemukan pola buruk dari coding agent: agent sering menambahkan tombol, toolbar, panel, pencarian, teks informasi, serta fungsi baru yang sebenarnya tidak diperlukan, sudah tersedia, atau bahkan mengganggu pengalaman pengguna.

Contoh nyata pada VibeScrape:

- Sudah tersedia tab "HTML Source", tetapi agent menambahkan lagi tombol "Lihat HTML Source" di bawah preview.
- Sudah ada navigasi preview, tetapi agent menambahkan dua toolbar tambahan.
- Screenshot yang berhasil ditampilkan masih memiliki "Coba lagi preview".
- Images Explorer diberi kolom Search meskipun nama gambar yang bisa dicari tidak terlihat oleh pengguna.
- Label dan penjelasan teknis dibuat untuk developer, bukan pengguna akhir.
- [DESIGN.md](http://DESIGN.md) yang seharusnya menjadi referensi desain dapat disalahgunakan agent sebagai konten halaman website.

Masalah ini dinamakan **functional slop**: UI yang terlihat memiliki banyak fitur, tetapi banyak kontrolnya redundant, tidak kontekstual, atau tidak memberikan nilai nyata.

Tujuan task ini adalah memperkuat aturan agent secara permanen, bukan melakukan redesign fitur secara langsung.

## TASK B — Mandatory Existing-Action Audit

Sebelum menambahkan kontrol UI, agent wajib melakukan audit:

```
          PROPOSED UI CONTROL
                  │
                  ▼
        User need established?
                  │
          ┌───────┴────────┐
          │                │
         NO               YES
          │                │
          ▼                ▼
       REJECT       Existing action?
                           │
                   ┌───────┴─────────┐
                   │                 │
                  YES                NO
                   │                 │
                   ▼                 ▼
             REUSE EXISTING    Is it essential
             OR FIX EXISTING   in this state?
                                     │
                              ┌──────┴──────┐
                              │             │
                             NO            YES
                              │             │
                              ▼             ▼
                          OMIT /        IMPLEMENT
                          CONTEXTUAL     MINIMALLY
```

Sebelum implementasi, jawab secara internal:

- Kebutuhan user apa yang diselesaikan?
- Apakah aksi ini sudah tersedia?
- Apakah kontrol harus selalu terlihat atau hanya pada state tertentu?
- Apakah penambahan ini meningkatkan clarity atau justru menambah decision burden?
- Bisakah masalah diselesaikan dengan memperbaiki komponen existing, bukan menambah komponen?

Jika jawabannya tidak membenarkan keberadaan kontrol baru, jangan dibuat.

## TASK C — Navigation and Toolbar Density

Tetapkan bahwa setiap surface harus memiliki hierarchy yang jelas.

Contoh buruk:

```
[Visual] [HTML Source]           Toolbar A
[DOM] [Screenshot]               Toolbar B
[Lihat HTML Source] [Retry]      Toolbar C
```

Contoh baik:

```
[Visual] [HTML Source]           Primary navigation
                     │
         only when Visual active
                     ▼
        [DOM] [Screenshot]       Relevant secondary mode
```

Toolbar kedua hanya dibenarkan jika pilihan tersebut benar-benar berbeda dan bermanfaat.

Toolbar ketiga tidak boleh muncul hanya untuk mengulangi tindakan existing.

Tidak semua tampilan harus memiliki dua toolbar. Jika satu sudah cukup, gunakan satu.

## TASK D — Contextual Action Discipline

Contoh:


| State                             | Expected UI                               |
| --------------------------------- | ----------------------------------------- |
| Preview normal                    | Preview, relevant controls                |
| Preview failed                    | Explanation + useful recovery action      |
| Screenshot successfully available | Screenshot, no redundant retry            |
| HTML Source                       | Source viewer, appropriate source actions |
| Image gallery                     | Images and meaningful filters             |


Contoh anti-pattern:

- Menampilkan "Retry" ketika tidak ada kegagalan.
- Menampilkan "Open Source" saat tab Source ada tepat di atasnya.
- Menampilkan technical status banner yang tidak dapat ditindaklanjuti.
- Menambahkan tooltip untuk menjelaskan kontrol yang sebenarnya tidak perlu.

Penting: jangan salah menafsirkan aturan ini sebagai larangan seluruh retry, error state, accessibility alternatives, atau bantuan kontekstual. Aksi tersebut tetap valid apabila kebutuhan dan state-nya memang mendukung.

## TASK E — Human-Centered Copywriting

Larangan:

- Istilah teknis internal yang tidak membantu pengguna.
- Penjelasan panjang tentang pipeline atau implementation details pada primary UI.
- Status dramatis atau generik untuk proses sederhana.
- Label yang menjelaskan cara kerja sistem tetapi bukan manfaat bagi user.

Aturan:

- Copy singkat, jelas, natural dalam Bahasa Indonesia.
- Tampilkan apa yang sedang terjadi dan apa yang dapat dilakukan pengguna.
- Technical details tetap boleh tersedia pada area detail yang relevan.
- Jangan menambahkan keterangan panjang hanya untuk membuat layout terlihat penuh.

- Design references mengatur styling, bukan otomatis menjadi konten halaman.

- Jangan memindahkan palette inspector, token tables, debug panels, atau design documentation ke website end-user kecuali diminta secara eksplisit.
- Preserve product scope dan existing functional requirements.

```
[ ] Keyboard/a11y behavior preserved
[ ] No needless abstraction or code expansion
```
