## 4. Perbaiki stable semantic token identity

Token harus memiliki identitas yang stabil dan bermakna, bukan bergantung pada posisi array.

Jangan menggunakan indeks seperti `color-measured-1`, `color-measured-2` sebagai identitas lintas capture apabila indeks tersebut bisa merujuk pada nilai atau peran berbeda.

Perhatikan perbedaan antara:

- **Raw observation:** nilai yang ditemukan.
- **Canonical value:** nilai yang dinormalisasi tanpa mengubah makna.
- **Semantic role:** fungsi nilai pada antarmuka.
- **Source identity:** elemen, komponen, atau custom property yang menjadi bukti.
- **Capture context:** viewport, theme yang teramati, dan sumber pengukuran.

Bangun aturan pencocokan yang deterministik berdasarkan bukti dan karakteristik tersebut. Jangan memaksa dua token menjadi sama hanya karena warnanya tampak mirip.

Contoh ilustratif:

```
DESKTOP CAPTURE

Text primary
  rgba(0,0,0,0.898)
          |
          v
Canonical semantic identity
  color.text.primary
          |
          v
MOBILE CAPTURE

Text primary
  rgba(0,0,0,0.898)

RESULT:
  Satu token bersama.
```

Sebaliknya:

```
DESKTOP
  color.text.primary -> black

MOBILE
  color.surface.accent -> green

RESULT:
  Dua identitas berbeda.
  DILARANG menggabungkannya ke --color-measured-1.
```

Jika bukti belum cukup untuk membentuk semantic role, simpan sebagai observed/unclassified token dengan identitas stabil yang tidak bertabrakan, bukan mengarang peran.

## 5. Perbaiki canonical value dan alias

Ikuti prinsip Design Tokens Community Group:

[https://www.designtokens.org/tr/2025.10/format/](https://www.designtokens.org/tr/2025.10/format/)

Bedakan:

- Base/raw color.
- Semantic aliases.
- Component-specific usages.
- Theme/viewport overrides yang benar-benar terbukti.

Contoh nilai yang ditemukan dalam sampel Notion:

- `#097fe8` — terklasifikasi sebagai Brand accent.
- `#0075de` — terklasifikasi sebagai Primary action.
- `#005bab` — terklasifikasi sebagai Text.
- `#1313ba` — terklasifikasi sebagai Surface.

**Jangan otomatis menggabungkan semua warna biru menjadi satu warna.**

Nilai tersebut berbeda. Evaluasi apakah klasifikasi rolenya didukung evidence, lalu pertahankan perbedaan yang benar-benar signifikan.

Satu canonical value boleh memiliki beberapa semantic aliases jika penggunaannya berbeda.

Normalisasi format warna harus tetap mempertahankan alpha, ruang warna, dan nilai yang sebenarnya. Jangan mengubah rgba/oklch/hex secara sembarangan atau membuat substitusi warna secara kira-kira.

## 6. Perbaiki multi-capture partitioning

Saat pengguna memilih beberapa viewport dan tema, sistem tidak boleh membuat token baru hanya karena satu token teramati dalam capture berbeda.

Target:

```
                   CAPTURE DATA
                         |
            Normalize + Verify Identity
                         |
              Compare Semantic Tokens
                         |
              +----------+----------+
              |                     |
         SHARED TOKENS        CONTEXT DIFFERENCES
              |                     |
      One canonical value       Only verified
      used across views         changes/overrides
              |                     |
              +----------+----------+
                         |
                 Canonical MODEL
                         |
                   CSS / Tailwind
```

Audit `partitionDesignViews()` dan fungsi serupa.

Pertimbangkan identity berdasarkan bukti, bukan sekadar JSON signature yang memasukkan field tidak stabil atau metadata yang berbeda tiap capture.

Jumlah sampel/frekuensi boleh berubah tanpa otomatis menjadikan token berbeda.

Pastikan:

- Tidak ada tabrakan nama token.
- Tidak ada penimpaan token beda makna.
- Tidak ada shared token yang digandakan menjadi banyak alias berindeks.
- Tidak ada penghapusan perbedaan komponen yang memang nyata.
- Data capture tetap dapat ditelusuri.

## 7. Verifikasi actual theme, bukan requested theme

Periksa bagaimana `inferTheme()` dan metadata observed appearance dibentuk.

Perlakukan dua informasi ini secara terpisah:

```
User requests DARK
        |
        v
Browser preference = DARK
        |
        v
Capture actual page appearance
        |
        +-- Observed DARK
        |      |
        |      +--> Verified dark styling
        |
        +-- Observed LIGHT
               |
               +--> No verified dark styling
```

Jika website tetap menampilkan Light ketika browser meminta Dark:

- Jangan menciptakan dark tokens.
- Jangan memberikan label dark pada nilai yang sebenarnya diambil dari halaman Light.
- Jangan menghasilkan `prefers-color-scheme: dark` overrides yang seolah-olah mewakili tema dark website.
- Jangan menyembunyikan fakta bahwa dark appearance tidak terverifikasi.
- Pertahankan pengukuran yang valid sebagai bukti light appearance.
- Jangan menganggap website mendukung dark mode hanya karena parameter dark dicentang.

Perhatikan juga kemungkinan website menggunakan theme toggle manual, cookie, atau local preference. Jangan menyimpulkan dukungan dark mode tanpa evidence.

## 8. Perbaiki output CSS dan Tailwind

Audit `scopedDeclarations()` dan `scopedStylesheet()`.

Saat ini kondisi scoped CSS perlu diperiksa karena diturunkan dari viewport dan requested color scheme.

Perbaiki agar:

- Override hanya muncul jika perbedaannya terverifikasi.
- Override tidak membandingkan token dari semantic role berbeda.
- Theme CSS mengikuti observed theme yang tervalidasi.
- Responsive CSS tidak menggunakan token yang salah karena collision.
- Nilai viewport yang diukur tidak diklaim sebagai breakpoint original website.
- Aturan CSS dan Tailwind konsisten menggunakan canonical model.
- Token shared tidak diduplikasi dalam scoped block.
- Identitas token tidak berubah ketika urutan capture berubah.

Jika output tidak cukup valid untuk dihasilkan, jangan mengarang nilainya. Gunakan hasil terverifikasi yang tersedia dan catat keterbatasannya pada metadata yang relevan.
