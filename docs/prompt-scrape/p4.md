## Product Goal

VibeScrape's [DESIGN.md](http://DESIGN.md) feature should generate a usable visual design reference that a coding agent can apply faithfully to an existing or new project.

The user reported that handing off a Notion-derived [DESIGN.md](http://DESIGN.md) to a coding agent produced a portfolio with:

- Square buttons even though the reference appeared to use rounded buttons.
- A visible section describing the Notion color palette, even though the user requested a portfolio using Notion's styling, not a design system showcase.
- Potentially other unrecognized deviations from the reference.

We must not assume whether the failure originated in:

1. Browser capture/evidence extraction.
2. Design token classification.
3. [DESIGN.md](http://DESIGN.md) document generation.
4. Agent handoff prompt.
5. Coding agent implementation.
6. Missing design compliance verification.

Investigate these layers and fix the verified causes.

The objective is NOT to produce artificially longer Markdown or claim perfect 1:1 fidelity without evidence.

## TASK C — Make Design Rules Operational

A useful design instruction should identify:

- Target component or UI role.
- Relevant measured token.
- Required implementation behavior.
- Evidence/confidence.
- Applicable scope.
- What must not be inferred.

Example:

Weak:  
"Use rounded corners."

Better:  
"Primary action buttons use the observed button-radius token from the reference; do not replace this with the project's default square button style."

If an actual radius is reliably measured, reference the correct measured value.

If radius evidence is missing, do NOT invent `12px` or any other value.

Avoid unconditional global rules that incorrectly force one radius onto all components.

## TASK E — Strengthen Agent Handoff Prompt

Inspect the current `buildDesignAgentPrompt()`.

Rewrite/refine it so it gives the agent concrete implementation responsibilities rather than vague instructions to "apply design system."

The handoff should require:

### Before Implementation

1. Read the actual project code and styling architecture.
2. Read [DESIGN.md](http://DESIGN.md) completely.
3. Identify applicable verified design constraints.
4. Map reference rules to existing UI components.
5. Identify missing evidence instead of guessing source-specific values.
6. Preserve content, features, flows and product requirements.
7. Do not recreate the reference website's structure unless explicitly requested.

### During Implementation

1. Apply relevant color tokens consistently.
2. Apply typography rules appropriately.
3. Apply component-specific radii and spacing.
4. Reuse existing UI components.
5. Avoid introducing contradictory styles.
6. Do not add decorative design system sections.
7. Prefer small, maintainable style changes over an unnecessary full rewrite.

### After Implementation

1. Verify key components against [DESIGN.md](http://DESIGN.md).
2. Check primary and secondary buttons.
3. Check inputs, cards, navigation, typography and spacing as applicable.
4. Report which rules were implemented.
5. Report which rules could not be applied and why.
6. Do not claim perfect 1:1 reproduction from incomplete evidence.

Do not output an absurdly long prompt by copying every token multiple times.

Keep the reference document intact and add concise, strong operational instructions.
