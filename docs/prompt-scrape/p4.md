## Konteks

VibeScrape memiliki fitur Generate [DESIGN.md](http://DESIGN.md) yang bertujuan menghasilkan design specification dari website referensi agar dapat digunakan sebagai panduan oleh AI coding agent.

Pada pengujian [`https://www.figma.com/`](https://www.figma.com/), saya mengaktifkan parameter:

- Desktop + Mobile.
- Light + Dark.
- Analisis mendalam.
- Token lengkap.
- Output CSS dan Tailwind.

Hasil [DESIGN.md](http://DESIGN.md) memiliki berbagai masalah kualitas.

Contoh temuan:

1. Do's and Don'ts berulang pada banyak capture.
2. Ada typography role `Unknown` dengan nilai `0px`.
3. `Body large` kadang berisi ukuran `88px` yang meragukan.
4. Banyak entri `Measured radius` dengan nilai berulang, termasuk `0px`.
5. Berbagai nilai radius tombol dicampur tanpa pemetaan komponen yang jelas.
6. Dokumentasi menyebut dark mode diminta tetapi tema aktual yang terlihat tetap light.
7. CSS/Tailwind dan pengukuran berulang membuat dokumen sangat panjang.
8. Bagian limitations dipenuhi log pengukuran dan pesan internal.
9. AI synthesis tidak selalu menghasilkan narasi berkualitas.
10. Dokumen belum cukup dapat diandalkan untuk dijadikan instruksi desain oleh AI coding agent.

**Tujuan utama bukan memperpendek dokumen secara asal. Tujuannya meningkatkan akurasi, konsistensi, keterbacaan, dan kegunaan implementasinya.**

## 3. Theme capture correctness

Bedakan secara eksplisit:

1. Theme yang diminta user.
2. Browser `prefers-color-scheme`.
3. Tampilan aktual website yang berhasil ditangkap.
4. Theme yang benar-benar bisa disimpulkan dari evidence.

**Requested dark ≠ verified dark.**

Contoh:

```
Requested capture: DARK
          │
          ▼
Browser prefers-color-scheme: dark
          │
          ▼
Website appearance examined
          │
          ├── Actual dark appearance verified
          │       └── Valid dark variant
          │
          └── Appearance remains light / ambiguous
                  └── Do not invent dark tokens
```

Jangan menyimpulkan dukungan dark mode dari parameter input saja.

Periksa bagaimana theme comparison dan measured appearance ditentukan dalam model.

Jika memang ditemukan bug pada theme inference, perbaiki dengan metode yang berbasis bukti.

Jangan mengubah tema website melalui cara yang merusak state autentikasi atau melewati pembatasan akses.

## 4. Typography validation

Audit klasifikasi role typography.

Masalah yang wajib diteliti:

- `Unknown` 0px.
- Body large dengan ukuran sangat besar.
- Elemen tersembunyi atau placeholder yang masuk sebagai typography token.
- Text styles yang terduplikasi.
- Style dominan versus outlier.
- Perbedaan typography antar-viewport.

Sistem harus membedakan:

- Display.
- Heading.
- Subheading.
- Body.
- Caption.
- Monospace.
- Role lainnya jika memiliki evidence yang kuat.

Jangan memaksakan role tertentu hanya berdasarkan ukuran font.

Jika elemen sebenarnya adalah angka statistik besar, jangan otomatis menyebutnya body copy.

Nilai invalid atau tidak representatif tidak boleh dijadikan guideline utama, tetapi evidence aslinya jangan dihapus tanpa alasan.

## 5. Normalize radius and component classification

Contoh yang tidak diinginkan:

```

Measured radius     0px
Measured radius     0px

```

Target:

```
COMPONENT RADII

Buttons
  Primary variant: observed value
  Secondary variant: observed value

Cards
  Observed representative value

Navigation
  Active item radius

Inputs
  Observed representative value

Other / unclassified
  Only when meaningful
```

Aturan:

- Deduplicate.
- Kelompokkan berdasarkan semantic component dan treatment.
- Pertahankan variasi jika memang berbeda.
- Jangan menganggap semua elemen dengan `0px` sebagai design token yang penting.
- Jangan menganggap `9999px` berlaku untuk seluruh button jika hanya sebagian button menggunakan pill.
- Jangan membuat `--radius-measured-radius-17` atau token berulang yang tidak jelas fungsinya.
- Jangan mengarang nilai tunggal jika evidence memang menunjukkan berbagai treatment.

## 6. Improve Do's and Don'ts quality

Saat ini Do's and Don'ts cenderung:

- Repetitif.
- Terlalu berorientasi pada angka pengukuran.
- Mengulangi informasi sama pada beberapa viewport.
- Tidak selalu memberikan instruksi implementasi yang berguna.

Target:

```
DESIGN GUIDELINES

DO
✓ Gunakan tipografi yang benar-benar teramati.
✓ Pertahankan hierarki visual utama.
✓ Terapkan radius sesuai jenis komponen.
✓ Gunakan warna dan spacing berdasarkan
  fungsi desainnya.

DON'T
× Jangan menyamakan semua varian button.
× Jangan mengarang dark mode jika tidak tersedia.
× Jangan memakai warna aksen untuk setiap elemen.
× Jangan menyalin konten website referensi
  sebagai konten aplikasi.
```

Contoh di atas adalah pedoman format, bukan aturan spesifik Figma yang boleh langsung di-hardcode.

Setiap guideline yang dihasilkan wajib:

- Berdasarkan evidence.
- Memiliki konteks penerapan.
- Tidak menjadi klaim global tanpa bukti.
- Tidak mengulang aturan identik.
- Dapat diterapkan oleh coding agent.
- Tidak mencampur observasi dan rekomendasi yang tidak terbukti.

Jangan memperpanjang daftar hanya demi terlihat lengkap.

- Model selection.

- Evidence payload.

- Validation.
- Claim checking.
- Retry policy.
- Failure handling.
- Persistence.

Jangan menganggap semua kegagalan synthesis sebagai kesalahan model tanpa bukti.

- Gunakan enrichment yang valid.
- Pastikan tidak mengarang token.
- Pastikan guideline tidak bertentangan dengan pengukuran.

Jika AI synthesis gagal:

- Jangan menyatakan enrichment selesai.
- Pertahankan measured output yang valid.
- Jangan menampilkan raw exception atau pesan internal sebagai panduan desain.
- Pastikan sistem dapat membedakan hasil lengkap dan hasil terbatas melalui status yang tepat.
- Jangan mempromosikan fallback deterministik sebagai analisis mendalam yang sukses.

## 8. CSS and Tailwind v4 output

Saat user memilih token lengkap:

- CSS Custom Properties dan Tailwind v4 harus sesuai hasil pengukuran yang sudah dinormalisasi.
- Token identik tidak boleh digandakan untuk setiap capture.
- Theme overrides hanya dibuat jika theme berbeda terverifikasi.
- Responsive overrides hanya dibuat jika perbedaannya terverifikasi.
- Jangan menghasilkan token invalid seperti `0px` untuk ukuran font yang sebenarnya tidak diketahui.
- Jangan membuat alias tak terbatas seperti `--radius-measured-radius-12`.
- Jangan mencampur Tailwind v3 dan v4.
- Jangan memaksakan token yang tidak memiliki makna implementasi.

Contoh struktur:

```
/* Illustrative structure only */

:root {
  /* Shared design tokens */
}

/* Scoped overrides only when verified */
@media (max-width: 640px) {
  /* Measured responsive differences */
}

/* Theme differences only when verified */
[data-theme="dark"] {
  /* Verified dark tokens */
}
```

Gunakan nilai nyata. Contoh tersebut tidak boleh di-copy sebagai output final tanpa evidence.
