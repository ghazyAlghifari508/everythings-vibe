# TASK — Phase 6: VibeDesign Studio Service Architecture &amp; Monster Service Refactoring

## Objective

Migrate Studio domain services into `src/features/studio/` and decompose the oversized `src/lib/services/studio-service.ts` into cohesive service modules.

Current audited size: approximately 2,545 lines.

Preserve all existing backend behavior, persistence guarantees, AI generation contracts, and security boundaries.

## 1. Investigation

Read [`AGENTS.md`](http://AGENTS.md), [TODO.md](http://TODO.md) Bagian 7, and applicable `.agents/rules/` to EOF.

Inspect the complete current implementation of:

- `src/lib/services/studio-service.ts`
- `src/lib/studio-*`
- Studio blueprint and generation utilities.
- Studio API routes.
- Database schema and transaction boundaries.
- Existing Studio integration and contract tests.
- UI/service consumers and server-only dependencies.

Determine which design-related utilities are Studio-owned, Scrape-owned, or genuinely shared.

Never migrate ambiguous modules by filename alone.

## 2. Architecture

Place canonical implementations under `src/features/studio/`.

Separate responsibilities where justified by the code:

- Project lifecycle and persistence.
- Frames and version history.
- Design generation orchestration.
- Blueprint validation.
- Design reference handling.
- Asset storage and authorization.
- Export operations.
- User preferences.
- Design skills and prompt contracts.

Use cohesive service modules with clear interfaces.

Target no more than 400 lines per implementation module, following existing repository rules.

Avoid one large facade containing duplicated business logic.

## 3. Behavioral Guarantees

Preserve:

- Studio project creation, retrieval, duplication, and deletion.
- Frame generation and regeneration.
- Saved design versions and revision history.
- Project preferences and persisted state.
- AI generation request/response validation.
- Existing generation progress and cancellation behavior.
- Asset authorization and storage.
- Consistency of database transactions.
- Current error mapping and recovery behavior.

Do not modify AI model selection, prompts, generation quality settings, or output schemas without demonstrated necessity.

## 4. Safe Migration Strategy

Perform this work incrementally:

1. Map exports, consumers, tests, and database effects.
2. Extract pure types and validators.
3. Extract independent services with stable contracts.
4. Isolate persistence and transactional operations.
5. Update internal imports and callers.
6. Maintain a compatibility facade where required.
7. Remove superseded implementation code.
8. Verify that no server-only dependency enters the client bundle.

Avoid circular imports and broad cross-feature dependencies.

Keep public Studio API contracts and existing routes unchanged.

## 5. Verification

Run the relevant existing Studio tests, including persistence, concurrency, frame operations, and asset contracts, when the required test infrastructure is available.

Do not weaken assertions, replace real implementations with mocks in production, or fake successful results.

Report infrastructure-dependent tests honestly if they cannot execute.

Do not launch Playwright browsers or perform browser QA.

Use atomic commits per logical service extraction and push to the working branch.

## Definition of Done

Studio service logic is feature-colocated, modular, type-safe, and compatible with current consumers.

The previous monster service is replaced by canonical domain modules and at most a minimal compatibility facade.

Preserve all functional behavior and report verified contracts, test results, and commit identifiers.
