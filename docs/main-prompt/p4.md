# TASK — Phase 4: Auth, Settings &amp; Billing Feature Architecture

## Objective

Complete feature-driven colocation of Authentication, User Settings, and Billing without changing security, payment, or credit behavior.

The credit service has already been modularized under `src/features/billing/`. Preserve this implementation.

## Preflight

Read [`AGENTS.md`](http://AGENTS.md), [TODO.md](http://TODO.md) Bagian 7, and all applicable rules, particularly no-assumptions, no-type-bypass, and atomic-commit.

Inspect the actual implementation and consumers of:

- `src/components/auth/`
- `src/components/settings/`
- `src/components/billing/`
- `src/features/billing/`
- `src/lib/services/payment-service.ts`
- `src/lib/services/billing-emails.ts`
- `src/lib/midtrans.ts`
- `src/app/actions/payment.ts`
- Auth/session infrastructure and Settings/Billing routes.

Inspect payment webhooks, API consumers, transaction tests, and authentication contracts before moving code.

## Architecture

Use:

- `src/features/auth-settings/`
- `src/features/billing/`

Authentication/session infrastructure used globally may remain under shared infrastructure when genuinely justified.

Do not create competing authentication providers or duplicate session-validation logic.

## Execution

### Auth &amp; Settings

Move domain-owned forms, preferences, account-management orchestration, API-key management, notification settings, and tests to `auth-settings`.

Preserve user session, OAuth callback, authorization checks, and authentication middleware.

### Billing

Move remaining domain-owned payment, invoice, credit UI, and billing notification logic into `billing`.

Retain the existing credit reservation, settlement, release, reconciliation, and ledger modules.

Preserve the original `credit-service.ts` facade if still required by active consumers.

### Integration

Update all affected imports and test mocks.

Keep server-only secrets and provider credentials out of client bundles.

Do not move shared infrastructure blindly.

## Security Requirements

Absolutely preserve:

- Tenant isolation.
- Better Auth session and OAuth behavior.
- Existing API-key storage/access boundaries.
- Midtrans signature and webhook verification.
- Credit atomicity and idempotency.
- Credit reservation and settlement lifecycle.
- Transaction reconciliation and refund behavior.
- Existing pricing and subscription rules.

No database schema changes unless objectively required and separately justified. Never perform destructive database operations.

## Verification

Establish baseline behavior and use focused tests covering auth, payment, API-key handling, and billing invariants.

Run database-backed integration tests only against an appropriate isolated test environment.

No browser QA, Playwright browsers, or external payment simulation against real users.

Use atomic commits per domain, push to the working branch, and verify a clean git tree.

Success requires clear domain ownership with zero behavioral or financial regressions.
