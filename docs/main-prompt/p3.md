## 2. Dependency Direction

Enforce:

Studio → Scrape public contracts  
Scrape ↛ Studio implementation

Scrape must never need to import Studio components, state stores, prompt generators, or canvas orchestration.

Studio may consume Scrape outputs through narrowly scoped public APIs or validated DTOs.

Do not make Studio directly depend on:

- Playwright or Chromium runtime.
- Scrape job workers.
- Crawl traversal internals.
- Browser process management.
- Internal Scrape storage implementation.

Avoid circular imports and broad barrels that expose internal server-only code to browser consumers.

## 3. Safe Scrape Artifact Consumption

Inspect the current [`DESIGN.md`](http://DESIGN.md) and design-reference integration.

If Studio already supports importing Scrape artifacts, preserve and simplify that integration.

If a required integration is missing, implement the smallest public contract necessary to let an authorized user select an existing Scrape result and use its [DESIGN.md](http://DESIGN.md) content in Studio.

Required safeguards:

- Verify ownership of the scrape record.
- Validate document existence and readiness.
- Return only the DTO required by Studio.
- Preserve document sanitization and size limits.
- Handle missing, failed, and inaccessible results.
- Maintain current Studio generation and persistence behavior.

Reuse the existing DB schema and contracts. Do not invent new storage tables or bypass authorization.

Do not create an entirely new import UI if the existing selector can support the interaction.

## 4. Worker Isolation

Audit how `scrape:worker` and `dev:all` start Scrape jobs.

Verify:

- The scraping worker is launched independently of the request-handling process where intended.
- Worker startup uses the current feature module path.
- Shutdown and job cleanup are safe.
- Job lease/recovery and retry semantics remain intact.
- Existing SSRF and destination validation remain enforced.
- Resource limits and concurrency settings are preserved.
- The Studio/client bundle does not transitively import crawler or Node-only worker code.

If isolation is already correct, preserve it. Do not replace the worker pipeline merely to demonstrate work.

## 5. Dependency Verification

Implement focused structural tests or static boundary checks that catch forbidden import directions.

Prefer checking resolved imports/dependency graph rather than only searching for a filename substring.

Test public DTO validation, ownership enforcement, artifact availability, and existing Studio generation integration.

No live external crawling or browser launching.

No Playwright browser QA.

## 6. Completion

The task is complete when:

- Studio and Scrape have independently maintainable implementations.
- Scrape does not depend on Studio.
- Studio consumes Scrape through stable, secured contracts.
- Worker isolation and server/client boundaries remain intact.
- Existing generation and scrape behavior is preserved.
- Relevant tests pass.

Commit atomically, push to the working branch, confirm clean git status, and summarize the dependency boundaries enforced.
